## 1. Where A2A stands

- **Releases.** 1.0.0 shipped on 2026-03-12 and 1.0.1 on 2026-05-28, whose fixes prefer the `application/a2a+json` media type and correct `TaskStatus` values ([CHANGELOG](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/CHANGELOG.md?plain=1#L3-L12)). `main` has since added documentation fixes and one normative section, §7.6.4 on what `AUTH_REQUIRED` authorizes (2.9 below). A `v1.1.0-rc` tag of 2026-10-29 marks a candidate with no release (section 3).
- **Governance.** A2A was accepted as a Growth Stage project of the Agentic AI Foundation, "Linux Foundation-directed", alongside MCP, goose and AGENTS.md ([blog, 2026-08-27](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/blog/posts/a2a-joins-aaif.md?plain=1#L10-L26)).
- **SDKs.** Official SDKs exist for Python, Go, Java, JavaScript, .NET and Rust ([SDK index](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/sdk/index.md?plain=1#L5-L12)). The Rust one, `a2a-rs`, has core types (`a2a-lf` 0.4.2), an async client, a server on `axum`, gRPC on `tonic`, and SSE streaming ([README](https://github.com/a2aproject/a2a-rs/blob/73d36984d4439656d676c5bbabe2461d88e4e20b/README.md?plain=1#L11-L44)).
- **A command-line client.** The official `a2a` CLI was announced on 2026-10-01 for "your shell, a CI pipeline, a test, or a coding assistant that just needs to hand off one task", with "protocol-native JSON output and predictable exit codes" and an Agent Skill that teaches Claude Code, Cursor and Codex to drive it ([blog](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/blog/posts/introducing-a2a-cli.md?plain=1#L17-L29), [L194](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/blog/posts/introducing-a2a-cli.md?plain=1#L194-L200)). Its specification is section 4, because it is the closest thing in A2A to `weave threads`.
- **Adoption among coding harnesses**, by the CLI specification's own account: "nearly nonexistent — one or two document A2A support today, and where it exists, it is labeled experimental" ([a2a-cli SPEC §1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L33)). This was not checked against Claude Code's or Codex's own documentation.

## 2. The A2A 1.0 model

### 2.1 Roles and discovery

- An A2A client "initiates requests to an A2A Server on behalf of a user or another system"; the server is a "Remote Agent" ([spec §2.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L131-L145)). A2A describes the agents it connects as "independent, often opaque" ([A2A and MCP](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/a2a-and-mcp.md?plain=1#L51-L52)).
- The Agent Card is found at `/.well-known/agent-card.json`, in registries, or by direct configuration ([§8.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1984-L1990)). It declares capabilities (`streaming`, `pushNotifications`, `extensions`, `extendedAgentCard`) and skills with an id, name, description, tags, examples and input and output media types ([a2a.proto](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L412-L453)).
- Several agents can sit behind one endpoint: an interface may carry an opaque `tenant`, which clients then put in every request, and whose meaning the server alone decides ([a2a.proto](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L336-L356)).

### 2.2 Tasks, messages, artifacts and parts

- **Send Message** answers with a `Task` that tracks the work or a `Message` for "simple interactions that don't require task tracking", and must return at once with one or the other ([§3.1.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L159-L180)).
- A **Message** has a client-created `messageId`, a role (`user` or `agent`), parts, optional `contextId` and `taskId`, and `referenceTaskIds` naming related tasks ([a2a.proto](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L254-L277)). A **Part** is one of text, raw bytes, a URL or JSON data, with a media type and filename ([L221-L242](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L221-L242)). An **Artifact** is an output with an id unique in its task, a name, a description and parts ([L279-L293](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L279-L293)), streamed in chunks with `append` and `lastChunk` ([L307-L322](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L307-L322)).
- **Messages are for communication, artifacts for results.** "Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts". Task history holds messages, but "not all Messages are guaranteed to be persisted", and a client that reconnects to a stream "MAY not receive all status update messages", so "Messages MUST NOT be considered a reliable delivery mechanism for critical information" ([§3.7](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L747-L764)).
- **Agent styles.** Message-only agents, task-generating agents ("even plain responses are modeled as completed tasks"), and hybrids that negotiate with messages and then commit to a task ([Life of a Task](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/life-of-a-task.md?plain=1#L45-L64)).
- **Tasks don't restart.** A terminal task "cannot restart"; a refinement "must initiate a new task within the same `contextId`" ([L77-L92](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/life-of-a-task.md?plain=1#L77-L92)). Follow-ups in one context may run as parallel tasks ([L94-L106](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/life-of-a-task.md?plain=1#L94-L106)). The client, not the agent, keeps the version history of refined artifacts; agents "should reuse a consistent `artifact-name`" for a refined version ([L117-L128](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/life-of-a-task.md?plain=1#L117-L128)).

### 2.3 Task states

| State | Kind | Meaning ([a2a.proto](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L186-L208)) |
| --- | --- | --- |
| `SUBMITTED` | in flight | submitted and acknowledged |
| `WORKING` | in flight | being processed |
| `INPUT_REQUIRED` | interrupted | the agent needs more input from the user |
| `AUTH_REQUIRED` | interrupted | authentication is required to proceed |
| `COMPLETED` | terminal | finished successfully |
| `FAILED` | terminal | finished with an error |
| `CANCELED` | terminal | canceled before completion |
| `REJECTED` | terminal | the agent decided not to perform it, at creation or later |
| `UNSPECIFIED` | none | unknown or indeterminate |

- A task in a terminal state accepts no more messages (`UnsupportedOperationError`) ([§3.1.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L172-L176)). "Agents MAY accept additional messages for tasks in non-terminal states" ([§3.3.3](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L565-L567)); 1.0 says nothing more about a message that reaches a `WORKING` task.
- **Blocking is the default.** Unless `returnImmediately` is set, Send Message "MUST wait until the task reaches a terminal state … or an interrupted state (`TASK_STATE_INPUT_REQUIRED`, `TASK_STATE_AUTH_REQUIRED`) before returning"; with it, the caller polls, subscribes or takes push notifications ([§3.2.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L442-L454)).

### 2.4 Contexts and tasks

- `contextId` groups tasks and messages "part of the same conversational session". Agents may generate it or accept a client's; clients should treat it as opaque; agents "MAY implement context expiration" ([§3.4.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L584-L602)).
- `taskId` is always server-generated; a client-sent one must name an existing task ([§3.4.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L604-L615)).
- Multi-turn: `contextId` alone starts a new task in the context; `taskId` continues that task, as in answering `input-required`; a mismatched pair is rejected ([§3.4.3](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L617-L644)).

### 2.5 Following a task

- **Get Task** returns status, artifacts and up to `historyLength` recent messages: unset is the server's default, 0 none ([§3.1.3](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L214-L230), [§3.2.4](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L465-L471)).
- **List Tasks** filters by `contextId`, state and `statusTimestampAfter`, pages by cursor (50 by default, 100 at most), sorts by last update, leaves artifacts out unless asked, and must return only tasks visible to the caller ([§3.1.4](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L232-L262), [a2a.proto](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L675-L713)).
- **Cancel Task** is an attempt, "success is not guaranteed", and idempotent ([§3.1.5](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L264-L283), [§3.3.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L492-L496)).
- **Streaming and resubscribing.** Send Streaming Message opens with the `Task`, then status and artifact events, and closes at a terminal state ([§3.1.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L204-L212)). Subscribe to Task works on any non-terminal task and must open with a `Task` snapshot, "to prevent a potential loss of information between a call to `GetTask` and calling `SubscribeToTask`" ([§3.1.6](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L285-L311)). Any number of streams may follow one task, each getting the same events in order, and "the task lifecycle is independent of any individual stream's lifecycle" ([§3.5.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L679-L700)). The JSON-RPC and REST bindings stream as Server-Sent Events ([§9.4.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L2347-L2361), [§11.7](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L2975-L3002)). 1.0 disagrees with itself on interrupted states: §3.1.2 closes the stream only at a terminal state, §11.7 "until the task reaches a terminal or interrupted state". The 1.1 candidate settles it (section 3).
- **Push notifications.** A client registers a webhook per task; the agent POSTs the same `StreamResponse` objects a stream carries, at least once, with optional retries; clients must answer 2xx and handle duplicates ([§4.3.3](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L842-L889)). Agents "SHOULD validate webhook URLs to prevent SSRF", rejecting private ranges and "localhost and link-local addresses" ([§13.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L3132-L3163)).
- **Idempotency.** Send Message "MAY be idempotent. Agents may utilize the messageId to detect duplicate messages" ([§3.3.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L492-L496)).

### 2.6 Extensions

- An extension is a URI an agent lists in its card, optionally `required`; a client opts in with the `A2A-Extensions` service parameter (an HTTP header or gRPC metadata) and puts extension data in `metadata` keyed by the URI, on messages and artifacts ([§4.6](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L998-L1141), [§3.2.6](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L477-L488)).
- Kinds foreseen: data-only, profiles that narrow core messages or add substates in metadata, method extensions that add RPCs, and state-machine extensions ([Extensions](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/extensions.md?plain=1#L18-L43)). Extensions may not add fields to core types or add enum values: "Extensions should use existing enum values and annotate additional semantic meaning in the `metadata` field" ([L76-L86](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/extensions.md?plain=1#L76-L86)). So a new task state such as "queued behind another" can only be metadata.
- The project hosts experimental extensions as `experimental-ext-*` repositories, among them one "for requesting schema-validated structured input from clients in the input-required state" (`a2aproject/experimental-ext-structured-input`, from its repository description; not read).

### 2.7 Bindings and versions

- Three bindings with the same operations and errors: JSON-RPC, gRPC and HTTP+JSON/REST ([§5.1–5.3](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1143-L1174)). The REST paths are `POST /message:send`, `POST /message:stream`, `GET /tasks/{id}`, `GET /tasks`, `POST /tasks/{id}:cancel`, `POST /tasks/{id}:subscribe` and the push-config resources.
- Clients send `A2A-Version` (major.minor); an empty one means 0.3 ([§3.6](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L706-L745)).

### 2.8 Authentication

- HTTPS in production, server identity by its TLS certificate, client credentials obtained out of band per the card's `securitySchemes`, and authorization "implementation-specific" ([§7.1–7.5](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1871-L1906)). The schemes are API key, HTTP auth, OAuth 2.0, OpenID Connect and mutual TLS ([a2a.proto](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/specification/a2a.proto#L501-L518)). Every operation must be scoped to what the caller may see ([§13.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L3102-L3130)).

### 2.9 In-task authorization

- `AUTH_REQUIRED` covers "an OAuth access token to call an API or another agent" and also "human approval before a destructive action is taken" ([§7.6](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1908-L1919)).
- The agent "MUST arrange to receive credentials via an out-of-band means" unless an in-band one was negotiated, and "MAY immediately continue Task processing after receiving the credential, without a requirement that clients send a follow-up message" ([§7.6.1](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1921-L1933)).
- A client that is itself an agent working on a task may pass the request up by moving its own task to `AUTH_REQUIRED`, "forming a chain"; a client without a stream open should subscribe, register a webhook or poll so it doesn't miss the agent continuing ([§7.6.2](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1935-L1951)).
- Added on `main` after 1.0.1: the state transition "by itself" authorizes nothing, and a credential obtained for it "MUST NOT be assumed to authorize subsequent messages" ([§7.6.4](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/specification.md?plain=1#L1964-L1972)).

## 3. What the 1.1 candidate adds

All of this is at the `v1.1.0-rc` tag, unreleased, and may change. Its ADR-002, the coherent task history behind most of it, is "Proposed" ([ADR-002](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/adrs/adr-002-coherent-task-history.md?plain=1#L1-L34)).

- **A generation counter.** Each task gets `generation`, starting at 1 and going up by exactly 1 per state-changing mutation, each mapped to one event that carries it, so a client "can detect that its view is behind by observing gaps" and should then re-fetch ([spec §3.2.7](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/docs/specification.md?plain=1#L572-L616), [a2a.proto](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/specification/a2a.proto#L214-L222)). Get Task with `currentGeneration` long-polls until the task moves past it.
- **Resuming from a position.** Subscribe to Task takes `lastSeenGeneration`: the server replays only what followed it, without a snapshot, and falls back to a snapshot if it no longer has that point ([a2a.proto](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/specification/a2a.proto#L905-L916), [spec](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/docs/specification.md?plain=1#L465-L470)).
- **A timeline** of client messages and agent status entries ordered by generation replaces `history`, which is deprecated and removed in 2.0. It records "the interaction on the wire", explicitly "not a full trajectory or trace of the agent's internal execution" ([ADR-002](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/adrs/adr-002-coherent-task-history.md?plain=1#L26-L34), [§3.2.8](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/docs/specification.md?plain=1#L617)).
- **Optimistic concurrency.** `ifGenerationMatch` on a follow-up message rejects it with `TaskGenerationMismatchError` (HTTP 409) if the task moved on ([a2a.proto](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/specification/a2a.proto#L176-L183)).
- **Input while the task works.** `SendLiveMessage` is a bidirectional exchange bound to one task: the first request either sends a message or subscribes; later messages are appended "by arrival"; an agent may decline one with a non-fatal `StreamError` and keep the stream open, and "an agent that accepts input while `TASK_STATE_WORKING` is not committing to accept every message". Over HTTP each later input is a short call of its own while the first call's response stays open ([spec §3.1.12](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/docs/specification.md?plain=1#L432-L483)). This is the first A2A operation with steer-like semantics.
- **Interrupted states are settled as non-terminal.** The server keeps control and "may continue processing the task and transition it to another state (including out of an interrupted state) without a message from the client"; a stream "SHOULD NOT" close on one ([a2a.proto](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/specification/a2a.proto#L226-L234), [spec §4.1.3](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/docs/specification.md?plain=1#L946-L955)).
- **Client-written artifacts** (`role: ROLE_USER`) behind a `userArtifacts` capability, and discovery that prefers an AI Catalog at `/.well-known/ai-catalog.json`, listing several agents, over one card per domain ([agent discovery](https://github.com/a2aproject/A2A/blob/78e1d6a1f7f118c8e9bc830b04a8579c1119cb78/docs/topics/agent-discovery.md?plain=1#L42-L49)).

## 4. The A2A CLI specification

The `a2a-cli` [SPEC.md](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md) specifies a command-line A2A client for "human developers, automated workflows, and AI coding harnesses". It is the nearest published design to `weave threads`, and it decides several questions weave decided too, some the other way.

- **Commands.** `send` (start or continue), `task get [--wait]`, `task cancel`, `task list`, `task subscribe`, `task push-config`, `task download`, `card get`, an interactive `chat` gated on a terminal, and a `server` mode for demos ([§7.1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L128-L152)). `server --exec` turns any program that reads stdin and writes stdout into an A2A agent ([blog](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/blog/posts/introducing-a2a-cli.md?plain=1#L74)).
- **Agent-first output.** "Where the two pull apart, the programmatic consumer sets the default": no prompts, no control sequences, no output shape that varies with the environment ([§6.1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L105)). `json` emits "the protocol's own response types unmodified" ([§6.2](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L107)); one document without `--stream`, JSON Lines with it, whose last line "MUST carry the terminal event" ([§11.3](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L406-L421)); payload on stdout, everything else on stderr ([§11.1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L392-L394)).
- **Stateless.** The CLI never stores the last `taskId` or `contextId` or offers "resume where I left off"; every identifier needed to continue is printed and accepted back as a flag, so concurrent runs from CI, shells and agents can't disagree about which interaction is current ([§6.3](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L109), [§8.3](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L221-L223)).
- **Reporting identifiers.** Every command that touches a task reports `taskId`, `contextId` and state, on completion and on interruption, and in text mode "SHOULD print the exact command required to resume" ([§8.2](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L213-L219)). A rejected `--task-id` is an error, and the tool "MUST NOT silently create a new task" ([§8.1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L199-L211)). `messageId` "SHOULD be reused when retrying a turn" ([§4.1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L75-L83)).
- **Waiting.** `send` blocks by default until a terminal or interrupted state, `--async` returns the identifiers, and a wait "stops immediately on an interrupted" state so the caller can act; `--poll-interval` and `--timeout`, whose expiry is an error ([§6.5](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L113-L122), [§9.1](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L260-L266), [§9.3](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L344-L351)).
- **Exit codes report the tool, not the task.** "A turn the CLI faithfully conducted and reported exits `0` whether the task completed, ended `FAILED` or `REJECTED`, or paused at `INPUT_REQUIRED`/`AUTH_REQUIRED`", because folding the agent's verdict in means "a non-zero status no longer distinguishes an unreachable agent from a working one that said no" ([§6.6](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L124)). Required: 0 success, 1 failure, 2 usage. Reserved: 3 agent unreachable, 4 authentication, 5 timeout. A later version "MAY … introduce codes for task outcomes should a transactional wrapper need them" ([§11.6](https://github.com/a2aproject/a2a-cli/blob/c65d3131f39f8ca7a176c0aca1a7229362188680/specification/SPEC.md?plain=1#L441-L463)).

## 5. A2A beside MCP and ACP

- **A2A's own framing.** "MCP is vertical. It deepens a single agent"; "A2A is horizontal. It connects agents across that boundary", to another team, department or organization ([A2A and MCP](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/a2a-and-mcp.md?plain=1#L12-L27)). An A2A server can expose well-defined, stateless skills as MCP tools, but A2A's strength is "flexible, stateful, collaborative interactions that go beyond a typical tool call" ([L140-L146](https://github.com/a2aproject/A2A/blob/d924e07b0c9d7ccd9ee62bc63cd6aa47dde9f4ee/docs/topics/a2a-and-mcp.md?plain=1#L140-L146)). A2A's docs don't mention ACP.
- **MCP has its own tasks.** MCP 2026-07-28 moved tasks out of the core protocol into an official extension, `io.modelcontextprotocol/tasks`, polled with `tasks/get`, with `tasks/update` for client input and no `tasks/list`, and lets servers return task handles unasked ([changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/84d845729393f79b3fd3d392aa17cb86f5b6f95c/docs/specification/2026-07-28/changelog.mdx?plain=1#L22)). The same revision answers a request needing more information with an `input_required` result the client retries ([L24-L26](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/84d845729393f79b3fd3d392aa17cb86f5b6f95c/docs/specification/2026-07-28/changelog.mdx?plain=1#L24-L26)). The tasks proposal named agent-to-agent calls as a motivating case ([SEP-1686](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/84d845729393f79b3fd3d392aa17cb86f5b6f95c/docs/seps/1686-tasks.mdx?plain=1#L92-L96)). The MCP docs don't otherwise mention A2A.
- **ACP has no A2A RFD.** Its RFDs mention A2A once, calling it "agent-to-agent transport, a fundamentally different abstraction layer than ACP's client-to-agent communication" ([client system prompt RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/rfds/client-system-prompt.mdx?plain=1#L46)). The v2 draft makes `initialize`'s implementation info role-agnostic "so agent-to-agent and other symmetric ACP connections do not need role-specific field names" ([v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/rfds/v2/overview.mdx?plain=1#L78)).
- **ACP's list of clients includes an A2A bridge**, `a2acode`, which "serves any ACP agent over the A2A protocol … turning `session/request_permission` into an A2A `input-required` pause the remote caller answers" ([clients](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/get-started/clients.mdx?plain=1#L201)). Its README, a third-party claim not tested here, maps assistant text to a streamed artifact, reasoning to a separate `thinking` artifact, tool calls and their outcomes to `working` status updates, the plan and each diff to artifacts, a permission request to `input-required`, and the ACP session id to `contextId`. Its `claude` preset authenticates with an Anthropic API key, because "when the server answers on behalf of other agents, a Claude credential has to be an Anthropic API key (or Bedrock / Vertex)" ([README](https://github.com/kanywst/a2acode/blob/65d44361f21c757180962c2681ea8a5c83208850/README.md?plain=1#L24-L36), [L52-L60](https://github.com/kanywst/a2acode/blob/65d44361f21c757180962c2681ea8a5c83208850/README.md?plain=1#L52-L60), [L165](https://github.com/kanywst/a2acode/blob/65d44361f21c757180962c2681ea8a5c83208850/README.md?plain=1#L165)). [ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md#L8) records the same terms question for a loop weave would own.
- **ACP is moving toward a task-like state.** The v2 draft reports foreground activity as `state_update` with `running`, `idle` or `requires_action`, moves the stop reason to the idle update, and inserts or holds prompts sent during active work rather than rejecting them; "steering and queueing remain separate concerns" ([v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/rfds/v2/overview.mdx?plain=1#L67-L69), [L141](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/rfds/v2/overview.mdx?plain=1#L141), [v2 prompt RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/rfds/v2/prompt.mdx?plain=1#L237-L268)). Subagent sessions are an Active RFD and `session/status` a Draft one ([RFD index](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/docs.json#L195-L215)). The subagents RFD's association "is not a task or a one-shot lifetime" ([subagents](https://github.com/agentclientprotocol/agent-client-protocol/blob/1c34114c2f406d0739e7e36a5a99bb6059ee7caf/docs/rfds/subagents.mdx?plain=1#L21-L24)).

So the three split the ground this way: ACP is a client driving one agent's session, transparently; MCP is an agent calling tools, now with optional task handles; A2A is a client delegating opaque work to a remote agent. None documents a bridge to another except the third-party `a2acode`.

## 7. Where the mapping breaks

### 7.1 Opaque work against a transparent thread

A2A shows a client status messages and artifacts and nothing of how the agent got there; the 1.1 timeline is explicitly not "a full trajectory" (section 3). A weave thread's journal is ACP's whole update stream, tool calls, thoughts, plans, diffs and terminal output, plus pending requests, and every weave client renders it ([spec](../specs/wve-85-host-protocol.md#L551-L577)). Serving a thread over A2A means flattening it, as `a2acode`'s table does (section 5), or carrying ACP's JSON in extension metadata that only a weave-aware client reads; and a weave-aware client can speak the Host protocol.

### 7.2 Turns have no identity

A2A addresses work by `taskId`. weave addresses a thread, and a turn only by a journal position, which the CLI's own guide shows is awkward: to wait for the turn `threads prompt` started, follow it `--after` "`prompt --json`'s `seq` less one" ([`cli/AGENTS.md`](../../cli/AGENTS.md#L40-L46)).

### 7.3 The queue has no A2A counterpart

A2A runs follow-ups in one context as parallel tasks (2.2); a weave thread runs one turn at a time and queues the rest, and pauses the queue when a turn is cancelled or fails ([spec](../specs/wve-85-host-protocol.md#L650-L710)). An A2A view could show a queued prompt as a `SUBMITTED` task, but "paused" exists only as metadata, since extensions can't add states (2.6).

### 7.4 Steering is new in A2A

1.0 lets a non-terminal task take more messages without saying what they mean (2.3). Only the unreleased `SendLiveMessage` gives a message for a working task defined semantics, close to `turn/steer`.

### 7.5 Who answers a waiting thread

`INPUT_REQUIRED` expects the A2A client to reply. In weave, only people answer pending requests: "One agent approving another's tools would step around the person's policy, which is the point of asking" ([ADR 0020](../adr/0020-agents-reach-the-host-as-clients-do-and-act-only-on-threads-they-start.md#L19)); the calling agent is told the thread waits and "can't answer it" ([spec](../specs/wve-85-host-protocol.md#L843-L846)). `AUTH_REQUIRED` fits weave better: it names human approval, has the answer arrive out of band, and lets the agent continue without a follow-up message (2.9). But A2A clients in general would read either state as "the caller must act", and `a2acode` does route permission requests to the remote caller.

### 7.6 Threads outlive their turns

A context has no lifecycle beyond optional expiry. A thread is open, suspended or closed, and can be closed, reopened on a new agent version, or deleted ([spec](../specs/wve-85-host-protocol.md#L306-L321), [L466-L505](../specs/wve-85-host-protocol.md#L466-L505)). An A2A view has nowhere to put these.

### 7.7 Reach and authentication

Every connection to a Host comes through the tailnet and proves a key the Host paired with; "being in the tailnet, or carrying a tag there, is never enough on its own" ([ADR 0017](../adr/0017-hosts-pair-as-peers-through-the-tailnet-and-are-managed-through-their-cli.md#L8)). No A2A client pairs, so an A2A endpoint would need a second way in (bearer tokens, which ADR 0010 rejected as copyable, or OAuth), or would serve only clients that weave pairs specially. A2A's push guidance also tells servers to refuse loopback webhook targets (2.5), which is where a local caller's receiver would be.

### 7.8 Policy

`session/run` takes a permission policy, and a delegated thread's is capped by its caller's ([spec](../specs/wve-85-host-protocol.md#L838-L842)). An outside A2A caller has no field for one and no thread whose policy would cap it, so a fixed policy per A2A entry point, or an extension, would have to decide what its threads approve.

### 7.9 Exit statuses

WVE-108 put the turn's outcome in `weave`'s exit status: 4 failed, 5 cancelled, 6 stopped short ([`exit.rs`](../../cli/src/exit.rs#L12-L39)). `a2a-cli` keeps outcomes out of exit codes on purpose and reserves 4 for authentication and 5 for timeouts (section 4). They share only 3, "unreachable". weave's choice is defensible: 3 still separates "couldn't reach the Host" from "the turn failed", which is the confusion `a2a-cli`'s rationale is about. But a script written for one means something else on the other.

## 8. Fit for weave

### 8.1 Where weave stands

Agents reach threads as clients do: Host tools on the Host MCP server, each a projection of a Host protocol method, `list_sessions`, `read_session`, `start_session`, `prompt_session`, `steer_session`, `cancel_session_turn` ([spec](../specs/wve-85-host-protocol.md#L800-L823), [ADR 0020](../adr/0020-agents-reach-the-host-as-clients-do-and-act-only-on-threads-they-start.md#L8)). They act on any thread on their Host, and the thread whose agent began a turn gets a report of how it ended or that it waits on a person ([ADR 0023](../adr/0023-agents-act-on-any-thread-and-the-hosts-reports-tell-nobody-back.md#L8), [`host_tools.rs`](../../host/src/host_tools.rs#L337-L381), [`session.rs`](../../host/src/session.rs#L1558-L1600)). The CLI does the same for scripts and agents' shells: `weave threads` lists, reads, prompts, steers, cancels, closes, follows and watches ([`sessions.rs`](../../cli/src/sessions.rs#L55-L79)), prints the protocol's own types with `--json`, and exits with a status that says how the command and its turn went ([`cli/AGENTS.md`](../../cli/AGENTS.md#L37-L66)). Peer Hosts are to reach each other's threads as remote clients over the same protocol ([ADR 0017](../adr/0017-hosts-pair-as-peers-through-the-tailnet-and-are-managed-through-their-cli.md#L10)). Weave stays single-user, with sharing between Hosts rather than tenancy inside one ([identity note §10.8](agent-identity-and-where-agents-run.md#108-sharing-deferred)).

Much of what A2A standardizes, weave has: a durable unit of work with states, a non-blocking send, cancel, list, resumable streams that several clients share, idempotent sends, and a push of the result to whoever asked. Its journal positions already do what 1.1's `generation` is being added for.

### 8.2 Option (a): the Host serves A2A

An A2A endpoint would let outside orchestrators (Google's ADK, LangGraph, cloud agent platforms, `a2a` itself) start and follow weave threads.

- **Costs.** An HTTP listener with SSE, or at least a path beside the WebSocket behind Serve; an authentication path besides pairing, or a pairing step no A2A client performs (7.7); a lossy projection of every thread (7.1); answers to who sets policy (7.8), what the card lists when the Host has many agents (`tenant` or the 1.1 catalog), what turn ids are (7.2), and what `INPUT_REQUIRED` means when the caller can't answer (7.5); and a second public API to keep in step with the Host protocol, across A2A's 1.0 to 1.1 changes. Serving agents other than the person's own would also raise the credential question `a2acode` documents (section 5). `a2a-rs` would supply the wire types and an `axum` server, a new dependency tree for the Host.
- **Benefit for a single user.** Small. The person's own agents already drive threads with Host tools or `weave threads`, and the callers A2A was built for are other teams' and organizations' agents (section 5), which the single-user, tailnet-only Host deliberately doesn't admit.
- **If it is ever wanted**, build it outside the Host, as a client of the Host protocol that pairs and connects like any service ([ADR 0017](../adr/0017-hosts-pair-as-peers-through-the-tailnet-and-are-managed-through-their-cli.md#L27)): a `weave a2a serve` bridge that maps thread to context and turn to task, and reports waiting as `AUTH_REQUIRED`, which A2A defines as resolved out of band (2.9). The Host and its protocol would then gain nothing for it. That is how `a2acode` is shaped, only fronting the Host rather than a bare agent.

### 8.3 Option (b): weave calls A2A agents

- **Without building anything.** An agent in a thread can already call A2A agents through the `a2a` CLI and its Agent Skill from its shell (section 1), or through an A2A-fronting MCP server configured as an upstream server ([ADR 0013](../adr/0013-configured-mcp-servers-through-the-host-mcp-server.md)). The Host sees nothing of either beyond a shell or tool call, which is acceptable for occasional use.
- **Building it into the Host**, as Host tools that call remote A2A agents, breaks ADR 0020's rule that a Host tool is a projection of a Host protocol method, and would make the Host an A2A client with credentials to keep for other services.
- **If a remote A2A agent should be a first-class thread**, the shape consistent with [ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md#L8) is an ACP agent that fronts it: a configured agent whose process speaks ACP to the Host and A2A to the remote agent, so the remote work gets a journal, a queue, cancel and reports like any thread. No such adapter was found; `a2acode` goes the other way.

### 8.4 Option (c): borrow ideas, recommended

Speak neither side of A2A now. Borrow from A2A 1.0, its 1.1 candidate and `a2a-cli` the pieces that make threads easier for agents and scripts to drive, as additions to the Host protocol (protocol version 2 stays) and to `weave threads`. In order of value:

1. **Stop waiting when a thread waits on a person.** A2A's blocking send returns at an interrupted state, and `a2a-cli` "MUST stop and report" with a resume hint (2.3, section 4). `weave threads follow --until-turn-ends` and `weave run` keep waiting and only print a note on stderr ([`sessions.rs`](../../cli/src/sessions.rs#L389-L392), [`run.rs`](../../cli/src/run.rs#L235-L238)), so a script or an agent's shell can hang on a permission request nobody is looking at. The Host tools already report this state to agents ([`host_tools.rs`](../../host/src/host_tools.rs#L371-L381)). Give the CLI the same: return with an exit status of its own, say 7, and the thread id, when the turn it waits for starts waiting, unless asked to wait through it.
2. **One turn state, terminal or interrupted.** Today a caller combines `LatestTurn.running`, `response`, `error` and the listing's `activity` to learn where a turn is ([`sessions.rs`](../../protocol/src/sessions.rs#L74-L83), [L271-L289](../../protocol/src/sessions.rs#L271-L289)). Add a derived `state` to `LatestTurn`, queued, running, waiting, ended (with its stop reason), failed or cancelled, and give `sessions/list` and `weave threads list` a filter on it, as A2A's List Tasks filters on state (2.5). ACP v2's `state_update` (section 5) is heading the same way, so the field can later be fed from it.
3. **Name turns.** Give a turn an id, or define it as its `turnStarted` position and its `queuedId` before that, return it from `queue/add`, `turn/steer` and `session/run`, and let `follow`, `read` and Host tools take it. This is A2A's `taskId` and `a2a-cli`'s "report identifiers back, with the resume command" (section 4), and it removes the "`seq` less one" step (7.2).
4. **`weave threads prompt --wait`.** A2A and `a2a-cli` block by default; weave's prompt never does, and waiting takes a second command (7.2). A `--wait` that exits as `follow --until-turn-ends` does, with idea 1's waiting status, makes "prompt and get the answer" one command, printing the agent's last message as `threads read` does. ADR 0020's reason against waiting Host tools, a calling turn blocked inside an MCP call ([L16](../adr/0020-agents-reach-the-host-as-clients-do-and-act-only-on-threads-they-start.md#L16)), weighs less for a shell command its caller chose to run, though agents' shell tools have their own time limits, so pair it with idea 6.
5. **`--key` on `threads prompt` and `run`.** The Host has request keys ([spec](../specs/wve-85-host-protocol.md#L712-L733)) but the CLI sends none ([`sessions.rs`](../../cli/src/sessions.rs#L210-L215)). A script that retries after a dropped connection can then reuse its key, as `a2a-cli` reuses a `messageId` (section 4).
6. **`--timeout` on anything that waits**, with an exit status of its own. `a2a-cli` reserves 5 for it; weave's 5 is "cancelled", so take a new number.
7. **Describe agents for the agents that delegate.** `start_session` tells a calling agent its `agentId` is "such as claude or codex; list_sessions shows which agents threads run" ([`tools.rs`](../../protocol/src/tools.rs#L157-L158)), while the Host already has `agents/list`. Add a `list_agents` Host tool as its projection, and an optional `description` under `[agents.<id>]`, the part of an Agent Card's `description` and skills that helps an agent choose whom to delegate to. Leave out the rest of the card: endpoints, security schemes, signatures.
8. **Keep WVE-108's exit statuses and say why.** Section 7.9 is a deliberate difference from the one published CLI convention in this space. A sentence in `cli/AGENTS.md` (that turn outcomes are in the status because scripts composing threads branch on them, and that 3 alone means the Host wasn't reached) keeps it from being "fixed" later. weave's 3 already agrees with `a2a-cli`'s.

Not worth borrowing now:

- **Webhooks.** The report and `sessions/watch` already push to the two kinds of caller weave has, threads and connected clients; outside senders wait for the edge Hosts dial out to (WVE-117, [identity note §10.5](agent-identity-and-where-agents-run.md#105-wve-117-an-edge-that-hosts-dial-out-to)).
- **Artifacts as a protocol type.** ACP has no artifact, so the Host would have to infer them or have agents declare them through a new Host tool. Visuals already keep the pages an agent makes. Reconsider if delegating agents keep needing a turn's result as something other than its last message.
- **`contextId` grouping beyond threads**, extended or signed cards, OAuth, multi-tenancy and `tenant`: these serve many callers and organizations, which a single-user Host doesn't have.
- **`ifGenerationMatch`.** `turn/steer`'s `notRunning` already covers the race that matters, a steer arriving as a turn ends.

### 8.5 Summary

| Idea | From | Change in weave | Size |
| --- | --- | --- | --- |
| Return when the turn waits on a person | A2A 1.0 §3.2.2, `a2a-cli` §9.3 | CLI: `follow`, `run`; a new exit status | small |
| One turn state; list filter on it | A2A `TaskState`, List Tasks | protocol: `LatestTurn.state`, a `sessions/list` param; CLI flag | small |
| Turn ids | `taskId`, `a2a-cli` §8.2 | protocol: ids on `queue/add`, `turn/steer`, `session/run`; CLI and Host tools take them | medium |
| `threads prompt --wait` | blocking Send Message | CLI only | small |
| `--key` | `messageId`, `a2a-cli` §4.1 | CLI only | small |
| `--timeout` | `a2a-cli` §9.3 | CLI only | small |
| `list_agents`, agent descriptions | Agent Card description and skills | Host tool; config field | small |
| Document why outcomes are in exit statuses | `a2a-cli` §6.6, by contrast | `cli/AGENTS.md` | trivial |
| A2A server | A2A | a bridge outside the Host, if ever | large; not now |
| A2A client | A2A | none; agents use `a2a` or an upstream MCP server | none |

### 8.6 Not verified

- Everything in section 3 is an unreleased candidate whose ADR is "Proposed"; names and semantics may change before 1.1.
- Whether Claude Code or Codex support A2A natively was not checked in their own documentation; the only source here is `a2a-cli`'s remark (section 1).
- No ACP adapter that fronts a remote A2A agent was found, but the search was limited to ACP's client list and the A2A organization's repositories.
- `a2acode` was read, not run; its mapping is its README's claim.
- The A2A SDKs' source wasn't read: the spec answered the questions here, apart from 1.0's disagreement on closing streams at interrupted states, which the 1.1 candidate settles.
- The `experimental-ext-structured-input` extension was seen only by its repository description.
