### 1.2 Shipped, announced, and vision

- **Shipped, in public beta**: the Delta desktop app, Delta on the web and in mobile browsers, threads with Delta worktrees and checkouts, sharing, comments anchored to deltas, forks and review subthreads, subagents, Land subthreads, skills and rules files, MCP servers, the `delta` command-line tool (`delta auth`, `delta update`, and the `delta thread` verbs the plugin calls), the Claude Code plugin, and early Jujutsu support ([docs index](https://delta.dev/docs/getting-started); [Delta & Git](https://delta.dev/docs/concepts/delta-and-git#jujutsu-repositories)).
- **Shipped, in private beta**: Cloud Runners, behind a signup form ([Cloud Runners](https://delta.dev/docs/agents/cloud-runners)).
- **On the roadmap as "In Progress"**: repository-based access from GitHub permissions, a "Remote runtime" ("persistent cloud development environments"), a Delta CLI that can "connect any agent to Delta threads and worktrees from the command line, and hand off work across people and machines", MCP support, @mentions, and ACP support ("Bring external agents like Claude Code into Delta through the Agent Client Protocol (ACP)") ([roadmap](https://delta.dev/roadmap)). MCP servers and mentions already have documentation pages, so these entries may describe further work on them.
- **On the roadmap as "Up Next"**: repository-level context, sandboxing, WSL, conversation branching, a graph view, and read and view permissions.
- **Described only as vision**: open-sourcing DeltaDB with an optional paid service (2025); DeltaDB inside Zed ("eventually"); Git storage in DeltaDB, "content-based builds" bringing CI into the thread, and replacing the other workflows of GitHub.com (2026-09-16). Agents that "convene the prior agents" (2026-06-11) exist in part: the agent "can search your other threads for relevant context on its own" ([Skills](https://delta.dev/docs/agents/skills#where-skills-live)).
- **Not built yet, by Delta's own account**: "Delta does not have an agent permission system", "Delta does not sandbox agents", and repository files such as `.agents/prepare` and `AGENTS.md` load without review ([Agentic Safety](https://delta.dev/docs/privacy-and-security/agentic-safety)).

### 1.3 What an agent is in Delta

Delta has no agent object with an identity of its own. The unit is the thread: "A thread is a conversation with an agent and the basic unit of work in Delta" ([Threads](https://delta.dev/docs/agents/threads)), and the home page calls a thread "the conversation with an agent and the checkout of the repository it works in, kept together as one shareable artifact" ([delta.dev](https://delta.dev)). A thread can stand alone or include projects (Git repositories with a remote); each project it touches gets a Delta worktree, "a copy of the project's files whose history is recorded in DeltaDB", which a desktop materialises as a checkout ([Core Concepts](https://delta.dev/docs/concepts/core-concepts)).

The agent loop is Delta's own. Its models come from Zed-hosted plans, subscriptions (ChatGPT, GitHub Copilot, Grok; "Coming soon: Sign in with a Claude subscription"), API keys, or compatible endpoints ([Models & Providers](https://delta.dev/docs/agents/models-and-providers)). The model is not the identity: "Switch its model. The conversation and any Delta worktrees carry on; the new model picks up where the last one left off" ([Threads](https://delta.dev/docs/agents/threads#thread-lifecycle)). Subagents are subthreads with a profile, Worker, Scout or Reviewer, that sets a role, a model and whether the subagent's worktree is isolated or shared ([Subagents](https://delta.dev/docs/agents/subagents#profiles)). Mentioning `@Delta` marks one reply "as coming from Delta" ([Getting Started](https://delta.dev/docs/getting-started#ask-delta-about-delta)).

External harnesses join a thread as producers rather than as the thread's agent: see 1.7.

### 1.4 What persists, and what it carries

- **The thread.** "A thread persists. Leave and come back later; the conversation and any project files are still there", and reverting rewinds conversation and files together ([Core Concepts](https://delta.dev/docs/concepts/core-concepts#threads-where-work-happens)). A delta "can represent a file edit, a change to the file tree, a message, a comment", and "each delta records who made the change and where it belongs in the thread's history" ([Delta & Git](https://delta.dev/docs/concepts/delta-and-git#what-is-a-delta)).
- **Storage.** "Delta's backend runs entirely on Cloudflare": file contents, commits and checkpoints in R2; "thread and Delta worktree deltas used for active synchronization" in Durable Objects backed by SQLite; account settings in Durable Objects; metadata in KV and D1 ([Data Storage & Deletion](https://delta.dev/docs/privacy-and-security/data-storage#where-your-data-lives)). Delta removes the local history of an archived thread three days after archiving once the server holds a full copy; "Threads that were never synced stay on your machine" ([Threads](https://delta.dev/docs/agents/threads#archive-and-reopen-threads)).
- **Instructions.** Personal rules (`AGENTS.md` in a per-OS folder) apply "to every thread on this machine"; project rules load the first non-empty of `AGENT.md`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` and other vendors' files; folder rules load as the agent reaches a folder ([Settings](https://delta.dev/docs/configuration/settings#rules)). Skills live in `.agents/skills/` (project) and `~/.agents/skills/` (personal); "Personal skills are stored on your computer, so browser turns cannot use them" ([Skills](https://delta.dev/docs/agents/skills#where-skills-live)).
- **No memory store.** Continuity is the thread and its searchable history. Nothing in the documentation describes memory that outlives a thread other than rules, skills and thread search.
- **Credentials, and whose.** Provider API keys and custom headers live in account settings that "sync across devices and use an encrypted local cache"; Zed Cloud stores the OAuth grants for ChatGPT and Grok and hands Delta short-lived tokens; GitHub Copilot credentials stay in the device keychain ([Models & Providers](https://delta.dev/docs/agents/models-and-providers); [Data Storage](https://delta.dev/docs/privacy-and-security/data-storage#what-delta-stores)). On a runner, "Git commands and `gh` … work as you, and commits use your name and email" ([Cloud Runners](https://delta.dev/docs/agents/cloud-runners#use-git-and-github-from-a-runner)).
- **Attribution.** "Each participant composes their own draft, attributed to them." "The agent sees who wrote each message and comment." Sending submits every trailing draft "in one turn charged to the sender", and "model usage belongs to whoever sends the request, not the thread's owner" ([Collaborate in a Thread](https://delta.dev/docs/collaboration/collaborate-thread#who-pays-for-model-usage)). A pull request opened from a shared thread gets an "Open in Delta" link back to it ([Settings](https://delta.dev/docs/configuration/settings#rules)), and commit diffs link to the thread that produced the commit ([release notes](https://delta.dev/docs/whats-in-the-latest)).

### 1.5 Where turns run

"An agent turn runs wherever the sender is using Delta, or on the sender's cloud runner. It never runs on the thread owner's device or another participant's device" ([Collaborate in a Thread](https://delta.dev/docs/collaboration/collaborate-thread#where-the-agent-runs)). There are three places:

- **The desktop app**, where a turn "can use mounted checkouts, installed tools, environment variables, credentials, network access, and running processes".
- **The browser**, where a turn "works with replicated thread and project data. It has no shell or checkout."
- **A cloud runner**, "a Linux sandbox that runs the agent's turns for a thread on your behalf" (Debian Bookworm, three sizes). "Each person who chooses Cloud gets a distinct runner that uses their own settings." It checks out the thread's worktrees from Delta's servers and "can't reach anything that exists only on your computer". Runners pause after 10 minutes idle, are deleted when the thread is archived, and "we may delete and reprovision Cloud Runners at any time" ([Cloud Runners](https://delta.dev/docs/agents/cloud-runners)).

"Delta syncs the conversation and recorded file changes, but it does not sync machine-local runtime state. If collaborators alternate between execution environments, the resources available to the agent can therefore change between turns." The thread's identity therefore never belongs to a machine; each turn is placed where its sender is.

Checkouts are managed per participant: "Each participant in a thread gets their own checkout of a worktree on their own machine." Managed checkouts sit in a `.delta` directory inside a local clone, or in a fully managed directory when there is none; archiving a thread removes its checkout, which is "re-create[d] on demand when you open an old thread, as long as its recorded worktree history is available". "Delta does not use git worktrees for its managed checkouts … to avoid limitations around how many threads can work on one branch." A new checkout runs `.agents/prepare` (or `.delta/prepare`), and `.agents/linked` lists ignored files, such as `.env`, to symlink from a shared location. A thread may instead adopt an existing checkout, after which "the location is locked" ([Delta Worktrees](https://delta.dev/docs/concepts/worktrees); [Prepare your project](https://delta.dev/docs/configuration/project-setup)).

### 1.6 How people and agents share a thread

- **Access** is "Only people invited", an organization, or "Anyone with the link"; only the owner changes it. Sharing a thread grants access to its repositories, and "Delta worktree history access is repository-wide" ([Collaborate in a Thread](https://delta.dev/docs/collaboration/collaborate-thread#choose-who-can-access-a-thread); [Data Storage](https://delta.dev/docs/privacy-and-security/data-storage#where-your-data-lives)).
- **Joining** on a desktop "creates isolated checkouts for any attached projects", even when the joiner has the repository already; browser participants use the replicated files.
- **The conversation is a shared document.** Drafts are visible as they are typed and anyone can edit them; "There is no way to send a message to collaborators only." Participants can follow each other between files, diffs and subthreads.
- **Review** happens in a review subthread with "its own isolated copy of the parent thread's worktrees"; reviewers submit an approval or change request back to the parent ([delta-public-beta](https://zed.dev/blog/delta-public-beta); [Review & Sync](https://delta.dev/docs/agents/review-and-sync)). Landing runs a project skill marked `delta-action: land` in a dedicated Land subthread.
- **Agents message each other** across threads ("Sent Agent Message" and "Received Agent Message" events), and forks start "from the source thread's recorded conversation and worktree state" ([Threads](https://delta.dev/docs/agents/threads#send-information-to-another-agent)).

### 1.7 The Claude Code plugin

The plugin "gives every agent thread a URL": Claude Code sessions "are recorded to Delta along with the Git checkout they work in", and teammates join "from their own Claude Code session, from delta.dev, or from the Delta app" ([README](https://github.com/zed-industries/delta-claude/blob/500bde479759fa0d62a7e525afda7b9ccd6e9a5c/README.md?plain=1#L1-L6)). A repository's sync choice (private, team, manual) is saved in `.delta/settings.json` and kept out of Git. Delta stores "your conversation, including tool inputs and outputs and Claude's thinking, plus the files in your checkout", and "a shared or joined session shows you as connected through Claude Code" ([README](https://github.com/zed-industries/delta-claude/blob/500bde479759fa0d62a7e525afda7b9ccd6e9a5c/README.md?plain=1#L94-L103)).

In the source, a Claude Code session is bound to a thread as a producer named by source and external id: the plugin runs `delta thread create|status|append|watch --source claude-code --external-id <Claude session id>`, and "every append names the producer, retries included, so attribution never depends on a live watch" ([`delta-cli.ts`](https://github.com/zed-industries/delta-claude/blob/500bde479759fa0d62a7e525afda7b9ccd6e9a5c/hooks/cli/delta-cli.ts#L225-L345)). Joining "a shared thread in a fresh session, in the thread's checkout" mounts the thread's worktrees on the joiner's machine through `delta thread mount` ([README](https://github.com/zed-industries/delta-claude/blob/500bde479759fa0d62a7e525afda7b9ccd6e9a5c/README.md?plain=1#L83); [`join.ts`](https://github.com/zed-industries/delta-claude/blob/500bde479759fa0d62a7e525afda7b9ccd6e9a5c/hooks/sharing/join.ts#L116-L121)), and a watch delivers other participants' turns into that Claude Code transcript ([`watch.ts`](https://github.com/zed-industries/delta-claude/blob/500bde479759fa0d62a7e525afda7b9ccd6e9a5c/hooks/watch/watch.ts#L1-L4)). Each participant's Claude Code runs on their own machine and their own login; the thread joins their sessions into one record.

### 1.8 Zed's editor: CRDT collaboration, channels, the agent panel, and ACP

- **Channels** are "persistent rooms for team collaboration" with shared projects, voice and Markdown channel notes. Sharing a project lets members "edit the code hosted on your machine as though they had it checked out locally"; guests are read-only, and "sharing a project gives collaborators access to your local file system within that project" ([channels](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/collaboration/channels.md?plain=1#L8-L62); [overview](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/collaboration/overview.md?plain=1#L19)). The project stays on the host's machine; collaborators edit replicas.
- **Agent paths.** Zed has three: the Zed Agent (Zed's own loop, providers, profiles, skills), External Agents ("ACP agent process and its own auth/config"), and Terminal Threads, which run an agent's CLI in a terminal ([agents.md](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/ai/agents.md?plain=1#L10-L15)). External agents "usually own [their] own runtime, auth, model selection, tools, and native configuration"; "Zed does not charge for External Agents"; Zed profiles and skills do not apply to them ([external-agents.md](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/ai/external-agents.md?plain=1#L123-L140)). Zed's "agent profiles" are tool and model presets (`Write`, `Ask`, `Minimal`), not identities ([agent-profiles.md](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/ai/agent-profiles.md)).
- **Where agents run.** In an SSH remote project, Zed's UI and model calls stay local while "the source code, language servers, tasks, and the terminal all run on the remote server" ([remote-development.md](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/remote-development.md?plain=1#L19)); an External Agent's process is launched through the project's remote client, so it runs on the remote host ([`transport.rs`](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/crates/agent_servers/src/acp/transport.rs#L30-L80)). In a project joined through collaboration, only the Zed Agent is offered: "Collab workspaces only support NativeAgent" ([`agent_panel.rs`](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/crates/agent_ui/src/agent_panel.rs#L1376-L1388)). Threads are stored in a local SQLite database ([`db.rs`](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/crates/agent/src/db.rs#L392)).
- **Parallel agents and worktrees.** Threads can run in a new Git worktree created in detached HEAD; archiving a thread "saves the worktree's Git state and removes it from disk. Restoring the thread from history restores the worktree" ([parallel-agents.md](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/ai/parallel-agents.md?plain=1#L82-L92)). Zed can import an external agent's existing threads into its history ([L46-L50](https://github.com/zed-industries/zed/blob/389c22e1c747d1a433c3b51c176936166c9cc1cf/docs/src/ai/parallel-agents.md?plain=1#L46-L50)).
- **Relation to Delta.** Zed's agent threads are local and single-user; channels share a machine's project with people, not agents' threads. Delta moves the thread into a replicated store and lets agents run on any participant's machine. DeltaDB has not reached Zed.

## 2. The agent as a teammate or seat

### 2.1 GitHub Copilot cloud agent

- **What an agent is.** A delegated task, run as a session, started from the Agents tab, a chat, or by assigning an issue to Copilot or mentioning `@copilot` on a pull request ([Copilot on GitHub.com](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github); [using the cloud agent](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github)). Copilot appears in the Assignees list like a person. Third-party agents (Anthropic Claude through the Claude Agent SDK, OpenAI Codex through the Codex SDK) can be assigned the same way, in public preview, and "can be powered by your existing Copilot subscription" ([third-party agents](https://docs.github.com/en/copilot/concepts/agent-capabilities/about-agents/about-third-party-coding-agents)). A custom agent is an "agent profile", a Markdown file in `.github/agents/` (or an organization's `.github-private`) with a name, description, tools, MCP servers and a prompt of up to 30,000 characters ([custom agents](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/create-custom-agents)).
- **What persists.** Copilot Memory stores "repository-level facts", with citations checked against the current branch and created only from activity of users with write access, and "user-level preferences" owned by the user's billing entity; unused entries are deleted after 28 days ([Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory)).
- **Attribution and approval.** "Copilot cloud agent's commits are authored by Copilot, with the developer who assigned the issue or requested the change to the pull request marked as the co-author"; commits are signed and link to the session log. Copilot pushes to one `copilot/` branch, cannot mark its pull request ready, approve or merge, and the person who asked for the pull request cannot approve it. When Copilot opens a pull request "under its own app identity", one more approval is required. Automations are "attributed to the user who created the automation" ([risks and mitigations](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)).
- **Where it runs.** "Its own ephemeral development environment, powered by GitHub Actions", prepared by `.github/workflows/copilot-setup-steps.yml`, on standard, larger or self-hosted runners ([agent environment](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)); one repository per task and at most 59 minutes per session.
- **Local sessions, steered remotely.** Copilot CLI's remote control lets the same account steer a local session from GitHub.com or GitHub Mobile: the session "continues to run on your local machine", events go to GitHub, remote commands are polled, both interfaces are live, and "Copilot CLI uses the first response it receives to any prompt or permission request". Only the account that started the session can use it ([remote control](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-remote-control)).

### 2.2 Linear's agent API (Developer Preview)

- **What an agent is.** An app user: "Agents behave similar to other users in a workspace. They can be @mentioned, delegated issues through assignment, create and reply to comments." An OAuth installation with `actor=app` acts as the app; the app has "a unique ID for each workspace it is installed within"; its name and icon are how it appears; installed agents are not billable users ([Getting Started](https://linear.app/developers/agents)). Scopes `app:assignable` and `app:mentionable` opt into delegation and mentions. "Assigning an issue to your app now sets it as the delegate, not the assignee—so humans maintain ownership while agents act on their behalf."
- **What persists.** Linear keeps an `AgentSession` per mention or delegation, with states `pending`, `active`, `error`, `awaitingInput`, `complete` and `stale`, and the agent's activities (`thought`, `elicitation`, `action`, `response`, `error`) as "frozen-in-time snapshots"; `externalUrls` point at the agent's own dashboard or pull request ([Agent Interaction](https://linear.app/developers/agent-interaction); [best practices](https://linear.app/developers/agent-best-practices)). Workspace and team "guidance" reaches each session in `promptContext`.
- **Where it runs.** Wherever the developer hosts it: Linear sends webhooks (answer within 5 seconds, first activity within 10) and the agent posts activities back. Linear's demo agent is built on its TypeScript SDK and Cloudflare.
- **Attribution.** With actor authorization, "actions performed with the received OAuth token will come from the app itself", optionally shown as "User (via Application)" ([OAuth actor authorization](https://linear.app/developers/oauth-actor-authorization)).

### 2.3 Devin

- **What an agent is.** A Devin session, in Devin's cloud, from the web app, Slack, Linear, the Devin CLI or Desktop. Long-lived agents exist as configurations of sessions: a "Triage Devin" is "a persistent Devin session that monitors a Slack channel" and spawns child sessions, sharing "a persistent scratchpad" that stores "context that persists across session restarts" (now legacy, replaced by Devin Oncall); an automation can either "Start session" per event or "Message session", which "sends a message to an existing, long-running Devin session" ([Auto-triage](https://docs.devin.ai/product-guides/auto-triage); [Automations](https://docs.devin.ai/product-guides/automations)).
- **What persists.** Memory is "personal to you within each organization", kept in "a memory drive: a persistent Git repository of Markdown notes" with a `MEMORY.md` index. Each session gets its own checkout; Devin commits edits and merges other sessions' changes, rejecting and retrying stale writes. "New memories apply to future sessions, not the one that wrote them." "Sessions started by automations don't read or write your memory." A daily "Dreaming" session consolidates notes. The format is the open Agent Memory Repo spec ([Memory](https://docs.devin.ai/product-guides/memory); [spec README](https://github.com/AgentMemoryRepo/agentmemoryrepo/blob/8798cb26c817d451a5ed6cba0ad8d9eca8d5ec3e/README.md)).
- **Credentials and attribution.** An organization-wide GitHub App, plus optional per-user linking "so that Devin can act under their identity". "Open PRs as" is Devin, the user, or user only; commit authoring has modes from "Devin only" to "You as author, Devin as committer". "Every Devin session boots from a fresh copy of the machine image", so keys must be configured in the environment ([GitHub integration](https://docs.devin.ai/integrations/gh)).
- **Where it runs.** A VM per session built from blueprints, or an Outpost: "Devin's agent loop … continues to run in Devin's cloud, while all command execution, file edits, and repository access happen on machines you operate", served by workers that "only need outbound HTTPS" ([Outposts](https://docs.devin.ai/cloud/outposts/overview)). Local Hands gives a cloud session a second set of tools on the owner's computer through `devin connect`, each call approved by default; only the session owner can connect, and connecting makes the session private ([Local Hands](https://docs.devin.ai/work-with-devin/local-hands)).
- **Local to cloud.** `/handoff` in the Devin CLI "packages up the conversation context and current git branch" into a cloud session; a plugin does the same from Claude Code or Codex, including `git diff HEAD` up to 100 KB ([handoff](https://docs.devin.ai/work-with-devin/devin-handoff)).

## 3. Cloud task agents in sandboxes

### 3.1 Cursor Cloud Agents

- **What an agent is.** A durable record with runs. `POST /v1/agents` "returns both the durable `agent` and the initial `run`"; a follow-up is a run that "uses the agent's current conversation and workspace state". An agent is `ACTIVE`, `IDLE` (its machine "may be hibernated or snapshotted") or `ARCHIVED` ([API](https://cursor.com/docs/cloud-agent/api/endpoints)).
- **What persists.** Conversation, workspace state, and the environment (agent-led setup, a snapshot, or a Dockerfile in `.cursor/environment.json`). Secrets are team-scoped. User-level hooks are unavailable "since cloud VMs don't have access to your local home directory" ([Cloud Agents](https://cursor.com/docs/cloud-agent)). An agent can mint OIDC tokens "bound to that agent and owner", with claims such as `cloud_agent_id` and `agent_runtime: managed` or `self_hosted` ([OIDC tokens](https://cursor.com/docs/cloud-agent/identity)).
- **Where it runs.** Isolated VMs that clone the repository and "work on a separate branch, then push changes to your repo for handoff". With My Machines, "a worker on your machine opens an outbound connection to Cursor. The agent loop runs in Cursor's cloud, but terminal commands, file edits, browser actions, and other tool calls execute on your machine" ([My Machines](https://cursor.com/docs/cloud-agent/self-hosted/my-machines)). The agent is not tied to a worker: releasing one "clears the claim and the agent's worker assignment together … The agent's next turn runs on another worker" ([API](https://cursor.com/docs/cloud-agent/api/endpoints)).
- **Local and cloud.** The Agents Window can "quickly move an agent from cloud to local to iterate quickly, and move it back to the cloud" ([Agents Window](https://cursor.com/docs/agent/agents-window)). Local worktrees are cleaned up to a machine-wide cap, 25 by default ([Worktrees](https://cursor.com/docs/configuration/worktrees#worktrees-cleanup)).
- **Sharing.** A teammate with access to the repository can open an agent's URL; "Viewing is read-only" unless an admin enables team follow-ups.

### 3.2 OpenAI Codex cloud, and remote connections

- **What an agent is.** A Codex chat or task. A chat runs Local, in a Worktree ("Both Local and Worktree chats run on your computer"), or in the Cloud, from a published environment; "Each Cloud task has its own working files", and "your computer's local files, running processes, browser sign-ins, and VPN access aren't automatically transferred" ([Codex environments](https://learn.chatgpt.com/docs/environments/modes); [Codex Cloud](https://learn.chatgpt.com/docs/cloud)).
- **What persists.** Instructions in layered `AGENTS.md` files, global under `~/.codex` and per project ([AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)); local Codex clients "use a separate local memory store" per machine ([Memories](https://learn.chatgpt.com/docs/customization/memories)).
- **Worktree lifecycle.** Managed worktrees live under `$CODEX_HOME/worktrees`; Codex keeps the most recent 15, never deletes one tied to a pinned or running chat, deletes one when its chat is archived, and "before deleting a Codex-managed worktree, Codex saves a snapshot of the work on it" that a reopened chat can restore. "Permanent worktrees" are never deleted automatically ([Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)).
- **Remote connections.** The ChatGPT mobile app controls chats on a connected Mac or Windows host, using "the connected host's projects, chats, files, credentials, permissions"; a QR code "pairs that phone with that host". With "Local computer access with Work Cloud", "OpenAI's cloud coordinates the task, and an online, connected computer can execute steps", and if the computer is unavailable when a turn starts the task "can continue in a cloud container", though "a task cannot switch from local execution to the cloud during a turn" ([Remote connections](https://learn.chatgpt.com/docs/remote-connections)).

### 3.3 Claude Code in the cloud

- **Cloud sessions.** "A Claude Code session that runs on cloud infrastructure instead of on your machine", Anthropic's or an organization's self-hosted environment; started from the browser, the mobile app, Desktop, `claude --cloud`, or scheduled tasks. In Anthropic-hosted environments, "your GitHub credentials stay encrypted on Anthropic's servers and never enter a session's VM"; a GitHub proxy attaches them ([cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)). When a VM is reclaimed after inactivity, reopening the session provisions a fresh VM: the conversation is restored, running shell commands and subagents are not.
- **Handoff.** From the CLI it is one-way: `--teleport` pulls a cloud session and its branch into the terminal, and "the terminal gets its own copy of the session". Desktop can send a local session to the cloud. Teleport requires the same claude.ai account, a clean working tree and a pushed branch.
- **Sharing.** Private or Team (Team and Enterprise) or Private or Public (Pro and Max); "recipients see the latest state … but their view doesn't update in real time".
- **Remote Control.** A local session "makes outbound HTTPS requests only and never opens inbound ports"; it "registers with the Anthropic API and polls for work". While connected, "the session transcript … is stored on Anthropic servers" so devices stay in sync; "execution and filesystem access stay on your machine". Trusted Devices ties access to an enrolled device and a sign-in at most 18 hours old ([Remote Control](https://code.claude.com/docs/en/remote-control)). Anthropic's own guidance: "If you want to run Claude Code on your own always-on machine and drive it from other devices, use Remote Control" ([self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)).
- **Projects** (public beta, Pro and Max): "one coordinating conversation with Claude plus the threads it starts". Every cloud thread starts with project instructions (up to 16,000 characters) and project memory, "notes Claude keeps about the project … stored as files", with a `MEMORY.md` index. A thread can run on the person's computer through Remote Control; it then "starts with the project's instructions, but not with its memory files loaded" ([Projects](https://code.claude.com/docs/en/claude-projects)).
- **Scheduled tasks** "belong to your individual claude.ai account"; "Commits and pull requests carry your GitHub user." A fired prompt is attested as stored by an authorized session and "can't act as approval or consent for actions during the run" ([scheduled tasks](https://code.claude.com/docs/en/routines)).
- **Cross-session messaging** reaches a person's sessions "on other machines or in the cloud" through Anthropic's servers while Remote Control is connected; `isolatePeerMachines` requires approval for such messages ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)).
- **Local identity on disk.** Auto memory lives at `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index, keyed by the Git repository; it "is machine-local … Files are not shared across machines or cloud environments" ([memory](https://code.claude.com/docs/en/memory)). Claude Code reads `CLAUDE.md`, or a repository's `AGENTS.md`. Logins live in the macOS Keychain or, on Linux, in `~/.claude/.credentials.json` with mode 0600; `CLAUDE_CONFIG_DIR` relocates them. In SSH sessions and containers, login shows a code to paste. "A … Remote Control session that outlives the login stops making progress once the credential expires" ([authentication](https://code.claude.com/docs/en/authentication)).

### 3.4 Claude Managed Agents

Anthropic's hosted agent harness, in beta (`managed-agents-2026-04-01`), has four concepts: an **agent** ("the model, system prompt, tools, MCP servers, and skills"), an **environment** (Anthropic's cloud sandbox or a self-hosted one), a **session** ("a running agent instance within an environment"), and **events** ([overview](https://platform.claude.com/docs/en/managed-agents/overview)).

- An agent is "a reusable, versioned configuration that defines persona and capabilities", referenced by ID; each change increments `version` ([agent setup](https://platform.claude.com/docs/en/managed-agents/agent-setup)).
- Memory stores are workspace-scoped collections of documents mounted as a directory in the session's sandbox; "every change to a memory creates an immutable memory version" ([memory](https://platform.claude.com/docs/en/managed-agents/memory)).
- Vaults hold an end user's credentials, referenced per session: "you can manage your product at the `agent` resource granularity and your users at the `session` resource granularity" ([vaults](https://platform.claude.com/docs/en/managed-agents/vaults)).
- A self-hosted environment "acts as a work queue": a worker on the customer's infrastructure claims sessions and runs tool calls, while "Anthropic keeps running the agent" ([self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)).
- Scheduled deployments start a new session on a cron schedule; on Claude Platform on AWS each run's session is created as a configured IAM role ([scheduled deployments](https://platform.claude.com/docs/en/managed-agents/scheduled-deployments)).

## 4. Persistent, stateful agents

### 4.1 Letta

- **What an agent is.** "A persistent AI identity with its own memory, model configuration, tools, and message history", with a name, a personality, MemFS memory and "one or more conversations" ([Stateful agents](https://docs.letta.com/concepts/stateful-agents)). The SDK separates three things: "An agent is the persistent entity with memory. A conversation is a thread on that agent. A session is the active connection" ([Sessions](https://docs.letta.com/agent-sdk/sessions)). Agent IDs are `agent-xxx` in Letta Cloud and `agent-local-xxx` locally. Letta Code's system prompt states the model plainly: "the model or machine you run on today will change many times across your lifetime — the model is the engine; *you* are the tokens", and "all of this memory belongs to a single agent identity, identified by a unique `agent_id`" ([prompt](https://github.com/letta-ai/letta-code/blob/035bb8c8917b5dd94a3989d4adf04860a2ce8fea/src/agent/prompts/letta_local_memfs.md?plain=1#L3-L6)).
- **What persists.** Memory is shared across an agent's conversations. MemFS is "a git-backed projection" of memory blocks and files; "Editing memory does NOT change your behavior in the current turn" because the prompt is compiled at the start of a conversation. Message history is kept as immutable recall memory. Secrets are kept out of memory, since "memory is git-tracked and may be synced off this machine" (same prompt).
- **Where it runs.** "The agent's identity and memory are separate from the computer": the current machine, a Letta cloud sandbox, or a connected machine (`letta server --computer-name …`) ([Computers](https://docs.letta.com/platform/computers); [README](https://github.com/letta-ai/letta-code/blob/035bb8c8917b5dd94a3989d4adf04860a2ce8fea/README.md?plain=1#L66-L105)). Teleportation moves an active conversation between computers. Memory, MemFS, message history, pending tool approvals and permission mode move; files, running processes, credentials and installed software stay. Letta Cloud asks the source to release the conversation, then starts it on the destination. "Agents on a local backend cannot teleport", and agents created without an account "are stored only on local disk" ([Teleportation](https://docs.letta.com/platform/computers/teleportation)).
- **Agent File.** `.af` packages model configuration, message history, system prompt, memory blocks, tool rules, environment variables and tools; secrets are set to null on export ([agent-file README](https://github.com/letta-ai/agent-file/blob/78212eb571e59e10b35b924375a997319b89c280/README.md?plain=1#L171-L201)). Letta Code has deprecated and removed `.af` import and export ([README](https://github.com/letta-ai/letta-code/blob/035bb8c8917b5dd94a3989d4adf04860a2ce8fea/README.md?plain=1#L106-L109)).

### 4.2 OpenClaw

- **What an agent is.** "The full per-persona scope: workspace files, auth profiles, model registry, and session store" ([multi-agent](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/multi-agent.md?plain=1#L9-L30)). The default agent is `main` and its main session key is `agent:main:main` ([L60-L66](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/multi-agent.md?plain=1#L60-L66)). Bindings route a channel account (a WhatsApp number, a Slack workspace) to an agent. The loop is a separate choice: an agent runtime "owns one prepared model loop", the built-in `openclaw` runtime or a harness such as `codex` (app-server), `copilot`, a `claude-cli` backend, or Codex over ACP ([agent-runtimes](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/agent-runtimes.md?plain=1#L10-L40)).
- **What persists.** The workspace is the agent's "only working directory" and holds `AGENTS.md`, `SOUL.md` (persona and tone), `IDENTITY.md` (name and emoji), `USER.md`, a one-time `BOOTSTRAP.md`, and `MEMORY.md`, injected on a session's first turn ([agent.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/agent.md?plain=1#L15-L40)). "The model only remembers what gets saved to disk; there is no hidden state": `USER.md`, `MEMORY.md`, dated `memory/YYYY-MM-DD.md` notes, and `DREAMS.md` ([memory.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/memory.md?plain=1#L9-L35)). Auth profiles are per agent in `<agentDir>`, and "never reuse `agentDir` across agents".
- **Where it runs.** One Gateway per host "owns sessions, auth profiles, channels, and state; everything else is a client". It binds to loopback and is reached through Tailscale Serve, a trusted LAN or tailnet bind, or an SSH tunnel; "Always-on Gateway in your tailnet" on a VPS or home server is a recommended topology ([remote.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/gateway/remote.md?plain=1#L8-L30)). A cloud session's coding work can be placed on a paired device or a throwaway cloud worker, while "the Gateway stays the owner of the conversation, the reconciled workspace, model credentials, and placement records"; "provider credentials never reach the remote machine" ([cloud-sessions.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/gateway/cloud-sessions.md?plain=1#L10-L20)).
- **Managed worktrees.** Recorded in the state database, stored under `<state-dir>/worktrees` or a configured `worktreeRoot` "without placing temporary directories inside the source repository". Removal first snapshots tracked and non-ignored files to `refs/openclaw/snapshots/<id>`; at run end a worktree is removed only if clean with no unpushed commits; idle worktrees are snapshotted and removed after 7 days; snapshots stay restorable for 30 days; a global cap (default 4096) can evict without a snapshot ([managed-worktrees.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/managed-worktrees.md?plain=1#L449-L473)).
- **Several people.** "Session ownership, visibility in the sidebar, and presence indicators are usability features, not security boundaries"; isolation needs separate agents or separate Gateways ([multi-user.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/concepts/multi-user.md?plain=1#L13-L16)).
- **Service.** On Linux the Gateway is a systemd user unit with `TimeoutStopSec=330` for "the Gateway's five-minute cooperative drain", and warns that Ubuntu 24.04's user manager allows five seconds at shutdown ([linux.md](https://github.com/openclaw/openclaw/blob/969d4e53445c80e060e170f267fa73981be6254b/docs/platforms/linux.md?plain=1#L565-L600)).

### 4.3 Hermes Agent

- **What an agent is.** Hermes separates the two words: a **profile** "is the persistent home for an assistant's configuration and data", a separate Hermes home with `config.yaml`, `.env`, `SOUL.md`, memories, sessions, skills, cron jobs and a state database; the **agent** is "the running Hermes assistant that uses that configuration and state" ([profiles](https://github.com/NousResearch/hermes-agent/blob/3d7e687462ca8edfa52142a4dafad12def723bd7/website/docs/user-guide/profiles.md?plain=1#L9-L40)). "Never point two agent processes at the same profile … two writers on one home compound each other's state."
- **What persists.** `MEMORY.md` (2,200 characters) and `USER.md` (1,375), "injected into the system prompt as a frozen snapshot at session start" and edited through a `memory` tool ([memory](https://github.com/NousResearch/hermes-agent/blob/3d7e687462ca8edfa52142a4dafad12def723bd7/website/docs/user-guide/features/memory.md?plain=1#L13-L28)).
- **Where it runs.** The profile lives on the machine running Hermes; shell commands run on one of seven backends: local, Docker, SSH, Modal, Daytona, Vercel Sandbox or Singularity ([configuration](https://github.com/NousResearch/hermes-agent/blob/3d7e687462ca8edfa52142a4dafad12def723bd7/website/docs/user-guide/configuration.md?plain=1#L225-L229)). Each profile's gateway installs as a LaunchAgent or a systemd user service, and the docs recommend `loginctl enable-linger` so user units keep "running across SSH disconnects and reboots" ([multi-profile gateways](https://github.com/NousResearch/hermes-agent/blob/3d7e687462ca8edfa52142a4dafad12def723bd7/website/docs/user-guide/multi-profile-gateways.md?plain=1#L1068-L1082)).
- **Over ACP.** Hermes runs as an ACP agent; "ACP is a good fit when you want Hermes to keep its existing identity, provider setup, memory, skills, and tools while another application owns the conversation transport" ([ACP](https://github.com/NousResearch/hermes-agent/blob/3d7e687462ca8edfa52142a4dafad12def723bd7/website/docs/user-guide/features/acp.md?plain=1#L13-L25)).

### 4.4 OpenAI dots

Not in the brief, but OpenAI's persistent agent product. "Your dot is an always-on agent" that "lives in the cloud and has its own computer and browser"; you name it, and its handle follows the name (`@tibo-alfred`) ([Meet dots](https://learn.chatgpt.com/docs/dots)).

- **One identity across channels.** "You reach the same dot in ChatGPT, Slack, Teams, or a call. Changing where you talk to it doesn't start a new dot or reset its memory."
- **What persists.** ChatGPT memory plus "its own saved notes about your preferences, decisions, and ongoing work". Work is delegated to background agents, cloud threads, or Codex tasks, each of which "has its own conversation" ([Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)).
- **Where it runs.** Its cloud computer, plus "only one personal computer at a time", which must be online with the ChatGPT app open; "changing your dot's selected computer doesn't move an existing task to that computer". It "can decide when to pause and wake up to continue work", runs saved schedules, and watches events in connected services.

### 4.5 Cloudflare Agents SDK

- **What an agent is.** A named Durable Object instance: "`Agent` directly extends Cloudflare's `DurableObject`, so every Agent is a globally addressable, single-threaded compute instance with durable KV/SQLite storage" ([agent-class.md](https://github.com/cloudflare/agents/blob/e18c094da1301499b2536e90f5208cd727fdbb10/docs/agents/agent-class.md?plain=1#L9)). Requests route to `/agents/{agent-name}/{instance-name}`, or by `getAgentByName` ([routing.md](https://github.com/cloudflare/agents/blob/e18c094da1301499b2536e90f5208cd727fdbb10/docs/agents/routing.md?plain=1#L5-L20)). "This is the actor model: each agent has an identity, durable state, and wakes on message"; a hibernated agent "consumes zero compute", and identity and routing are "built-in (name → agent)" ([long-running-agents.md](https://github.com/cloudflare/agents/blob/e18c094da1301499b2536e90f5208cd727fdbb10/docs/agents/long-running-agents.md?plain=1#L9-L21)).
- **What persists.** State and SQL in the object, schedules (alarms), and WebSocket connections that stay open while the object leaves memory ([lifecycle.md](https://github.com/cloudflare/agents/blob/e18c094da1301499b2536e90f5208cd727fdbb10/docs/agents/lifecycle.md?plain=1#L453-L463)).
- **Patterns relevant to an edge.** Webhooks route to "dedicated agent instances", one per source, after verifying signatures ([webhooks.md](https://github.com/cloudflare/agents/blob/e18c094da1301499b2536e90f5208cd727fdbb10/docs/agents/webhooks.md?plain=1#L3)). Push notifications store browser Web Push subscriptions in agent state and send through VAPID when an alarm fires ([push-notifications.md](https://github.com/cloudflare/agents/blob/e18c094da1301499b2536e90f5208cd727fdbb10/docs/agents/push-notifications.md?plain=1#L3-L20)).

## 5. Protocols

### 5.1 ACP

- **`agentInfo` describes the program.** "Both Clients and Agents SHOULD provide information about their implementation in the `clientInfo` and `agentInfo` fields": `name`, `title` and `version`; "in future versions of the protocol, this information will be required" ([initialization](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/protocol/v1/initialization.mdx?plain=1#L301-L322)). The registry's `id` names an agent program and how to obtain it ([registry RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/rfds/acp-agent-registry.mdx?plain=1#L30-L37)). The Agent assigns a `sessionId` "that identifies this conversation" ([session setup](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/protocol/v1/session-setup.mdx?plain=1#L71)). Nothing in v1 names an agent instance, a persona, an owner, or memory.
- **Persona.** The draft "client system prompt" RFD notes that today "behavioral instructions, persona definitions, and platform context all compete with user content in the same message role" and proposes system-level instructions from the client ([RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/rfds/client-system-prompt.mdx?plain=1#L12)).
- **User identity.** The completed elicitation RFD binds an agent's OAuth state to the user: "When an Agent authenticates users, state MUST be bound to the Agent-authenticated user" ([RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/rfds/elicitation.mdx?plain=1#L792-L797)).
- **Remote agents.** v1 defines stdio, where "the client launches the agent as a subprocess" ([transports](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/protocol/v1/transports.mdx?plain=1#L17-L21)). The Streamable HTTP and WebSocket RFD is Active and targeted at v1. It separates `Acp-Connection-Id` from `Acp-Session-Id`, promises that "sessions survive disconnects" (resumed through `session/load`), and says "in-flight messages are not replayed" until v2 adds message IDs and resumable streams ([RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/rfds/streamable-http-websocket-transport.mdx?plain=1#L12-L90)). Authentication "is orthogonal and layered on" ([L405-L410](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/rfds/streamable-http-websocket-transport.mdx?plain=1#L405-L410)).
- **Subagents** (draft RFD) give each child its own session ID, with `senderSessionId` and `recipientSessionId` on messages between sessions ([RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/rfds/subagents.mdx?plain=1#L12-L25)).
- **Statuses** at this commit: session compaction, additional directories, session list, resume, close and delete are Completed; Streamable HTTP is Active; subagents, MCP-over-ACP, proxy chains and the client system prompt are Draft ([docs.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/c9806acdd794362cdc0a9f3f59ce7123b431c104/docs/docs.json#L186-L260)).

### 5.2 A2A Agent Cards

- **The card is the server's identity.** "A2A Servers MUST make an Agent Card available. The Agent Card describes the server's identity, capabilities, skills, and interaction requirements", discovered at `/.well-known/agent-card.json`, through registries, or by configuration, and optionally signed with JWS ([spec §8](https://github.com/a2aproject/A2A/blob/98279d62316361ba8451eaef300f72b72e169185/docs/specification.md?plain=1#L1974-L2012)). Its fields are a name, description, version, provider (organization and URL), interfaces (URL, protocol binding, `tenant`), capabilities (streaming, push notifications, extensions, an extended card for authenticated clients), security schemes, skills and an icon ([a2a.proto](https://github.com/a2aproject/A2A/blob/98279d62316361ba8451eaef300f72b72e169185/specification/a2a.proto#L336-L420)).
- **Identity is an endpoint.** The client verifies the server's TLS certificate and authenticates with credentials obtained out of band; the server authorises "based on the authenticated identity and its own policies" ([§7](https://github.com/a2aproject/A2A/blob/98279d62316361ba8451eaef300f72b72e169185/docs/specification.md?plain=1#L1877-L1910)).
- **Continuity** is a server-generated, opaque `contextId` that groups tasks and messages "part of the same conversational session"; agents "MAY implement context expiration" ([§3.4](https://github.com/a2aproject/A2A/blob/98279d62316361ba8451eaef300f72b72e169185/docs/specification.md?plain=1#L584-L646)). Several clients may stream the same task, and push notifications are webhooks the agent POSTs to client-registered endpoints ([§3.5](https://github.com/a2aproject/A2A/blob/98279d62316361ba8451eaef300f72b72e169185/docs/specification.md?plain=1#L646-L700)).

## 6. Other shared workspaces

### 6.1 Amp

- **Threads** are private, workspace-wide, or group-visible; workspace-owned projects share by default ([Threads](https://ampcode.com/docs/threads)).
- **Multiplayer** lasts 7 days on a thread running in an orb or on a shared runner. "All agent and orb costs are billed to the thread owner." "The agent calls your remote MCP servers with your credentials, including when a teammate prompts it." Threads on a runner that has not been shared cannot become multiplayer, "because that would give your teammates access to a machine you never shared" ([Multiplayer](https://ampcode.com/docs/collaborate/multiplayer)).
- **Orbs** are remote machines that sleep when idle and wake "with your conversation, files, and services still in place" ([Orbs](https://ampcode.com/docs/orbs)). Runners (`amp --no-tui --runner-id …`) run remotely created threads on a person's own machine ([Runners](https://ampcode.com/docs/cli/runners)), and cross-client access continues a running CLI thread from the web ([Cross-Client Access](https://ampcode.com/docs/cli/remote-control)).
- **Puck** is "your personal Amp assistant" that starts and monitors agents; "Each conversation has its own history and its own Puck" ([Puck](https://ampcode.com/docs/puck)).
- **Commit identity.** Amp acts on GitHub as the user through a GitHub App. A per-user or per-project Git identity sets the author; in "Amp" mode, `Amp <amp@ampcode.com>` is the author and the user a co-author ([GitHub & Git](https://ampcode.com/docs/github)).

### 6.2 Coder

- **Coder Agents** runs "the agent loop directly within the Coder control plane", so "workspaces can be completely network isolated"; it is "not a wrapper around third-party agent tools like Claude Code or Codex" ([Coder Agents](https://coder.com/docs/ai-coder/agents)).
- **Agent Relay** (closed preview) connects Cursor Cloud Agents and Claude Code hosted sessions to self-hosted workspaces, where "a worker process inside the workspace executes the agent's tool calls".
- **Vendor CLIs in workspaces.** Templates can also install Claude Code or Codex directly into a workspace ([Run AI Coding Agents](https://coder.com/docs/ai-coder)). The Claude Code module accepts an API key, an `apiKeyHelper`, Coder's AI Gateway, or a "Claude.ai OAuth token … generate one by running `claude setup-token` locally and pass it as `claude_code_oauth_token`", a Terraform variable of the workspace template ([module README](https://github.com/coder/registry/blob/01a5e162d165e80b78a10bf81742acc96a5c2c36/registry/coder/modules/claude-code/README.md?plain=1#L27-L32)).

### 6.3 Left out, and why

- **Ona (formerly Gitpod) and Replit** were checked only at their documentation indexes. Ona's environments with agents in them, run on the customer's cloud, are the same placement pattern as Devin Outposts, Cursor My Machines, Claude Code self-hosted environments, Managed Agents self-hosted sandboxes and Coder. Replit's agent builds apps in Replit's workspace, and its collaboration adds nothing that Delta and Amp do not already show.
- **Sourcegraph Amp** is covered in 6.1.
- **VS Code's agent sessions and Gemini CLI** appear only as clients of the products above.

## 8. Patterns across the products

- **The durable unit is a conversation record, not a process.** Delta's thread (1.3), Cursor's durable agent (3.1), a Claude cloud session restored on a fresh VM (3.3), a Devin session, Linear's `AgentSession`, A2A's `contextId` and ACP's `sessionId` all outlive the process or machine that served them.
- **A second tier sits above sessions where products persist across tasks.** Letta's agent with many conversations, OpenClaw's agent with its main session, Hermes's profile, OpenAI's dot, Claude Code Projects, Devin's memory and persistent sessions, and Managed Agents' agent configuration. Where the format is documented, memory is Markdown files the agent edits, usually with a `MEMORY.md` index: Claude Code auto memory and Projects, Devin, OpenClaw, Hermes, Letta's MemFS, and the Agent Memory Repo spec. Three of them version memory with Git (Devin, Letta, Agent Memory Repo). The exceptions are Managed Agents' memory stores, documents the service versions and mounts as a directory, and Copilot Memory, a service store with citations; dots' notes are not described.
- **Memory changes apply to later sessions.** Letta, Hermes and Devin say so explicitly (4.1, 4.3, 2.3).
- **The loop and the place it acts are separated.** In Devin Outposts, Cursor My Machines and Team Pools, Managed Agents self-hosted sandboxes, Claude Code self-hosted environments, Coder Agents and Agent Relay, OpenClaw cloud sessions, Letta computers and Amp runners, the record and loop stay in a control plane while tool calls run on a placed machine. Identity moves because the record never lived on the machine. Paths, files, credentials and running processes do not move with it (Letta teleport, Delta runners, Codex cloud).
- **The other shape keeps the whole agent on the person's machine and relays.** Claude Code Remote Control, Copilot CLI remote control, Codex remote connections and Amp cross-client access all let the agent run where it started, with the vendor's cloud relaying clients. Claude Code and Copilot document that session events pass through their cloud, and Claude Code that it stores the transcript there.
- **Connections from the person's machines are outbound.** Every product that reaches a person's machine has it dial out: Devin, Cursor, Claude Remote Control and self-hosted runners, Managed Agents workers.
- **Credentials in cloud products sit outside the sandbox.** They are injected by a proxy or a control plane: Claude's GitHub proxy and network secrets, Delta account settings, Managed Agents vaults, OpenClaw's Gateway proxying inference. Local-first tools leave the login with the agent's own CLI (Zed External Agents, Claude Code's credentials file).
- **Attribution follows three patterns.** The agent authors and the human co-authors (Copilot, Amp's "Amp" mode, Devin's co-authored mode); the agent acts as the human (Claude scheduled tasks, Delta runners, Amp's GitHub App, Devin's "User" PRs, Copilot automations credited to their creator); or the agent is an app user acting for a human who keeps ownership (Linear delegation). Of the products surveyed, only Copilot documents that the requester cannot approve the agent's pull request.
- **Multiplayer splits on where a guest's turn runs.** Delta runs it on the guest's machine with the guest's model credentials and bills the guest; Amp runs it in the owner's orb or runner, bills the owner, and uses the owner's MCP credentials; Cursor and Claude share read-only by default.
- **Managed directories are bounded and restorable, not kept forever.** Codex keeps 15 and snapshots before deleting; Cursor caps at 25; OpenClaw cleans up after 7 idle days and keeps snapshots for 30; Zed saves Git state on archive; Delta recreates checkouts from DeltaDB history.

## 10. Fit for weave

Judged against weave at `b953de30`.

### 10.1 Where weave stands

The Host is a per-user process that runs ACP agents (Claude Code and Codex) on the person's own CLI logins, which weave never reads or stores ([`AGENTS.md`](../../AGENTS.md#L119-L120)). A session is one agent in one directory. Its journal header records the agent, the agent id it was chosen by, the directory, the permission policy and the creation time ([`journal.rs`](../../host/src/journal.rs#L80-L97)); clients attach and catch up from a position. A client chooses the directory: `session/create` and `session/run` take `{agentId, cwd, additionalDirectories?, …}` ([spec](../specs/wve-85-host-protocol.md#L384-L390), [L571-L578](../specs/wve-85-host-protocol.md#L571-L578)). Each prompt is journaled in `turnStarted` with its origin: the client, its paired device's name, or `{"run": {}}` for a headless run ([spec](../specs/wve-85-host-protocol.md#L505-L507)). Journals untouched for 14 days are pruned ([`host/AGENTS.md`](../../host/AGENTS.md#L19)). In the glossary an Agent is the ACP program ([`CONTEXT.md`](../../CONTEXT.md#L29-L31)). [ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md) keeps the agent loop in vendor ACP agents. [ADR 0017](../adr/0017-hosts-pair-as-peers-through-the-tailnet-and-are-managed-through-their-cli.md) reaches every Host through the tailnet and pairs a person's Hosts as peers, with none coordinating the others. Weave is single-user and personal by choice.

Of the two shapes in section 8, weave is the one that keeps the whole agent on the person's machine and lets clients reach it. It differs from Remote Control, Copilot CLI and Codex remote connections in that no vendor cloud relays it or stores its journal. The tailnet carries the connection, and the Host keeps the journal.

### 10.2 What the evidence says about identity, for weave

- **A session is already the durable unit.** It plays the part of Delta's thread or Cursor's agent record, but it lives on one Host. Products whose identity moves between machines (Letta, Delta, Cursor, Devin, Managed Agents, OpenClaw for its placements) move it because the record lives in a control plane that never runs on the person's machine. ADR 0017 rules out a coordinating Host, so in weave a record belongs to the Host that holds it, and moving one is an explicit act.
- **Only part of a record can move.** Letta's teleport list is the most precise evidence (4.1). Memory, history, pending approvals and the permission mode can move; files, processes and credentials cannot. A vendor agent's own conversation history stays on its machine as well: Claude Code's `--resume` reads "this machine's local history", and the CLI's teleport works only from Anthropic's cloud to a terminal (3.3). A weave session therefore cannot move to a peer Host without the agent's cooperation, but a record the Host owns (a name, a home directory, a policy, triggers) can.
- **ADR 0011 holds up.** Delta, Zed and OpenClaw sit above vendor harnesses without owning their loops: Delta records Claude Code sessions as producers in a thread (1.7), Zed hosts ACP agents that "usually [own their] own runtime, auth, model selection, tools" (1.8), and OpenClaw separates its per-persona agent from the runtime that runs each turn (4.2). Hermes shows the other direction: a persistent identity can present itself as an ACP agent and keep "its existing identity, provider setup, memory" (4.3).

### 10.3 WVE-115: the Host makes a session's directory

**Supports.**

- Host-made directories are standard: Delta's managed checkouts, Zed's and Codex's worktrees, Cursor's worktrees, OpenClaw's managed worktrees.
- Recording where a directory came from has precedents. OpenClaw records each worktree in its state database, and Delta identifies a repository by its remote URL ("Delta uses the remote to identify the repository").

**Complicates.**

- "Keeps it as long as the session can be reopened." Every product that manages directories bounds disk instead: Codex keeps 15, Cursor 25, OpenClaw cleans up after 7 idle days, Zed and Delta remove on archive. They make removal recoverable with a snapshot or a recorded history.
- In weave, "can be reopened" has two meanings. A suspended session reopens from its journal, which is pruned after 14 days untouched. A closed session can reopen from the agent's own history with no bound at all. Tying the directory's life to the journal's gives a natural bound.
- Before removing a directory, a snapshot pinned as a Git ref (OpenClaw's `refs/openclaw/snapshots/<id>`, Codex's restore offer) would let a later reopen from the agent's history restore it.
- OpenClaw's run-end rule is a safe default for what to remove: only a clean checkout with no unpushed commits.

**Adds.**

- **Plain clones or detached worktrees.** Delta avoids Git worktrees "to avoid limitations around how many threads can work on one branch", and Zed creates worktrees in detached HEAD. A per-session branch or detached HEAD avoids the one-branch-per-worktree conflict.
- **Location.** OpenClaw (`<state-dir>/worktrees`, so as not to place "temporary directories inside the source repository") and Codex (`$CODEX_HOME/worktrees`) keep managed checkouts under their own state directories, each with a configurable root. The Host's state directory (`~/.local/state/weave/daemon`) with a configurable root fits that.
- **Setup and ignored files.** Delta runs `.agents/prepare` and links ignored files listed in `.agents/linked`; Cursor reads `.cursor/worktrees.json`; OpenClaw provisions ignored files and snapshots them. Delta, OpenClaw and Letta Code all read skills from `.agents/skills`, so `.agents/` is already shared across vendors.
- **Scratch directories** have counterparts in Delta's projectless threads and OpenClaw's "New workspace starts empty".
- **Shared directories.** Delta warns that threads sharing an existing checkout "are not isolated". A record that marks a directory as adopted rather than made would let the Host warn when two open sessions use one directory.
- **What to record:** the kind (scratch, worktree or clone, or adopted), the source repository's path and remote URL, the base commit, the branch, and what created it (a client's origin or a Trigger).
- **For later sharing**, recording the remote URL and base commit, not only a path, is what lets a peer Host or a cloud Host recreate the directory. Delta and Letta both note that paths do not transfer.

### 10.4 WVE-118: always-on agents

**Supports.**

- **The record's shape is common.** Name, agent id, home directory, permission policy, Triggers, and a series of sessions with one current: OpenClaw's agent (workspace, `agentDir`, sessions, main session `agent:main:main`), Hermes's profile, Letta's agent with its conversations, OpenAI's dot, Claude Code Projects (a coordinating conversation and threads), and Managed Agents (agent configuration plus scheduled deployments).
- **Memory as files in the home directory, with no Host memory store,** is the majority design. OpenClaw says "there is no hidden state"; Hermes, Devin, Claude Code auto memory and Projects, and Letta's MemFS are all files. The vendor agents already read the files WVE-118 names: Claude Code reads `CLAUDE.md` or a repository's `AGENTS.md`, and Codex reads layered `AGENTS.md`. A session whose working directory is the home gets that memory with no Host involvement.
- **"Durable across turns, not inside one"** is exactly Letta's, Hermes's and Devin's rule (8).

**Complicates.**

- **"The latest one current."** Products offer two ways for a Trigger to reach a long-lived agent: deliver into a running session (Devin's "Message session", Triage Devin, OpenClaw's main session, a dot that "works between conversations") or start a session per occurrence (Devin's "Start session", Managed Agents deployments, Claude Code scheduled tasks, Copilot automations). Devin offers both, and so should a weave Trigger. The first relies on the vendor agent's compaction to keep a long session going; ACP session compaction is Completed at this ACP commit.
- **Two writers on one home.** Hermes forbids two processes on one profile; Devin rejects stale writes and merges; Letta versions memory in Git. If a Trigger opens a new session while the current one runs, or a peer Host's agent opens one (ADR 0017), two vendor processes may edit `CLAUDE.md` at once. The record needs a rule: either one open session per always-on agent, with Triggers queued as prompts to it, or a home under Git that tolerates merges.
- **Coding outside the home.** Dots and Claude Projects send coding work to separate tasks with their own workspace, and only OpenClaw makes the workspace the agent's only directory. An always-on agent that codes would open sessions in WVE-115 directories with the home as an additional directory, or start them through Host tools. Whether the vendor agents read instruction files from an additional directory is open (9).
- **Expiring logins.** "A … Remote Control session that outlives the login stops making progress once the credential expires" (Claude Code). An always-on agent needs a way to tell the person, as a pending request or through WVE-117.
- **Separation by home, not by config directory.** Don't give each always-on agent its own `CLAUDE_CONFIG_DIR` or `CODEX_HOME`: Claude Code keeps its credentials under that directory, so each agent would need its own login. OpenClaw's per-agent auth profiles show the cost of that design, with inheritance rules and warnings against reuse. Claude Code's auto memory is already keyed by the working directory's repository, so each home gets its own auto-memory directory. That is a second, machine-local memory layer the Host does not own and that does not move with the home.

**Adds.**

- **A Git home.** Devin, Letta and the Agent Memory Repo spec give memory an audit trail and a merge rule, and a Git home is what makes moving an always-on agent to a peer Host or a cloud Host a copy and not a migration. It isn't needed for one Host, but it is cheap to allow.
- **Attribution.** Copilot credits automation work to its creator, and Claude Code's scheduled tasks act as the person. Weave's equivalent is already true, since the agent runs on the person's login. Journaling the Trigger's name in a headless turn's origin, beside `{"run": {}}`, would make a run traceable to its Trigger.
- **Identity across machines.** The products that keep an agent's identity off any one machine do it with a cloud control plane (Letta Cloud, Cursor, Devin, Delta). Weave has no such plane, so an always-on agent belongs to one Host. Naming it by its name together with the Host's id from `devices.json`, not by its home's path, keeps a later move or a peer's reference unambiguous.

**Names.** "Agent" is taken by the ACP program, and the surveyed products use most of the obvious alternatives for something else:

| Name | Used elsewhere for | Fit |
| --- | --- | --- |
| Profile | Hermes's exact concept, but also Zed's and Delta's tool and model presets, Copilot's agent profiles, and Claude Code's credential profiles | Avoid: a reader from Zed, Delta or Copilot expects a preset |
| Project | Claude Code Projects; Delta's repository folders | Avoid |
| Thread, conversation | Delta, Amp and Letta use these for what weave calls a session | Avoid |
| Workspace | Delta and OpenClaw directories; Amp's and Coder's teams and environments | Avoid |
| Deployment | Managed Agents' scheduled configuration | Avoid |
| Bot | Hermes's chat-platform account; OpenClaw's rescue bot | Avoid |
| Persona | OpenClaw's "per-persona scope" names this record; Managed Agents' configuration "defines persona"; elsewhere it means the instruction layer (`SOUL.md`, ACP's client system prompt RFD) | Possible, but suggests a prompt rather than a record with a home, policy and Triggers |
| Resident | Not used by any surveyed product (the author's coinage) | Possible: it lives on a Host, in its own home, and stays; "the resident's current session" and "a Host's residents" read naturally next to Host and session |

"Resident" fits best. "Persona" is the fallback if the glossary prefers a word readers already know.

### 10.5 WVE-117: an edge that Hosts dial out to

**Supports.**

- **Dialing out** is how every surveyed product reaches a person's machine (8).
- **One Durable Object per Host** fits Cloudflare's model: a named, addressable object whose WebSocket connections can stay open while it leaves memory, with webhooks routed per source and Web Push from stored subscriptions (4.5). Delta runs its live-sync backend on Durable Objects with SQLite (1.4), so the platform already carries this kind of fan-in for a product in public beta.

**Complicates.**

- **Holding no sessions** is a deliberate difference. Claude Code Remote Control stores transcripts on Anthropic's servers to keep devices in sync and to reconnect, Copilot sends session events to GitHub, and Delta stores threads. An edge without sessions can, when the Host is offline, only queue an occurrence or say the Host is away. That matches ADR 0018's note that reaching an unconnected client "belongs to the Host or a service beside it".
- **Accepting webhooks while the Host is away.** WVE-64's rule of one durable record per accepted occurrence needs either the edge to acknowledge only after the Host accepts, or the Durable Object to keep the occurrence in its SQLite until the Host takes it. Cursor's "claimed_offline" with a wake timeout and Devin's outpost queue show how others hold work for an absent worker.
- **Pushing to iOS.** The weave app is a Capacitor iOS app, so it needs APNs, not the Web Push Cloudflare documents (open question, 9). A notification's text must come from the Host through the edge, so the edge sees it in passing.
- **The tailnet rule.** The edge sits outside the tailnet, so it is the WVE-98 decision that ADR 0017 left open. Because Hosts dial out, it opens no way into a Host.
- **Proving the Host.** The Durable Object can be named by the Host's id and require the Host to prove the key it pairs with (ADR 0017).
- **For later sharing**, an object per Host keyed by Host id can later route for one person's several Hosts, or between people, without becoming the coordinating Host ADR 0017 rejected, as long as it keeps no sessions.

### 10.6 WVE-116: the Host on Linux as a systemd user service

- **Supports.** OpenClaw and Hermes both install their long-lived process as a systemd user unit on Linux (4.2, 4.3). Claude Code keeps its Linux login in `~/.claude/.credentials.json`, so it needs no desktop keyring (3.3).
- **Linger.** Hermes recommends `loginctl enable-linger` so that user units keep "running across SSH disconnects and reboots". A Host managed over SSH (ADR 0017) needs the same, or it stops when the person logs out.
- **Stop timeout.** OpenClaw sets `TimeoutStopSec=330` to fit a five-minute drain and warns that Ubuntu 24.04's user manager allows five seconds at shutdown. ADR 0011's drain on restart needs a stop timeout sized to it, and a status or doctor check for the user manager's limit.

### 10.7 WVE-119: a Host in a cloud container

**Supports.**

- **The shape.** Anthropic's own advice for running Claude Code on "your own always-on machine and drive it from other devices" is a long-lived machine with the CLI on the person's login (3.3), which a cloud Host is.
- **Signing in over SSH.** Claude Code prints a code to paste when its browser callback cannot be reached, which it calls "common in WSL2, SSH sessions, and containers", and on Linux writes the login to a file in the home directory, so it lands on the volume.
- **Repositories.** Cloning into Host-made directories is what every cloud product does (3.1–3.3).
- **Reaching it.** OpenClaw's recommended "always-on Gateway in your tailnet" on a VPS, reached through loopback and Tailscale Serve, is the same arrangement as ADRs 0016 and 0017.

**Complicates.**

- **Credentials inside the container.** Cloud products keep Git and API credentials out of the sandbox and inject them through a proxy (8). A weave cloud Host holds the person's CLI logins and Git credentials on its own volume, which is acceptable for one person's container but makes the container a single trust boundary. Weave's rule holds only if the person signs in over SSH and the CLI writes its own file. Coder's `claude setup-token` pattern, which passes a token in through configuration, would have weave or its deployment carry a credential and should not be copied.
- **Ephemeral sandboxes are a different model.** Devin boots each session from a fresh image, Delta runners pause after 10 idle minutes and are deleted, Claude Code reclaims idle VMs, and Amp's orbs sleep. WVE-119's state on a volume is closer to a home server than to a per-task sandbox, which is what lets suspended sessions reopen from their journals. The idle cost of that choice was not researched.
- **Isolation.** All sessions in one container share it. Delta says the same of its own checkouts ("This isolates project files; it does not sandbox the agent from the rest of the selected machine"); Hermes offers a container per session. That is acceptable for a personal Host.
- **For later sharing**, a cloud Host stays one person's. OpenClaw's warning that session ownership and presence "are usability features, not security boundaries" means sharing a Host between people later would mean a Host per person.

### 10.8 Sharing, deferred

Weave defers channels, multiplayer sessions, several users per Host and hosted tenancy, and nothing here argues for taking them up now. The evidence does say what each later choice would cost:

- **Where a guest's turn would run.** Delta runs it on the guest's machine with the guest's model credentials and bills the guest; Amp runs it in the owner's environment, bills the owner and uses the owner's MCP credentials (8). Weave's Host-centred model is Amp's shape: a guest's prompt would run on the owner's Host and the owner's login, which raises the terms question in section 9. Delta's shape needs a replicated store in a shared cloud backend, which conflicts with peers without a coordinator.
- **Attribution is already recorded.** `turnStarted` names the client and its paired device, so a later sharing model starts with every prompt attributed.
- **Peer Hosts.** WVE-106 lets one person's agents reach their other Hosts' sessions. Between people, the same pairing would be one person's Host acting for another, a trust decision for later. Recording a directory's remote URL and base commit (10.3) and naming always-on agents by name and Host id (10.4) are what keep either kind of sharing possible without changing records.
