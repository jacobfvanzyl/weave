# devvm and weave

Research snapshot, 2026-11-18. Primary sources only. devvm was read from a shallow clone of `devvmhq/devvm` at [`ba5613e1`](https://github.com/devvmhq/devvm/tree/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513) (`main`, 2026-11-16; `VERSION` says `0.1.1-rc.3`), which holds the source, the README and the whole documentation site (`docs/content`, about 2 MB of Markdown), with its issues, pull requests, releases and repository numbers read through the GitHub API on 2026-11-18. [devvm.dev](https://devvm.dev) was fetched the same day; its only GitHub links are to `devvmhq/devvm`, so there was one candidate repository and nothing to choose between. Nothing from the clone was built or run, and devvm was not installed, so every statement about how devvm behaves is from its documentation or its source, never from a measurement. Where a statement was checked in the Go source it says so; otherwise it is the project's own claim.

The question: what devvm is and how it works, and what, if anything, it could do for weave.

This note uses weave's words (Host, Dispatcher, client, thread, Session, Block, Bot, home, Project, worktree, terminal, holder, permission policy) as `CONTEXT.md` defines them. devvm's own words are defined where they first appear. One collision to watch: devvm's documentation says *host* for the person's computer and *this machine* for the same thing. Here "Host" is always weave's, and devvm's host is "the computer".

## 1. In brief

- **devvm is a command-line tool that gives each project folder a Linux virtual machine of its own on the person's computer**, with the folder mounted at the same path, so that installs, project code and coding agents run in the VM and not on the computer. Its tagline is "One VM for every project" ([README](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/README.md?plain=1#L8-L10)). It is free, MIT-licensed, written in Go, and runs its VMs with [Lima](https://lima-vm.io) on macOS and Linux.
- **It is twelve days old in public.** The repository was created on 2026-11-06 and v0.1.0 was published the same day; three release candidates of 0.1.1 followed in a week. It has one author (749 of 752 commits), 692 stars, and unusually thorough documentation, including a list of the attacks it does not stop.
- **It is a sandbox, not an environment manager with snapshots.** Its own comparison page says it has no snapshots of a VM and no SDK or API, "though most commands have `--json` output" ([compared](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/compared/_index.md?plain=1#L53-L59)). A VM is running or stopped, nothing else. There is no fork, no suspend, no hosted service and no daemon.
- **Its three distinctive mechanisms** are a per-VM proxy on the computer that confines the VM's network to an allowlist and puts credentials into requests so that the VM holds only placeholders; a lock on `.git` hooks and config so that the VM cannot make git run code on the computer; and `--clone`, where the VM works on its own copy of the repository and its work comes back only when the person fetches it as `devvm/<branch>`.
- **weave has no sandbox today.** A thread's permission policy decides what an agent is allowed to ask for, and an agent's own mode can approve more than the policy would ([ADR 0026](../adr/0026-headless-threads-start-in-the-agents-configured-mode-and-say-what-their-policy-rejected.md)). Nothing limits what an approved command reaches. That is the gap devvm addresses, and it is the only part of weave it bears on.

Top recommendations, in order of value against effort:

1. **Try an agent inside a devvm VM as a config agent, with no weave code** (§7.1). It is an afternoon's experiment on the Mac and answers the main open question: how much of weave still works when the agent's process is in a VM and the Host is outside it.
2. **Borrow `--clone`'s rule that work is saved before its place is removed** (§7.3), and the rule that a directory is known by more than its path (§7.4). Both are small and need no devvm.
3. **Do not build on devvm yet.** It has no API, a state layout that is still changing, one maintainer, and a model (one VM per folder, 8 GiB each by default) that sits badly with worktrees on a MacBook Air. Read §8 before anything larger than the trial.

The comparison table says "no account, free" ([compared](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/compared/_index.md?plain=1#L16)). Guests are Linux only: Ubuntu's cloud image by default, or a Debian-, Ubuntu- or Alpine-based container image with `--from` ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L14)).

## 3. How it works

### 3.1 What runs where

Everything runs on the person's computer, as the person. There is no service and no long-lived devvm daemon.

- **The `devvm` command** runs for as long as its command does. `devvm` in a folder ends by replacing itself with a shell in the VM ([overview](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/overview.md?plain=1#L40)).
- **Lima** runs each VM. On macOS it uses Apple's Virtualization framework (Lima's `vz`) with virtiofs mounts; on Linux it uses QEMU with KVM and 9p mounts ([home page](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/_index.md?plain=1#L142); [Lima requirements](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/lima.md?plain=1#L14-L23)). The source branches on exactly those two cases ([limactl.go](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/internal/backend/lima/limactl.go#L467), [and here](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/internal/backend/lima/limactl.go#L496)). devvm keeps a Lima home of its own, `~/.local/share/devvm/lima`, so the person's other Lima VMs and settings never touch its VMs ([lima](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/lima.md?plain=1#L32)). A *backend* is devvm's word for the program that runs its VMs; Lima is the only one, and no flag chooses another ([backends](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/_index.md?plain=1#L7), [L33](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/_index.md?plain=1#L33)).
- **Helper processes per running VM**, each the `devvm` binary under a hidden command, started detached so they outlive the terminal: the VM's proxy (`devvm _proxy` and a sandboxed child), a port forwarder (`devvm _ports`), and a link session (`devvm _links`) when the VM has links. Each ends when the VM's Lima process does ([processes](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/processes.md?plain=1#L11-L32)). The proxy's child is confined with a Seatbelt profile on macOS and with Landlock and seccomp on Linux; the repository has `internal/seatbelt` and `internal/landlock` packages for this, which were not read line by line.
- **In the guest**: Ubuntu by default, a user with passwordless sudo, and a few helper scripts (`devvm-help`, `devvm-why`, `devvm-fetch`). The security model starts from that: "devvm treats everything in a VM as untrusted, including a coding agent with root" ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L7)).

### 3.2 A VM's life

- **Defined by** the folder and flags, not by a file devvm owns. `devvm` in a folder with no VM detects toolchains from the project's files, shows what the VM would get, and makes it; `--tools`, `--agents`, `--layers`, `--network`, `--ports`, `--cpus`, `--memory`, `--disk`, `--from` and `--clone` answer the questions beforehand ([devvm reference](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/cli/devvm.md)). It also reads a project's `devcontainer.json` for an image, ports, environment and commands, running nothing from it on the computer ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L30-L32)). Defaults for new VMs live in `~/.config/devvm/config.toml` and `devvm setup`.
- **Created** in ten steps: check everything, build the image if needed, write the VM's state, clone the image, lock `.git`, start the proxy and then the VM, self-check that the VM really is confined, set the VM up, open a shell ([overview](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/overview.md?plain=1#L11-L40)). If interrupted before the shell opens, it removes everything it made ([L42](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/overview.md?plain=1#L42)).
- **Images, layers, shared tools.** An *image* is a stopped Lima VM; a project VM is a `limactl clone` of it, checked in the source ([lima.go](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/internal/backend/lima/lima.go#L462-L468)). On macOS the clone's disk is an APFS copy-on-write copy; on Linux it is a qcow2 overlay of the image's disk ([lima internals](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/lima.md?plain=1#L19-L22)). A *layer* is a setup script built into an image (`docker`, `nix`, `desktop`, or the person's own). *Shared tools* are toolchains and coding agents built once and mounted read-only into every VM that wants them, which is why a tool cannot update itself in a VM ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L12-L13)).
- **States.** "A VM is running or stopped from the time devvm makes it until you delete it" ([vms](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/vms.md?plain=1#L13)). `devvm stop` stops it and its proxy; `devvm restart` applies changes that need a start; `devvm update` makes it again from a newer image, keeping the home folder; `devvm rm` deletes it, exporting agents' history first ([vms](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/vms.md?plain=1#L33-L65)).
- **No snapshot, fork or suspend.** The comparison page says so for snapshots ([compared](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/compared/_index.md?plain=1#L57)), and a search of the Go source for `snapshot`, `suspend` and `hibernate` finds only an unrelated internal type in the `.git` scanner and a Cursor API path. The copy-on-write clone goes from an image to a VM only; nothing copies one project VM into another.
- **One VM per folder, identified by more than its path.** devvm records the folder's device, inode and birth time, so a folder deleted and made again at the same path does not silently get the old VM, and a moved folder is offered its VM back ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L26)). A subfolder uses its parent's VM unless `--here` says otherwise.
- **Size.** Base's size is 4 CPUs, 8 GiB of memory and a 100 GiB disk, fitted down to the computer ([images](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/images.md?plain=1#L86)); `devvm size` changes it, and disks never shrink ([ports and size](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/ports-size.md?plain=1#L89-L99)).
- **How long things take.** The project gives no measured figures. The README says the first run builds the base image "once, in a few minutes. Later VMs start in seconds" ([README](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/README.md?plain=1#L52)). Neither was measured here.

### 3.3 Files: a mount, or a clone

- **Mounted (the default).** The VM mounts the project folder read-write at the same path, plus the shared tools and the agents' settings folders read-only, and nothing else of the home folder ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L15)). The person's editor and the VM see the same files.
- **`.git` protection.** devvm locks the hooks and config of the folder's `.git`, so the VM cannot plant a hook that runs on the computer. On macOS it sets a file flag the VM cannot clear; on Linux it makes the paths read-only in the user namespace QEMU runs in, and where the kernel forbids that (Ubuntu 23.10 and newer are named) it only reports changes afterwards ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L46); [limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L25-L26)).
- **`--clone`.** The VM gets its own clone of the repository on its own disk, with the local branches, tags, uncommitted changes and stash, and mounts nothing. devvm adds a git remote named `devvm` to the person's repository; `devvm clone fetch` brings the VM's branches back as `devvm/<branch>`, a detached HEAD's commits and stash entries as `saved/devvm/...` branches, and Git LFS objects; fetching "runs nothing from the VM on this machine" ([clone](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/clone.md?plain=1#L171-L200)). `devvm rm` looks for unfetched commits and uncommitted changes first and offers to save them ([vms](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/vms.md?plain=1#L65)). The documentation recommends it "for a repo or an agent you don't trust" ([safety](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/safety/_index.md?plain=1#L13)).
- **What stays open in mounted mode.** Everything else in the folder: `.husky/`, `.claude/settings.json`, `.mcp.json`, `.vscode/tasks.json`, `.envrc`, symlinks out of the folder. "Running an agent on this machine in the folder after the VM has worked in it runs what the VM wrote, so run your agents in the VM" ([attack vectors](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/safety/attack-vectors.md?plain=1#L136-L145)).

### 3.4 Network and credentials

- **Four *network tiers***, chosen per VM: `open` (whatever the computer reaches), `internet` (public hosts only), `allowlist` (the default: only hosts the allowlists name) and `none` (only the agents' and secrets' hosts and the VM's links) ([network](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/safety/network.md?plain=1#L31-L36)). On every tier but `open` the VM "reaches nothing but its proxy, and a direct connection from it fails" ([L44](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/safety/network.md?plain=1#L44)), enforced from outside the VM: a macOS sandbox around the Lima process, a restricted QEMU network on Linux ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L50)). Rules can name host and port, and HTTP method and path. A VM can start on `internet` while devvm records the hosts it uses, then `devvm network lock` keeps the ones the person chooses.
- **Secrets stay on the computer.** A *secret* is a credential devvm keeps for VMs to use: a GitHub token, a Claude Code token, an agent's login, or any API key the person saves. The VM's environment and files hold a placeholder; the VM's proxy swaps in the real value only in requests to that secret's hosts, using a CA that only that VM trusts ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L68-L72)). Secrets are in the macOS Keychain, or in private files on Linux ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L32)). This was read in the documentation; `internal/proxy/secrets.go` exists but the swap was not traced in the code.
- **Private addresses.** The proxy "refuses the host's own addresses and internal addresses unless a rule names them" ([security](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L52)).

### 3.5 How a person or a program gets in

- **A shell.** `devvm` opens one at the folder's path; the prompt starts with `(devvm)`. "Without a terminal, the shell reads its commands from devvm's input" ([overview](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/overview.md?plain=1#L40)).
- **SSH by name.** Each running VM is `ssh devvm-<folder>` through entries devvm writes to `~/.local/share/devvm/ssh_config`, which the person includes from `~/.ssh/config` or passes with `ssh -F`. Entries exist only for running VMs, pin the VM's host keys, reach it on `127.0.0.1` only, and turn off everything else ssh could share ([ssh](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/ssh.md?plain=1#L11-L25)). SSH agent forwarding is off by default; devvm can forward an agent of its own holding only chosen keys ([L89](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/ssh.md?plain=1#L89)).
- **Editors.** `devvm code` and `devvm cursor` open the folder in VS Code or Cursor over Remote-SSH, with a warning that the editor's own sign-ins may reach the VM ([ssh](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/ssh.md?plain=1#L38-L62)).
- **Ports.** TCP ports the VM listens on appear at the same port on the computer's `localhost`, loopback only, at most 256 at once, within a few seconds ([ports](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/ports-size.md?plain=1#L28-L44)). Nothing is exposed beyond the computer.
- **Links between VMs.** A *link* lets one VM reach a published TCP port of another by name (`db:5432`), carried over ssh through the computer; a *group* links several VMs to each other. A link "joins the two VMs' trust" ([links](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/links.md?plain=1#L7-L16), [L77](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/links.md?plain=1#L77)).
- **A desktop.** The `desktop` layer and `devvm desktop` serve the VM's graphical desktop on loopback.

### 3.6 Coding agents

- **Five agents are packaged** as shared tools: Claude Code, Codex, opencode, pi and Cursor's CLI, each with its self-update and telemetry turned off and its hosts on the allowlist ([coding agents](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/coding-agents.md?plain=1#L44-L50)). A request for more was closed on 2026-11-16 ([#53](https://github.com/devvmhq/devvm/issues/53)); any other program can still be installed in a VM by hand.
- **The person starts the agent in the VM's shell.** "An agent runs where you start it" ([L10](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/coding-agents.md?plain=1#L10)). devvm launches no agent and speaks no agent protocol: a search of the repository finds no mention of ACP, and "MCP" appears only where devvm copies agents' MCP settings and keeps their secrets.
- **The *agent store*.** devvm keeps agents' settings in `~/.config/devvm/agents/<agent>/` and logins in `~/.local/share/devvm/logins/<agent>/`, and never reads `~/.claude`, `~/.codex` and the like for a VM. `devvm agent import` copies them in once; `devvm agent login claude` logs in from inside a VM and keeps the login on the computer. Settings folders are mounted read-only; logins reach the VM as placeholders ([agent store](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/coding-agents.md?plain=1#L65-L72); [Claude login](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/coding-agents.md?plain=1#L193-L200)). The documentation notes that Anthropic does not document the login's requests, so "a new Claude Code release can change them".
- **A guide for the agent.** Every VM has `/usr/share/doc/devvm/README.md`, printed by `devvm-help`, telling an agent what the VM is, how the network tiers work, and which commands to ask the person to run on the computer ([guide](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/assets/guest/guide.md?plain=1#L1-L3)).
- **Parallel agents.** Two documented shapes: several agents in one `--clone` VM, each in a git worktree inside the clone (`.worktrees/NAME`), sharing the VM's network, secrets and ports and able to read each other's work; or a folder and a VM per agent when they must be kept apart ([clone](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/clone.md?plain=1#L216-L231)). Nothing coordinates them.
- **Agents with their checks off** are the stated use: "a mistaken `rm -rf ~` or `sudo` command reaches only the VM" ([attack vectors](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/safety/attack-vectors.md?plain=1#L83)).

## 4. For an orchestrator

- **No API, SDK, socket or MCP server.** The comparison page says so, and the source has none.
- **The CLI is scriptable.** Every command that shows something takes `--json` and prints one versioned object ([command line](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/command-line.md?plain=1#L66-L93)); `--no-input` makes devvm ask nothing and fail naming the flag that would have answered ([L62](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/command-line.md?plain=1#L62)); `devvm rm` needs `--force` without a terminal. `devvm ls --json` gives each VM's name, status, image, tools, tier and folder ([vms](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/vms.md?plain=1#L93-L114)).
- **SSH is the stable way in for a program.** `devvm host` starts the folder's VM if needed and prints its ssh name, after which `ssh -F ~/.local/share/devvm/ssh_config devvm-<folder> <command>` is an ordinary ssh with a binary-safe stdin and stdout.
- **State is files** under `~/.local/share/devvm` and `~/.config/devvm`, with a layout version; a VM whose state names a backend this devvm lacks is refused ([backends](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/_index.md?plain=1#L33)).

## 5. Limits and known problems

From [Known limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L9-L37), the issue tracker and the code:

- **File watchers in the VM miss edits made on the computer**, on both platforms, so a dev server must poll to reload on the person's edits ([lima](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/lima.md?plain=1#L51)).
- **Linux hosts are the weaker platform.** Mounts are 9p: watchers miss more, SQLite's WAL mode and programs that map files for writing fail in the project folder, and set-id bits set by root in the VM reach the computer ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L27-L31)). A reported silent data loss on the 9p share, where a file written and fsynced came out 0 or 4096 bytes and Claude Code's Edit tool emptied a file several times, was closed by changing new VMs' cache mode to `none` ([#36](https://github.com/devvmhq/devvm/issues/36); [limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L28)). `.git` protection is weaker there and absent on some kernels.
- **Linux needs `/dev/kvm`**, so a Linux host that is itself a VM needs nested virtualization ([lima](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/backends/lima.md?plain=1#L23)).
- **A linked git worktree mounted as the project folder has its repository outside the VM.** The `.git` protection page lists "The project folder's `.git` file, if the project folder is itself a linked worktree. The repo it points to is outside the VM" ([git protection internals](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/git-protection.md?plain=1#L23)). The inference, not tested: git commands in such a VM cannot find the repository. `--clone` handles a worktree explicitly, copying its branch and leaving the repository's other branches behind ([clone](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/clone.md?plain=1#L70)).
- **Changing layers remakes the VM**, losing everything on its disk outside the home folder ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L13)).
- **Ports are TCP only**, and links carry TCP over IPv4 only ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L16-L17)).
- **Tools that ignore proxy settings** reach the proxy only over HTTPS and HTTP by host name; other protocols need the tool's own proxy settings ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L18)). A WebSocket through an HTTP `CONNECT` tunnel should pass, but that is an inference.
- **Intel Macs are untested** ([limits](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/using/limits.md?plain=1#L37)).
- **Open issues** on 2026-11-18: GPG agent forwarding ([#34](https://github.com/devvmhq/devvm/issues/34)), a local reverse proxy with HTTPS and host names ([#11](https://github.com/devvmhq/devvm/issues/11)), and pinned versions to bump ([#51](https://github.com/devvmhq/devvm/issues/51)).
- **Pace as a risk.** The tool is at 0.1.x with prereleases every few days, and its agent logins follow undocumented requests. Its documentation is frank about what it has not checked (Cursor's behaviour, what editors' sign-ins leak).

## 6. Where weave stands

What bears on devvm, from the ADRs and guides:

- **Agents run as the person, on the Host's computer.** The Host launches one agent process per open thread and speaks ACP to it over stdio. An agent is a command with arguments and environment (`agents/src/config.rs`, `AgentConfig`), so any command that speaks ACP on its stdin and stdout can be one.
- **Permissions are approvals, not confinement.** A permission policy answers an agent's permission requests; an agent's own mode may approve what the policy would reject ([ADR 0026](../adr/0026-headless-threads-start-in-the-agents-configured-mode-and-say-what-their-policy-rejected.md)). No ADR from 0008 to 0034 decides a sandbox, and a search of `docs/adr` and `CONTEXT.md` for "sandbox" and "isolat" finds only the sandboxed frame a view renders in (ADR 0012) and a glossary line saying not to call a worktree one.
- **The Host does things on its own computer for the agent**: ACP's `fs/*` and `terminal/*` client services (`acp-core`), the Host MCP server, which most agents reach through the stdio command `weave mcp-bridge` talking to `mcp.sock` beside the Host's socket and which agents that advertise `mcpCapabilities.acp` reach over ACP instead (`host/AGENTS.md`), and Session terminals, each kept by a holder ([ADR 0022](../adr/0022-each-terminal-lives-in-a-holder-of-its-own-and-belongs-to-a-worktree.md)).
- **Worktrees are linked worktrees beside the repository**, `<repo>.<branch>`, which belong to the person ([ADR 0019](../adr/0019-the-host-manages-worktrees-with-git-in-worktrunks-layout.md)). A Session is one directory on one Host, for a repository one of its worktrees ([ADR 0031](../adr/0031-the-app-lays-out-blocks-in-sessions-their-host-keeps-under-projects-the-dispatcher-keeps.md)).
- **A Bot lives in a home on one Host**, a git repository that Host makes, and uses tools the Dispatcher declares through the Host MCP server for its wake-ups and schedules ([ADR 0028](../adr/0028-bots-are-dispatcher-records-whose-work-goes-on-in-ordinary-threads.md)).
- **Hosts dial out to the Dispatcher** and need no address of their own; ADR 0030 names "A Host in a container or behind NAT" as a case it serves ([ADR 0030](../adr/0030-the-dispatcher-is-the-hub-hosts-dial-out-to-it-and-devices-reach-every-host-through-it.md)). ADR 0019 mentions container Hosts as WVE-119, which was not read for this note.
- **Credentials.** "Agents authenticate with their own CLI logins, and this project never reads or stores them" (root `AGENTS.md`).
- **The person's setup** (from the brief, not the repository): one person, two Hosts, a MacBook Air and a Linux machine, `homelab`, which also runs the Dispatcher; an iPad and iPhone reach both through the Dispatcher over Tailscale.

## 7. Applications for weave, ranked

Ranked by value against effort. Each says whether it adopts the tool or borrows an idea. These are evidence for a decision; none is a plan, and the only steps given are a cheap trial.

| # | Kind | Application | Value | Effort |
| --- | --- | --- | --- | --- |
| 7.1 | Adopt, as a trial | An agent with a loose permission policy runs inside a devvm VM, as a config agent over ssh | High, if it works | Low: no weave code |
| 7.3 | Borrow | Work is saved before its place is removed, and comes back by fetch | Medium | Low |
| 7.4 | Borrow | A directory is known by more than its path | Low to medium | Low |
| 7.2 | Adopt | A whole Host inside a devvm VM | High for isolation | Medium |
| 7.5 | Borrow | Placeholder credentials and a network tier as part of what a thread may do | High | High |
| 7.6 | Adopt | The Host makes a VM per Session or worktree | Medium | High |
| 7.7 | Borrow | A guide in the environment for the agent | Low | Low |

### 7.1 An agent inside a devvm VM, as a config agent (adopt, trial only)

- **Uses**: a VM per folder at the same path, the allowlist tier, placeholder credentials, and ssh by name with a binary-safe stdio.
- **Touches**: only the Host's configuration, `[agents.<id>]` with `command = "ssh"` and arguments naming the VM and the agent's ACP program. No weave code. Because the folder is mounted at the same path, the directory a thread names is the same string in the VM, so paths in the journal and in tool calls stay true.
- **Gives the person**: a place to run an agent in `bypassPermissions` or under a headless thread's permissive policy where its commands reach only the VM and an allowlist of hosts, and where the Claude or Codex login is not readable by what it runs. Today such an agent runs as the person with the whole home directory and network.
- **Costs and conflicts**:
  - *The Host MCP server.* An agent that reaches it through `weave mcp-bridge` cannot: the bridge is the Host's own binary talking to a Unix socket on the Host's computer, and neither is in the VM. Agents that advertise `mcpCapabilities.acp` would still reach it over ACP. Without it a thread loses client tools, Host tools and service tools, which is why this suits a coding thread and not a Bot, whose wake-ups and schedules are service tools (ADR 0028).
  - *ACP client services.* `fs/*` and `terminal/*` are answered by the Host on its own computer. With a mounted folder `fs/*` reads and writes the same files, but a `terminal/create` would run outside the VM. Which agents use it under which capabilities was not checked here.
  - *Session terminals* stay on the Host's computer, outside the VM (ADR 0022), and so do the terminal tools agents have since WVE-233.
  - *Worktrees.* A Session in a linked worktree would mount a folder whose repository is outside the VM (§5), so the trial belongs in a primary worktree or a `--clone` VM.
  - *Logins.* devvm keeps its own copy of the agents' logins and settings. weave still reads none, but there is now a second place they live, and the person logs in again through `devvm agent login`.
  - *The agent's ACP program.* devvm packages `claude`, not an ACP adapter; the adapter would be installed in the VM's home with npm, which the allowlist for node permits.
- **Cheap trial**: on the Mac, in a scratch repository, make a VM with Claude Code and node; install the ACP adapter in it; add a config agent whose command is `ssh -F ~/.local/share/devvm/ssh_config devvm-<folder> <adapter>`; run `weave agents smoke --agent <id>`, then one interactive thread. Note what breaks: the MCP bridge, permission requests, file edits showing in the transcript, a blocked host. That list is the real finding.

### 7.2 A whole Host inside a devvm VM (adopt)

- **Uses**: the VM as a Linux computer (Ubuntu, so presumably with systemd for weave's user service, which was not checked), the mounted folder or a clone, the network tier, and ssh by name.
- **Touches**: nothing in the Host's design. The Host, its holders, the MCP bridge and ACP's client services would all be inside the boundary, which removes every conflict in §7.1. ADR 0030 already lets a Host behind NAT join the Dispatcher by dialling out. `scripts/update-hosts` installs over ssh, and a devvm VM is an ssh host by name.
- **Gives the person**: a Host that is itself the sandbox, listed in the app like any other, for one Project location. Bots would work in it unchanged.
- **Costs and conflicts**:
  - One VM serves one folder, so this is a Host per Project location, and the Dispatcher's list of Hosts grows with projects. ADR 0031 gives a Project at most one location on each Host, which fits, but the app's Hosts section and pairing-by-joining were designed around a few computers.
  - The Host must reach the Dispatcher on the tailnet through devvm's proxy, which refuses internal addresses unless a rule names them. Whether a rule for the Dispatcher's tailnet name carries the WebSocket was not tested.
  - weave would be built for Linux in the VM, holder and pinned Zig included, on the VM's default 8 GiB.
  - A Host in the VM runs only while the VM does and the Mac is awake, so it is no better than the laptop for schedules, as ADR 0027 already says of a single laptop.
- **Cheap trial**: `scripts/update-hosts --hosts-only devvm-<folder>` against a VM on the `internet` tier, then `weave hosts add` inside it and see whether it appears in the app. If it does, tighten to `allowlist` and note which hosts it needed.

### 7.3 Work is saved before its place is removed, and comes back by fetch (borrow)

- **The idea**: `--clone`'s contract. The agent's work lives in a repository of its own; it reaches the person's repository only as remote-tracking branches they fetch and review; and deleting the place first saves unfetched commits, a detached HEAD and stash entries as `saved/...` branches, never overwriting one (§3.3).
- **Touches**: worktree removal in the Host (ADR 0019), and delegated threads. ADR 0019 removes a worktree's branch only when git counts it merged, and rejected Host-owned directories partly because safe automatic removal "needs snapshots". devvm's answer is narrower and cheaper than a snapshot: look for work that exists nowhere else and give it a branch.
- **Gives the person**: removing a worktree from the iPad without wondering what uncommitted or unpushed work went with it.
- **Costs**: a decision about uncommitted changes, which devvm deletes only after the person confirms. No conflict with an ADR found.
- **Cheap trial**: run `devvm --clone` once in a worktree the Host made and read what `devvm rm` offers; or simply list, for the person's last ten removed worktrees, what such a check would have saved.

### 7.4 A directory is known by more than its path (borrow)

- **The idea**: devvm ties a VM to the folder's device, inode and birth time as well as its path, refuses to hand a new folder at an old path the old VM, and offers a moved folder its VM back (§3.2).
- **Touches**: Sessions and Project locations in the Host and Dispatcher, and threads whose directory is gone (WVE-120, named in ADR 0019).
- **Gives the person**: a Session that follows a renamed directory, and no Session quietly attached to a different repository cloned where an old one was.
- **Costs**: devvm lists the file systems where this is unsafe (network shares, FUSE, FAT), which weave would have to respect too.
- **Cheap trial**: none needed beyond reading [the rule](https://github.com/devvmhq/devvm/blob/ba5613e1ed9bc1c2592f1fa1af81a6e89f97f513/docs/content/docs/internals/security.md?plain=1#L26) against how the Host keys Sessions today.

### 7.5 Placeholder credentials and a network tier as part of what a thread may do (borrow)

- **The idea**: a permission policy says which tool kinds are approved; devvm adds two dimensions a policy lacks, which hosts the work may reach and which credentials it may use without holding them, and a way to learn the first by watching ("learn, then lock").
- **Touches**: the permission policy in `protocol/`, the Host, and Bots' policies in the Dispatcher.
- **Gives the person**: a Bot whose reach is stated and enforced, not only approved call by call.
- **Costs**: this is the hard part of devvm, a TLS-intercepting proxy with per-VM CAs and enforcement from outside a VM boundary. Without a boundary there is nothing to enforce it against: an agent running as the person can go around a proxy. So the idea cannot be borrowed without also adopting some sandbox, and building one is far outside weave's scope.
- **Cheap trial**: none that is cheap. Worth keeping as vocabulary for a future permission policy: tier, allowlist, placeholder.

### 7.6 The Host makes a VM per Session or worktree (adopt)

- **Uses**: `devvm --no-input` with flags to create, `devvm ls --json` to list, `devvm host` and ssh to enter, `devvm rm --force` to delete.
- **Touches**: Session creation in the Host, a new kind of terminal whose shell is in the VM, agent launch, and the app's New Session form.
- **Gives the person**: a checkbox, "isolated", when starting a Session.
- **Costs and conflicts**: every cost in §7.1, plus the Host driving a CLI with no API and a state layout twelve days old; one VM of up to 8 GiB per worktree on a MacBook Air; linked worktrees needing `--clone`, which moves the work off the person's working tree and so away from `wt` and the layout ADR 0019 chose so that the person's tools and weave manage the same worktrees; and "Never branch on which agent is connected" strained by devvm's per-agent packaging.
- **Cheap trial**: none worth doing before §7.1 says what survives.

### 7.7 A guide in the environment for the agent (borrow)

- **The idea**: a fixed document in every VM, and a command that prints it, telling the agent where it is and what to ask the person for.
- **Touches**: the Host MCP server or a Bot's first files (`repos/init`).
- **Gives**: little that Host tools' descriptions do not already give. Listed for completeness.

## 8. Where devvm does not fit

- **Snapshots, forks and undo.** devvm has none and says so. It cannot give parallel agents a forked environment or roll a thread's work back. The nearest thing is `--clone`, where the person's working tree is untouched until they fetch.
- **Replacing anything weave builds.** It does not keep terminals alive (its shell is an ssh session that ends with its terminal), so it is no holder. It has no notion of a thread, a journal or a client. It does not manage worktrees. It reaches nothing beyond the computer's loopback, so it adds nothing to remote access, and the iPad still goes through the Dispatcher to a Host.
- **A Bot's home.** A Bot needs the Dispatcher's tools through the Host MCP server, and its home is a small repository of notes; the risk devvm addresses, project code and installs, is mostly absent there. A Bot in a VM is only reasonable as §7.2, a whole Host.
- **`homelab`, as things stand.** Linux is devvm's weaker platform (9p, weaker `.git` protection), it needs `/dev/kvm` and QEMU, and whether `homelab` has them was not checked.
- **Many worktrees on the MacBook Air.** One VM per folder at 8 GiB by default does not match a habit of several worktrees per repository. devvm's own answer, worktrees inside one clone VM, is a different layout from ADR 0019's.
- **As a dependency today.** One maintainer, 0.1.x, release candidates every few days, no API. The trial in §7.1 costs nothing to throw away; anything the Host calls would not be.

## 9. Not verified

- **Nothing was run.** devvm was not installed. Start times, build times, whether confinement holds, and whether the proxy injects credentials as described are the project's claims.
- **The proxy, sandbox and `.git` lock code** were not read line by line. What was checked in source: the Lima `clone` calls, the `vz` and 9p branches, the dependency list, the absence of snapshot, suspend, ACP or an MCP server, and the list of commands.
- **Every weave-side consequence in §7 is an inference** from weave's guides and ADRs and devvm's documentation: that the stdio MCP bridge cannot work across the VM boundary, that `terminal/create` would run outside it, that git fails in a mounted linked worktree, that an ACP adapter installs and logs in inside a VM, and that a Host in a VM can reach the Dispatcher through the proxy. The trials in §7.1 and §7.2 exist to test them.
- **`homelab`'s** KVM access, kernel and file systems were not looked at.
- **WVE-119** (container Hosts) and other issues were not read from the tracker.
- **The maker's background** is from a GitHub profile only. No blog post, video or announcement about devvm was read.
- **Star and issue counts** are one reading on 2026-11-18 of a repository twelve days old.
