## 1. The layers

These projects are often compared as if they were alternatives. They sit at different places in the stack, and several of them now carry each other.

| Protocol | Who produces the UI | What carries it | Who renders it | UI model | Status, 2026-10-18 |
| --- | --- | --- | --- | --- | --- |
| **MCP Apps** (`io.modelcontextprotocol/ui`) | MCP server (tool author) | An MCP resource (`ui://`, `text/html;profile=mcp-app`) named by the tool's `_meta.ui.resourceUri`, then JSON-RPC over `postMessage` between host and view | The MCP host, i.e. whichever application owns the MCP client connection | Web bundle in a sandboxed iframe | Official MCP extension; stable spec 2026-01-26; SEP-1865 Final |
| **MCP-UI** (legacy protocol) | MCP server | An embedded resource returned inside the tool result (`ui://`, `text/html`, `text/uri-list`, Remote DOM script) | The MCP host via `@mcp-ui/client` | HTML or URL in an iframe, or Remote DOM mirrored into host components | Superseded; the `@mcp-ui/*` packages now implement MCP Apps |
| **OpenAI Apps SDK** (now "plugins" UI) | MCP server | MCP Apps, plus optional `window.openai` and OpenAI MCP Extensions | ChatGPT | Web bundle in an iframe | ChatGPT declares full MCP Apps compatibility since 2026-02-22 |
| **A2UI** | Agent (or an MCP tool) | Any transport: A2A, AG-UI, MCP embedded resource (`application/a2ui+json`), WebSocket | The client application's A2UI renderer | Declarative component catalog rendered with native widgets | v0.9.1 current; v1.0 release candidate |
| **AG-UI** | Agent backend | HTTP + SSE or HTTP + Protobuf event stream | The frontend application's own code | Event stream for app-owned UI; carries A2UI and MCP Apps as activity events | 1.0 released 2026-09-17 |
| **ACP Embedded Views** (proposal) | ACP agent | ACP (proposed capability and resource reads) | ACP client | Immutable web bundle in a client-owned opaque-origin sandbox | Open RFD PR, unreviewed |
| **Vercel AI SDK** tool parts | App backend | AI SDK UI message stream | The app's React components | App-owned components keyed to tool results; MCP Apps renderer is experimental | AI SDK 7; RSC `streamUI` marked experimental |
| **json-render** | Model output constrained by a catalog | JSON spec | The app's renderer (React, Vue, Svelte, React Native, Ink, ...) | Declarative component catalog | Vercel Labs project |
| **Shopify Remote DOM** | Sandboxed JavaScript | DOM mutation messages | Host page mapping elements to its components | Remote DOM | Library, 1.12.0 |

Two structural facts matter for anything built on an agent protocol:

- In MCP Apps the renderer is the party that holds the MCP client connection. The host reads the `ui://` resource itself and proxies the view's `tools/call` to the same server ([stable spec](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L386-L401), [transport](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L415-L468)).
- In ACP the agent is the MCP client. An ACP client sees whatever the agent chooses to project into `session/update`; it never sees MCP tool descriptors as such. Section 8 shows what the adapters weave runs actually project.

## 2. MCP-UI

### 2.1 Identity and maintainers

MCP-UI began as `idosal/mcp-ui`; the GitHub API now redirects that name to `MCP-UI-Org/mcp-ui`. The README names Ido Salomon as the author "in collaboration with" Liad Yosef ([README](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/README.md?plain=1#L464-L465)). Both are authors of SEP-1865 and two of the three leads of the MCP Apps Working Group; the third is Olivier Chafik of Anthropic ([WG charter](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/community/working-groups/apps.mdx?plain=1#L42-L48)). The MCP Apps SEP credits MCP-UI with developing "the bi-directional communication model and the HTML, external URL, and remote DOM content types", and names Postman, HuggingFace, Shopify, Goose, and ElevenLabs as adopters ([SEP-1865 draft](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L19)).

### 2.2 The legacy protocol (v5, before January 2026)

At tag `client/v5.17.3` a UI resource was an MCP embedded resource returned in the tool result. Its URI used the `ui://` scheme, and its MIME type chose the renderer ([v5 protocol details](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/docs/src/guide/protocol-details.md?plain=1#L5-L33)):

| MIME type | Server content type | Rendering |
| --- | --- | --- |
| `text/html` | `rawHtml` | Sandboxed iframe via `srcdoc` |
| `text/uri-list` | `externalUrl` | Sandboxed iframe via `src`; one http(s) URL used, others logged and ignored |
| `application/vnd.mcp-ui.remote-dom+javascript; framework=react` or `framework=webcomponents` | `remoteDom` | Script runs in a sandboxed iframe; Shopify Remote DOM mirrors its tree into host-supplied components |

The type union also listed `text/html;profile=mcp-app` and `text/html+skybridge` (the OpenAI Apps SDK type) for adapters ([v5 types](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/sdks/typescript/server/src/types.ts#L12-L18), [content payloads](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/sdks/typescript/server/src/types.ts#L36-L43)). The Remote DOM renderer took a component library that mapped remote tag names to host React components ([v5 remote-dom renderer](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/docs/src/guide/client/remote-dom-resource.md?plain=1#L1-L24)). Resource metadata used `mcpui.dev/ui-` keys such as `preferred-frame-size` and `initial-render-data` ([v5 types](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/sdks/typescript/server/src/types.ts#L157-L168)).

The iframe talked to the host with untyped `postMessage` objects, not JSON-RPC. The five UI actions were ([v5 types](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/sdks/typescript/server/src/types.ts#L170-L218)):

- `tool` with `{ toolName, params }`
- `prompt` with `{ prompt }`
- `link` with `{ url }`
- `intent` with `{ intent, params }`
- `notify` with `{ message }`

Each could carry a `messageId`; the host answered with `ui-message-received` and then `ui-message-response`. Reserved lifecycle messages were `ui-lifecycle-iframe-ready`, `ui-size-change`, `ui-request-data`, and `ui-request-render-data` from the iframe, and `ui-lifecycle-iframe-render-data` from the host ([v5 embeddable UI guide](https://github.com/MCP-UI-Org/mcp-ui/blob/fd89e2942eb7148d83245397be0b6ad34ce538b0/docs/src/guide/embeddable-ui.md?plain=1#L141-L256)).

### 2.3 Folding into MCP Apps

On 2026-01-26, the day the MCP Apps spec was published as stable, `server/v6.0.0` and `client/v6.0.0` shipped as "mcp-ui -> mcp apps!" with the breaking note "removed discarded content types, changed mimetype" ([client v6.0.0 release](https://github.com/MCP-UI-Org/mcp-ui/releases/tag/client%2Fv6.0.0)). The README now says MCP-UI "pioneered" the pattern and that "The `@mcp-ui/*` packages implement the MCP Apps standard. `@mcp-ui/client` is the recommended SDK for MCP Apps Hosts" ([README](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/README.md?plain=1#L32-L36)). The MCP project says the same from its side: "MCP-UI isn't going anywhere. The SDKs support MCP Apps patterns, with the Client SDK as the recommended framework for Hosts" ([MCP Apps launch post](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/blog/content/posts/2026-01-26-mcp-apps.md?plain=1#L156-L159)), and the MCP Apps overview recommends `@mcp-ui/client` or the ext-apps App Bridge to host builders ([overview](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/extensions/apps/overview.mdx?plain=1#L186-L198)).

From the source, the current packages are narrower than the README suggests:

- `@mcp-ui/server` 6.1.0 emits only `text/html;profile=mcp-app`, with `rawHtml` or `externalUrl` content ([types](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/sdks/typescript/server/src/types.ts#L11-L31)). For `externalUrl` the TypeScript SDK fetches the page server-side, injects a `<base>` tag, and returns HTML; the Python and Ruby SDKs store the URL instead ([protocol details](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/docs/src/guide/protocol-details.md?plain=1#L87-L96)). Remote DOM is gone.
- `@mcp-ui/client` 7.1.1 exports `AppRenderer`, `AppFrame`, and re-exports `AppBridge` and `PostMessageTransport` from ext-apps ([index](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/sdks/typescript/client/src/index.ts#L12-L32)). It no longer exports `UIResourceRenderer`, although the README still documents it for legacy hosts ([README](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/README.md?plain=1#L138-L149)).
- The client depends on `@modelcontextprotocol/ext-apps` `^1.2.0` and the 1.x MCP SDK ([package.json](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/sdks/typescript/client/package.json#L21-L22)), not ext-apps 2.x.
- A legacy adapter translates old widgets to MCP Apps calls: `tool` → `tools/call`, `prompt` → `ui/message`, `link` → `ui/open-link`, `notify` → `notifications/message`, `intent` → `ui/message`, `ui-size-change` → `ui/notifications/size-changed` ([translation table](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/docs/src/guide/mcp-apps.md?plain=1#L184-L196)).

Other SDKs: `mcp-ui-server` 1.0.0 on PyPI (2025-11-04) and `mcp_ui_server` 0.1.0 on RubyGems (2025-07-19) (registry queries, 2026-10-18). Release cadence has slowed: the last client release is 7.1.1 on 2026-05-09 and the last commit on `main` is 2026-07-08. The README roadmap still lists "Add declarative UI content type" and "Support generative UI?" as open ([README](https://github.com/MCP-UI-Org/mcp-ui/blob/2b10490910943640deeb2d9012ad417d4c0e9025/README.md?plain=1#L451-L462)).

The WG changelog dates the stable spec to 2026-01-26 and Final status to 2026-01-28 ([WG charter](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/community/working-groups/apps.mdx?plain=1#L116-L124)). The launch post calls it "the first official MCP extension" and "ready for production" ([post](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/blog/content/posts/2026-01-26-mcp-apps.md?plain=1#L15-L18)).
- The normative text lives in ext-apps, not the core spec. The stable file says `Status: Stable (2026-01-26)` ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1-L11)); a separate `draft/apps.mdx` carries later additions and says `Status: Draft` ([draft](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L1-L9)).

- The **2026-07-28** core revision added the `extensions` field to `ClientCapabilities` and `ServerCapabilities` ([changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/specification/2026-07-28/changelog.mdx?plain=1#L32)); the schema's own example is the MCP Apps capability ([schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/schema/2026-07-28/schema.ts#L775-L785)). Its scope includes "generative UI, with interoperability with external protocols such as A2UI and AG-UI" and non-HTML hosts; members include Anthropic, OpenAI, and Google ([charter](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/community/working-groups/apps.mdx?plain=1#L14-L26), [membership](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/community/working-groups/apps.mdx?plain=1#L63-L72)).

### 3.2 How a tool declares its UI

A tool names its view in `_meta.ui.resourceUri`. The older flat key `_meta["ui/resourceUri"]` is deprecated "and will be removed before GA" ([draft](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L338-L366)); the SDK tells hosts to check both ([constants](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/src/constants.ts)). `_meta.ui.visibility` is an array of `"model"` and `"app"`, default both. The host MUST NOT give the model tools without `"model"`, MUST reject app `tools/call` for tools without `"app"`, and cross-server calls to app-only tools are always blocked ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L324-L403)).

The UI is a predeclared resource:

- URI MUST start with `ui://`; MIME type MUST be `text/html;profile=mcp-app`; content is `text` or base64 `blob` and MUST be a valid HTML5 document ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L265-L270)).
- Resource `_meta.ui` holds `csp` (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`), `permissions` (`camera`, `microphone`, `geolocation`, `clipboardWrite`), `domain` (a host-defined dedicated origin), and `prefersBorder` ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L112-L262)). It may appear on the `resources/list` entry or on the `resources/read` content item; the content item wins ([draft](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L263-L272)).
- The host MUST fetch the view with `resources/read`, MAY prefetch and cache it, and servers MAY omit UI-only resources from `resources/list` ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L386-L393)).

The SEP chose predeclared resources over MCP-UI's embedded resources so hosts can prefetch and review templates, and it deferred external URLs (`text/uri-list`) over "model visibility, inability to screenshot content, and review process" ([rationale](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1584-L1633)).

### 3.3 Capability negotiation and fallback

The client advertises `io.modelcontextprotocol/ui` with a REQUIRED `mimeTypes` array, e.g. `["text/html;profile=mcp-app"]` ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1492-L1527)). Servers SHOULD check this before registering UI tools (the SDK's `getUiCapability`) and MAY register a text-only variant instead. Servers SHOULD provide text-only fallback, and tools MUST return a meaningful `content` array even when UI is available ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1529-L1560)). A host that does not support MCP Apps treats the tool as a standard tool ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L389)).

The MCP Apps spec text still shows this exchange inside `initialize`. Under 2026-07-28 there is no `initialize`: the client sends its capabilities in every request's `_meta["io.modelcontextprotocol/clientCapabilities"]`, and the server advertises `extensions: { "io.modelcontextprotocol/ui": {} }` in its `server/discover` result ([extensions overview](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/extensions/overview.mdx?plain=1#L131-L196), [2026-07-28 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/specification/2026-07-28/changelog.mdx?plain=1#L12-L16), [versioning](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/specification/2026-07-28/basic/versioning.mdx?plain=1#L80-L125)). The open elicitation PR is the first ext-apps document to spell out "the `2026-07-28` path using request-scoped client capabilities, `server/discover`, and core MRTR" ([PR #733](https://github.com/modelcontextprotocol/ext-apps/pull/733)).

`structuredContent` is "optimized for UI rendering (not added to model context)"; `content` is the text representation for the model and text-only hosts ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1470-L1476)). Clients do not all honour that split (Claude Code, section 4.2).

### 3.4 Host ↔ view protocol

The view and host speak JSON-RPC 2.0 over `postMessage`. The view acts as an MCP client; the host acts as an MCP server that "can proxy the actual MCP server" ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L411-L468)). The bridge has its own protocol version, `"2026-01-26"` ([spec.types.ts](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/src/spec.types.ts#L29)).

Handshake: the view sends `ui/initialize` with `appInfo` and `appCapabilities` (`availableDisplayModes`, optional `tools`). The host returns `McpUiInitializeResult` with `hostCapabilities`, `hostInfo`, and `hostContext`. The view then sends `ui/notifications/initialized`, and the host MUST NOT send anything before that ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L489-L531), [sandbox rule 6](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L470-L487)).

Messages in the stable spec ([requests and notifications](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L959-L1230)):

| Direction | Method | Notes |
| --- | --- | --- |
| View → host | `tools/call`, `resources/read`, `notifications/message`, `ping` | Standard MCP; `tools/call` needs host `serverTools` and `"app"` visibility |
| View → host | `ui/open-link` `{ url }` | Host SHOULD open in the user's browser |
| View → host | `ui/message` `{ role: "user", content }` | Host SHOULD add it to the conversation; MAY ask consent |
| View → host | `ui/request-display-mode` `{ mode }` | Returns the mode actually set |
| View → host | `ui/update-model-context` `{ content?, structuredContent? }` | Each call overwrites the last; host MAY defer to the next user message |
| View → host | `ui/notifications/size-changed` `{ width, height }` | Required for flexible container dimensions |
| Host → view | `ui/notifications/tool-input` | MUST, once, complete arguments |
| Host → view | `ui/notifications/tool-input-partial` | MAY, while arguments stream |
| Host → view | `ui/notifications/tool-result` | A standard `CallToolResult` |
| Host → view | `ui/notifications/tool-cancelled` | MUST on cancellation |
| Host → view | `ui/notifications/host-context-changed` | Partial `HostContext` |
| Host → view | `ui/resource-teardown` (request) | Host MUST send before teardown and SHOULD wait for the reply |

The draft adds `ui/download-file` (an embedded resource or resource link, because `allow-downloads` is not set), `ui/notifications/request-teardown`, `sampling/createMessage` gated on `hostCapabilities.sampling`, and **app-provided tools**: when the view declares `tools`, the host can call `tools/list` and `tools/call` on the view, so the agent can query and drive it. App tools are ephemeral, untrusted, and MUST disappear when the iframe is torn down ([draft messages](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L1066-L1131), [sampling](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L534), [app tools](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L1739-L1900), [app tool lifecycle](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L2637-L2644)). The draft describes this as inspired by W3C WebMCP ([draft](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx?plain=1#L2167-L2177)).

`HostContext` carries `toolInfo`, `theme`, `styles.variables` (a fixed list of 76 CSS custom properties for colours, type, radii, and shadows; spacing deliberately excluded), `styles.css.fonts`, `displayMode`, `availableDisplayModes`, `containerDimensions` (fixed or max height and width), `locale`, `timeZone`, `userAgent`, `platform` (`web` | `desktop` | `mobile`), `deviceCapabilities`, and `safeAreaInsets` ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L531-L668), [theming](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L791-L958)). Display modes are `inline`, `fullscreen`, and `pip`; the host MUST NOT switch a view into a mode it did not declare ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L735-L790)).

### 3.5 Sandbox and security model

- All view content MUST be rendered in sandboxed iframes ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1696-L1700)).
- **Web hosts** MUST put a sandbox proxy between host and view. The host and proxy MUST have different origins, and the proxy MUST have `allow-scripts allow-same-origin`. The proxy announces `ui/notifications/sandbox-proxy-ready`, receives the HTML, CSP, and permissions in `ui/notifications/sandbox-resource-ready`, loads the view in an inner iframe, and relays every message except `ui/notifications/sandbox-*` ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L470-L487), [reserved messages](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1231-L1270)). **Desktop and native hosts** render the view in an iframe directly; the lifecycle diagram has no proxy branch for them ([lifecycle](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1288-L1325)).
- CSP: hosts MUST build CSP from the declared domains, MUST use a restrictive default (`default-src 'none'`, inline scripts and styles allowed, `connect-src 'none'`) when `ui.csp` is absent, MUST NOT allow undeclared domains, and MUST block connections to them ([stable](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L272-L290), [enforcement](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1723-L1758)). Permissions map to the iframe `allow` attribute, and apps are told not to assume they were granted.
- `domain` format is host-defined. Claude requires the first 32 hex characters of SHA-256 of the connector URL followed by `.claudemcpcontent.com`, and local stdio connectors cannot use it ([Claude getting started](https://claude.com/docs/connectors/building/mcp-apps/getting-started), [troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting)).
- From the source, the reference `basic-host` sandbox gives the inner view iframe `allow-scripts allow-same-origin allow-forms` ([sandbox.ts](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/examples/basic-host/src/sandbox.ts#L40-L48)). A2UI's MCP App component takes the opposite position and requires the inner iframe to omit `allow-same-origin` ([A2UI guide](https://github.com/a2ui-project/a2ui/blob/cbaa5ee62c737b50d0695c1e5794d0f648b61dca/docs/public/guides/mcp-apps-in-a2ui.md?plain=1#L17-L30)).
- An open PR by Google's Dominic Farolino would relax the double-iframe requirement to any framing that meets stated security criteria. It says "Google Gemini will be using a single sandboxed iframe architecture" ([PR #717](https://github.com/modelcontextprotocol/ext-apps/pull/717); companion [#718](https://github.com/modelcontextprotocol/ext-apps/pull/718)).

### 3.6 SDKs and reference host

`@modelcontextprotocol/ext-apps` 2.0.3 (2026-09-25; 1.0.0 was 2026-01-26) exports `.` (the view-side `App`), `./react` (hooks), `./app-bridge` (host side), and `./server` (`registerAppTool`, `registerAppResource`, `getUiCapability`, `RESOURCE_MIME_TYPE`) ([package.json](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/package.json#L17-L40)). 2.x moved to the split MCP TypeScript SDK 2.x packages and zod 4.2+, but "The `ui/*` messages exchanged over the iframe channel are byte-identical to 1.x" ([migrate to 2](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/migrate-to-2.md?plain=1#L9-L18)). There is no official non-TypeScript MCP Apps SDK in the repository; servers in other languages set `_meta.ui` themselves.

`AppBridge` is the host-side reference. It accepts an MCP client and forwards view requests automatically, or `null`, in which case the host registers `oncalltool`, `onlistresources`, and similar handlers itself ([app-bridge.ts](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/src/app-bridge.ts#L497-L536)). The second mode is the one a host uses when it does not own the MCP connection. `examples/basic-host` is the reference integration ([overview](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/extensions/apps/overview.mdx?plain=1#L193-L198)).

### 3.7 Native and non-web hosts

The spec defines only HTML. ext-apps contains no WebView, iOS, or Android guidance beyond the "Desktop/Native hosts" branch above (a search of the repository's spec, docs, source, and reference host found none). What exists:

- Claude for iOS renders MCP Apps "inside a `WKWebView`" ([Claude troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting)). An open third-party report says the Claude iOS host delivers no `tool-input`, `tool-result`, or `size-changed` traffic ([ext-apps #734](https://github.com/modelcontextprotocol/ext-apps/issues/734)); Anthropic has not responded there.
- ChatGPT supports the modes on mobile but notes "On mobile, picture-in-picture may be presented as fullscreen" ([OpenAI reference](https://developers.openai.com/plugins/reference)).
- Non-HTML views are an open question. Issue [#28](https://github.com/modelcontextprotocol/ext-apps/issues/28) asks for "a declarative model instead of explicit HTML/CSS" for non-browser clients; issue [#654](https://github.com/modelcontextprotocol/ext-apps/issues/654), by WG lead Liad Yosef, notes that `mimeTypes` is already an array and most `ui/*` methods do not depend on HTML. The WG lists "Address dynamic resource content and non-HTML hosts" as Draft ([charter](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/community/working-groups/apps.mdx?plain=1#L98-L106)). The concrete proposal is PR #699 (section 10.1).

### 3.8 Lifecycle, history, and a worked example

**Who writes the HTML.** The server's author, not the model. The view is a predeclared `ui://` template that the host fetches from the server; the SEP chose this over inline embedding so hosts can prefetch and review templates (3.2). The model writes only the tool's arguments, and the server writes the result. A server can still offer a generic tool whose argument is content that its fixed template draws. The official Excalidraw app is that pattern. Claude's "custom visuals", which the model does write, are a separate feature (9).

**The lifecycle** ([stable spec](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx?plain=1#L1272-L1383)):

1. **Discovery.** `tools/list` carries `_meta.ui.resourceUri`. The host may prefetch and cache the `ui://` resource.
2. **The model calls the tool.** The host sends `tools/call` to the server and, in parallel, renders the view from the template. The view sends `ui/initialize` and receives the host context, then sends `ui/notifications/initialized`. While the model is still generating the arguments, the host MAY stream them as `tool-input-partial` notifications. It then sends the complete `tool-input`, and finally `tool-result` or `tool-cancelled`.
3. **Interactive phase.** The view calls tools (including app-only ones), reads resources, sends `ui/message` (a new user message), overwrites the model context, asks for display modes, and reports its size. The host sends `host-context-changed`.
4. **Cleanup.** The host sends `ui/resource-teardown`, and "Cleanup may be triggered at any point in the lifecycle following View initialization."

Each tool call gets a new view instance. Reusing a view across calls (#430) and pinned or persistent views (#754) are open issues.

**Older messages.** Neither spec text defines what a host does with a view in an earlier part of a conversation, whether that is after scrolling back, reopening the conversation, or reloading. Claude's [design guidelines](https://claude.com/docs/connectors/building/mcp-apps/design-guidelines) and OpenAI's [reference](https://developers.openai.com/plugins/reference) do not say either. OpenAI's `widgetState` is "persisted between renders", but its scope and when it is restored are not stated. What the ext-apps docs do say implies views come and go:

- Views should pause expensive work while offscreen ([patterns](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/patterns.md?plain=1#L572-L600)).
- Recoverable view state should go in `localStorage` under a `viewUUID` the server mints in the result's `_meta`. State that represents user effort should go to the server through app-only tools ([patterns](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/patterns.md?plain=1#L503-L570)). The protocol itself has no state API (#417, #465).

A host re-creating an old view therefore needs four things: the stored tool input and result, the template (re-read from the server or cached), live server access for the view's own calls, and whatever state the view persisted itself.

**Worked example: Excalidraw** ([`excalidraw/excalidraw-mcp`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/README.md) at `157aa23c`; it is the demo in the ext-apps README):

- **Tools.** `read_me` returns the element format and tells the model to call it first. `create_view` is model-visible, points at `ui://excalidraw/mcp-app.html`, is annotated read-only, and takes `elements`, a JSON string of Excalidraw elements ([server.ts](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L419-L436)). The model writes that JSON, not HTML. The template bundles Excalidraw and draws it.
- **Streaming.** The view handles `ontoolinputpartial` and draws elements as the model generates them ([mcp-app.tsx](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L804-L814)). This is the "draw-on animation".
- **Result and handles.** The result's text tells the model the diagram is shown and gives a checkpoint id. Its `structuredContent` is `{checkpointId}` ([server.ts](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L495-L506)). To continue a diagram, the model starts its next `elements` with a `restoreCheckpoint` element instead of re-sending the whole diagram ([server.ts](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L287-L300)). This is the explicit cross-call handle that 2026-07-28 asks for in place of session state.
- **App-only tools.** `export_to_excalidraw`, `save_checkpoint`, and `read_checkpoint` are `visibility: ["app"]` ([server.ts](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L512-L520), [L604-L637](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L604-L637)). The editor mounts only in fullscreen ([mcp-app.tsx](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L741)). The person's edits are saved through `save_checkpoint` and also in `localStorage` under the checkpoint id ([mcp-app.tsx](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L816-L831)), so the model's next `restoreCheckpoint` includes them.
- **Lifetime of state.** Checkpoints go to a temporary directory locally and to Redis with a 30-day expiry on the hosted service ([checkpoint-store.ts](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/checkpoint-store.ts#L29-L32), [L107-L127](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/checkpoint-store.ts#L107-L127)). An old view re-created after that can still draw the model's original elements from its tool input, but the person's edits are gone unless that origin's `localStorage` still holds them.

### 4.2 Terminal agents

No terminal agent examined renders MCP Apps. The details differ:

- **Claude Code** stays a text-only client. Two first-party details matter. First, when a tool returns `structuredContent`, "the `tool_result` Claude receives is that JSON object as a string ... rather than your `content` text" ([Claude quickstart](https://claude.com/docs/connectors/building/mcp-apps/quickstart)), so the MCP Apps convention that `content` is for the model and `structuredContent` for the UI does not hold there. Second, since 2.1.281 Claude Code hides MCP Apps UI resources from `@` suggestions and the resource-list tool ("pages for a host application to render rather than content for Claude to read"), though reading one by URI still works ([CHANGELOG](https://github.com/anthropics/claude-code/blob/c017428c8c27e604840435048d5bce6a9a22c040/CHANGELOG.md?plain=1#L1891); [MCP docs](https://code.claude.com/docs/en/mcp)). The Agent SDK exposes host hooks for embedding applications (section 8.3).
- **Codex CLI** does not advertise the extension (above). The Codex app-server, which other OpenAI surfaces embed, does carry MCP App metadata (section 8.5).
- **Gemini CLI** passes embedded resource text through to the model and the screen (above).
- **Goose CLI** does not advertise the extension by default (above).
- An open ext-apps issue asks for host guidelines for command-line hosts. Its author reports that Datadog shipped "a separate UI host in Claude Code launched via session hook" in which `callServerTool` cannot work, and names a third-party Pi adapter as the only general-purpose CLI host they had seen ([ext-apps #689](https://github.com/modelcontextprotocol/ext-apps/issues/689)). That is the issue author's account, not a vendor statement.

## 5. OpenAI Apps SDK

### 5.1 It is now documented as "plugins", on top of MCP Apps

`developers.openai.com/apps-sdk` now resolves to the Plugins documentation, and OpenAI's documentation index lists the section as "ChatGPT plugins and Apps SDK" ([llms.txt](https://developers.openai.com/llms.txt)). A plugin can contain skills, an MCP server, or both, plus lifecycle hooks; "ChatGPT and Codex share one universal plugin directory", and "Custom UI is not required for an MCP server" ([plugin architecture](https://developers.openai.com/plugins/concepts/plugins)). On UI, OpenAI says "ChatGPT implements the open MCP Apps standard" and instructs: for new UI, declare `_meta.ui.resourceUri`, use the `ui/*` bridge over `postMessage`, and keep tools useful without UI. `window.openai` is now for "capabilities that the shared specification does not cover" ([Add UI to your MCP server](https://developers.openai.com/plugins/build/chatgpt-ui)). The reference opens with "Start with the open standard" and calls `window.openai` "compatibility aliases and optional ChatGPT extensions" ([reference](https://developers.openai.com/plugins/reference)).

| Goal | MCP Apps | ChatGPT alias |
| --- | --- | --- |
| Link tool to UI | `_meta.ui.resourceUri` | `_meta["openai/outputTemplate"]` |
| Tool input | `ui/initialize` + `ui/notifications/tool-input` | `window.openai.toolInput` |
| Tool result | `ui/notifications/tool-result` | `window.openai.toolOutput` |
| Call a tool | `tools/call` | `window.openai.callTool` |
| Follow-up message | `ui/message` | `window.openai.sendFollowUpMessage` |

(From [Add UI to your MCP server](https://developers.openai.com/plugins/build/chatgpt-ui).)

The relevant changelog entries ([plugin UI changelog](https://developers.openai.com/plugins/changelog)):

- 2026-02-22: "ChatGPT is now fully compatible with the MCP Apps spec."
- 2026-05-27: for approval-gated tools, input arrives through `ui/notifications/tool-input` after approval; `toolResponseMetadata` keeps the canonical MCP result envelope including hidden `_meta`.
- 2026-05-28: ChatGPT supplies the standard MCP Apps CSS variables.
- 2026-07-21: `_meta["openai/visibility"]` deprecated in favour of `_meta.ui.visibility`.

### 5.2 The ChatGPT-specific surface

- **Legacy names.** Before MCP Apps, OpenAI used `text/html+skybridge`, `_meta["openai/outputTemplate"]`, `openai/widgetAccessible` and `openai/visibility` (two fields where MCP Apps has one array), and snake_case `openai/widgetCSP` ([ext-apps migration guide](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/migrate_from_openai_apps.md?plain=1#L22-L62)). `openai/widgetCSP` is still required for `redirect_domains`, which MCP Apps lacks ([reference](https://developers.openai.com/plugins/reference)).
- **`window.openai`.** Properties: `toolInput`, `toolOutput`, `toolResponseMetadata`, `widgetState`, `theme`, `displayMode`, `maxHeight`, `safeArea`, `view`, `userAgent`, `locale`. Methods: `setWidgetState`, `callTool`, `sendFollowUpMessage`, `uploadFile`, `selectFiles`, `getFileDownloadUrl`, `requestDisplayMode`, `requestModal`, `requestClose`, `notifyIntrinsicHeight`, `openExternal`, `setOpenInAppUrl`, plus `requestCheckout` for Instant Checkout ([reference](https://developers.openai.com/plugins/reference), [Add UI](https://developers.openai.com/plugins/build/chatgpt-ui)).
- **Display modes.** `inline`, `fullscreen`, `pip`. Servers can pre-declare them with `_meta["openai/ui"].availableDisplayModes` on the resource so ChatGPT can choose before loading ([reference](https://developers.openai.com/plugins/reference)).
- **Widget state.** `widgetState` / `setWidgetState` persist a UI snapshot between renders. MCP Apps has no equivalent; ext-apps' own migration guide says to use `localStorage` or server-side state ([migration guide](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/migrate_from_openai_apps.md?plain=1#L276-L297)), and parity requests remain open ([#465](https://github.com/modelcontextprotocol/ext-apps/issues/465), [#417](https://github.com/modelcontextprotocol/ext-apps/issues/417)).
- **OpenAI MCP Extensions** (`openai/mcp-extensions`, first commit 2026-09-29, the DevDay launch date) is a formal spec that "extends MCP and MCP Apps" for ChatGPT, ChatGPT Work, Desktop, and mobile. It adds app entrypoints (global sidebar, thread panel, file-extension viewers) under `_meta["openai/ui"]["entrypoints"]`, structured settings, onboarding, extensions to `ui/update-model-context` and `ui/message`, composer mentions, and form elicitation. A per-platform support table is included ([spec](https://github.com/openai/mcp-extensions/blob/0d606217705e0e71eb21fff009619b67b80611dc/docs/spec.md?plain=1#L1-L60)). Servers advertise these in `server/discover` for 2026-07-28 and in `initialize` for older revisions ([spec](https://github.com/openai/mcp-extensions/blob/0d606217705e0e71eb21fff009619b67b80611dc/docs/spec.md?plain=1#L38-L45)). SDKs: `@openai/mcp-extensions` and `openai-mcp-extensions` ([README](https://github.com/openai/mcp-extensions/blob/0d606217705e0e71eb21fff009619b67b80611dc/README.md?plain=1)).
- **Directory.** Plugins are published to one directory shared by ChatGPT and Codex ([submission](https://developers.openai.com/plugins/deploy/submission)). OpenAI also publishes a guide to converting a Claude Code plugin for submission ([guide](https://developers.openai.com/plugins/guides/submit-claude-plugin)).
- **Component library.** `@openai/apps-sdk-ui` (0.2.2) provides ChatGPT-styled components ([Add UI](https://developers.openai.com/plugins/build/chatgpt-ui)).

## 6. AG-UI

AG-UI is the Agent–User Interaction protocol from CopilotKit. Its 1.0 specification defines it as "one request in, one ordered stream of typed events out, carrying everything the user sees of the agent", and is normative for behaviour, with the JSON Schema normative for structure ([spec 1.0](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/spec/1.0/index.mdx?plain=1#L6-L43)). Transports are HTTP + SSE and HTTP + Protobuf, with a contract for custom bindings ([spec 1.0](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/spec/1.0/index.mdx?plain=1#L72-L87)). The `EventType` enum has 31 members ([schema](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/spec/1.0/schema.json#L45-L81)):

- Lifecycle: `RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`, `STEP_STARTED`, `STEP_FINISHED`
- Text: `TEXT_MESSAGE_START`, `_CONTENT`, `_END`, `_CHUNK`
- Tool calls: `TOOL_CALL_START`, `_ARGS`, `_END`, `_CHUNK`, `TOOL_CALL_RESULT`
- State: `STATE_SNAPSHOT`, `STATE_DELTA`, `MESSAGES_SNAPSHOT`
- Activity: `ACTIVITY_SNAPSHOT`, `ACTIVITY_DELTA`
- Reasoning: seven `REASONING_*` events
- Subagents: `SUBAGENT_STARTED`, `SUBAGENT_FINISHED`, `SUBAGENT_ERROR`
- Pass-through: `RAW`, `CUSTOM`

1.0 is the first release with a normative specification. It added run outcomes and interrupt/resume, subagents, the reasoning family, and activity events ([1.0 key changes](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/spec/1.0/changelog.mdx?plain=1#L9-L60)). `@ag-ui/core` 1.0.0 was published 2026-09-17 and 1.0.3 on 2026-10-16; a 1.1 draft is in progress, and SDKs are generated only from frozen versions ([spec README](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/spec/README.md?plain=1#L31-L55)).

**Layer.** AG-UI connects an agent backend to the user-facing application, alongside MCP (agent to tools) and A2A (agent to agent) ([agentic protocols](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/agentic-protocols.mdx?plain=1#L13-L33)). It says it "is not a generative UI specification" but a runtime connection that supports such specs ([generative UI specs](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/concepts/generative-ui-specs.mdx?plain=1#L10-L20)).

**How it carries MCP Apps and A2UI.** Both travel as activity events:

- `@ag-ui/mcp-apps-middleware` (0.1.2) discovers model-visible MCP tools, injects them into the agent, and, for tools with a UI resource, emits `ACTIVITY_SNAPSHOT` with `activityType: "mcp-apps"` and content `{ result, resourceUri, serverHash, serverId?, toolInput }`. The frontend fetches the resource and proxies the view's `tools/call` by sending a `ProxiedMCPRequest` in the run input's `forwardedProps.__proxiedMCPRequest` ([README](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/middlewares/mcp-apps-middleware/README.md?plain=1#L31-L109)). The MCP connection lives in the agent-side middleware and the frontend reaches it through AG-UI, which is the same split an ACP client faces.
- `@ag-ui/a2ui-middleware` emits `ACTIVITY_SNAPSHOT` with `activityType: "a2ui-surface"` ([source](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/middlewares/a2ui-middleware/src/index.ts#L56)).

AG-UI's specs page attributes MCP-UI to "Microsoft + Shopify" and "Open-JSON-UI" to OpenAI ([generative UI specs](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/concepts/generative-ui-specs.mdx?plain=1#L12-L16)). MCP-UI's own README credits Ido Salomon and Liad Yosef, and no OpenAI-published Open-JSON-UI specification was found, so both attributions are unverified.

**Adopters** listed first-party: CopilotKit (frontend); LangGraph, Microsoft Agent Framework, Google ADK, Google Antigravity, AWS Strands, Mastra, Pydantic AI, Agno, LlamaIndex, CrewAI, AG2, Claude Managed Agents, the Claude Agent SDK, Langroid, Cloudflare Agents, Omnara; Amazon Bedrock AgentCore for deployment; A2UI and MCP Apps under generative UI ([integrations](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/integrations.mdx?plain=1#L8-L43)). A draft "Generative User Interfaces" extension proposes a two-step generate-then-render tool flow ([draft](https://github.com/ag-ui-protocol/ag-ui/blob/75be44e4e443469b48e5be3c79e9cb690d3bf89e/docs/drafts/generative-ui.mdx?plain=1#L16-L27)).

### 8.3 Claude Code and the Agent SDK

Claude Code itself does not render (4.2). The Agent SDK has added primitives for an embedding application to act as the MCP Apps host while Claude Code stays the MCP client:

- **Tool descriptors.** `mcpServerStatus()` tool entries carry "the MCP Apps (SEP-1865) members of the tool's `_meta`", i.e. `ui` (`resourceUri`, `visibility`, other members) and the deprecated flat `ui/resourceUri`, validated and size-bounded, from CLIs that advertise `mcp_tool_ui_meta_v1`. Every other `_meta` key is withheld (`@anthropic-ai/claude-agent-sdk@0.3.302` [`sdk.d.ts`](https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.302/sdk.d.ts) lines 1298–1310).
- **Resource reads.** `readMcpResource(serverName, uri)` (`@alpha`) reads a `ui://` resource "so the host can render a tool's widget", returning contents with the item's `_meta` (where MCP Apps keeps `ui.csp` and `ui.permissions`). It is advertised as `mcp_read_resource_v1`, refuses non-`ui://` URIs, and is refused for cloud-hosted sessions and redacting lanes (`sdk.d.ts` lines 3215–3227 and 4805–4836).
- **View-initiated calls.** The `mcp_call` control request invokes an MCP tool without a model turn. With `result_not_for_model`, "content is then the server's own content blocks as MCP defines them ... no embedded resource is flattened, and text blocks beside `structuredContent` stay". It is feature-detected as `mcp_call_result_not_for_model_v1` and honoured only for a host on the CLI's own pipes (`sdk.d.ts` lines 4739–4762). The type is declared but not exported, and no public `Query` method wraps it in 0.3.302.
- **Tool results.** For MCP tools, `tool_use_result` is `{ content, _meta }` and carries `structuredContent`, with caps that MCP Apps tools raise to 8,388,608 JSON characters ([SDK changelog](https://github.com/anthropics/claude-agent-sdk-typescript/blob/9cf9f23b757f881c82fc2bfee459429ea26187df/CHANGELOG.md?plain=1#L71-L73), [earlier entries](https://github.com/anthropics/claude-agent-sdk-typescript/blob/9cf9f23b757f881c82fc2bfee459429ea26187df/CHANGELOG.md?plain=1#L105-L128)).
- **Versions.** The first two primitives arrived in SDK 0.3.280, published 2026-09-22 ([changelog](https://github.com/anthropics/claude-agent-sdk-typescript/blob/9cf9f23b757f881c82fc2bfee459429ea26187df/CHANGELOG.md?plain=1#L193-L198)).

No document states whether Claude Code advertises `io.modelcontextprotocol/ui` to MCP servers, or whether an SDK host can make it do so; `sdk.d.ts` has no option for declaring MCP client extensions. Servers that follow the spec's advice and register UI tools only for capable clients would not attach `_meta.ui` otherwise (section 11).

- An MCP tool call is reported as an ACP tool call with `rawInput = { server, tool, arguments }` and `rawOutput = { result, error }`, and "no `content`" ([McpToolReporter.ts](https://github.com/agentclientprotocol/codex-acp/blob/59974c7d173e4fd6ef9498fc1e91779606c2404d/src/tool-calls/reporters/McpToolReporter.ts#L7-L48), [renderer](https://github.com/agentclientprotocol/codex-acp/blob/59974c7d173e4fd6ef9498fc1e91779606c2404d/src/tool-calls/AcpToolCallRenderer.ts#L22-L30)). `result` is Codex's `McpToolCallResult`, `{ content, structuredContent, _meta }` ([type](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/app-server-protocol/schema/typescript/v2/McpToolCallResult.ts)).
- The item's `mcpAppUi` and `mcpAppResourceUri` fields are present in the generated types but never read.

**Result: an ACP client of codex-acp receives the MCP result's content blocks (including any embedded resources), `structuredContent`, and `_meta` inside `rawOutput`, but not the tool's `_meta.ui.resourceUri`, and the server will not have been told the client can render.**

### 8.5 The Codex app-server already models MCP Apps hosting

### 8.6 A worked example of MCP Apps over ACP: Goose

Goose Desktop renders MCP Apps while talking to its agent over ACP, using a Goose-specific profile. From the source:

1. The ACP client declares `clientCapabilities._meta.goose.mcpHostCapabilities.extensions`, for example `{"io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}}`. The agent forwards it to MCP servers ([server.rs](https://github.com/aaif-goose/goose/blob/34a222e3f2b95d8b4a43482b53c2cc957ecce26d/crates/goose/src/acp/server.rs#L413-L462), [client defaults](https://github.com/aaif-goose/goose/blob/34a222e3f2b95d8b4a43482b53c2cc957ecce26d/ui/goose-acp-client/src/mcp-apps.ts#L13-L73)).
2. After a UI tool returns, the agent strips any server-supplied `goose.mcpApp` as untrusted, reads the `ui://` resource itself, and attaches a trusted record ([extension_manager](https://github.com/aaif-goose/goose/blob/34a222e3f2b95d8b4a43482b53c2cc957ecce26d/crates/goose/src/agents/extension_manager/mod.rs#L499-L541)). The ACP layer emits it as `tool_call_update._meta.goose.mcpApp = { toolName, extensionName, resourceUri, toolMeta, resourceResult, readError }` ([conversion.rs](https://github.com/aaif-goose/goose/blob/34a222e3f2b95d8b4a43482b53c2cc957ecce26d/crates/goose/src/acp/server/tool_calls/conversion.rs#L216-L226)).
3. The view's `tools/call`, `resources/read`, and `tools/list` go back over custom ACP requests `_goose/unstable/tools/call`, `_goose/unstable/resources/read`, and `_goose/unstable/tools/list` ([generated client](https://github.com/aaif-goose/goose/blob/34a222e3f2b95d8b4a43482b53c2cc957ecce26d/ui/goose-acp-client/src/generated/index.ts#L15-L35), [desktop use](https://github.com/aaif-goose/goose/blob/34a222e3f2b95d8b4a43482b53c2cc957ecce26d/ui/desktop/src/acp/mcp-apps.ts#L118-L147)).

The profile is not standardized in ACP. It is, however, a working instance of an agent projecting MCP Apps into ACP `_meta` and accepting proxied calls back.

### 10.1 First-party roadmap statements

### 10.2 Convergence and divergence

- **The web-bundle model has converged on MCP Apps.** ChatGPT, Claude, VS Code, Microsoft 365 Copilot, Cursor, and Goose all host the same `io.modelcontextprotocol/ui` extension. OpenAI has turned its own keys into "compatibility aliases", and MCP-UI has become an implementation of MCP Apps (sections 2.3, 4.1, 5.1). Vendor-specific additions now sit on top as named extensions (OpenAI MCP Extensions) rather than as forks.
- **The declarative catalog model has not converged and is being bridged instead of merged.** A2UI, json-render, ChatKit widgets, and the unverified Open-JSON-UI each define their own component schema. A2UI and MCP Apps now nest in both directions (an `McpApp` A2UI component, and A2UI rendered inside an MCP App). MCP Apps PR #699 would let MCP Apps carry declarative payloads to a renderer view (sections 7, 10.1).
- **The event-stream model positions itself as the carrier for both.** AG-UI calls itself "not a generative UI specification" and carries MCP Apps and A2UI as activity snapshots (section 6).
- **The agent-protocol layer has no UI standard.** ACP has no accepted UI mechanism. Agents that want UI in an ACP client either use private `_meta` profiles (Goose) or offer richer protocols of their own (Codex app-server, Claude Agent SDK control requests). The two ACP adapters weave runs forward none of the MCP Apps metadata (section 8).
- **Terminals do not render.** Every terminal agent examined either ignores the UI or passes text through. The CLI vendors instead expose hooks for an embedding application to host the UI (sections 4.2, 8.3, 8.5).

### 10.3 Speculation (not sourced; the author's reading)

- MCP Apps looks likely to become the only interoperable way to ship third-party web UI from a tool. Declarative formats look likely to reach MCP through the Dynamic View Content mechanism (#699) or an A2UI MCP extension, rather than displacing HTML.
- The SDK-level host hooks in Claude Code and Codex suggest both vendors expect embedding applications, not their terminals, to render MCP Apps. An ACP-level standard would probably follow, not precede, those private surfaces.

## 12. Fit for weave

Judged against weave at `cbb22e77`: the Rust weave Host of [ADR 0008](../adr/0008-weave-daemon-is-the-host.md), its Host protocol ([spec](../../tui/docs/specs/wve-85-host-protocol.md)), the accepted but unbuilt Host-owned MCP server of [ADR 0009](../adr/0009-client-tools-through-a-host-owned-mcp-server.md) (WVE-89), and the planned mobile client (WVE-91). This section replaces the delivery plan of the [August A2UI note](a2ui-over-current-acp.md), which assumed the agent itself would emit UI and that Portal would carry it.

### 12.1 Where weave sits

In MCP Apps, the renderer is whoever holds the MCP client connection (section 1). In weave, that party is the agent. Claude Code and Codex dial MCP servers, and weave sees only what their ACP adapters project into `session/update`. A tool's UI would have to cross four links to reach a weave client: MCP server → agent → ACP adapter → Host → client. Today it is lost at the third. claude-agent-acp drops `_meta.ui`, `structuredContent`, and result `_meta`. codex-acp forwards the result inside `rawOutput` but not the tool's `resourceUri`, and Codex never tells servers that a UI could render (8.2, 8.4).

The Host itself is not an MCP client of any third-party server. Under ADR 0009 it will own exactly one MCP server, `weave`, whose calls it answers itself. That gives weave three possible sources of UI, and they differ in who has to cooperate:

| Source | Example | Who must cooperate | Possible today |
| --- | --- | --- | --- |
| Tools on the Host's own `weave` server | A chart or review view weave ships; a generic "render this" tool | Nobody. The Host serves the tool and its `ui://` resource, and knows when the tool is called. | Once WVE-89 exists |
| Third-party MCP servers in weave's `[[mcp_servers]]` | A Linear or Figma app | Nobody, if the Host dials them and re-exposes their tools through `weave` (12.3) | Through the `weave` gateway |
| MCP servers the agent loads itself (`.mcp.json`, Claude plugins, Codex config) | Anything the person installed into Claude Code directly | The adapters. The SDK hooks exist (8.3, 8.5) but the adapters don't use them. | No |

UI generated by the agent itself (A2UI, json-render, or model-written HTML) has no carrier through vendor agents. The practical route is the first row: a Host tool whose arguments are the UI. That replaces the August note's plan for agents to emit `application/a2ui+json` resources, which no vendor agent will do.

### 12.2 The shape: the Host is the MCP side of the host, and clients render

MCP Apps splits the host into an MCP side (holding the connection, reading `ui://` resources, proxying `tools/call`) and a rendering side (sandbox, bridge, lifecycle). In weave the MCP side belongs in the Host and the rendering side in each client.

- **The Host** reads and caches `ui://` resources, keeps the complete `CallToolResult` (including `structuredContent` and `_meta`, which the adapters drop), journals each view, and carries out a view's requests against the server under the session's permission policy.
- **The agent gets text only.** For tools the Host answers, the Host returns the model's text in `content` and gives views their data itself. Claude Code hands the model `structuredContent` as a JSON string in place of `content` (4.2), so view data sent through the agent would reach the model.
- **Each client** runs the ext-apps `AppBridge` with no MCP client. That is the reference host's second mode (3.6), where the host registers its own `oncalltool` and `onreadresource` handlers. The handlers become Host protocol requests.

This split keeps ADR 0009's two invariants: clients never speak MCP to a server, and the Host never sends clients requests. A client speaks the `ui/*` dialect only to its own sandboxed frame.

Host protocol additions, all of them additive under the protocol's existing rules (unknown event kinds are skipped, new requests go behind `features`):

- **`host/hello`.** The client lists which view types it renders, such as `text/html;profile=mcp-app`, and later `application/a2ui+json`. This works like `capabilities.clientTools`.
- **A `view` journal event**, linked to the tool call by `toolCallId` where the Host can match it. It carries server, tool, `resourceUri`, a content hash of the resource, `csp`, `permissions`, display modes, the complete tool input, and the complete result. The Host already turns agents' terminal `_meta` into events of its own, so this follows precedent.
- **`views/resource {hash}`.** Content-addressed resource reads, so megabyte-sized HTML is fetched once rather than journaled per call.
- **`views/callTool` and `views/readResource`.** Calls from a view, with the calling client as origin.
- **View messages and model context.** A view's `ui/message` becomes a prompt, or a steer while a turn runs. Its origin records the client and the view. `ui/update-model-context` is held and joined to the next prompt, which the spec allows (3.4).

**Advertise the UI extension always, not per attachment.** Servers may register different tools depending on whether the client can render (3.3), and changing an agent's tools mid-session discards its prompt cache. ADR 0009 rejected per-attachment tool lists for the same reason. A headless session therefore gets the same tools as an attended one. Its views render when someone attaches, or later from the journal.

### 12.3 Third-party servers: `weave` as a gateway

For servers weave configures, the Host can dial each server itself, as a real MCP client, and re-expose its tools through the one `weave` server that every session already gets. It should not pass those servers to the agent or rewrite the agent's traffic to them. The Host then stands at both ends of every call. Toward upstream servers it is an MCP client that can truthfully declare `io.modelcontextprotocol/ui`, because its clients render. Toward the agent it is the `weave` server. An earlier draft of this section proposed an inspecting proxy on the `mcp-bridge` relay; the gateway is better on every count that mattered there:

- **No message rewriting.** The bridge stays the byte relay ADR 0009 describes. The Host terminates both sides, so the UI capability is honest and each call's complete result (`structuredContent`, `_meta`, embedded resources) is captured where it arrives.
- **Older servers are the Host's business, not the agent's.** The Host speaks whatever revision an upstream server needs (2025-11-25 sessions included) while the agent sees only `weave` on 2026-07-28. ADR 0009's single-revision choice then constrains one connection, not every server.
- **No call matching.** The Host answers the agent's `tools/call` itself, so it knows which upstream call and which view belong to it.
- **Upstream interaction becomes Host pending requests.** Elicitation arrives from upstream as MRTR `input_required` results under 2026-07-28, or as server requests on older revisions. Either way the Host makes it a pending request every attached client sees, instead of a dialog inside one agent's terminal.
- **Availability belongs to the Host.** Under 2026-07-28 the Host can change the `weave` tool list and announce it on a `subscriptions/listen` stream with `notifications/tools/list_changed` ([tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/specification/2026-07-28/server/tools.mdx?plain=1#L236-L250)). Two rules bound this. The list "MUST NOT vary per-connection or as a side effect of other requests on the connection", though it may vary by per-request caller context ([tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/1155ca460e5097019f32769b38dcba194432e2fb/docs/specification/2026-07-28/server/tools.mdx?plain=1#L61-L69)). And changing a model's tools mid-session costs its prompt cache (ADR 0009). Availability can therefore follow Host state, such as the person enabling a server, an upstream server's own list changes, or its health, with infrequent, preferably additive changes in a deterministic order. It cannot follow the agent's own calls: an "enable these tools" tool breaks the first rule. Claude Code softens the second cost. With tool search, its default, only tool names load at session start, and a server's tools that arrive mid-turn are listed on the next request ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). Claude Code refreshes its tool list on `list_changed` and, on its 2026-07-28 runtime, holds the subscription stream open (same page). Codex's behaviour was not checked.
- **Client tools keep a stable list.** With `list_changed`, ADR 0009's objection that ACP fixes MCP servers at session setup no longer applies, because the server registration stays fixed while its tools change. Its prompt-cache and routing objections still apply, and device attachment changes far more often than configuration. Client tools should stay always declared and fail at call time, as ADR 0009 decided.

The gateway has costs:

- **Permissions.** An agent's per-server permission rules collapse into one `weave` namespace. Per-tool gating moves to the Host's permission policy, which sees every call anyway.
- **Tool names.** Namespaced names must fit agent limits; Claude Code leaves out MCP tools whose full name exceeds 128 characters (same page).
- **OAuth tokens.** The Host would hold tokens for remote upstream servers, a new kind of credential in a project whose rule so far is never to store credentials ([`tui/AGENTS.md`](../../tui/AGENTS.md)). That needs its own decision.
- **Fallback for older agents.** An agent that cannot speak 2026-07-28 would lose every gatewayed server, not only client tools. For such agents the Host should keep declaring upstream servers directly, as today, without views or availability control.
- **Claude Code's MCP runtime.** Claude Code speaks 2026-07-28 only on its v2 MCP runtime. That is the default only in some sessions (third-party clouds, the Claude apps gateway, telemetry or feature-flag fetching off) and is otherwise chosen by fetched feature flags. `MCP_SDK_GENERATION=v2` forces it ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). Setting that in the Claude preset's environment is what makes ADR 0009's server dependable for Claude, gateway or not.

MCP servers the agent loads itself (the third row of 12.1) stay outside the gateway; only the adapters can bring those through.

### 12.4 What weave adds that no spec covers: several clients, replay, and headless runs

Every MCP Apps host is one application showing one conversation. Weave has any number of attached clients on several devices, a journal that late attachers replay, and sessions nobody is watching. The MCP Apps lifecycle fits this better than it might seem, because a view is built from its tool input and result (3.4):

- **Each client renders its own instance**, the way Client Browser Panes share placement while live page state belongs to each client. A view's internal state survives a re-render only if the view saved it: in `localStorage`, which stays on that device under the server's origin, or on its server, which follows the person (3.8). MCP Apps has no shared view state, and the parity issues are open (5.2).
- **Replay rebuilds views from the journal.** A client that attaches late, reconnects, or scrolls back sends a fresh view the journaled `tool-input` and `tool-result`. Calls a view made after its first render are not replayed into other clients' views; those calls are journaled with their origin.
- **Old views use the template they were made with.** The Host caches each resource by content hash, so an old view renders as it first did even if the server has since changed its HTML or gone away. Its own calls then go to the server as it is now, and fail visibly if the server is gone.
- **Views mount lazily.** A view mounts when it scrolls into sight, is torn down (`ui/resource-teardown`) when it is far out of sight, and is rebuilt from the journal when it returns. This is how the TUI already treats image cells, of which the transcript keeps the newest 64.
- **Headless runs leave views behind.** A scheduled run can produce a dashboard nobody sees until a phone attaches the next morning. This follows from journaling views, not from anything in the spec.
- **Calls from a view are calls from a person's device**, but the code making them is third party. Apply `visibility` as the spec requires. Treat tools annotated `destructive`, or calls without `"app"` visibility, as pending requests for the client that made them. Journal every call.

These semantics are weave's to define. The Goose profile (8.6) and Embedded Views (8.1) both assume a single client.

### 12.5 Surfaces

- **TUI.** No terminal agent renders MCP Apps (4.2), and the TUI should not try. The tool's text `content` already arrives as the tool call's output. The tool call cell can add a marker saying a view exists and which attached devices can show it. Opening views in a local browser would need the Host to serve untrusted HTML on a second loopback origin through the web-host sandbox proxy (3.5). Leave that until someone asks; the Host's WebSocket origin must never serve view content. A declarative tier is what would let the TUI render at all: a small catalog (text, table, list, buttons) maps onto ratatui, as json-render's Ink renderer shows (9).
- **iPad and iPhone (WVE-91).** Claude for iOS renders views in `WKWebView` (3.7). Weave already has `WKWebView` lifecycle, non-persistent data stores, and popup and navigation policy from the Client Browser (WVE-80). A native host renders a view in an iframe directly, without the web-host proxy (3.5). The view's SDK sends to and accepts messages only from `window.parent` ([message-transport.ts](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/src/message-transport.ts#L71-L80)). A small trusted host page that runs the bridge and embeds the view in a sandboxed iframe works with every unmodified view. Claude's mobile apps instead render in "a native WebView… rather than a sandboxed iframe" ([design guidelines](https://claude.com/docs/connectors/building/mcp-apps/design-guidelines)), which implies an injected bridge. That host page can be one weave-owned page shared by every web-capable client; only its link to the Host differs per platform. Storage should be per server, not per view. The ext-apps persistence pattern and Excalidraw both keep view state in `localStorage` (3.8), so each server needs a stable origin and its own persistent store, much as Claude derives `ui.domain` from the connector URL (3.5). A store per view would lose that state on every re-render. It still stays on one device; state that should follow the person across devices has to live on the server. That bears on WVE-91's first decision. A native SwiftUI client gets this isolation and the official A2UI SwiftUI renderer (7). A Capacitor client would host views as iframes inside its own web view and needs a second origin for the proxy. Both can work. The native path is the simpler place to get the sandbox right.
- **Desktop.** If Alpha's Electron shell becomes a Host client, an isolated partition per view and the React `AppBridge` cover it. `@mcp-ui/client` wraps the same bridge but still depends on ext-apps 1.x (2.3), so use ext-apps directly.
- **Display modes.** `inline` maps to a transcript cell. `fullscreen` and the proposed `split` (#739) map to weave's Pane model where a client has one. `pip` has no weave equivalent and can fall back to fullscreen, as ChatGPT does on mobile (3.7). The spec names modes but not geometry, and the host has the last word (3.4), so a view's mode and placement are per-client presentation, not journaled session state. The same view can sit in its own Pane on an iPad and inline on a phone. Moving a view between transcript and Pane should keep its frame alive, as the proposed `split` mode asks and as Client Browser Pane moves already do.

### 12.6 Security

- **Views are third-party code on the person's devices.** Render them sandboxed, build CSP only from the declared `_meta.ui.csp` domains with the spec's restrictive default, and grant `permissions` per device rather than by default (3.5).
- **Follow the stricter sandbox.** The reference host's inner iframe keeps `allow-same-origin` and A2UI's forbids it (3.5). Apple clients sidestep the question with one `WKWebView` per view.
- **Links.** `ui/open-link` follows the TUI's rule for URL elicitations: show the full URL and its host, default to not opening, and open only on explicit consent ([`tui/AGENTS.md`](../../tui/AGENTS.md)).
- **Views never reach the MCP server directly.** It may be a stdio process on the Host's computer, so every call goes through the Host, which applies the session's policy. That is also what makes remote devices safe: a paired iPad's view can do what the Host allows, and nothing that only the Host's loopback can reach.
- **Treat `ui/message` as a prompt from that device.** It is journaled with its origin. In a headless session's policy it is never auto-approved.

### 12.7 What not to adopt

- **AG-UI.** It connects an agent backend to a frontend application. Weave already has that layer twice: ACP to agents, and the Host protocol to clients. A third event model would duplicate both; WVE-47 rejected CopilotKit for the same reason ([evaluation](wve-47-acp-chat-ui-library-evaluation.md)). Its MCP Apps middleware is worth reading as prior art, because it faces the same split as weave (6).
- **Legacy MCP-UI and Remote DOM.** MCP-UI is now an implementation of MCP Apps, and Remote DOM was dropped (2.3, 9).
- **`window.openai` and OpenAI MCP Extensions.** They are compatibility aliases and ChatGPT-only surfaces (5). Implement the standard only.
- **Waiting for ACP.** Embedded Views is unreviewed and no UI RFD exists (8.1). Weave's design keeps UI in the Host protocol, so it does not depend on ACP moving.

### 12.7a Websites are not views

A view is an HTML document its server ships. External URLs (`text/uri-list`) were deliberately left out of the spec (3.2), so showing someone else's website means framing it inside a view, which needs `frameDomains`; Claude restricts that pending security review (3.5). Most web apps refuse to be framed anyway. On 2026-10-19, `linear.app` sent `frame-ancestors 'self' https://cms.linear.app`, and its login page also sent `X-Frame-Options: SAMEORIGIN` (response headers fetched with `curl -I`). Signing in would also fail inside a sandboxed frame with partitioned storage and no popups. Such a framed site would also ignore the tool input and result. Weave already has the right surface for websites: the Client Browser Pane, with its profiles and sign-ins (WVE-80). A product such as Linear appears in a conversation as a view built on its API or MCP tools, served by its own MCP server or through the `weave` gateway with a template weave writes. A web app weave owns is a different case. Bundled as a self-contained document, with its data coming through tools, it can be a view.

### 12.8 Where this is headed, for weave

The facts in section 10 point the same way on four counts.

1. **The web tier has settled on MCP Apps.** ChatGPT, Claude, VS Code, Microsoft 365 Copilot, Cursor, and Goose host the same extension, and OpenAI's own keys are now aliases. Building a web tier on anything else would mean converting later.
2. **Declarative UI is arriving inside MCP Apps, not against it.** A2UI and MCP Apps already nest in both directions, and #699 would let a predeclared renderer view receive A2UI payloads. Native renderers are maturing, with an official SwiftUI renderer since 2026-10-07. Weave needs the declarative tier more than most hosts do, because two of its surfaces (the TUI and a native iPad client) are not browsers.
3. **Rendering is moving to embedding applications, and the agent protocol lags.** Anthropic and OpenAI built host hooks into the Agent SDK and the Codex app-server rather than rendering in their terminals. ACP has no standard, and Goose filled the gap with a private profile. A standard will follow implementations, and weave is placed to write one: it has the multi-client and replay requirements the Goose profile ignores. A small upstream proposal could carry three things. claude-agent-acp would use `mcpServerStatus()._meta.ui`, `readMcpResource`, and `mcp_call`; codex-acp would declare `extensions` and forward `mcpAppUi`; ACP would define a neutral `_meta` profile modelled on Goose's. That would make the third row of the 12.1 table work.
4. **Views are becoming two-way tool surfaces.** The draft's app-provided tools let an agent query and drive a live view (3.4, #798). That is the inverse of ADR 0009's client tools, which run on the client that sent the turn. In weave both should become one concept: a capability on a particular client that the agent can call. Today that is the clipboard; later it is a live view or the Client Browser.

### 12.9 Recommended sequence

1. **Record the Host/client split of 12.2 in an ADR before WVE-91 settles its client technology**, because how views render affects that choice (12.5).
2. **Build WVE-89 with views from the start.** Teach the Host's MCP service `_meta.ui` and `ui://` resources, add the `view` journal event and the `views/*` requests, and ship one Host-owned app tool. The best first candidate is a visual tool in the Excalidraw pattern (3.8):
   - **One fixed template, model-written content.** One fixed `ui://weave/visual` template takes HTML, or later a declarative spec, written by the model.
   - **Visuals live apart from the call.** The Host stores each visual as an object with its own identity and revisions, independent of the tool call, under the Host's state directory. It returns the model a short text plus a handle. A later call updates the visual by handle and makes a new revision, and the person can pin the latest revision into a Pane.
   - **Untrusted content stays boxed.** Model-written HTML runs in a nested sandboxed frame with no bridge and a CSP the Host sets. It may carry instructions injected from the model's context, so it must not reach `tools/call` or `ui/message`.
   - **Claude must see the tool.** Mark the tool `_meta["anthropic/alwaysLoad"]` so Claude Code's tool search does not hide it from the model ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)).
3. **Render views in the first non-terminal client.** For the native Apple client, use one `WKWebView` per view, reusing WVE-80's isolation. Add the TUI's view marker at the same time.
4. **Make `weave` the gateway for servers in `[[mcp_servers]]`**, under its own ADR (12.3): the Host dials them as an MCP client, re-exposes their tools and views through `weave`, controls availability with `list_changed`, and keeps declaring them directly to agents that cannot speak 2026-07-28.
5. **Add a declarative tier** when A2UI 1.0 is final or #699 lands. Accept it in the `render` tool and give the TUI and the native client their own renderers for a narrow catalog.
6. **Propose the ACP projection upstream** (12.8, item 3), with weave's multi-client semantics as the case the existing profiles miss.
