The question: what OpenBot is, what CopilotKit and the standards around it offer, and which of it weave could apply. Two earlier notes cover much of the ground and aren't repeated: [MCP-UI, MCP Apps, and the agent UI protocols around them](mcp-ui-and-agent-ui-protocols.md) (2026-10-18) has AG-UI 1.0's events, A2UI, MCP Apps, the ACP adapters and the design that became [ADR 0012](../adr/0012-views-the-host-does-the-mcp-side-and-clients-render.md); [T3 Code's thread view, weave's chat, and chat UI libraries](t3code-chat-and-chat-ui-libraries.md) (2026-11-10) has CopilotKit's chat kit beside the others. This note reports what changed since, adds OpenBot and CopilotKit proper, and looks again at the verdicts those notes reached. [A2A and agents controlling threads](a2a-and-agents-controlling-threads.md) (2026-10-30) covers A2A, which wasn't read again. It uses weave's words (Host, client, thread, turn, steer, pending request, Bot, Block) and puts another project's word in italics where it differs. AG-UI calls a turn a *run*; OpenBot's *Bot* is not weave's Bot.

## In brief

- **OpenBot is CopilotKit's own product**, [`CopilotKit/OpenBot`](https://github.com/CopilotKit/OpenBot): a self-hosted workspace of "AI coworkers", each an AG-UI endpoint with a browser and shell in a container, with policy, approvals and an audit trail in a server between them. MIT, three months old, 11,382 stars, v1.0.2. It needs CopilotKit Intelligence, which is separately licensed. The name is certain: the README says "From CopilotKit, creators of AG-UI". Two other projects share it and aren't meant (1.1).
- **AG-UI still doesn't fit as weave's wire, and 1.0's text now says why in one sentence**: "The protocol has no mid-run channel from the consumer". A permission request or a client's tool ends the run, and a new run answers it. Weave's steers, queued prompts and pending requests all happen inside a turn, with several clients attached. ADR 0012's rejection stands.
- **OpenBot's maintainers declined ACP**: "OpenBot's bring-your-own-agent model is AG-UI endpoints. A protocol-level ACP provider that spawns local coding harnesses is out of scope". No official AG-UI to ACP mapping exists in either project. One community bridge is listed on ACP's own clients page; it maps a permission request to a state event and a REST call, outside both protocols.
- **CopilotKit's React hooks need an AG-UI agent object and own the messages.** Feeding them from the Host protocol means writing an `AbstractAgent`, registered through a prop named `agents__unsafe_dev_only` or one the code calls part of the "Enterprise Intelligence tier". Not worth it; the chat note's verdict holds.
- **What is worth taking is not the protocol.** A2UI 1.0 is now the current version, with a stable React renderer, which makes a declarative tier for Views buildable. OpenBot's approvals and its policy's `initiator` field are a better-worked version of what weave's permission policy does for headless threads. Its guardrails on schedules and Bot-to-Bot handoffs are cheap to copy.

### 1.2 What it is

- **A workspace of *Bots*.** A *Bot* has "eight things": Conversations, Routines, Memory, Skills, Apps, Computer, Approvals and Activity ([README L344-L348](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L340-L342)). It comes in a personal edition (one person, nobody signs in, one computer, one Bot to start) and a team edition with sign-in, roles and admin pages ([personal-edition.md L3-L5](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/personal-edition.md?plain=1#L3-L5)).
- **A Bot is an AG-UI endpoint.** "A Bot is any endpoint speaking AG-UI ... so OpenBot is not tied to a framework" ([README L331](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L331)). Built-in Bots run inside the OpenBot server; others are registered by URL with an optional write-only authorization header ([README L408-L421](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L408-L419)). The repository ships fifteen `agent-*` sample Bots, one per framework (LangGraph, Mastra, ADK, Claude Agent SDK, Strands, Pydantic AI and others).
- **Parts** ([architecture.md L3-L24](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L3-L24)): a React and Vite app; a Hono API server that holds the CopilotKit runtime, auth, policy, audit, credentials and connectors; PostgreSQL; `agent-computer`, a container with Chromium, a workspace and a shell per person or per isolated Bot; a supervisor that makes those containers; a worker for schedules; and CopilotKit Intelligence for "durable threads, memory, Learning, and realtime gateway". Its packages pin `@copilotkit/react-core` and `@copilotkit/runtime` 1.85.0 and `@ag-ui/core` 1.0.2 ([app/package.json](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/app/package.json#L17-L20), [server/package.json](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/server/package.json#L15-L29)). The desktop app is Tauri 2 around the same page, running the backend in Docker; the phone app is Expo and React Native ([desktop/package.json](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/desktop/package.json#L14-L20), [mobile/package.json](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/mobile/package.json#L18-L33)).
- **A turn's path** ([architecture.md L34-L41](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L34-L41)): the app opens a conversation; the server resolves the person and the Bot; the CopilotKit runtime sends the turn to the Bot's AG-UI endpoint; the browser registers *frontend tools* for that Bot (browser and file tools, and the components granted to it) while app and MCP tools are registered on the server's runtime; every acting call goes through the server for authorization and audit.
- **Protocols.** AG-UI to Bots; MCP to tools, through a catalogue the deployment vouches for, with Composio or Arcade as broker ([README L398](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L398)); A2UI for rendered results (the app's source refers to it throughout). Not ACP (1.5), and no A2A was found.

### 1.3 The parts weave has a counterpart for

- **The gateway and its policy.** The server is "the action boundary": it resolves the target, evaluates the policy, writes an audit row, and only then calls the computer. Rules are CEL expressions over `tool.name`, `intent`, `bot.id`, `actor.id`, `page.*`, `element.*`, `command`, `file.*`, `mcp.*` and `initiator.kind`. Deny rules run before allow rules, a missing policy permits nothing, and a `dry-run` mode "decides and records every action but lets it through" ([architecture.md L43-L79](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L43-L79)).
- **What started a run.** Every audit row names an initiator: `person`, `deployment`, `routine`, `responsibility`, `memory` or `handoff`. It "is the only field that can tell an unattended run from somebody typing", so "a rule can refuse a scheduled routine what it would allow a person", and the Activity page has a "Nobody watching" filter ([architecture.md L65-L70](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L65-L70), [L102-L123](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L102-L123)). The value travels in a run assertion the deployment signs, so "a Bot cannot relabel its own run" ([L130-L136](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L130-L136)).
- **Approvals** ([approvals.md](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/approvals.md?plain=1#L1-L45)). Six kinds of action always ask: deleting, sending to other people, sharing, posting, paying, and changing credentials or account settings. They are recognized "by what the action is called, never by what it carries": a tool's first verb, a button's label, an MCP tool's `destructiveHint`. A card answers Allow once, Allow for this conversation, Always allow here, or Deny; the conversation answer covers "the same Bot, the same tool, the same place and the same account" and nothing wider. A credential change on a website is handed to the person instead: "I did it myself" or "Don't do it". A task started from a schedule's check-in "asks before every change". The document also lists what it fails to recognize.
- **Routines** (weave's schedules). A standing instruction fires on a schedule, "runs as the person who created it, and posts the Bot's reply into its conversation". The work queue is one PostgreSQL table claimed with `select ... for update skip locked` ([architecture.md L200-L211](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L200-L211)). Guardrails: a 15-minute floor, "because a model can be talked into anything a sentence can describe, including 'every minute'", a cap of 20 enabled routines, and ten consecutive failures switch one off ([routines.md L106-L120](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/routines.md?plain=1#L106-L120)).
- **One Bot handing work to another.** `message_bot` takes typed fields (the task, what bounds it, what a good answer looks like) because "free text is the commonest way a handoff goes quietly wrong". The deployment, never the model, decides who is addressed, where the answer lands, who is asking and how deep the chain is; depth and per-run caps "refuse rather than truncate"; a hop that fails for good is said in the conversation the person watches. `ask_person` is offered beside it, since "a model with no named way to stop takes one of the two it has" ([architecture.md L231-L300](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L231-L300)).
- **Taking the wheel.** A Bot that meets a login wall asks for help; the person drives its browser or shell in the same panel; "while a person controls the browser, Bot actions are refused rather than queued" ([architecture.md L154-L170](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L154-L170)).
- **Components.** "Components are frontend tools a Bot can call instead of answering only in prose": compiled React components in a gallery, and sandboxed ones authored in an admin playground and "published with no deployment". Every call asks the server whether the component exists, is published and isn't withheld from that Bot, and its data functions need a grant of their own ([architecture.md L213-L229](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/docs/architecture.md?plain=1#L213-L229)).

### 1.4 Licence, maturity and what isn't open

- **Licence.** "The OpenBot application template is open source under the MIT license ... It uses CopilotKit Intelligence, which is separately licensed": a free local licence on a laptop, a trial licence for a Kubernetes evaluation, a production licence beyond that ([README L107-L115](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L107-L115)). Conversations and memory live in Intelligence ([README L405](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L405)), whose source is in none of the repositories read. The local licence "lasts 30 days" and is renewed with the CopilotKit CLI ([README L270-L275](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L270-L275)); "initial downloads, account sign-in, and local license renewal need internet access" ([L115](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L115)).
- **Maturity.** Created 2026-08-17, first release v0.0.1 that day, 27 stable releases since, v1.0.2 on 2026-11-11. 1,088 commits on `main`, 558 of them since 2026-10-13, 58 contributors, 83 open issues and pull requests (GitHub API). It ships notarized Mac and signed Windows installers. Web, iOS, Android, Slack and Teams are links to an early-access sign-up, not downloads ([README L55-L57](https://github.com/CopilotKit/OpenBot/blob/ece78095741476dfaeab88231c099813f252ecde/README.md?plain=1#L55-L57)).
- **How it relates to CopilotKit.** It is CopilotKit's reference application and the base of a commercial product: "CopilotKit Soar ... AI coworkers your company owns, running on your own servers. Powered by OpenBot", in early access ([CopilotKit README L45](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/README.md?plain=1#L45)), and "OpenBot for Business" in OpenBot's own README.

### 1.5 OpenBot and ACP

- **Asked for and declined.** Issue [#295](https://github.com/CopilotKit/OpenBot/issues/295) (2026-08-30) proposed "a Bot that speaks the Agent Client Protocol over stdio, so a coworker can run on a coding harness a person already has a subscription to". A CopilotKit contributor closed it on 2026-09-13: "OpenBot's bring-your-own-agent model is AG-UI endpoints. A protocol-level ACP provider that spawns local coding harnesses is out of scope, consistent with other harness-shim requests we've declined." Pull request [#542](https://github.com/CopilotKit/OpenBot/pull/542), an AG-UI gateway with Codex app-server, Grok ACP and Claude CLI drivers, was closed unmerged two days later.
- **The issue's account of ACP's limits** is its author's, not a maintainer's, but matches what weave has seen: "ACP cannot take a harness's tools away", and a harness in a read-only mode "read `/etc/hosts`, an absolute path outside its workspace, and asked nobody", so "the boundary has to come from the OS".
- **None of the three repositories mentions ACP** (a search of OpenBot, CopilotKit and ag-ui for "Agent Client Protocol", `agentclientprotocol` and `ACP`, changelogs and lockfiles aside, found nothing).

## 2. CopilotKit

- **What it is now.** "The open-source stack for putting AI agents in front of real users": bring an agent "on any framework, and give it chat, generative UI, shared state, and human-in-the-loop in React, Angular, Vue, React Native, Slack, and Microsoft Teams" ([README L35](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/README.md?plain=1#L35)). 38,668 stars, MIT, v1.87.0 on 2026-11-11, two or three releases a week.
- **Packages** (each `package.json` under [`packages/`](https://github.com/CopilotKit/CopilotKit/tree/d0f7fa783a85364063bf077a210dbc3593616e12/packages), all MIT): `@copilotkit/core`, `react-core`, `react-ui`, `runtime`, `react-native`, `vue`, `web-components`, `a2ui-renderer`, `mcp-apps-renderer`, `voice`, `sqlite-runner` and `learning` at 1.87.0; `@copilotkit/angular` at 0.6.0; `@copilotkit/channels` and its Slack, Teams, Discord and WhatsApp adapters at 0.12.0. The current API is the `/v2` entry of each package; v1 remains as `v1-deprecated`.
- **The runtime.** "Your frontend needs a trusted server between it and your agents. The Copilot Runtime is that server": it keeps keys out of the browser, authenticates, and routes each chat to an agent ([copilot-runtime.mdx L11](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/%28shared%29/backend/copilot-runtime.mdx?plain=1#L11)). It is a Node HTTP handler. An `AgentRunner` behind it has `run`, `connect`, `isRunning` and `stop`, with in-memory and Intelligence implementations ([agent-runner.ts L208-L220](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/packages/runtime/src/v2/runtime/runner/agent-runner.ts#L208-L220)); `connect` is how a second tab joins a run.
- **Without the runtime.** "If you host and secure your own AG-UI agent, the frontend can call it directly, without the CopilotKit runtime. Use `selfManagedAgents` in production. For local development, use `agents__unsafe_dev_only`" ([self-managed-agents.mdx L6-L9](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/%28shared%29/backend/self-managed-agents.mdx?plain=1#L6-L9)). Both take a record of `AbstractAgent` objects from `@ag-ui/client`. From the source: "`selfManagedAgents` is part of CopilotKit's Enterprise Intelligence tier. The signal is advisory and client-side only (not enforced)"; without a licence key it logs a warning in development and production ([CopilotKitProvider.tsx L661-L674](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/packages/react-core/src/v2/providers/CopilotKitProvider.tsx#L661-L674)). This answers the chat note's open item on CopilotKit without an AG-UI agent: there is no such mode; every hook reads an AG-UI agent.
- **Headless.** `@copilotkit/react-core/v2/headless` exports the hooks with "no CSS and no built-in chat UI components" and without the Markdown stack, and is what the React Native package builds on ([headless.ts L1-L17](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/packages/react-core/src/v2/headless.ts#L1-L17)). Three hooks carry a custom chat: `useAgent` (messages, `isRunning`, state), `useCopilotKit` (`runAgent`) and `useRenderToolCall`; `useRenderActivityMessage` draws A2UI and MCP Apps ([headless-ui.mdx L25-L56](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/custom-look-and-feel/headless-ui.mdx?plain=1#L25-L56)). The full `react-core` depends on `rxjs`, `lit`, Radix, `recharts`, `streamdown` ^1.3.0, `@tanstack/react-virtual` and `@scarf/scarf` ([package.json L88-L113](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/packages/react-core/package.json#L88-L113)).
- **Frontend tools (formerly *actions*).** `useFrontendTool` registers a tool the page runs; `useComponent` and `useRenderTool` draw a tool call as a component. They travel to the agent in each run's `tools` list (3.2).
- **Human-in-the-loop** has two forms ([index.mdx L42-L52](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/human-in-the-loop/index.mdx?plain=1#L42-L52)): `useHumanInTheLoop`, where the model decides to pause by calling a client-side tool whose `render` collects the answer; and `useInterrupt`, where the agent's code pauses, "for example LangGraph `interrupt()` or Mastra `suspend()`", which is AG-UI's interrupt outcome.
- **Shared state.** "A two-way connection between your UI and agent state": components read it with `useAgent` and re-render when the agent changes it, and the page can write it back ([shared-state/index.mdx L3](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/shared-state/index.mdx?plain=1#L3), [L42-L65](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/shared-state/index.mdx?plain=1#L42-L65)). It is AG-UI's state events under a hook. *CoAgents*, the 2024 name for this (LangGraph agents with shared state), survives only in older pages and the v1 hook `useCoAgentStateRender`.
- **Generative UI, as CopilotKit sorts it** ([generative-ui/index.mdx L10-L33](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/generative-ui/index.mdx?plain=1#L10-L33)), "by who decides what renders":
  - **Controlled**: "You build the components. The agent's tool calls and state decide what they show."
  - **Declarative**: "The agent writes a UI spec. Your app renders it from a catalog of allowed components": A2UI, json-render, Hashbrown.
  - **Open-Ended**: "The agent or an MCP server brings its own UI": MCP Apps, and *Open Generative UI*, where the model writes HTML, CSS and JavaScript through a `generateSandboxedUi` frontend tool and it runs "in an isolated iframe without same-origin access", with optional functions the page lets it call ([open-generative-ui.mdx L8-L44](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/generative-ui/open-generative-ui.mdx?plain=1#L8-L44)).
  - "Open-JSON-UI", which the October note couldn't trace to OpenAI, is gone from CopilotKit's documentation (no file under `showcase/shell-docs/src/content` mentions it) and remains only on AG-UI's concept page ([generative-ui-specs.mdx L10-L16](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/concepts/generative-ui-specs.mdx?plain=1#L10-L16)).
- **The renderers are separable.** `@copilotkit/a2ui-renderer` depends on `@a2ui/web_core` 0.15.0, `@copilotkit/shared`, `marked` and `zod`, with React as its peer; `@copilotkit/mcp-apps-renderer` depends on `@modelcontextprotocol/ext-apps` ^1.7.5 and the MCP SDK ([a2ui-renderer](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/packages/a2ui-renderer/package.json), [mcp-apps-renderer](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/packages/mcp-apps-renderer/package.json)). The second is still on ext-apps 1.x, as `@mcp-ui/client` was in October.
- **Hosted versus open.** The SDKs and runtime are MIT. **CopilotKit Intelligence** is the commercial layer: saved threads (*AG-UI Streams*), user memory, Automatic Learning, Channels delivery and analytics. "Every organization starts on Developer, which is free"; Pro and Team are paid; self-hosting on Kubernetes needs "Team Self-hosted or Enterprise" ([plans.mdx L12-L42](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/%28shared%29/intelligence/plans.mdx?plain=1#L12-L42)). It records "its own copy of the supported AG-UI interaction history that passes through your connected CopilotKit runtime", "not a copy of your framework database" ([bring-your-own-thread-system.mdx L9-L26](https://github.com/CopilotKit/CopilotKit/blob/d0f7fa783a85364063bf077a210dbc3593616e12/showcase/shell-docs/src/content/docs/%28shared%29/intelligence/bring-your-own-thread-system.mdx?plain=1#L9-L26)). Without it, thread history is whatever the agent framework keeps.

### 3.2 The shape that decides fit

- **One message goes from the application to the agent.** "Events flow from producer to consumer. Exactly one message flows the other way: `RunAgentInput`, sent once to open each exchange" ([run-input.mdx L6-L8](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/basic/run-input.mdx?plain=1#L6-L8)). It carries `threadId`, `runId`, `messages`, `tools`, `context`, `state`, `forwardedProps` and `resume`.
- **The application carries the history.** `messages` is required: "A producer MUST treat it as the complete history it is being shown — the protocol has no side channel through which earlier turns arrive" ([L36-L40](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/basic/run-input.mdx?plain=1#L36-L40)). A producer "that carries nothing across the gap is conformant".
- **No channel into a running run.** "A run sometimes needs something only the outside world can give it — an approval, a credential, a choice. The protocol has no mid-run channel from the consumer, so the run does not wait: it ends, saying what it is waiting for, and the run that continues from it carries the answers" ([interrupt-resume.mdx L6-L9](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/basic/patterns/interrupt-resume.mdx?plain=1#L6-L9)).
  - **Interrupts.** The run ends with `RUN_FINISHED` whose outcome lists `Interrupt` objects: an `id`, an open `reason`, a `message`, the `toolCallId` an approval concerns, and a `responseSchema` "carried opaquely so a consumer can build a form for it". The next run's `resume` list must answer or explicitly abandon every one; "omission is not abandonment", and the consumer enforces that ([L13-L66](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/basic/patterns/interrupt-resume.mdx?plain=1#L13-L66)).
  - **Frontend tools.** "The agent proposes a call, the application executes it ... the answer can only cross a run boundary": the run finishes as a success naming `pendingToolCallIds`, and the result rides the next input's messages ([tool-calls.mdx L155-L177](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/events/tool-calls.mdx?plain=1#L155-L177)).
  - Nothing corresponds to a steer. A cancelled run has its own outcome.
- **State.** `STATE_SNAPSHOT` replaces the state, `STATE_DELTA` amends it with an RFC 6902 patch, and "the next run's input carries it back as the starting value — the loop that keeps both sides agreed". State is "any JSON value". Two rules worth keeping whatever carries state: "State events are remote writes into application state. An application MUST validate what it reads out of state before acting on it", and a producer "SHOULD NOT put secrets in state" ([state.mdx L13-L26](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/events/state.mdx?plain=1#L13-L26), [L54-L96](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/events/state.mdx?plain=1#L54-L96)).
- **Transports.** HTTP with SSE is required of anything that speaks HTTP; HTTP with protobuf frames is optional. WebSockets, buses and pipes are allowed as custom bindings that keep the event model and frame JSON "exactly as the SSE binding does". "AG-UI defines no credential" ([transports/index.mdx L14-L71](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/basic/transports/index.mdx?plain=1#L14-L71)).
- **Capabilities** are optional groups an agent declares (`tools`, `state`, `multiAgent`, `reasoning`, `humanInTheLoop` and others). "An omitted field means undeclared, not unsupported", and "the event stream is authoritative" over any declaration ([capabilities.mdx L26-L43](https://github.com/ag-ui-protocol/ag-ui/blob/8a951d14144e7dde986ccec23364e01a36111a63/docs/spec/1.0/basic/capabilities.mdx?plain=1#L26-L43)).

### 3.3 AG-UI and ACP

- **Official: nothing in either direction.** The AG-UI and CopilotKit repositories don't mention ACP (1.5). ACP's repository has no AG-UI binding; its only reference is a line on the clients page (below). CopilotKit places AG-UI beside MCP and A2A, not beside ACP ([October note §6](mcp-ui-and-agent-ui-protocols.md#6-ag-ui)).
- **AG-UI's Claude adapter is not ACP.** [`integrations/claude-agent-sdk`](https://github.com/ag-ui-protocol/ag-ui/tree/8a951d14144e7dde986ccec23364e01a36111a63/integrations/claude-agent-sdk) wraps the Claude Agent SDK directly (TypeScript 0.0.9, Python 0.2.4). Much of its README is about recovering a native session whose approval was cut off, which is what bridging a blocking request to a run boundary costs.

- **Other bridges** were found by search and judged by description only: `sparkprime/agui-on-acp` ("Wrap ACP agent in AGUI protocol", no stars), `agentsyaml/uni-acp-agui` ("Rust impl for ACP & AG-UI bridge", one star, no licence), and multi-protocol runtimes that serve one agent over several protocols (`phil65/agentpool`, `awakenworks/awaken`). ## 5. Fit for weave

Judgement from here on.

### 5.1 What weave is that these aren't

CopilotKit's world is an application with an agent inside it: one person, one page, one conversation at a time, and a server the application owns. Weave differs on four counts, and each rules something out.

- **The Host is the runtime authority and keeps the record** ([ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md)). Clients attach to a thread, catch up from its journal, and hold no history the Host needs back. AG-UI has the application carry the messages and state into every run.
- **Things happen inside a turn.** A person steers a running turn, queues prompts behind it, and answers pending requests while the agent's process waits, and any attached client may answer. ACP's `session/request_permission` is a blocking request. AG-UI has one message in and a stream out.
- **Several clients, some of which can't draw a page.** The TUI and a headless thread have a text floor ([ADR 0018](../adr/0018-clients-decide-enrichment-above-a-text-floor-and-the-tui-composes-with-its-multiplexer.md)). CopilotKit's model is a renderer per frontend framework.
- **Agents are other people's programs, spoken to over ACP, and weave never branches on which one is connected.** CopilotKit's features assume the agent cooperates: emits state events, offers the application's tools to its model, calls a `generateSandboxedUi` tool. Claude Code and Codex do none of that over ACP. Whatever weave adds has to come through the one thing every agent gets, the Host MCP server ([ADR 0009](../adr/0009-client-tools-through-a-host-owned-mcp-server.md)).

### 5.2 The candidates

| Candidate | Verdict | What it would cost and displace |
| --- | --- | --- |
| AG-UI as the wire between Host and app | Doesn't fit | The Host protocol, its golden snapshots and generated TypeScript, for less than it carries |
| Agents and Bots drawing UI in a Block | Fits with caveats, through ADR 0012, not AG-UI | A Host tool, a journal event, a Block type, a renderer |
| CopilotKit's components or hooks in the app's chat | Doesn't fit | `app/src/chat`, for a second state layer |
| Shared state between an agent and a Block | Fits with caveats, as a Host-kept document | A document kind, two tools, a Block type |
| Human-in-the-loop patterns | The mechanism doesn't fit; OpenBot's policy ideas do | Additions to the permission policy |
| A Host serving AG-UI clients | Fits with caveats, little value today | A small service; lossy |
| AG-UI agents as weave agents | Fits with caveats, little value today | An ACP adapter nobody has written |
| OpenBot as a design reference for Bots | Fits, as reading | Nothing |

**AG-UI as the wire between Host and app: doesn't fit.** Nothing in 1.0.4 or the 1.1 draft changes ADR 0012's reason, and 3.2 sharpens it.

- Steers, queued prompts and answering a pending request mid-turn have no AG-UI form. A bridge would end a run at every permission request and start another, while the Host's turn stays one turn. The Claude adapter's recovery rules (3.3) show what that costs even with one client.
- `messages` and `state` on every run input put history in the client. Weave's journal positions, late attach and catch-up would sit beside it, not in it.
- It covers threads only. Sessions and their layout documents, terminals' streams, worktrees, Projects, Bots and pairing would still need the Host protocol, so the app would speak two.
- There is no Rust to build on: the community crates are a client for 0.x (3.1). The Host would hand-write a 1.0 encoder, and the app would swap types generated from the Rust for `@ag-ui/core`'s.
- The TUI gains nothing.

What is worth copying into the Host protocol's own spec, as text: the snapshot-and-patch pattern with its rule that a patch that fails to apply is skipped with a warning and one that is malformed is fatal; an interrupt's `responseSchema` as a way for a tool to say what answer it wants; "omitted means undeclared, not unsupported" for capabilities.

**Agents and Bots drawing UI in a Block: fits with caveats.** ADR 0012 already settles how: the Host does the MCP side, journals a view, clients render, and what a model wrote runs in a nested sandbox without the bridge. None of it is built (no view event in `protocol/src`, no renderer in `app/src`, at `d6210089`). CopilotKit's three kinds line up with what weave could offer, in order of cost:

- **Open-ended, model-written.** CopilotKit's Open Generative UI is the October note's Visual under another name: a tool whose argument is HTML, run in an iframe without same-origin, with a short list of functions the page lets it call. That it ships as a default in a 38,000-star library is evidence the pattern holds. Weave's version is a tool on the Host MCP server. Cost: the tool, a `view` journal event, a content-addressed read, a Block type, and the sandbox under the app's Content Security Policy in both WKWebView and Tauri.
- **Declarative.** A2UI 1.0 is current and its React renderer stable (4), which removes the October note's reason to wait ("when A2UI 1.0 is final"). The same Host tool could take an A2UI surface. `@a2ui/react`, or CopilotKit's thin wrapper `@copilotkit/a2ui-renderer`, would draw it in a Block with weave's own components as the catalog; the TUI could draw a narrow catalog or fall back to the tool's text. This is the tier that reaches every client, and a declarative surface is data, so it needs no sandbox. To check first: that the renderer loads nothing from the network and runs under `script-src 'self'`; what a model writes unprompted against a small catalog; whether Claude Code's tool search hides the tool.
- **MCP Apps** from upstream servers stays as ADR 0012 and [ADR 0013](../adr/0013-configured-mcp-servers-through-the-host-mcp-server.md) have it. `@copilotkit/mcp-apps-renderer` is no shortcut: it is on ext-apps 1.x and expects an AG-UI agent to proxy through.
- **A Bot's own components.** OpenBot's gallery is the nearest thing to Block types of the person's own (WVE-206): compiled components the app ships, plus sandboxed ones published without a release, each checked on every call and granted per Bot. Worth reading before WVE-206 is planned. Its split between "exists", "published" and "withheld from this Bot" is more than a single-user weave needs.

**CopilotKit's components or hooks in the app's chat: doesn't fit.** The chat note ruled out kits that own the messages ([§5.1](t3code-chat-and-chat-ui-libraries.md#51-what-differs-and-what-it-rules-out)). Looking closer confirms it. The only seam is an `AbstractAgent` that turns the Host's journal into AG-UI events, handed to the provider through a prop named unsafe-for-dev or one marked for a paid tier (2). Then steers, the queue and pending requests are bolted on beside hooks that don't know them; the headless example "only get[s] text" until tool calls and activity are wired by hand; and the full package brings `rxjs`, `lit`, Radix beside Base UI, and Streamdown 1.x beside the app's 2.x. Weave would write an adapter to rent a message list it already has.

**Shared state between an agent and a Block: fits with caveats, as a Host-kept document.** The idea is good: a plan, a checklist or a form that the agent and the person both edit, shown in a Block. AG-UI's way needs the agent to emit state events, which ACP agents don't. Weave's way would be:

- a small JSON document the Host keeps per thread or per Session, versioned as a Session's layout is, with the newest write refused when it's stale (`ifRevision`);
- two tools on the Host MCP server for the agent, read and patch;
- a request for clients to patch it, and a watch;
- a Block type that draws it, with a text rendering for the TUI.

The agent learns of the person's edit on its next read, or the Host joins a note to the next prompt, as ADR 0012 has `ui/update-model-context` do. AG-UI's two cautions apply as written: treat the document as untrusted input, and keep secrets out of it. Caveat: ACP's plan updates already cover the commonest case, the agent's own task list, one way. This earns its cost only with a second use, such as a Bot's standing checklist the person ticks off. Cost: a document kind and store in the Host, protocol additions with snapshots and generated types, and the Block.

**Human-in-the-loop: the mechanism doesn't fit, the policy ideas do.** Weave's pending requests are already the stronger mechanism: they wait inside the turn, every attached client sees them, the first answer counts, and a policy answers for headless threads ([ADR 0026](../adr/0026-headless-threads-start-in-the-agents-configured-mode-and-say-what-their-policy-rejected.md)). `useHumanInTheLoop` is a client tool with a form, which weave has as client tools and elicitations. What weave's permission policy lacks is OpenBot's depth. Today it is a list of ACP tool kinds to approve and whether the rest ask or are rejected (`protocol/src/policy.rs`). From 1.3, in rising cost:

- **What started the turn, as a policy input.** The Host protocol already records a turn's origin (a schedule, a Bot, a paired device). Letting a policy say "ask when nobody is watching, approve when a person sent the prompt" is OpenBot's `initiator.kind`, and it bears directly on Bots and delegated threads.
- **A dry-run policy** that records what it would have rejected and lets it through, for tuning a Bot's policy before trusting it. ADR 0026's "say what their policy rejected" is half of this.
- **An answer scoped to the thread.** ACP's `allow_always` leaves the scope to the agent. OpenBot's "for this conversation" is the Host remembering an answer for one thread, one tool and one target.
- **Kinds of action that always ask** (send, share, post, pay, delete, credentials), recognized by a tool's name and annotations. This matters once agents reach upstream servers through the Host MCP server, where the Host sees each call and its `destructiveHint`. For agents' own tools the Host sees only what ACP's request carries.

Caveat: OpenBot can enforce its policy because every tool goes through its gateway. Weave can only answer what an agent asks, and the issue in 1.5 is a reminder that some agents read without asking. Policy in weave bounds what is approved, not what is possible.

**A Host serving AG-UI clients: fits with caveats, little value today.** A service (a client of the Host, as the Dispatcher is) could take a `RunAgentInput`, prompt a thread, turn the journal into events, end the run with an interrupt at each pending request, and send the next run's `resume` as `pending/answer`. The Host's turn would stay open across the gap, which the Host handles well since the journal holds it. It would be lossy: no steers, no queue, no terminals, and one answerer. What it would buy is every AG-UI client: a Bot of weave's as a *Bot* in OpenBot, or reached from Slack, Teams, Discord or WhatsApp through CopilotKit's MIT Channels SDK. That last one is the only use that isn't a curiosity. If the person wants to message a Bot from a chat platform, this is a cheaper road than building each platform into the Edge, and it should be weighed against A2A, which the A2A note already judged for agents reaching threads. Cost: a small Node service using `@ag-ui/core`, or a hand-written encoder in Rust.

**AG-UI agents as weave agents: fits with caveats, little value today.** The Host launches ACP agents and doesn't branch on which, so an AG-UI endpoint would arrive as an ACP adapter: a stdio program that keeps each thread's messages, since the endpoint may keep nothing, POSTs a run per turn, and maps the events to `session/update`. Interrupts map naturally to `session/request_permission`. Frontend tools have no ACP counterpart beyond offering the Host MCP server. No such adapter exists (3.3). It would bring LangGraph, Mastra, ADK and hosted agents into threads, but those agents have no notion of a working directory, a worktree or a terminal, which is what a thread is for. Not worth building until the person has such an agent they want in a Session.

**OpenBot as a design reference for Bots: fits, as reading.** OpenBot and weave's Bots ([ADR 0028](../adr/0028-bots-are-dispatcher-records-whose-work-goes-on-in-ordinary-threads.md)) answer the same want differently. OpenBot owns the loop's surroundings (computer, gateway, memory service) and takes any agent that speaks AG-UI. Weave owns nothing but the thread and takes any agent that speaks ACP, with memory as files in the Bot's home. Running OpenBot beside weave, or building on it, would mean a second server, PostgreSQL, Docker and a licence that phones home to renew, for a single person who already has Hosts. And it turned ACP down. Its documents are worth lifting from directly, though:

- **Schedule guardrails**: a floor on how often, a cap on how many, and switching one off after repeated failures (1.3). Weave's Bots now make their own wake-ups and schedules by tool (WVE-178), which is exactly where "a model can be talked into ... 'every minute'" applies.
- **Handoff rules**: typed fields for a delegation, a depth cap that refuses, and saying so in the thread the person watches when a delegated turn fails for good. Weave's delegated threads and reports have the last; the first two are cheap.
- **A named way to stop and ask.** `ask_person` beside the delegation tool. Weave's agents can end a turn with a question, but a Bot working unattended has no tool that says "this waits on the person" and raises a notification. A Host tool that makes a pending request of it would give one.
- **"Nobody watching"** as a filter on what Bots did. The Dispatcher's occurrences and the Hosts' journals hold the data.

### 5.3 What is worth a spike, in order

1. **A declarative View from a Host tool, in a Block.** One tool on the Host MCP server whose argument is an A2UI 1.0 surface, journaled, drawn by `@a2ui/react` in the app with a catalog of five or six of weave's components, and by its text in the TUI. It tests the whole of ADR 0012's path with the least sandbox work, on the tier every client can reach, and it tells whether Claude and Codex write usable surfaces. An HTML Visual in a nested sandbox is the same spike's second half.
2. **What started the turn, and dry-run, in the permission policy.** A paper spike first: the spec change to `PermissionPolicy` and what a Bot's policy would then say. Small, and it makes Bots safer to leave alone, which is the open "live multi-day check".
3. **Guardrails on Bots' schedules and delegations.** Not a spike so much as an issue: a floor, a cap, failure cut-off, a depth cap. Copy the reasons from OpenBot's documents.
4. **A shared document between a thread's agent and a Block.** Design only, and only after 1 shows agents use a Host UI tool at all: reuse the Session layout's document mechanics and decide whether a checklist is the first type.
5. **An AG-UI face on a Bot, for Channels.** Only if reaching Bots from Slack or Teams becomes a want. Compare with A2A first.

Not worth a spike: AG-UI as the Host protocol, CopilotKit's hooks or components in the app, an ACP adapter for AG-UI agents, running OpenBot.

### 5.4 Open questions

- Does a Host tool that takes an A2UI surface get called well by Claude Code and Codex without a system prompt of weave's, and does Claude Code's tool search need `anthropic/alwaysLoad` to show it?
- Does `@a2ui/react` 0.15.0 fetch anything, or need `unsafe-eval` or `blob:` workers, under the app's Content Security Policy in WKWebView and Tauri?
- Where does a View live in the layout: a Block of its own (`weave.view`), inline in the thread's Block, or both, and is a Bot's standing surface a Block locked beside its thread?
- Should a turn's origin reach the permission policy as it is recorded today, or does the policy need a smaller, fixed set (person, schedule, Bot, delegated), as OpenBot's has?
- Is a thread-scoped "allow" the Host's to remember, given that ACP leaves `allow_always` to the agent and agents differ in what they then stop asking?
- Will ACP gain interrupts that survive the agent's process, or UI, in v2? Nothing opened since October says so.
- Is `nightly-labs/openbot` worth its own note? It is the nearer relative: an ACP client with persistent agents, queues and agent-to-agent messages, under a non-commercial licence.
