# Standard Agents, the Standard Agent Specification, and what weave could align with

Research snapshot, 2026-11-12. Primary sources only. The specification was read from a clone of `standardagents/spec` at [`ef1610f6`](https://github.com/standardagents/spec/tree/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2) (`main`, 2026-11-12; specification version 0.2.0), with its issues and pull requests through the GitHub API; `standardagents/skills` at [`9935b491`](https://github.com/standardagents/skills/tree/9935b491a0011cd5eae83c22a89b6104a70563ca) was listed only. The product was read from [standardagents.ai](https://standardagents.ai/), its documentation at [docs.standardagents.ai](https://docs.standardagents.ai/llms.txt) (the `.md` form of each page; the pages carry no version or date), and the published npm packages at 0.45.10 (2026-11-11): registry metadata, `LICENSE`, `README`, type declarations and, for `@standardagents/builder`, a text search of the `dist/runtime.js` bundle, fetched as single files from jsDelivr. The runtime's source repositories are private, so nothing about its internals was read as source. Stars, issues and commit counts come from the GitHub API through `gh`, versions and dates from the npm registry, all on 2026-11-12. Nothing was installed, built or run, and no account was made. Weave is judged at `d6210089` plus the uncommitted WVE-220 work. Sections 1 to 4 are facts. Section 5 judges them for weave. Section 6 lists what wasn't verified.

The question: what Standard Agents is, and how it might fit into weave or what would make sense to align with. This note is a sibling of [OpenBot, CopilotKit and AG-UI](openbot-copilotkit-and-ag-ui.md), written the same day, and compares against it where that helps. [Mastra and Pi Durable](mastra-vs-pi-durable-agent-runtime.md) (2026-10-18) judged two other TypeScript agent runtimes against the Host, and [agent identity and where agents run §4.5](agent-identity-and-where-agents-run.md#45-cloudflare-agents-sdk) covers the Cloudflare Agents SDK, whose thread-per-Durable-Object model Standard Agents' runtime shares; neither is repeated. This note uses weave's words (Host, client, thread, turn, steer, pending request, Bot, Session, Block) and puts Standard Agents' word in italics where it differs. Its *thread* is an instance of one of its *agents*, kept by its runtime, and has no directory. Its *agent* is a definition of a conversation loop, not a program. Its *session* is one stretch of work in a *thread*, from a message to a stop, close to weave's turn.

## In brief

- **Standard Agents is three things from one company.** An open specification (the Standard Agent Specification, 0.2.0, MIT), a proprietary runtime and builder UI (Standard Agents Builder, on Cloudflare Workers and Durable Objects), and a hosted platform that is the only place the runtime may run in production. The company is FormKit Inc., doing business as Standard Agents. The name is unambiguous and the site points where expected. Confidence in this is high: it rests on the licence text, the spec repository and the npm registry.
- **The specification is one vendor's, days old in public, with one runtime.** The site's invite gate came off on 2026-11-09. The spec repository has 19 stars, two committers, no outside pull requests and no foundation. The only listed runtime is the authors' own. Two small outside repositories use the definition format.
- **It standardises an agent loop written in TypeScript, and weave owns no loop.** A Standard Agent is models, prompts, tools, hooks and stop rules as TypeScript files that a runtime executes. Weave launches other people's agent programs over ACP and never looks inside them. The two meet only at the edges: a Standard Agent could be reached from a weave thread, or shown as one, through an adapter.
- **It has no ACP, no A2A and no AG-UI, and MCP only as an unmerged draft.** The spec's one statement on MCP is that MCP and skills "do not make an agent composable or shareable". A draft pull request of 2026-11-11 would let a runtime expose an *agent* as an MCP server; if it lands and ships, that is the cheapest way for a weave agent to talk to one, with no weave code.
- **Nothing here is worth building now.** Its thread client API is nearer to weave's model than AG-UI is (the runtime keeps the history, and a message sent during a run joins it), but it has no pending requests, no journal positions and nothing for a directory, and the client libraries that speak it are proprietary. What is worth taking is reading: its rules for parent and child threads, for deleting a thread with its descendants, and its write-only credential grants.

## 1. What Standard Agents is

### 1.1 The name, and who is behind it

- **One organisation, three products.** [standardagents.ai](https://standardagents.ai/) describes "a hosted runtime for domain-specific agents written to conform with the Standard Agent Specification" and links the specification at [standardagentspec.org](https://standardagentspec.org), the documentation, and the GitHub organisation [`standardagents`](https://github.com/standardagents) ("Creating portable, vendor-agnostic, effective AI agents for everyone", created 2025-12-02, 188 followers).
- **The company is FormKit Inc.** The runtime's licence opens "Copyright (c) 2024-2025 FormKit Inc. All Rights Reserved ... FormKit Inc., a Delaware C corporation, doing business as Standard Agents" ([`@standardagents/builder` LICENSE](https://cdn.jsdelivr.net/npm/@standardagents/builder@0.45.10/LICENSE)). The spec's lead maintainer is Justin Schroeder, "a co-founder of Standard Agents" who "created the open source projects ArrowJS, AutoAnimate, dmux, FormKit, and Tempo" ([community.md L32-L34](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/src/data/community.md?plain=1#L32-L34)). The spec repository's 161 commits are his (117) and Andrew Boyd's (44).
- **No other project of the name was found.** A GitHub repository search for `standardagent` returns the organisation's own repositories, one outside catalogue (1.4) and forks of an unrelated tool of theirs.
- **The same organisation publishes other things**, which matter here only as context: [`dmux`](https://github.com/standardagents/dmux), "a dev agent multiplexer for git worktrees and coding agents" (MIT, 1,819 stars, last pushed 2026-08-16); ArrowJS; and **Standard Code**, npm packages `@standardagents/code`, `code-web` and `code-network`, described as a "platform launcher for the Standard universal terminal network" and "the TUI compiled to wasm", marked `UNLICENSED`, with a private repository (`standardagents/code-rs`) and hundreds of branch builds since 2026-06-25 (npm registry). A closed spec issue says "Standard Code packages call tools on an execution-owner client and durably park while that client is unavailable or waiting for human approval" ([#1](https://github.com/standardagents/spec/issues/1)). Standard Code is the nearer relative of weave's app and wasn't read further (5.4).

### 1.3 The licence decides most of the fit

The runtime, the CLI, the client libraries and the provider packages all declare `SEE LICENSE IN LICENSE`, and the `LICENSE` in `@standardagents/builder`, `client` and `react` is the same "PROPRIETARY SOFTWARE LICENSE" ([text](https://cdn.jsdelivr.net/npm/@standardagents/builder@0.45.10/LICENSE)):

- **The grant**: "a limited, non-exclusive, non-transferable, revocable license to install and use the Software: 1. for local development and testing; and 2. in production only on hosting that Standard Agents operates".
- **The restriction**: "No permission is granted to host, deploy, or run the Software in production anywhere other than Standard Agents Hosting." The documentation adds that "the `builder()` plugin stops a production build (`vite build`) outside the platform" ([installation](https://docs.standardagents.ai/introduction/installation.md)).
- **What stays the author's**: "This license applies to the Software. It does not apply to the agents, prompts, tools, and other definitions that you write ... You may run Your Agents on any runtime that conforms to the Standard Agent Specification."

So the definitions are portable in law, and there is nowhere else to run them. This is the arrangement the sibling note found in OpenBot, whose MIT template needs the separately licensed CopilotKit Intelligence ([§1.4](openbot-copilotkit-and-ag-ui.md#14-licence-maturity-and-what-isnt-open)), one step stricter: here the runtime itself is closed.

## 2. The specification's shape

### 2.1 An agent is two sides

- **Files.** Definitions are TypeScript modules under `agents/`, one per file, each a default export of a `define*` call: `agents/models/`, `agents/prompts/`, `agents/tools/`, `agents/agents/`, `agents/hooks/`, `agents/handlers/`, `agents/effects/` and `agents/api/` ([examples §1](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/getting-started/examples.md?plain=1#L27-L60)). Names are `snake_case` and mostly come from the file name. A build step generates a `StandardAgentSpec` type namespace so that references between them are checked.
- **Sides and backings.** "An agent has **exactly two sides**, and each side is **backed** by exactly one of three things: a human, a prompt, or a handler. There is no agent 'type'" ([agents.md L3](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/agents.md?plain=1#L3)). An assistant is `sideA: { prompt }, sideB: { human: true }`. Two prompts make a worker and a reviewer. A *handler* is "deterministic code" that takes a side's turns with no model call. `role: 'user'` is always side B's perspective and `role: 'assistant'` side A's.
- **Stopping is declared.** A prompt side sets `stopOnResponse`, a `stopTool`, `maxSteps`, and tool bindings that end the *session* in success or failure or publish a status; the agent sets `maxSessionTurns` ([agents.md §1.2-§4](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/agents.md?plain=1#L34-L124)).
- **Prompts, models, providers.** A prompt names a model, its text, its tools, a `requiredSchema` for when it is called as a tool, and reasoning settings. A model names a provider, a model id, fallbacks, pricing and capabilities. A provider is an interface (`generate`, `stream`, `getModels`, `getTools`) that provider packages implement. "Agents should be coupled to a model" is one of the five principles: the definition, not the person, picks the model.
- **The loop is the runtime's, and specified.** One step at a time per thread; drain the queue, assemble context, call the model, persist the reply, run tool calls "sequentially in the returned order", persist results, check stops ([runtime.md §3-§6](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/infrastructure/runtime.md?plain=1#L40-L109)).

### 2.2 Tools, hooks, handlers, effects

- **Tools** are in-process TypeScript functions: `defineTool({ description, args, execute(state, args), variables })`, with `args` a Zod schema. A prompt or an *agent* can also be a tool; an agent in a prompt's `tools` is a **handoff**, which "transfers control of the *same thread* to the target agent, preserving history" ([agents.md §5](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/agents.md?plain=1#L126-L130)). Two details worth knowing: a tool may name a `progressArgument`, so a client can show "writing index.html" as soon as that one argument has streamed and before a large one finishes; and a packed tool must list in `uses` whatever it invokes by name, which the runtime enforces ([tools.md §2.1, §7](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/tools.md?plain=1#L36-L121)).
- **Variables and secrets.** Tools and prompts declare the variables they need, `text` or `secret`, optionally `scoped` so a child thread doesn't inherit them.
- **Hooks** are fourteen named interception points in the loop: on the request context (`after_system_message`, `filter_messages`, `prefilter_llm_history`), on messages (before and after create and update), and on tool calls (`tool_call_started`, `before_store_tool_result`, success, failure, done) ([hooks.md §1.1](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/hooks.md?plain=1#L17-L36)). None of them asks anyone anything; a hook can transform or observe, and its failure is "non-fatal to the decorated turn".
- **Effects** are scheduled side effects: `state.scheduleEffect(name, args, delayMs)` runs a function later, outside any turn, with no output to the model ([effects.md](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/effects.md?plain=1#L1-L90)). There is no cron; the runtime's triggers are a message, a queued message or tool, and "a scheduled effect alarm" ([runtime.md §2](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/infrastructure/runtime.md?plain=1#L27-L38)).
- **Thread endpoints** are HTTP routes a package defines beneath a thread (`agents/api/issues.post.ts` becomes `POST …/threads/{id}/issues`), which is how an outside event reaches an agent: the spec's "remote trigger" example has a GitHub Actions workflow post an issue to one, which queues it as a message ([examples §9](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/getting-started/examples.md?plain=1#L1340-L1400)).
- **Also specified**: a per-thread key-value store and file system; `state.runCode`, TypeScript run in a fresh isolate with only what the caller bridges in; `state.decide`, typed questions put to a model without advancing the conversation; and optional *runtime streams*, "live, runtime-authorized byte streams" to "an execution host", whose capability names the spec leaves opaque ([runtime-streams.md](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/threads/runtime-streams.md?plain=1#L1-L62)).

### 2.3 Subagents

- **A child is a thread of its own.** A side declares `subagents`, each a relationship to another agent with a name (`as`), `maxInstances`, `blocking`, `immediate`, `hidden`, and how creation arguments map to the child's first message ([subagents.md §1](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/subagents.md?plain=1#L7-L46)). "Every child instance is a persistent thread ... Session end never terminates a thread"; a later message "starts a new session with history intact" (§4.1).
- **Three tools the runtime injects** for a prompt side: `subagents` (list), `subagent_create` (which "MUST require a non-empty `name`") and `subagent_message`. Their descriptions "SHOULD direct the model to call `subagents` before `subagent_create` so existing instances are reused rather than duplicated", and a create past `maxInstances` returns a tool error "explaining the cap and suggesting messaging an existing instance" (§1, §5).
- **No ambient registry.** Runtimes "MUST NOT additionally inject an ambient registry system message — a registry block that mutates between requests invalidates provider prefix caches and reads as out-of-dialogue state. Completions arrive as messages" (§4.2).
- **Results come back as a queued message**, silent, in a fixed form ("Subagent (reference: {uuid}) has returned the following result"), unless the relationship's `parentCommunication` is `explicit`, in which case a child's finish "does not wake the parent at all" and the child calls `state.notifyParent` when it means to (§6).
- **Attachments are copied**, never linked, across the boundary in both directions.

### 2.4 Human-in-the-loop

- **A person is a side, not a request.** For a human backing "the specification defines only the waiting state": the *session* parks, and "the turn is fulfilled by an inbound message". It "deliberately does **not** define who the person is or how their input arrives" ([agents.md L19](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/agents.md?plain=1#L19)).
- **Approval is a child agent.** The canonical pattern is an `approval_gate` agent, a prompt on side A and a human on side B, composed as a subagent; "the child parks in `awaiting_human` until the approver responds. The runtime does not define who sees the parked session or through which interface they answer" ([agents.md §7](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/agents.md?plain=1#L169-L191)).
- **There is no permission request, and no tool a client runs.** Nothing in 0.2.0 lets the runtime ask before a tool runs or forward a call to a client's device. The maintainers' own product needs both: issue [#1](https://github.com/standardagents/spec/issues/1) (2026-08-10) asked for "a runtime-neutral client-forwarded call surface" with "durable park semantics when no eligible client is attached", "approval allow and denial while parked", and a rule that "after hard stop returns, no result associated with the stopped execution generation may resume that generation", because the agent "currently uses `state.callClient(...)`" outside the spec. It is closed, and its companion [#3](https://github.com/standardagents/spec/issues/3) was withdrawn as "framed ... around the needs of one product".

### 2.5 Threads, messages and the client API

- **A *thread* is an instance of an agent**, created with an `agent_id`, optional `tags` and `env`. Creating one "MUST NOT start an execution".
- **A message is a row** in the shape of a chat-completions message: `id`, `role` (`system`, `user`, `assistant`, `tool`), `content`, `tool_calls` as a JSON-encoded string, `tool_call_id`, `tool_status`, `status` (`pending`, `completed`, `failed`), `attachments`, persisted reasoning, `parent_id` and `depth` for sub-prompts, `silent`, `metadata`, and nine `subagent_*` columns ([messages.md §1](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/threads/messages.md?plain=1#L9-L38)). `silent` is "a client-presentation flag": hidden from ordinary lists, still in the model's context.
- **A message sent during a run joins it.** Queued messages: "if active: inject before next model call; if idle: queue and force next turn; if multiple: process in FIFO order" ([runtime.md §9](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/infrastructure/runtime.md?plain=1#L219-L225)). That is one behaviour where weave has two, the steer and the queued prompt.
- **Run status** is `idle`, `running` or `failed`, with a `reason` code and `since`. It "describes execution, not turn ownership": a run that hands the turn to a person settles as `idle` with reason `awaiting_human`. Other reasons include `stop_on_response`, `aborted_by_user`, `max_session_turns`, `session_fail` and `execution_lost`, the last for a run whose executor went away ([execution-state.md §4](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/threads/execution-state.md?plain=1#L91-L122)).
- **The thread client API** (added 2026-11-10; "A runtime **SHOULD** expose" it) is thirteen routes: list agents; create, list, read, update and delete threads; read, send and delete messages; read a file; stop; a WebSocket stream; and a ticket for it ([client-api.md §2](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/threads/client-api.md?plain=1#L16-L35)).
  - **Sending** returns `202` and `{ status: 'queued', messageId }` once the message is durably accepted, without waiting for the run (§12).
  - **The stream** has five frames: `thread_status`, `message_data` (a whole record, which replaces any the client holds), `message_chunk`, `reasoning_chunk` (opt-in) and `event` (a package's own `state.emit`). The first frame is always a status snapshot, and several connections to one thread are allowed. "Delivery is at-most-once. The stream carries no history and no acknowledgements" (§16.2); a client that reconnects reads the messages route again. Every client-to-server frame but a ping is "implementation-defined".
  - **Auth** is a bearer credential on HTTP and, for the WebSocket, a single-use ticket bound to one path that expires within 60 seconds (§4). How a caller signs in is left out.
  - **Deleting a thread** is the most carefully specified part: the deletion set is the thread and every descendant; all become unavailable to new work first, executions are aborted, queues and scheduled effects discarded, streams closed, and a failure part-way leaves the thread addressable "so that the request can be repeated" (§10).
  - **Rough edges** a week-old text shows: `threadId` beside `agent_id` in one response, and timestamps in seconds, milliseconds and microseconds depending on the field (§3.3).
- **Builder's stream adds telemetry frames** (`step_started`, `tool_started`, `stopped`) beyond the spec's five ([WebSocket reference](https://docs.standardagents.ai/api-reference/websocket/stream.md)), and `@standardagents/react` wraps it all in `useThread()`: messages, `sendMessage`, `stopExecution`, attachments, files, `onEvent`, and *workblocks* that group a run's tool calls ([React package](https://docs.standardagents.ai/user-interfaces/react.md)). There is a Vue package and a framework-free `@standardagents/client`. All three are under the proprietary licence (1.3).

### 2.6 Users, credential grants, packaging

- **Users (draft).** A runtime resolves each request to a user id; "a runtime with exactly one principal MUST resolve all requests to a single constant user id" ([users.md §1](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/users.md?plain=1#L7-L24)).
- **Credential grants (draft)** are the one piece of security design worth reading on its own. A grant is a named credential with a `kind`, the `origins` it may be sent to, and an `allow` list of the tools, endpoints and agents that may use it. "Secret material is write-only: it MUST NOT be readable by packaged code, models, or clients"; code calls `fetch(grant, …)` and the runtime injects the credential; "an absent `allow` denies all callers" ([users.md §6](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/specification/users.md?plain=1#L184-L206)).
- **Packaging.** An agent and everything it needs is one npm package whose `package.json` has a `standardagent` field and keyword, a name that "SHOULD start with `standardagent-`", and an entry point exporting registries of lazily loaded definitions plus `__meta`. Only its entry agents are visible outside it; other code refers to them as `{packageId}/{name}`. "Downloading or installing a package is inert"; composing it is what activates it ([packaging.md](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/distribution/packaging.md?plain=1#L149-L266)). There is no registry of its own: discovery is npm.
- **Portability rule.** "Packed definitions MUST NOT require private runtime RPCs, implementation-specific storage schemas or bindings, undocumented events, sidecar services" ([packaging.md L9-L19](https://github.com/standardagents/spec/blob/ef1610f6ab24d6d6f1eb655df16f83bad6589ac2/content/0.2.0/distribution/packaging.md?plain=1#L7-L19)). A tool that reads the runtime's own context (`_notPackableRuntimeContext`, the example being a database binding) can't be packed.

**The draft MCP servers capability** is the one bridge to weave's world, so its shape matters ([#39](https://github.com/standardagents/spec/pull/39), unmerged):

- `defineMcpServer` binds one *agent* to a declared list of its function tools and, optionally, four conversation tools: `thread_send`, `thread_reply`, `thread_create`, `thread_list`. "An agent without a server definition MUST NOT be reachable over MCP", and nothing of the agent's prompts or subagents is exposed.
- One endpoint per server, `POST {runtime_prefix}/mcp/{server}`, on MCP revision 2026-07-28 over Streamable HTTP, with the runtime as an OAuth resource server and RFC 9728 metadata. A token is valid for one server.
- `thread_send` accepts a message durably and answers `completed` with the assistant messages that followed, or `pending` with a `messageId` that `thread_reply` reads later.
- Its own open questions are ones weave has met: a send whose reply can't be attributed when queued messages are delivered together; "a client that disconnects before the `thread_send` result has no message id to poll with. An idempotency key would close this", which is weave's request key.

## 5. Fit for weave

Judgement from here on.

### 5.1 What differs, and what it rules out

Standard Agents and weave answer different questions. Standard Agents asks how a company writes a domain agent (a support concierge, an issue triager) once and runs it anywhere; its unit is a definition of a loop. Weave asks how one person keeps other people's coding agents going on their own computers and reaches them from anywhere; its unit is a thread in a directory. Four differences each rule something out.

- **Weave owns no loop, and never branches on which agent is connected.** Everything Standard Agents specifies inside an agent (prompts, models, hooks, stop rules) is inside Claude Code or Codex already and out of weave's sight. Weave has nowhere to put a hook.
- **A weave thread is for a directory.** A Standard Agent's thread has a virtual file system in its runtime's database and no notion of a worktree or a terminal. The sibling note said the same of AG-UI agents ([§5.2](openbot-copilotkit-and-ag-ui.md#52-the-candidates)).
- **Agents run locally on the person's logins.** A Standard Agent runs in Standard Agents' cloud, on provider API keys or the platform's metered inference. Locally it runs only as a development server that signs in to the platform, and the licence allows that for "development and testing".
- **There is one closed runtime.** A standard is worth aligning with for the things that speak it. Today that is Builder and its three proprietary client libraries.

### 5.2 The candidates

| Candidate | Verdict | What it would cost and displace |
| --- | --- | --- |
| A Standard Agent as a weave agent, through an ACP adapter | Fits with caveats, little value today | A stdio adapter nobody has written, in front of a cloud runtime |
| A Standard Agent as an upstream server, through the draft MCP capability | Fits with caveats, when it exists | Nothing in weave, if it ships as drafted |
| Weave running Standard Agents itself (a conforming runtime) | Doesn't fit | An owned loop, a provider layer and a TypeScript sandbox |
| Its definition format for weave's agent config or for Bots | Doesn't fit; Agent Skills and AGENTS.md are the shared part | Nothing to adopt |
| Its thread and message model in the Host protocol | Doesn't fit as a wire; a few rules are worth lifting | Spec text only |
| Its tools, hooks and human-in-the-loop against service tools and the permission policy | Doesn't fit; weave's are the stronger | Nothing; credential grants are worth reading |
| A Host or the Dispatcher serving the thread client API | Doesn't fit | A lossy service for clients weave can't use |
| The app showing a Standard Agents thread | Doesn't fit | A Block type for something not on a Host |

**A Standard Agent as a weave agent: fits with caveats, little value today.** The Host launches ACP agents and doesn't branch on which, so a Standard Agent would arrive as the sibling note's AG-UI agent would: a stdio program that speaks ACP to the Host and the thread client API to a runtime.

- **The mapping is cleaner than AG-UI's**, because the runtime keeps the history and takes messages mid-run. `session/new` creates a *thread*; `session/prompt` posts a message and follows the stream until `thread_status` settles; `message_chunk` becomes `agent_message_chunk`; a `message_data` with `tool_calls` becomes a tool call update; `session/cancel` is the stop route, which is idempotent; `session/load` reads the messages back. A steer is just another post.
- **What has no counterpart**: permission requests (nothing in the API asks), the working directory, ACP's file and terminal methods, modes, and the Host MCP server, which the adapter has no way to hand to a cloud runtime. A parked approval-gate child would show only as the run going `idle` with `awaiting_human`.
- **What it costs beyond the adapter**: an API key for the runtime in the adapter's environment, which is a credential weave's agent config would then carry, and a runtime to point at. The only one is the platform, or a development server on this computer under a licence that allows development and testing.
- **What it would buy**: a domain agent the person had built there, in a Block beside their coding threads. Not worth building until the person has such an agent. The adapter would be small, and it belongs outside weave's repository, as any agent's adapter does.

**A Standard Agent as an upstream server: fits with caveats, when it exists.** If pull request #39 lands and Builder implements it, a Standard Agent becomes an MCP server at a URL, and weave already has the place for that: an upstream server in the Host's configuration, offered to every thread's agent through the Host MCP server ([ADR 0013](../adr/0013-configured-mcp-servers-through-the-host-mcp-server.md)). Claude Code in a weave thread could then send a Standard Agent a message and read its reply as a tool call, which is the composition that makes sense between the two: the coding agent stays the thread's agent, and the domain agent is something it consults. The caveats are that it is an unmerged draft with no known implementation, that it needs OAuth as a resource server (whether the Host's upstream connections can do that flow wasn't checked), and that its reply attribution is unsettled by its own account. Nothing to do but watch.

**Weave as a conforming runtime: doesn't fit.** Running Standard Agents on a Host would mean executing TypeScript definitions, calling model providers with API keys, running the step loop, the hooks, the per-thread stores and a code sandbox: the owned loop that [ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md) keeps out of the Host. The Mastra note's answer for a loop of weave's own still holds: build it as an ACP agent the Host launches ([§5.5](mastra-vs-pi-durable-agent-runtime.md#55-recommendation)). A conforming runtime packaged that way, as a Node program speaking ACP, would be the right shape, but it is a large piece of work whose only users are agents written for a week-old spec, and the spec has no test suite to build against. If someone else publishes an open runtime that runs locally, the adapter above would point at it instead, and the local-login objection would shrink to "it needs provider API keys".

**Its definition format for weave's agents or Bots: doesn't fit.** The two formats describe different layers and share no field that means the same thing.

- **Agent config.** Weave's says how to launch a program: a command, arguments, environment, which ACP capabilities to advertise, a mode, which Host tools it gets (`agents/src/config.rs`). Standard Agents' says what the loop is. `title`, `description` and `icon` are the only overlap, and weave's agents have a description already. Mirroring names would suggest a portability that isn't there.
- **Bots.** A weave Bot is a Dispatcher record (a name, an agent id, a permission policy, a Host, schedules) and a home whose files are its memory ([ADR 0028](../adr/0028-bots-are-dispatcher-records-whose-work-goes-on-in-ordinary-threads.md)). A Standard Agent is a package of code with a fixed prompt and model. A Bot could not be exported as one without writing its loop, and a Standard Agent has no home to import. Wake-ups and schedules, which a Bot manages by tool, have only a faint counterpart in delayed effects.
- **What is portable is what both already lean on.** A Bot's home carries `AGENTS.md`, and Standard Agents adopts Agent Skills for what an agent reads on demand. If a Bot's knowledge should travel to another system, a `SKILL.md` folder in its home is the format every party here reads, Standard Agents included. That is alignment with Agent Skills, not with Standard Agents.
- **The idea of sides** is tidy (a thread's other side is a person, a model or code) and weave has it under other names: a headless thread, a turn's origin. No change suggested.

**Its thread and message model in the Host protocol: doesn't fit as a wire.** It is closer to weave than AG-UI is: the runtime is the authority on history, several clients can watch one thread, a status snapshot leads every connection, and sending is durable and asynchronous. It is still a subset.

- **No journal.** "The stream carries no history and no acknowledgements"; a client that drops re-reads the message list. Weave's numbered journal and catch-up from a position are what make a phone that sleeps mid-turn work.
- **No pending requests, no queue a client can see or edit, no distinction between a steer and a queued prompt.**
- **Messages are chat-completions rows**, with tool calls as a JSON string inside a column. The Host protocol carries ACP's content and updates as they are, which is what lets the TUI and the app render diffs, plans and terminals without knowing the agent.
- **Nothing for Sessions, terminals, worktrees, Projects or pairing.**
- **Vocabulary.** Its *tags* are weave's labels, and `CONTEXT.md` already avoids "tag". Its *session* is nearer a turn. Renaming anything toward it would trade settled words for a 0.2.0 draft's.

Worth lifting into weave's own specs, as text:

- **The deletion rules** (client API §10), when weave specifies ending a thread with the delegated threads under it: make the whole set unavailable first, then abort, then discard, and leave the root addressable if it fails part-way so the request can be repeated.
- **Reason codes on an idle thread**, as a closed list clients must treat as open: `awaiting_human` apart from `stop_on_response` apart from `execution_lost`. Weave's listings say a thread needs the person; a short code for why a turn ended, in the listing, would let the app's sidebar say more without opening the journal.
- **`progressArgument`**: a tool naming the one short argument that says what it is doing, so a client can show it while a long argument streams. For weave's own Host tools and service tools this is a convention on the tool's schema, to be read in `tui/src/conventions.rs` and the app's equivalent, with ACP's title as the fallback.
- **A `depth` on a watch**, for clients that want a thread without its subagent threads' traffic.

**Tools, hooks and human-in-the-loop: doesn't fit; weave's are the stronger.** Standard Agents' tools run inside its runtime, so it needs no permission step and has none; its approval is a child agent that waits for a message. Issue #1 shows the authors reaching for exactly what weave has: a tool call forwarded to a client's device, parked durably while nobody is attached, answered or denied, and fenced so a late answer can't revive a stopped turn. Weave's client tools, pending requests and permission policy cover that list, and service tools add a second kind of runner. Hooks have nowhere to attach in weave. Two things are worth reading:

- **Credential grants** (2.6), if the Host ever holds a secret on a Bot's behalf, for an upstream server or a service tool: write-only material, an origin list, an allow list of callers that denies by default, and injection on the Host's side of a `fetch` so the agent never sees the value. Weave's rule that agents keep their own logins is unaffected; this would be for credentials that aren't an agent's.
- **The subagent rules** (2.3), against the Host tools for delegated threads. Weave has the caps (`delegation.depth` and `delegation.running`) and the report. What Standard Agents adds: the tool description telling the model to list before it starts another; an error at the cap that says to message an existing thread; a required name for what is started; and the reason for keeping the list out of ambient context, which is prompt caching. Its `explicit` mode, a child whose finish wakes nobody, is the opposite default to ADR 0023's report and is worth knowing as an option for a Bot's background threads.

Compared with what the sibling note took from OpenBot (a policy input for what started a turn, dry-run, guardrails on schedules), Standard Agents has less to offer the permission policy, because it has no policy.

**A Host or the Dispatcher serving the thread client API: doesn't fit.** A service could present a Host's agents and threads through the thirteen routes: agents as the Host's agents, messages projected from the journal, the stop route as cancel. It would be lossy in the ways listed above, and pending requests would have to ride in `event` frames of weave's own invention. The sibling note found one reason to wear another protocol's face, CopilotKit's MIT Channels SDK for Slack and Teams. There is no such prize here: the clients that speak this API are Builder's UI and three libraries licensed for development and for production on Standard Agents' hosting only.

**The app showing a Standard Agents thread: doesn't fit.** A Block shows "a thread, a terminal, or another thing on the Session's Host". A Standard Agents thread is on nobody's Host. If the person wants one beside their work, the adapter route makes it an ordinary thread in an ordinary Block, with the Host's journal in front of it, and the app learns nothing new.

### 5.3 What to do, in order

Worth doing now, all of it cheap and none of it code:

1. **Read the subagent rules against the Host tools' descriptions** and take what improves them: list before starting, a named thing, an error at the cap that points at reuse. An afternoon, in the tools' text and their tests.
2. **Note the deletion rules and the idle reason codes** where the Host protocol's spec next touches ending threads and thread listings. Text, when those are next open.
3. **Keep what a Bot knows in formats others read**: `AGENTS.md` and Agent Skills folders in the home. Standard Agents is one more system that reads skills. Check that the home `repos/init` writes leaves room for a skills folder; no schema to adopt.

Worth a spike only on a condition:

4. **An ACP adapter over the thread client API**, if the person builds or is given a Standard Agent they want in a Session. A few hundred lines of Node outside this repository, launched as a config agent. It would also be the first test of whether the thread client API is as implementable as it reads.

Watch:

- **Pull request #39**, the MCP servers capability: whether it merges, and whether Builder ships it. Then try a Standard Agent as an upstream server.
- **A second runtime**, above all an open one that runs on a person's computer. That would change the licence and Cloudflare objections at once.
- **The runtime's licence.** Self-hosting is prohibited today.
- **Client-forwarded calls** coming back to the spec (issues #1 and #3). If Standard Agents specifies parked, approved, fenced tool calls on a client, compare it with weave's pending requests line by line; it would be the first outside statement of the same contract.
- **Where the spec is donated**, if it is. The Agentic AI Foundation holds MCP, A2A and AGENTS.md ([A2A note §1](a2a-and-agents-controlling-threads.md#1-where-a2a-stands)); a spec there, with a second implementer, is a different thing from a vendor's 0.2.0.
- **Standard Code.**

Not worth doing: a conforming runtime in or beside the Host; the thread client API on a Host or the Dispatcher; Standard Agents' message shape, vocabulary or definition schema in weave's protocol, config or Bots; `@standardagents/react` in the app.

### 5.4 Open questions

- Does Builder already let a prompt use an MCP server's tools (the `mcp:` prefix), and if so, could a Standard Agent be given the Host MCP server of a weave Host over Streamable HTTP? That would be the reverse bridge: a Standard Agent using weave's Host tools.
- Is running a Builder development server day to day, on one's own computer, for one's own agent, "local development and testing" under the licence? The text doesn't say, and it is the only way to run one off the platform.
- Does the development server work offline, or does it need the platform for sign-in and inference each time?
- Can the Host's upstream connections act as an OAuth client to a protected MCP resource, as #39 would need?
- Is Standard Code worth its own note? It is the same team's terminal network for coding agents, with panes, plugins, a web build and tool calls forwarded to an "execution-owner client": closer to weave's app and Host than anything in the specification, and closed.
- Does `runtime streams` to an "execution host" mean what it appears to, a Standard Agent in the cloud driving a shell on the person's computer? If so, it is their answer to the question weave answers by running the agent there.
