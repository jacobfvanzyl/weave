# T3 Code and the weave Host

Research snapshot, 2026-10-30. Primary sources only. Repositories were read at these commits: `pingdotgg/t3code` [`32ecd717`](https://github.com/pingdotgg/t3code/tree/32ecd71726fee16f335484c1f95cbce126d461f6) (`main`, 2026-10-30; the server package `t3` is at 0.1.5; latest release [v0.1.5](https://github.com/pingdotgg/t3code/releases/tag/v0.1.5), 2026-10-29; latest nightly [v0.1.6-nightly.20261030.3917](https://github.com/pingdotgg/t3code/releases/tag/v0.1.6-nightly.20261030.3917), 2026-10-30), the community terminal client `Pajn/tria` [`ff50b09c`](https://github.com/Pajn/tria/tree/ff50b09cb98dc92e320cfae1726789dbad026a98) (0.3.0; README and two source files), and `Effect-TS/effect` at the `effect@4.0.5` tag [`7f524e25`](https://github.com/Effect-TS/effect/tree/7f524e25cfb49a71ac39b0f44278d08d40dda5de) (the RPC module only, because T3 Code pins `effect` 4.0.5 and its wire format is Effect RPC). Issues, pull requests, discussions and releases were read through `gh` on 2026-10-30. Nothing from T3 Code was installed, built or run; its clone is untrusted data and was only read. Sections 1–5 are facts about T3 Code and their sources, with weave beside them where a table compares the two; section 6 judges them against weave at `343633b4`, and every weave line reference in this note is at that commit.

The question is whether the T3 Code server could replace the weave Host, with a terminal client written for it in place of weave's TUI. T3 Code calls its server an *environment* and its clients *clients*; it says *thread* and *turn* as weave does, but its *session* is the provider process attached to a thread, close to what weave calls an agent process ([glossary](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/glossary.md?plain=1#L10-L45)). T3 Code's *provider* is weave's agent. This note uses weave's words except when it quotes T3 Code.

## 1. Where T3 Code stands

### 1.1 Project and pace

- **What it is.** "An 'agent harness control surface'" for "the agents on your machine", through a mobile app, a web app and an Electron desktop app ([README](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/README.md?plain=1#L3-L11)); to its agents' guide, "a minimal GUI for coding agents" and an "open source 'bring-your-own-subscription' alternative to apps like Claude Desktop, Codex App, Cursor Glass and Conductor", with "over 500,000 users" ([AGENTS.md](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/AGENTS.md?plain=1#L3-L9)). It is built by T3 Tools Inc.; the guide names Theo and Julius as the maintainers ([L48](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/AGENTS.md?plain=1#L48)).
- **Licence.** MIT ([LICENSE](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/LICENSE)). The README invites forks: "If we ever go the wrong direction, we want you to have everything you need to fork" ([L11](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/README.md?plain=1#L11)).
- **Maturity, by its own account.** "We are very very early in this project. Expect bugs." ([L99](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/README.md?plain=1#L99)).
- **Size and attention.** Created 2026-02-08; 32,193 stars and 8,541 forks on 2026-10-30.
- **Releases.** 757 releases since `v0.0.0-alpha.3` on 2026-03-02. Since 2026-07-30 there have been 19 stable releases, 7 of them in October, and 425 nightlies, several a day. v0.1.0 (2026-10-15) was "the first stable release of T3 Code Orchestrator V2" ([release](https://github.com/pingdotgg/t3code/releases/tag/v0.1.0)).
- **Pace of change.** The repository took 3,788 commits in the 30 days to 2026-10-30, 1,528 of them by Julius Marminge and 477 by Theo Browne; 6,054 since 2026-08-01. `packages/contracts`, which holds the wire schemas, took 630 commits since 2026-08-01 and 351 since 2026-10-01 (counted with `git log` in the clone).

### 1.2 The V2 cutover

- The orchestration protocol constant was introduced as 1 on 2026-09-15 ([#11974](https://github.com/pingdotgg/t3code/pull/11974), commit `2c16c1d2`) and set to 2 seventeen days later by the new orchestrator ([#2829](https://github.com/pingdotgg/t3code/pull/2829), commit `de343914`, 2026-10-02), which the V2 design documents describe as an orchestrator rewrite that "intentionally ignores migration/backward compatibility" in its target model ([v2 README](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/orchestration-v2/README.md?plain=1#L1-L5)).
- The v0.1.0 notes: "A V2 server and a V1 app can't talk to each other. Whichever side is older refuses the connection", and the data move is "a one-way copy" ([release](https://github.com/pingdotgg/t3code/releases/tag/v0.1.0)). The V1 import kept messages but not "provider session identity, native provider runs, checkpoints and diffs, activities and tool calls, approvals, or proposed plans" ([legacy migration](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/legacy-orchestration-migration.md?plain=1#L22-L24)), and V2 removed the HTTP dispatch route that headless users drove ([#21375](https://github.com/pingdotgg/t3code/issues/21375)).
- Within V2, the wire shape has kept moving, mostly behind opt-in subscription flags and advertised capabilities rather than version bumps: compact id tables and once-sent message bodies (2026-10-24, `80455376`, `e19fe083`), smaller checkpoints (2026-10-29, `7f39a860`), shells that leave out settled and idle threads (2026-10-24 and 25), paged history (2026-10-28, `d2429f73`). Forward-compatible decoding of unknown union members landed on 2026-10-05 (`ca3f9738`, [#15951](https://github.com/pingdotgg/t3code/pull/15951)).

### 1.3 Stance on third-party clients and the API

- **Not a public contract.** Asked for a supported status stream for an outside tool, Julius named the shell subscription as "the existing interface" and called its auth and reconnect details "implementation facts for first-party clients, **not** a published external-client contract" ([#10929](https://github.com/pingdotgg/t3code/issues/10929#issuecomment-5601670045), 2026-09-09). After V2: "integrations need the current V2 contracts. This does not promise a stable public SDK", and "No claim of a stable external SDK" ([comment](https://github.com/pingdotgg/t3code/issues/10929#issuecomment-5961597620), 2026-10-02). The issue was closed as not planned.
- **No skew tolerance on nightlies.** To a headless user whose setup broke: "`orchestration.dispatchCommand` over `/ws` is the supported path", and "Nightlies are pre-release builds. We don't promise client/server version skew tolerance or a migration note for every internal change between them" ([#21375](https://github.com/pingdotgg/t3code/issues/21375#issuecomment-6256730673), 2026-10-18, posted as "Grok responding on behalf of Julius").
- **Exact-match versions are intended.** The client "deliberately rejects any client whose orchestration protocol doesn't match the server's"; "This behavior is intended, so we will not change it" ([#19410](https://github.com/pingdotgg/t3code/issues/19410#issuecomment-6167859455), [comment](https://github.com/pingdotgg/t3code/issues/19410#issuecomment-6315308473), 2026-10-14 and 2026-10-21, both posted by models on the maintainers' behalf).
- **A TUI was proposed and closed.** PR [#5188](https://github.com/pingdotgg/t3code/pull/5188), a `t3 tui` on Bun and OpenTUI, was closed on 2026-08-23 by an automated pass "on behalf of Theo": "A 171-file terminal-client proposal has only the vague title 'tui review'." An SDK idea ([discussion #6977](https://github.com/pingdotgg/t3code/discussions/6977), 2026-08-13) has no replies; a typed client for paired environments ([PR #15874](https://github.com/pingdotgg/t3code/pull/15874)) is open and was flagged by the policy bot as lacking prior approval. On a plugin PR, Theo: "Cool - let us handle this tho :)" ([#16047](https://github.com/pingdotgg/t3code/pull/16047#issuecomment-6434999726), 2026-10-27).
- **Contributions.** "We are (mostly) not accepting contributions yet. Small fixes may be considered. Big features will not be." ([README](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/README.md?plain=1#L101)). Features "require a prior discussion with explicit maintainer approval of the direction and scope" ([CONTRIBUTING](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/CONTRIBUTING.md?plain=1#L10-L34)).
- **What is supported for outsiders** is the MCP endpoint, documented for Claude Code, Codex, ChatGPT and bots, and `t3 thread` for scripts on the host ([outside agents](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/outside-agents.md?plain=1#L1-L115)). No maintainer statement welcoming third-party clients, promising a stable API, or planning a terminal client was found.

### 1.4 Terminal clients that exist

- **Official:** none interactive. `t3 thread start|send|show|list` arrived in v0.1.2 ([#22732](https://github.com/pingdotgg/t3code/pull/22732), merged 2026-10-21); section 4.2.
- **`Pajn/tria`**, a Rust and ratatui chat client: a thread picker, a chat view, a composer and the thread's terminals, "No diff viewer, browser, or settings" ([README](https://github.com/Pajn/tria/blob/ff50b09cb98dc92e320cfae1726789dbad026a98/README.md?plain=1#L1-L6)). It pairs with `t3 pair` and stores a bearer token ([L45-L60](https://github.com/Pajn/tria/blob/ff50b09cb98dc92e320cfae1726789dbad026a98/README.md?plain=1#L45-L60)), speaks Effect RPC itself, acknowledging every chunk because "the server withholds the next chunk until it sees this" ([`rpc.rs`](https://github.com/Pajn/tria/blob/ff50b09cb98dc92e320cfae1726789dbad026a98/src/rpc.rs#L322-L324)), and keeps a hand-written reading of the V2 projection from which it "derives" an older model for its views ([`v2.rs`](https://github.com/Pajn/tria/blob/ff50b09cb98dc92e320cfae1726789dbad026a98/src/v2.rs#L1-L8)). It is 50 Rust files, about 2 MB of source, written since 2026-09-15 in about 200 commits, with commits "Speak orchestration protocol 2" (2026-10-09) and "Fix worktree recreate after protocol update" (2026-10-29). One star.
- **Others:** `maria-rcks/t1code` (539 stars), an OpenTUI fork bundling its own server, idle since 2026-06-03, before V2; small CLIs and libraries (`wyrd-company/t3code-client`, pinned to "stock T3 Code 0.1.2, orchestration protocol 2"; `tarik02-org/t3code-cli`; `MajesteitBart/t3code-cli`), and unofficial protocol notes (`some-du6e/tern`) that say "None of it is a stable public API." These were read only at their READMEs and metadata.

## 2. The server, beside the Host

### 2.1 Shape

T3 Code's own account of itself: "A Node WebSocket server wraps provider CLIs and agents (Codex, Claude Code, Cursor, Grok, OpenCode, Antigravity) and serves web, desktop, and mobile clients" ([AGENTS.md](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/AGENTS.md?plain=1#L3)). The server keeps "provider processes, terminals, Git, and project files"; "shared connection and domain state belongs in `packages/client-runtime`" ([overview](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/overview.md?plain=1#L8-L14)). The monorepo has five apps (`server`, `web`, `desktop`, `mobile`, `marketing`) and 29 packages, among them `contracts` (the wire schemas), `client-runtime`, `effect-acp`, `effect-codex-app-server`, a `provider-*` package per non-built-in agent family, `source-control-*` per forge, `ssh` and `tailscale`.

### 2.2 The API a client would use

- **Transport.** `GET /ws` upgrades to a WebSocket served by Effect RPC with `RpcSerialization.layerJson` ([`ws.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/ws.ts#L3275-L3290), [L3336-L3338](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/ws.ts#L3336-L3338)). Effect RPC's frames are its own, not JSON-RPC: requests are `{_tag: "Request", id, tag, payload, headers}`, stream values come back as `{_tag: "Chunk", requestId, values}` and every request ends with `{_tag: "Exit", requestId, exit}` carrying an encoded Effect `Exit` ([`RpcMessage.ts`](https://github.com/Effect-TS/effect/blob/7f524e25cfb49a71ac39b0f44278d08d40dda5de/packages/effect/src/rpc/RpcMessage.ts#L71-L81), [L257-L261](https://github.com/Effect-TS/effect/blob/7f524e25cfb49a71ac39b0f44278d08d40dda5de/packages/effect/src/rpc/RpcMessage.ts#L257-L261), [L313-L317](https://github.com/Effect-TS/effect/blob/7f524e25cfb49a71ac39b0f44278d08d40dda5de/packages/effect/src/rpc/RpcMessage.ts#L313-L317)). On the WebSocket transport the server waits for the client's `Ack` after each chunk of a stream before sending more ([`RpcServer.ts`](https://github.com/Effect-TS/effect/blob/7f524e25cfb49a71ac39b0f44278d08d40dda5de/packages/effect/src/rpc/RpcServer.ts#L443-L460), [L1497](https://github.com/Effect-TS/effect/blob/7f524e25cfb49a71ac39b0f44278d08d40dda5de/packages/effect/src/rpc/RpcServer.ts#L1497)). Effect marks these message types `@stability unstable` ([`RpcMessage.ts`](https://github.com/Effect-TS/effect/blob/7f524e25cfb49a71ac39b0f44278d08d40dda5de/packages/effect/src/rpc/RpcMessage.ts#L63-L70)).
- **Surface.** One RPC group, `WsRpcGroup` ([`rpc.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/rpc.ts#L1953)), with 206 `Rpc.make` definitions: projects and files, provider sign-in and installation, VCS and Git, review and pull requests (about 35 methods), terminals, browser previews, iOS and Android device streaming, server settings and diagnostics, scheduled tasks, secrets, guest shares, peer links and the ACP registry ([method names](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/rpc.ts#L403-L606)). Threads go through 19 orchestration methods ([`orchestrationV2.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L3523-L3543)), the core of which are:
  - `orchestration.dispatchCommand`, which takes any member of the command union and answers only `{sequence}`, the last committed event's position ([L3612-L3614](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L3612-L3614), [L4110-L4113](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L4110-L4113)). The union has about 70 command types, from `thread.create` and `message.dispatch` to `thread.pin.reorder` and `thread.guest-share.open` ([L2854](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L2854-L3500)). Clients allocate the command, thread and message ids, and a repeated command id returns the stored receipt without repeating side effects ([v2 README](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/orchestration-v2/README.md?plain=1#L108)).
  - `orchestration.subscribeShell`, a stream of the thread list: a snapshot, then `project.updated`, `thread.updated` and removals, each with a sequence ([L2191-L2221](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L2191-L2221)).
  - `orchestration.subscribeThread{threadId, afterSequence?}`, a stream that sends a `snapshot` (the whole thread projection at `snapshotSequence`), then `event` items with domain events ([L3721-L3731](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L3721-L3731), [L3832-L3855](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L3832-L3855)). The client applies the events to the snapshot itself ([`orchestrationV2Projection.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/client-runtime/src/state/orchestrationV2Projection.ts#L259-L300)); most events carry the whole updated entity, so applying one is an upsert. Bounded snapshots, compact ids and deduplicated bodies are opt-in flags on the subscription, so a simple client can leave them off.
  - `orchestration.getTurnDiff` and `getFullThreadDiff`, and `subscribeCommandOutput` for a command's live output.
- **Authentication.** Every RPC declares a required scope, checked before its handler runs ([environment auth](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/environment-auth.md?plain=1#L73-L86)). A bearer or DPoP client first gets a short-lived ticket from `POST /api/auth/websocket-ticket` ([`environmentHttp.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/environmentHttp.ts#L558-L566)). On the host, `t3 auth session issue` mints "a scoped bearer access token for headless or remote clients" ([`auth.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/cli/auth.ts#L169-L178)); other devices pair with a one-time link (`t3 pair`).
- **Versions.** The socket URL must carry `orchestrationProtocol=2`, or the upgrade fails with HTTP 426 `orchestration_protocol_incompatible` before any authentication ([`environment.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/environment.ts#L13-L16), [`ws.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/ws.ts#L3281-L3290)). There is no range and no negotiation: "Clients and servers must agree", and either side refuses rather than run "half-upgraded" ([legacy migration](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/legacy-orchestration-migration.md?plain=1#L33-L42)). Within version 2, compatibility is by capability flags in the server's descriptor and forward-compatible decoding: unknown union members, unknown events and unknown turn items are skipped while the cursor advances ([`baseSchemas.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/baseSchemas.ts#L150-L177), [`orchestrationV2.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L3799-L3812)). The overview calls the RPC contract "the boundary between independently versioned clients and servers" and keeps legacy fields "because older clients still read them" ([overview](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/overview.md?plain=1#L16-L30)).
- **No published contract.** `@t3tools/contracts` and `@t3tools/client-runtime` are `"private": true`, export TypeScript sources, and are not on npm (the registry answers "Not found" for both) ([contracts manifest](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/package.json#L1-L4)). No JSON Schema, OpenAPI document or generated types for the WebSocket API were found in the repository. The schemas are Effect `Schema` values in 29,000 lines of TypeScript, `orchestrationV2.ts` alone 4,220.
- **A second surface: MCP.** `/mcp` serves T3's orchestration tools to agents T3 did not launch, after an OAuth sign-in the owner approves with a read-only or runtime-mode ceiling ([outside agents](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/outside-agents.md?plain=1#L1-L54), [environment auth](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/environment-auth.md?plain=1#L42-L66)). The tools are `t3_thread_list`, `_read`, `_search`, `_launch`, `_send`, `_wait`, `_interrupt`, `_update`, `_configure`, `t3_project_*`, `t3_worktree_*`, `t3_pending_request`, `t3_queue` and others; one service, `ThreadManagementService`, answers both the WebSocket commands and MCP ([orchestrator MCP](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/orchestration-v2/orchestrator-mcp-server.md?plain=1#L1-L37)). This is the surface `t3 thread` uses (section 4.2).

### 2.3 Where the two models differ most

- **Normalized graph against ACP payload.** T3 Code turns every provider's protocol into its own model, "designed around the real provider behavior observed in the Codex app-server probes", with Codex "treated as the richest protocol" ([v2 README](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/orchestration-v2/README.md?plain=1#L7)). Clients see turn items such as `assistant_message`, `reasoning`, `proposed_plan`, `todo_list`, `user_input_request`, `file_change`, `command_execution`, `web_search`, `approval_request`, `checkpoint`, `compaction`, `handoff`, `subagent` and `dynamic_tool` ([L1560-L1782](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L1560-L1782)). The weave Host carries ACP's own types and leaves rendering to clients ([spec](../specs/wve-85-host-protocol.md#L69-L82)).
- **Event-sourced commands against direct requests.** A T3 command answers with a sequence once its intent is committed; the client learns the outcome from the stream. A weave request answers with its outcome (`turn/start` → `{seq, turnId}` once the turn has started, [`turns.rs`](../../protocol/src/turns.rs#L27-L50)).
- **Provider capabilities.** T3 Code describes each provider by capability flags (sessions, threads, turns, streaming, tools, approvals, planning, subagents, context, checkpointing, identity, runtime policy; [L373-L389](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L373-L389)) and fills gaps in the server, for example steering by interrupting and restarting when a provider can't steer ([feature lifecycles](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/orchestration-v2/feature-lifecycles.md?plain=1#L61-L90)). weave advertises what ACP and its two unstable RFDs offer and withholds them per agent.
- **Who decides what runs.** T3 clients may send a terminal's `cwd` and `env` and choose terminal ids ([`terminal.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/terminal.ts#L24-L45)), add a local ACP command by executable path ([ACP providers](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/providers-acp.md?plain=1#L31-L40)), and edit project files. weave's protocol has no field for a command, an environment or a path to write ([spec](../specs/wve-85-host-protocol.md#L1355-L1364)). T3 states its boundary differently: a session with `terminal:operate` "is a shell as the server's user", so scopes, not fields, limit a client ([environment auth](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/environment-auth.md?plain=1#L9-L17)).

### 3.2 Starting and following a thread

A client that wants weave's `weave --agent claude` loop on T3 Code sends `thread.create` with a project id, model selection, runtime mode, interaction mode and workspace, then `message.dispatch` with `start_immediately`, and reads `subscribeThread` ([L2866-L2893](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/orchestrationV2.ts#L2866-L2893)). `orchestration.launchThread` does creation and the first message in one call. A project must exist first: `t3 project add`, or `projects.createNew` over RPC.

### 3.3 Restart behaviour

T3 Code's recovery service decides after a restart whether to continue each cut-off run, requiring "matching durable run, provider thread, session, and native resume identity", holding queued runs, refusing threads that wait on a person, and stopping after three continuations in one chain ([server updates](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/server-updates.md?plain=1#L66-L104)). weave's ADR 0011 allows a headless policy to continue a cut-off turn, but the code always ends it `cancelled` ([ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md#L8), [`client.rs`](../../host/src/client.rs#L2566-L2574)). For terminals the comparison runs the other way.

### 3.4 Agents and ACP

- **Built-in providers do not use ACP.** Claude runs through `@anthropic-ai/claude-agent-sdk`, Cursor through `@cursor/sdk` and Muse through its SDK ([server manifest](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/package.json#L35-L41)); Codex through its app-server protocol, in `packages/effect-codex-app-server`.
- **ACP is a provider family.** Registry agents and local ACP commands use one generic adapter; "an agent gets a dedicated driver only when it needs behavior the spec does not cover", as Grok and Antigravity do ([adding a provider](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/adding-a-provider.md?plain=1#L9-L16)). T3 Code prefers the ACP v2 preview protocol and negotiates v1 for agents that haven't moved ([ACP providers](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/providers-acp.md?plain=1#L12-L19)). Native session listing and import are supported ([L94-L105](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/providers-acp.md?plain=1#L94-L105)).
- **The ACP client is partial by default.** The adapter advertises `fs.readTextFile: false`, `fs.writeTextFile: false` and `terminal: false` unless a driver overrides them ([`AcpSessionRuntime.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/provider-acp/src/server/AcpSessionRuntime.ts#L1766-L1780)), so registry agents read, edit and run commands themselves; T3 shows what they report "but does not run or stop their terminals" ([ACP providers](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/providers-acp.md?plain=1#L107-L121)). ACP agents cannot roll back their conversation, so after a checkpoint rollback the next turn starts a fresh agent session ([L127-L131](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/providers-acp.md?plain=1#L127-L131)).
- **Adding an arbitrary ACP agent** needs no code: Settings, Add provider, Local ACP command, or a registry search ([L21-L40](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/user/providers-acp.md?plain=1#L21-L40)).

### 4.2 How T3's own CLI reaches threads

`t3 thread` does not use the WebSocket API. It reads the running server's origin from its state file, issues itself an MCP client session with `full-access` ceiling, calls the MCP tools (`t3_thread_list`, `t3_thread_send` with `mode: "queue"`, `t3_thread_wait`) and revokes the session when done ([`thread.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/cli/thread.ts#L205-L244), [L615-L647](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/cli/thread.ts#L615-L647)). It must run on the host, and it can't answer a pending request: "Open it in T3 Code to respond" ([L96-L106](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/cli/thread.ts#L96-L106)). The MCP tools are a smaller, documented surface than the RPC, and `t3_pending_request` exists among them, but MCP is a request-response surface with no event stream.

### 4.3 How the web client consumes the API

The shared runtime owns one connection per environment, a retry supervisor with jittered backoff and probes, an authorization service for HTTP credential renewal, a registry that scopes caches by environment, and thread-detail subscriptions with a replay cursor kept five minutes for back navigation ([connection runtime](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/connection-runtime.md?plain=1#L9-L125)). Its rules are subtle: shell snapshots can leave out idle subagent children and older settled threads, so "a missing shell row therefore does not prove a thread is gone" ([L71-L85](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/connection-runtime.md?plain=1#L71-L85)). Projection, pending-input, command-label and tool-presentation logic live in `client-runtime/src/state` and `src/work-log`; the server sends the normalized projection and `visibleTurnItems`, and the clients derive labels, grouping and presentation from it.

## 5. What a T3 Code TUI would involve

### 5.1 The API surface it would consume

1. **Credentials.** On the host, `t3 auth session issue` for a scoped bearer token; from elsewhere, `t3 pair` and a one-time exchange, as `tria` does (sections 2.2 and 1.4). Then `POST /api/auth/websocket-ticket` before every socket.
2. **Socket.** `GET /ws?orchestrationProtocol=2&…`, Effect RPC frames as JSON, an `Ack` after every stream chunk, and readiness only after the server configuration arrives ([connection runtime](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/connection-runtime.md?plain=1#L57-L64)).
3. **Thread list.** `orchestration.subscribeShell`, merging omitted rows on demand (section 4.3).
4. **A thread.** `orchestration.subscribeThread` with a cursor; `dispatchCommand` with `thread.create` or `launchThread`, `message.dispatch` (start, queue or steer), `run.interrupt`, `runtime-request.respond`, `thread.user-input.dismiss`, `thread.runtime-mode.set`, `thread.interaction-mode.set`, `thread.model-selection.set`, `thread.metadata.update`; `getTurnDiff`; `subscribeCommandOutput`.
5. **Providers and models** from the server configuration; projects from `projects.*` or `t3 project add`.
6. **Terminals**, if wanted: `terminal.open`, `attach`, `write`, `resize`, `close`, with output as text chunks for the client's own emulator.

### 5.2 Client-side logic it would reimplement or import

- **Projection.** Holding the thread projection and applying each event to it, including the derived `visibleTurnItems` ([`orchestrationV2Projection.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/client-runtime/src/state/orchestrationV2Projection.ts#L259-L300)), and skipping unknown events and turn items while advancing the cursor (2.2).
- **Reconnection.** The cursor, a fresh snapshot after a gap, backoff that doesn't stampede a restarted server, and rules for not overwriting newer data with cached data ([connection runtime](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/connection-runtime.md?plain=1#L9-L69)).
- **Presentation.** Labels for commands and tools, pending input, and the grouping of a run's items (`client-runtime/src/work-log`, `src/state`; 4.3). weave's TUI does the equivalent for ACP in [`tool_call.rs`](../../tui/src/tool_call.rs#L667-L695) and [`conventions.rs`](../../tui/src/conventions.rs).
- **Version tracking.** Every server release can add fields, flags or items; a mismatch of the protocol constant shuts the client out entirely. `tria`'s history shows this cost: a port to protocol 2 a week after the cutover, and another fix after a protocol update on 2026-10-29 (1.4).

### 5.3 Language

- **TypeScript.** The only way to reuse T3's schemas and `client-runtime` exactly, but neither is published: a TUI would vendor the monorepo or depend on it by Git, build with its toolchain (`vp`, pnpm catalogs, Effect 4), and move whenever upstream does. The closed `t3 tui` proposal chose Bun and OpenTUI (1.3).
- **Rust.** Keeps weave's stack, ratatui and the existing TUI code, but the types are hand-written: there is no exported JSON Schema or OpenAPI for the WebSocket API (2.2). Effect can derive JSON Schema from its schemas, and T3 does so for its MCP tools ([`advertisedJsonSchema.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/mcp/advertisedJsonSchema.ts#L105-L106)), so a weave-side script could generate one from a pinned checkout; that script would be weave's to keep. `tria` shows the hand-written route works, at about 2 MB of Rust.
- **Neither** reuses much of weave's TUI below the rendering layer. The TUI renders ACP updates and drives Host protocol requests through `host-client`; on T3 it would render T3 turn items and dispatch T3 commands. The chat state, composer, markdown and terminal plumbing could carry over; the event model, pending-request handling and tool rendering could not.

## 6. Fit for weave

### 6.1 Where weave stands

The question has a precedent. ADR 0011 kept the Host as "the authority for threads, journals, attached clients, pending requests, permission policies, remote devices and triggers" after weighing Mastra and Pi Durable as replacements, and turned Mastra down partly for size (about 331,000 lines), telemetry on by default and breaking changes in minor releases, and a TypeScript Host because weave "would rebuild the journal and attach contract it already has, in a second language" ([ADR 0011](../adr/0011-the-host-stays-the-runtime-authority.md#L8-L14)). T3 Code is a stronger candidate than either: it is a finished product with a server, authentication, replay, durable intent before effect, and restart recovery, and it runs ACP agents. It also shares each of those objections, at a larger scale.

### 6.2 What T3 Code has that weave doesn't

- Native integrations for Codex's app-server and the Claude Agent SDK, with Codex's richer semantics (rollback, goals, questions that outlive a restart) carried into the model (3.4).
- Checkpoints as hidden Git refs, per-turn diffs and rollback (3.1).
- Turns continued after a restart (3.3), where weave ends them `cancelled` though ADR 0011 allows otherwise.
- Triggers: schedules and webhooks with filters, signatures and deduplication (3.1), which ADR 0011 plans for the Host.
- Forks, merge-back, provider switches with a context handoff, peer links between machines, pull-request review on six forges, previews and device streaming.
- Clients on web, desktop, iOS, iPad and Android, and a team committing over a hundred times a day.

### 6.3 What weave would lose

- **ACP as the payload.** The Host carries ACP unchanged and implements ACP v1 completely, checked by a conformance test against every client method ([AGENTS.md](../../AGENTS.md#L38), [conformance](../../AGENTS.md#L138-L143)). T3 normalizes every provider into its own graph, and its generic ACP client turns file and terminal methods off by default (3.4). Claude and Codex would no longer run through ACP at all.
- **Policies.** `PermissionPolicy{approve, otherwise}` approves by tool kind and rejects what nobody approved, which is what makes headless runs safe ([`policy.rs`](../../protocol/src/policy.rs#L17-L40)). T3 has four runtime modes mapped onto each provider's own mechanism, and its default is full access (3.1).
- **Terminals that outlive the Host**, in holders, belonging to a worktree ([ADR 0022](../adr/0022-each-terminal-lives-in-a-holder-of-its-own-and-belongs-to-a-worktree.md#L10-L14)). T3's terminals belong to a thread and die with the server.
- **Worktrees in worktrunk's layout** with busy checks and the `pre-remove` hook ([`worktrees.rs`](../../protocol/src/worktrees.rs#L1-L51)); T3 manages its own worktree directory.
- **Client tools** that run on the device of whoever sent the turn ([ADR 0009](../adr/0009-client-tools-through-a-host-owned-mcp-server.md#L8-L10), [`tools.rs`](../../protocol/src/tools.rs#L1-L46)); no equivalent was found.
- **Attach and observe.** Attaching keeps a thread open and decides where a client tool runs; observers follow without holding ([`sessions.rs`](../../protocol/src/sessions.rs#L406-L433)). T3 has subscribers only.
- **The protocol's security rule** that clients never send a command, an environment or a path to write ([spec](../specs/wve-85-host-protocol.md#L1355-L1364)). T3 bounds clients by scopes and lets them open shells with their own `env`.
- **A contract weave controls**: version ranges negotiated in `host/hello`, the previous major version kept from version 3 on, additive changes only within a major, golden fixtures, and a JSON Schema the app's TypeScript is generated from ([spec](../specs/wve-85-host-protocol.md#L1327-L1353), [`lib.rs`](../../protocol/src/lib.rs#L53-L58), [`schema.rs`](../../protocol/tests/schema.rs#L1-L4)).
- **Reach and privacy defaults**: a Unix socket and a tailnet-only WebSocket with device keys ([ADR 0010](../adr/0010-remote-clients-through-the-tailnet-with-device-keys.md#L8)), and no telemetry. T3's service listens on LAN and tailnet addresses and sends product events unless told not to (2.1).
- **The weave app.** It speaks the Host protocol and would have nothing to talk to; T3's own mobile app, which supports iPad ([`app.config.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/mobile/app.config.ts#L245)), would replace it.
- **Understanding the whole system.** The Host and its crates are about 32,000 lines of Rust. T3's server and packages are about 520,000 lines of TypeScript and Effect, rewritten in large part in October.

### 6.4 Upstreaming or forking

- **Upstreaming** any of 6.3 runs into a contribution policy that wants prior maintainer approval for features and says unsolicited ones are unlikely to be accepted (1.3). Several are product decisions T3 has made the other way: provider-native modes rather than a T3 policy, thread-scoped terminals, full access by default. A policy model or holder-style terminals would be large changes to the server, not small fixes.
- **Forking** the server means following about 120 commits a day and keeping a database a fork can't safely migrate: T3's migrator compares ids only, so "there is no safe id range for a fork inside this ledger", and fork schema changes "belong in a separate migration table or outside the migrator entirely" ([legacy migration](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/legacy-orchestration-migration.md?plain=1#L44-L54)). A fork that stops following upstream is a TypeScript Host to maintain alone, larger than the Rust one it replaced.

### 6.5 Risks

- **API stability.** The maintainers say in writing that the WebSocket API is not a published contract and that no stable SDK is promised (1.3). Versions must match exactly; the constant went from 1 to 2 seventeen days after it appeared, and a mismatched client is refused before it can do anything (2.2). Within version 2 the wire moves weekly behind flags (1.2). The one Rust TUI that exists needed protocol fixes in its first six weeks (1.4).
- **Not meant as a public surface.** The contracts and client runtime are private, unpublished TypeScript; T3 builds for three surfaces, web, desktop and mobile, and "change the schema and the server, web, mobile, and desktop all follow" ([AGENTS.md](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/AGENTS.md?plain=1#L65-L73)). A fourth client outside the repository does not follow.
- **The framing.** Effect RPC marks its own message types unstable, and a client must implement its acknowledgements (2.2). A change in Effect's RPC wire would reach any non-Effect client.
- **Licensing** is not a risk for a client: MIT. The hosted pieces (T3 Connect, its machine limits tied to T3 Chat plans) are optional.
- **Direction.** T3 Code is a GUI product for a large audience, run by a company; a terminal client has been proposed and closed, and many maintainer replies are written by models on the maintainers' behalf (1.3). Nothing in its stated scope or roadmap points toward a terminal client or a stable external API.

### 6.6 Verdict

Not viable as the foundation for weave today. The T3 Code server is capable, and in places ahead of the Host (6.2), and a terminal client for it is possible, `tria` shows that much. But building on it means giving up most of what distinguishes weave (6.3) to stand on an API whose maintainers have said it is not a contract and which has already broken all outside clients once, with no channel for getting weave's needs upstream (6.4).

A T3 Code TUI would have to: pair and keep a bearer token; implement Effect RPC over the WebSocket with acknowledgements; hold and update thread projections with forward-compatible decoding; reimplement T3's presentation of turn items; send T3's commands for prompts, queueing, steering, interrupts and approvals; and be revised whenever the server changes, at the server's pace (5.1, 5.2). In Rust, its types would be hand-written or generated by weave from a pinned checkout (5.3). It would keep little of weave's TUI below the rendering layer.

If the aim were only to use T3 Code from a terminal, the cheaper path is to try `tria` or the MCP surface `t3 thread` uses, pinned to one T3 release, with `T3CODE_HOST=127.0.0.1` and `T3CODE_TELEMETRY_ENABLED=false`, rather than write a client. That is a decision to adopt T3 Code as a product, not to build weave on it.

These would change the answer:

- T3 publishing its contract as a versioned package or schema with a compatibility policy, such as negotiated ranges or support for the previous protocol version, or a maintainer statement that third-party and terminal clients are supported.
- A permission model in T3 that approves by kind and rejects the rest for headless threads, an ACP client with file and terminal methods on, and terminals that outlive the server; each would remove an item from 6.3.
- On weave's side, the cost of keeping the Host growing faster than the value of 6.3, for example if most of the person's work moved to providers T3 integrates natively and ACP stopped mattering.

### 6.7 What to borrow instead

- **Continuing cut-off turns** under a policy that allows it, with T3's checks: matching resume identity, refusing threads waiting on a person or stopped by one, and a cap on consecutive continuations (3.3). ADR 0011 already allows it.
- **Checkpoints as hidden Git refs**, giving per-turn diffs and rollback without touching the branch (3.1).
- **Trigger details** for when the Host gets them: webhook filters, signatures, a maximum delivery age and deduplication ([`scheduledTask.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/scheduledTask.ts#L100-L135)).
- **Steering by interrupt and restart** as a fallback where an agent can't steer, behind the same request (3.1).
