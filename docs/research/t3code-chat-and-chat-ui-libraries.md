## In brief

- **T3 Code's thread view is almost all its own code.** Four libraries carry weight: `@legendapp/list` virtualizes the timeline, `@pierre/diffs` draws diffs and highlights code, Tiptap is the composer's editor, and Base UI is under the controls. Rows, the grouping of work, Markdown rendering, approvals, the queue and the composer's menus are hand-built, in about 62,000 lines under `components/chat` and `ChatView.tsx`, tests aside.
- **Weave is on the right library already, and on its newest versions.** Vercel's AI Elements is deprecated at the end of November 2026 in favour of shadcn/ui's own AI Elements, which has Base UI variants and whose scroller (`@shadcn/react`) weave's chat already uses. Streamdown is at 2.7.1, which the app's lockfile resolves. No other kit fits better; assistant-ui is the only serious alternative and costs more than it gives.
- **The gaps are features, not the library.** Weave has no diff rendering, no changed-files summary, no message actions, no file mentions, no pasted images, no editing of queued messages, no virtualization and no paging of history. Diffs, virtualization and the composer's menus each have a library answer; checkpoints, forks and history paging need the Host first.

### 1.3 The timeline

- **Rows, not messages.** The server's turn items are projected to a flat array of rows of 15 kinds: `message`, `assistant-meta`, `work`, `work-live`, `work-toggle`, `thinking`, `working`, `turn-fold`, `attempt-fold`, `context-compaction`, `event`, `proposed-plan`, `html-render`, `mcp-app` and `worktree-setup` ([MessagesTimeline.logic.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.logic.ts#L499-L645)). One function, `deriveMessagesTimelineRows`, makes them ([L1502](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.logic.ts#L1502)), and one memoized component dispatches on the kind ([MessagesTimeline.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L1420-L1500)).
- **Virtualized with LegendList.** `<LegendList>` gets the rows with `estimatedItemSize={90}`, `initialScrollAtEnd`, `maintainScrollAtEnd` (on data change, item layout and layout; animated only while a turn runs and reduced motion is off), `maintainVisibleContentPosition` for data and size, and `maintainScrollAtEndThreshold={1}`; the scroller sets `overflow-anchor: none` ([L192-L205](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L192-L205), [L1300-L1345](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L1300-L1345)). Rows are typed for size estimates: LegendList "estimates unmeasured rows from their type's average", so a message over about 4,000 characters gets a type of its own ([L1410-L1418](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L1410-L1418)). An opened work group is a second, nested LegendList with `recycleItems`, 24 px rows and a height capped at `min(18rem, 50dvh)` plus what's expanded ([TimelineWorkGroupRows.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineWorkGroupRows.tsx#L237-L265)).
- **The patch is the mobile app's.** T3 patches `@legendapp/list` 3.7.2 to hold the end in the same pass that repositions items, "so the feed visibly jumps twice" otherwise; the patch touches only `react-native.js` and `react-native.mjs` ([patch](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/patches/@legendapp__list@3.7.2.patch#L1-L30)), and the package's `./react` entry is `react.mjs`, a different file (npm registry, `exports` of 3.7.2). The web timeline therefore runs the published package (inference from those two facts).
- **Following and anchoring are T3's.** Whether the view follows the end is a small state machine per visit to a thread ([useTimelineFollow.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/useTimelineFollow.ts), `timelineViewport.ts`); a sent message is anchored near the top with space reserved below it (`anchoredEndSpace`, [MessagesTimeline.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L808-L820)); the scroll position of each thread is remembered and restored before paint ([L711-L716](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L711-L716)).
- **History in pages.** A thread opens with a bounded window: "Cold opens and history pages stop at about 1 MiB of encoded rows", 10 user turns or 500 rows ([performance-regressions.md](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/docs/internals/performance-regressions.md?plain=1#L15-L21)); a "Load earlier turns" row at the top fetches more ([MessagesTimeline.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L1370-L1397)).
- **Around the list.** A minimap of the person's messages beside the scroller, each a strip that jumps to its turn ([TimelineMinimap.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineMinimap.tsx#L37), [L162](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineMinimap.tsx#L162)); find in thread on ⌘F ([keybindings.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/packages/shared/src/keybindings.ts#L115)), which turns end-following off while open ([MessagesTimeline.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.tsx#L327)); timestamps on rows; long prompts collapsed past 8 lines or 600 characters ([MessagesTimeline.logic.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.logic.ts#L2648-L2673)); consecutive prompts drawn closer together (`groupedWithNext`, [L604-L609](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.logic.ts#L601-L606)).

### 1.4 Work between messages

- **A finished turn folds.** Everything between the prompt and the final answer folds under one row labelled "Worked for 2m 17s", or "You stopped after …" for the latest interrupted turn; work after a steer folds under its own "Continued for …" row below that steer ([MessagesTimeline.logic.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.logic.ts#L1165-L1218)). The elapsed time is the *run*'s start to completion.
- **Inside a turn, tool calls group by what they did.** Adjacent calls collapse into a toggle row with a summary by kind: "Read 3 files", "Ran 2 commands", "Searched the web 2 times", "Searched code 4 times" ([presentation.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/packages/client-runtime/src/work-log/presentation.ts#L478-L492), kinds at [L122-L129](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/packages/client-runtime/src/work-log/presentation.ts#L122-L129)). Each call is one line: an icon for its kind, a label derived from its input (a 44 kB module only for command labels, [`commandLabel.ts`](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/packages/client-runtime/src/work-log/commandLabel.ts)), a failure mark, a timestamp ([TimelineWorkEntryRow.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineWorkEntryRow.tsx#L174)). This grouping lives in `packages/client-runtime`, shared with the mobile app.
- **While it runs.** The latest call shows as a live row, thinking as a "Thinking" row with the thought's first line rendered inline as Markdown ([TimelineWorkEntryRow.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineWorkEntryRow.tsx#L424-L436)), and with nothing else to show, "Working for 12s" ([TimelineWorkGroupRows.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineWorkGroupRows.tsx#L278-L310)). The timer writes the element's `textContent` on a shared one-second tick, "so a ticking label never re-renders the timeline or composer around it" ([tickTextContent.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/lib/tickTextContent.ts#L3-L19)).
- **Details load when a row opens.** "Raw command output, dynamic-tool result bodies, and inline file-change bodies are omitted at the wire boundary", and "Live command output reaches a client only through `orchestration.subscribeCommandOutput`, which an expanded command row opens and closes with itself" ([performance-regressions.md](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/docs/internals/performance-regressions.md?plain=1#L35-L51)). The output panel is a 20 rem scroller of ANSI-coloured spans that sticks to its own bottom ([CommandOutputPanel.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/CommandOutputPanel.tsx#L26-L84)).
- **Other rows.** Subagents as a group with avatars, status and elapsed time, each opening its thread ([V2LifecycleRow.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/V2LifecycleRow.tsx#L397), [AgentElapsed.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/AgentElapsed.tsx)); context compaction as a divider with token counts; superseded attempts folded; an agent's proposed plan as a card that can be saved to the worktree ([ProposedPlanCard.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/ProposedPlanCard.tsx#L41)); failures as rows, a usage limit with its reset time and a retry where one applies ([TimelineWorkEntryRow.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineWorkEntryRow.tsx#L209-L266)); MCP Apps and rendered HTML in frames.
- **After the answer.** The last assistant message of a turn carries a card of the files the turn changed, as a tree with added and removed line counts, each opening the diff panel at that file ([TimelineAssistantRows.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/TimelineAssistantRows.tsx#L297-L364), [ChangedFilesTree.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/ChangedFilesTree.tsx#L28)). The data is the server's checkpoint for the turn (`TurnDiffSummary`), not something the client derives.

### 1.5 Markdown, code, diagrams

- **Its own renderer.** One frozen `unified` processor per plugin set, rendered to React with `hast-util-to-jsx-runtime`, as react-markdown does ([markdownRenderer.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/markdownRenderer.ts#L47-L62)). Rendered elements are cached by source text, up to 500,000 characters: "a remount (a thread switch, a row scrolled back into view) reuses one instead of parsing again. Parsing is most of the cost of rendering markdown" ([L21-L45](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/markdownRenderer.ts#L21-L45)). With a virtualized list, rows remount as they scroll, which is what the cache is for.
- **Streaming by block.** While a message streams, its text is cut "at blank lines that close every open block, so each piece renders exactly as it would inside the whole text", and only the last block is parsed again; text with link definitions, footnotes, raw HTML or display math isn't cut ([markdownStreamBlocks.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/markdownStreamBlocks.ts#L1-L11), [ChatMarkdown.tsx](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/ChatMarkdown.tsx#L1739-L1800)). A second path caches completed fences when the text can't be cut ([markdown-incremental.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/markdown-incremental.ts#L33-L40)). Streamed text isn't animated in.

### 1.9 How it stays fast

- **Rows keep their identity.** While only message text streams, the previous projection is patched, "so a streamed text update patches its message rows instead of deriving every row again" ([useTimelineRows.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/useTimelineRows.ts#L38-L62)); then each new row is compared with the last one of its id and the old object kept when nothing changed, so memoized rows skip rendering ([MessagesTimeline.logic.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/MessagesTimeline.logic.ts#L2496-L2514)).
- **Context split by how often it changes.** Rows read what's stable (callbacks, settings) from one context and what changes while a turn runs from another (`TimelineRowCtx`, `TimelineRowActivityCtx`, [timelineRowContext.ts](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/apps/web/src/components/chat/timelineRowContext.ts)).
- **React Compiler everywhere**, enforced (1.2), with handlers in the large components written to avoid retaining old renders ([web-ui.md](https://github.com/pingdotgg/t3code/blob/d313b2aff31991ab94c8ac80cdc38a54dd575604/docs/internals/web-ui.md?plain=1#L41-L55)).
- **Less on the wire.** Bounded history, bodies fetched when a row opens, command output on its own subscription (1.3, 1.4).
- **Timers and shimmer outside React.** Text written to the DOM on a tick (1.4); shimmer animations run only while visible (`observeVisibleAnimation`).

## 5. Fit for weave

Judgement from here on.

### 5.1 What differs, and what it rules out

- **The transcript is weave's own.** It comes from ACP through the Host protocol, already reduced to entries. A kit that wants to own messages (CopilotKit, ChatKit, TanStack AI's client) is out; one that takes props (shadcn's) or a store adapter (assistant-ui's) is in.
- **ACP carries less than T3's server keeps.** T3's per-turn diffs, "Edit from here" and fork rest on server checkpoints of the worktree and on provider sessions that can fork. ACP gives a tool call's `diff` content (old and new text) and no checkpoints. Weave can show what a turn's tool calls said they changed; it can't revert or fork from the chat until the Host does git checkpoints, and the same goes for paging a journal. Those are Host protocol work, outside what a UI library decides.
- **WKWebView.** The iPad and iPhone run the page in WKWebView, where the app has already met a scroll jump from `content-visibility` (2.2). Each of the candidate virtualizers has iOS caveats in its own tracker (3.2), and both rich editors have open iOS input issues (3.4). T3 doesn't face this: its phone app is native.
- **Inert Markdown.** Anything that renders agent text must keep weave's rules. T3's renderer parses raw HTML and loads images, so its Markdown code isn't a model to copy. A diff or code viewer is fed file text, not Markdown, but it must load nothing from the network and work under `script-src 'self'`: workers bundled with the app are fine, `blob:` workers and WebAssembly are not without loosening the policy (2.2).

### 5.2 Verdict on the libraries

**Stay on shadcn's AI Elements and Streamdown.** The reasons, in order:

1. **It's where the ecosystem moved.** The one comparable kit, Vercel's, is being folded into shadcn's at the end of this month, and shadcn's is the only one with Base UI variants, copy-in source and React 19 only. Weave already uses its scroller and chat components.
2. **Nothing else covers more of the gap.** No kit ships a virtualized transcript, a diff viewer or a file-mention composer; assistant-ui, shadcn and CopilotKit all point at `@tanstack/react-virtual` for long threads. T3 Code, the reference here, uses no chat kit at all.
3. **assistant-ui would be a rewrite for a second state layer.** `ExternalStoreRuntime` works and is documented, and its message model has parts for what weave shows. But it brings its own store, Radix beside Base UI, a hard dependency on its cloud client, a 0.x API with experimental fields where weave would lean on it (queue, approvals), and every view in `app/src/chat` rebuilt on its primitives. Its ACP adapter is unpublished and assumes a socket per agent. What's worth taking from it are two designs: rows rather than messages for virtualization, and a trigger popover over a textarea.
4. **Streamdown is ahead of what T3 hand-built for streaming.** 2.7 reuses parsed blocks and tokenizes only new code lines, which is what T3's block splitting and incremental highlighter do. It's the most-downloaded piece here (10.8 million a week), and weave's inert rules are already built on its plugin seams.

What to do about the deprecation: nothing urgent. The seven files in `components/ai-elements` are weave's own code and import nothing from Vercel. Rebuild one on shadcn's Trace when it's being changed anyway.

### 5.3 Already in the stack, not used

- **Trace, Task and Chain of Thought** for the work log: one-line steps with an icon, a label and a status, a summary that expands. This is the shape of T3's work rows, and would replace the card-in-card look of `work-run-view.tsx` and `tool-call-view.tsx`.
- **Queue** for queued messages, in place of the hand-built list in `chat-pane.tsx` (L443-L483).
- **Checkpoint**, a marker to return to, for when the Host has checkpoints.
- **File Tree** for a turn's changed files; **Terminal** for command output; **Code Block** for resources and raw tool input.
- **Suggestion** for prompts to send next; **Model Selector** if the config menu is split into pickers; **Subagent** for the subagent row; **Questionnaire** as an alternative shell for elicitations.
- **Streamdown's** `fallbackComponent` and `portal` props from 2.7.

### 5.4 Needs another library

- **Diffs: `@pierre/diffs`.** `MultiFileDiff` takes two files, which is what ACP's `diff` content is, so no patch has to be made. It brings line and word diffs, highlighting with the Shiki the app already ships, split or stacked layout and its own virtualization. To check before committing: that its shadow roots style and scroll properly in WKWebView, that its worker loads under the app's policy, the Safari freeze on long wrapped lines (#1234), and what it adds to the bundle with grammars loaded on demand. `react-diff-viewer-continued` is the small fallback: old and new text in, no shadow DOM, plainer.
- **Virtualization: `@tanstack/react-virtual`, on MessageScroller's viewport**, following shadcn's recipe and assistant-ui's rows. It keeps the scroller weave has. `@legendapp/list` is what T3 runs, but it would replace MessageScroller and its anchoring, its web entry is six months old, and its tracker has an open report of janky touch scrolling on iOS; T3's own use of it on the web is desktop browsers and Electron.
- **Composer: no editor library.** A textarea with a trigger popover gets `/`, `@` and keyboard navigation. Chips inside the text are what would need Tiptap, and T3's use of it is about 2,000 lines of editor and a larger document model, on desktop only. `rich-textarea` is a middle step if mentions should be coloured in place.

### 5.5 Hand-built either way

T3 writes these itself, and no library has them: the grouping and labelling of work (`transcript-runs.ts` is weave's start on it), the fold per turn, message actions, queue editing, prompt history, find in thread, the minimap, scroll position per thread, and stable row identity. Weave's reducer already keeps entry identity, which is the expensive part.

### 5.6 Order of work, by value for effort

1. **The work log as lines, not cards** (small; `work-run-view.tsx`, `tool-call-view.tsx`, `transcript-runs.ts`). Rebuild on Trace: one line per tool call with an icon by ACP tool kind, failure mark and no status badge; adjacent calls of a kind summarized as T3 does; thinking folded into the log with a one-line preview instead of an open collapsible; "You stopped after …" for a cancelled turn; the timer written to the DOM rather than through state. Consider folding a whole finished turn under one row, as T3 does, with the final message outside it.
2. **Message actions and small transcript features** (small each; `chat-pane.tsx`). Copy a message as Markdown; timestamps on hover, from the times entries already carry; collapse long prompts; edit a queued message (remove it and put its text back in the composer) and steer with it now; ArrowUp for earlier prompts; the send button as stop when the draft is empty; the Queue pattern for the list.
3. **Real diffs** (medium; `tool-call-view.tsx` L71-L86, a new changed-files card). `@pierre/diffs` for each `diff` content, after a spike in the iOS simulator and on a device. Then a card at the end of a turn listing the files its tool calls changed, built from the same content with the File Tree pattern. It says what the agent reported, not what git sees; say so in the UI.
4. **The composer's menu** (medium; `chat-pane.tsx` L488-L517 and the textarea). One popover for `/` anywhere a token starts and `@` for files through `files/list`, with arrow keys and Enter; a mentioned file sent as an ACP `resource_link`. Paste and drop for images through the existing `promptImage`. Shortcuts for the settings menu on the Mac.
5. **Virtualize when a long thread is measured to need it** (medium to large; `chat-pane.tsx` L830-L860). First flatten work runs into rows so no row is a whole turn, then `@tanstack/react-virtual` on the viewport, tested on an iPad before anything else. Collapsed runs already keep most of a long thread's DOM out (inference: Base UI's Collapsible doesn't mount a closed panel by default). Turning React Compiler on is a cheaper first step for render cost; T3 runs it everywhere.
6. **Needs the Host first.** Paging a journal (which also bounds what's mounted), command output fetched on demand, checkpoints with revert and a per-turn diff panel, and forks. Each is a protocol decision before it's a view.
7. **Later, and only on the Mac at first:** find in thread and a minimap. Both read the list's state, so they follow whatever step 5 settles.

### 5.7 Risks

- **Shadow DOM and workers in WKWebView** for `@pierre/diffs`; a spike answers it in a day.
- **Virtualization on iOS** is where each library's tracker is busiest. A regression there costs more than long threads do today, so measure first.
- **Copy-in components drift.** shadcn's patterns are source in the repository; upstream fixes don't arrive by themselves. That's already true of what weave has.
- **A changed-files card built from tool calls can be wrong**: an agent that edits through a shell command reports no diff. T3's is right because its server reads git.
- **`@shadcn/react` is at 0.3** with one release in 90 days; the scroller is young, and its benchmark doesn't cover Safari.
