# T3 Code's Device panel, and a device Block

Research snapshot, 2026-11-15. Primary sources only. Repositories were read from shallow clones at these commits: `pingdotgg/t3code` [`c2e54e3a`](https://github.com/pingdotgg/t3code/tree/c2e54e3ac9c8c0d5ceaf7df5acd4f4374fa19b6f) (`main`, 2026-11-15); `expo/expo-device-hub` [`46952456`](https://github.com/expo/expo-device-hub/tree/469524564f7d31c9450d0bd50b1c83d2b3c745b8) (`main`, 2026-11-13, package version 0.23.2); `callstack/agent-device` [`7848a1a9`](https://github.com/callstack/agent-device/tree/7848a1a9283fe36626f5cb6bb62423b9a084f09d) (`main`, 2026-11-15, 0.21.38-dev). T3 Code pins older releases of the last two (section 1), so their sources here are slightly newer than what T3 Code runs. Paths that start `apps/`, `packages/client-runtime`, `packages/contracts` or `docs/internals`, `docs/user` are in the T3 Code clone; `llp/` and `packages/serve-sim`, `packages/serve-emu` are in the Expo clone; `apple/`, `android/` and `website/` are in the agent-device clone. Nothing was built, installed or run, and no stream was seen. Weave is judged at `6bdd342c`. Sections 1 to 8 are facts. Section 9 lists what wasn't verified. Sections 10 to 12 are analysis for weave, not a plan.

The question: how T3 Code shows an iOS Simulator or Android Emulator live in its Device panel, how its agents drive one, and whether weave could do the same. This is the companion to [Sill's window streaming, and a screen Block](sill-window-streaming-and-a-screen-block.md), which covers showing a window of a Host's computer and describes how weave's Blocks and terminal streams work; this note refers to it and doesn't repeat it.

This note uses weave's words (Host, Dispatcher, Session, Block, thread, device). T3 Code's *environment server* is its counterpart of a weave Host, as in [T3 Code and the weave Host](t3code-and-the-weave-host.md). Weave's *device* is the person's iPad, iPhone or Mac running the app. T3 Code's *device* is a simulator or emulator, written "simulator", "emulator" or "simulated device" here except in quoted names such as `device_open`. T3 Code's *device host* is the computer the simulators run on, written "simulator computer".

## In brief

- **It is video, not screenshots, and none of it is T3 Code's own.** T3 Code installs two npm packages and puts a proxy and four tools in front of them: Expo's `expo-device-hub` streams and takes the person's input, and Callstack's `agent-device` drives for agents (`docs/internals/devices.md`).
- **iOS: the simulator's framebuffer, read through private frameworks.** `serve-sim`, inside the hub, loads CoreSimulator and SimulatorKit from Xcode, reads the display's IOSurface, encodes H.264 with VideoToolbox (60 fps and 6 Mbps by default), and serves it as a long HTTP response of length-prefixed chunks. It doesn't capture a window: no ScreenCaptureKit, no Simulator.app window needed.
- **Android: the emulator's gRPC screenshots through ffmpeg, or scrcpy.** `serve-emu` encodes an emulator's gRPC frames to H.264 with ffmpeg (libx264) on the computer, and uses scrcpy's own H.264 for physical phones. Both go out over one WebSocket.
- **The page decodes with WebCodecs and draws to a canvas.** Where WebCodecs is missing (a page that isn't a secure context), iOS falls back to MJPEG in an `<img>`; a hub locked to WebRTC is played through a `<video>` that feeds the same canvas.
- **The person's input** goes down a WebSocket as fractions of the screen and is injected as simulator HID events (iOS) or scrcpy control packets (Android). It never touches the Mac's pointer.
- **Agents get four tools and a command line.** `device_open` returns a launcher for `agent-device` bound to one simulated device. The agent reads the accessibility tree as a "snapshot" with `@e1`-style refs and acts on refs. `agent-device` uses its own means (an XCTest runner, an accessibility bridge, adb), separate from the hub.
- **A simulator on another computer** is reached by `ssh -L`: the tools are installed and run there, and their two loopback ports are forwarded to T3 Code's server.
- **Licences.** T3 Code MIT; expo-device-hub MIT, vendoring serve-sim and serve-emu, both Apache-2.0; agent-device MIT.
- **For weave, a simulator is better served by a Block of its own than by a window-capture Block.** The framebuffer route appears to need none of the things the Sill note found hardest: Screen Recording and Accessibility grants, an uncovered window, a virtual display. It shares the rest with a screen Block (a third stream kind, WebCodecs in the page, fractional input), so it is the cheaper place to prove those. It costs a Node dependency on the Host's computer and a reliance on private Apple frameworks through someone else's package.

## 1. What T3 Code built and what it took

- **Shipped 2026-09-10** in [#10677](https://github.com/pingdotgg/t3code/pull/10677), "feat(devices): add simulator and emulator support" (the first commit of `docs/internals/devices.md`, `dca7b59b`, by the GitHub API).
- **Two external tools.** "expo-device-hub streams and agent-device drives. Each is npm-installed at a pinned version into the T3 home after its matching Device panel consent step" (`docs/internals/devices.md`). The pins are `agent-device` 0.21.36 and `expo-device-hub` 0.22.1 (`apps/server/src/device/deviceToolVersions.json`), installed with `npm install --prefix` into `tools/<name>/<version>` (`apps/server/src/device/DeviceToolchain.ts`).
- **Run with the server's Node, not `npx`**, which "would make the first `device_open` after a reboot depend on the registry". The hub is "a supervised child rather than an imported middleware because serve-sim loads private CoreSimulator frameworks through a native addon, and a crash there must not take the server down" (`docs/internals/devices.md`).
- **The hub** is Expo's [expo-device-hub](https://github.com/expo/expo-device-hub), "an Expo DevTools plugin that lets you preview and control your iOS simulators and Android emulators right from the browser", which also runs standalone (`README.md`). It vendors two servers: `serve-sim` for iOS, a fork of [EvanBacon/serve-sim](https://github.com/EvanBacon/serve-sim) (`packages/serve-sim/NOTICE`), and `serve-emu` for Android, from [jiunshinn/serve-emu](https://github.com/jiunshinn/serve-emu) (`llp/0000-expo-device-hub.explainer.md`, `llp/0008-serve-emu-protocol.spec.md`).
- **T3 Code's own code** is `apps/server/src/device/` (8,505 lines without tests), the viewer in `packages/client-runtime/src/device/stream.ts` (1,464 lines) and `apps/web/src/components/device/`, and four MCP tools in `apps/server/src/mcp/toolkits/device/`.
- **One seam.** "Everything platform-specific sits behind `DeviceHost`": a local computer, an SSH computer, an Expo cloud session, or a Simlock pool. "The proxy and the MCP tools only see a hub origin and an agent-device endpoint" (`docs/internals/devices.md`, `apps/server/src/device/DeviceHost.ts`).
- **Requirements.** iOS needs macOS with Xcode. Android needs the SDK's Platform-Tools, Emulator and Command-line Tools, and "Android emulator video also needs `ffmpeg` with the libx264 encoder" (`docs/user/devices.md`). Off macOS the hub is started with `--platform android` (`apps/server/src/device/LocalDeviceHost.ts`, `hubPlatformArguments`).

## 2. iOS: from the simulator to bytes

- **Private frameworks, loaded at run time.** serve-sim `dlopen`s CoreSimulator and SimulatorKit from the active Xcode and uses them "purely through the Objective-C runtime (NSClassFromString / KVC / selectors), never linked or imported". The comment records that "Xcode 27 moved SimulatorKit from `Developer/Library/PrivateFrameworks` to `Contents/SharedFrameworks`" (`packages/serve-sim/packages/serve-sim/Sources/SimNative/SimFrameworks.swift`).
- **Capture is the display's IOSurface.** "Headless simulator frame capture via direct IOSurface access. Uses SimulatorKit frame callbacks (via a private Objective-C protocol) plus an IOSurface seed poll … Pipeline: IOSurface (shared memory) → CVPixelBuffer (zero-copy) → H.264 encode" (`Sources/SimNative/FrameCapture.swift`). The capture queue then copies each frame once so encoders can keep it after the simulator reuses the surface (`llp/0001-serve-sim-video-pipeline.explainer.md`, Frame flow).
- **Frame pacing.** Frame callbacks, plus a 60 Hz poll of the surface's seed as "a fallback cadence, not a ceiling", plus "a 5fps idle floor for late-joining clients". Unchanged surfaces aren't copied except at that floor (`FrameCapture.swift`; `llp/0001`).
- **Encoding.** One VideoToolbox H.264 session, real time, defaulting to 60 fps and 6 Mbps, a keyframe at most every five seconds of frames, High profile unless constrained baseline is asked for, low-latency rate control with a fallback to the default (`Sources/SimNative/H264Encoder.swift`, `init(fps: Int = 60, bitrate: Int = 6_000_000 …)`). The command line takes `--video-fps` 1 to 140 and `--video-bitrate` (`packages/serve-sim/packages/serve-sim/README.md`).
- **A fix worth knowing.** VideoToolbox's default-mode SPS omits the VUI, and "Chromium then infers a reorder window from the DPB size and holds about 14 frames before output: about 3 s on a still screen". serve-sim rewrites the SPS to add `max_num_reorder_frames = 0` (`llp/0001`, HTTP AVCC decoder configuration).
- **Three ways out.** `/stream.avcc`, `/stream.mjpeg`, and WebRTC (`src/device-session.ts` header; `README.md`). HTTP is the default transport; `--transport webrtc` "locks the preview to WebRTC" and then the HTTP streams answer `409 stream_transport_locked`.
- **The AVCC stream** is one HTTP response that never ends. Each chunk is "a 4-byte big-endian length (covering the tag byte + payload) followed by a one-byte tag and the payload": `0x01` the avcC parameter sets, "emitted once per encoder session and replayed to late joiners"; `0x02` a keyframe; `0x03` a delta frame; `0x04` a seed, "a JPEG painted immediately on connect so the viewer sees the current screen before the first IDR decodes" (`Sources/SimNative/StreamFormat.swift`).
- **MJPEG** is `multipart/x-mixed-replace`, which "works in any `<img>`; high bandwidth"; AVCC is "~5-10x less bandwidth" (same file).
- **WebRTC** uses libwebrtc (LiveKit's build), one shared H.264 encoder for all H.264 viewers, per-viewer congestion control, and a shared canvas that steps down to 0.75 and 0.5 when the slowest viewer's bitrate stays low (`llp/0001`, WebRTC viewers; `Package.swift`). T3 Code uses it only when a hub refuses AVCC, as Expo's cloud simulators do (section 5).
- **Xcode support.** The published serve-sim is built with Xcode 26 and tested on the iOS 26 and iOS 27 Simulators; this is a Draft decision record (`llp/0014-serve-sim-xcode-support-and-ci.decision.md`).

## 3. Android: from the emulator to bytes

- **Two sources.** "By default, `serve-emu` starts the vendored scrcpy server on the device and streams H.264 through an adb tunnel. Android Emulators can instead use the built-in emulator gRPC screenshot and input APIs, with H.264 encoded by ffmpeg on the host" (`packages/serve-emu/packages/serve-emu/README.md`).
- **The hub chooses gRPC for emulators.** Its defaults are `grpc-screenshot`, image mode `rgb888`, the `software` encoder and 60 fps (`packages/expo-device-hub/src/server/cli/options.ts`). T3 Code checks for a working ffmpeg before opening an emulator, and says "physical Android devices use scrcpy and do not need ffmpeg" (`apps/server/src/device/DeviceService.ts`, `open`; `docs/user/devices.md`).
- **What that path costs.** "This path still requires GPU-to-CPU readback inside the emulator. It is not GPU texture sharing, zero-copy, or hardware encoding; speed depends on the workload and must be measured." A slow encoder keeps "only the newest pending image" (`serve-emu/README.md`). A hardware encoder through ffmpeg (VideoToolbox, NVENC, VAAPI) exists as an option (`llp/0009-serve-emu-hardware-encoder-spike.research.md`).
- **scrcpy** is version 4.0: its server is pushed to the phone, reached through `adb forward`, with a video socket of framed Annex-B and a control socket (`llp/0008`).
- **On the wire** each WebSocket binary message is a `SEMU` header and one Annex-B access unit. The header is 16 bytes in version 1 (magic, version, key-frame flag, PTS) and 24 in version 2, which adds the server's send time; "the server writer always emits v2". serve-emu "caches the latest configuration and prepends it to key frames so that a browser joining or refreshing mid-stream can initialize its decoder. Slow clients drop frames until the next key frame and may request a video reset" (`llp/0008`).

## 4. T3 Code's proxy and transport

- **The hub binds loopback and is never exposed.** "serve-sim has a shell-exec route whose token is readable from its own unauthenticated `/api`, and serve-emu's action routes have no auth at all." The only way in is T3 Code's proxy, which "allowlists the stream, config, and screenshot routes and authenticates every request as an environment session" (`docs/internals/devices.md`; the lists are `ALLOWED_PATHS`, `MUTABLE_PATHS` and `ALLOWED_WS_PATHS` in `apps/server/src/device/DeviceHubProxy.ts`).
- **Reading and operating are separate scopes.** Streams need the read scope; the input sockets and stream tuning need the operate scope (`DeviceHubProxy.ts`, `controlsDevice`).
- **Authentication for things that can't carry headers.** "`<img>` and `WebSocket` cannot carry headers, so the proxy authenticates like the `/ws` upgrade: cookie, or a short-lived `wsTicket` that bearer and DPoP clients mint over authenticated HTTP. The ticket is stripped before the request reaches the hub" (`docs/internals/devices.md`).
- **The proxy passes bytes through**, HTTP bodies as streams and WebSocket frames either way (`proxyHttp`, `proxyWebSocket`, `pumpFrames`). It sets `Cache-Control: no-store, no-transform` because "the compression middleware would otherwise buffer an MJPEG body that never ends".
- **A still screen in MJPEG.** "Browsers paint an MJPEG part only once the next part begins and the hub writes one only when the screen changes", so the proxy re-sends the last part after 100 ms of quiet (`apps/server/src/device/mjpegStillFrame.ts`).
- **Settings and tools don't go through the hub.** serve-sim's own Tools panel sends shell commands over its exec channel; "proxying it, even allowlisted, would hand any environment session arbitrary command execution on the host". T3 Code runs `simctl`, `adb` and serve-sim's helper binaries itself, "one typed action per control" (`docs/internals/devices.md`; `apps/server/src/device/DeviceActions.ts`).
- **So the path from a remote client** is the client's ordinary connection to the server (local network, Tailscale, or T3 Connect), an HTTP response or WebSocket through the proxy, and loopback to the hub. "The device stream goes through the environment server, so it works over the local network, Tailscale, and T3 Connect" (`docs/user/devices.md`).

## 5. The viewer

- **One client for both formats**, written without a framework so the web app and the mobile app share it: `createDeviceStreamClient` in `packages/client-runtime/src/device/stream.ts`. The mobile app (React Native) shows it in a `react-native-webview` (`apps/mobile/src/features/devices/DeviceStreamWebView.tsx`).
- **iOS video** is `fetch` of `/helper/<udid>/stream.avcc`, read with a stream reader, split by `AvccDemuxer`, and decoded: the `description` chunk configures a `VideoDecoder` with `codec: avc1.<profile bytes>`, `description` and `optimizeForLatency: true` after `VideoDecoder.isConfigSupported`; keyframe and delta chunks become `EncodedVideoChunk`s; the seed JPEG is painted through `createImageBitmap` until the first decoded frame (`stream.ts`, lines 197 to 310 and 610 to 800).
- **Android video** is a WebSocket to `/ws?device=<serial>&frame-meta=1`; the client parses the `SEMU` header, scans the access unit for an SPS and a keyframe, and feeds the same decoder (`parseSemuPacket`, `scanAccessUnit`). Its parser accepts version 1 only and treats anything else as a raw access unit, while the hub it pins writes version 2 (checked in the published 0.22.1 package, `vendor/serve-emu/dist/shared/frame-meta.js`). So the header's 24 bytes reach the scanner and decoder in front of the first start code. Nothing in the source says whether that is intended.
- **Drawing** is `drawImage` of each `VideoFrame` onto a 2D canvas, which is resized to the frame (`packages/client-runtime/src/device/frame.ts`). There is no `<video>` element on this path and no Media Source Extensions.
- **Falling behind.** When the decoder's queue passes eight chunks, the Android client asks for a keyframe with `{"type":"reset-video"}`; the iOS client aborts the HTTP response and reconnects, because "native IDRs are spaced by frame count, so an idle simulator may take minutes to produce one. A new AVCC subscription forces a fresh IDR" (`stream.ts`, `decode`).
- **Fallbacks.** "WebCodecs is secure-context only, so the viewer probes `isConfigSupported` and falls back to MJPEG on iOS when decoding is unavailable. Android's SEMU socket has no MJPEG; there the panel reports that it cannot decode" (`docs/internals/devices.md`). For users: "Live video needs a secure page (HTTPS or localhost); on a plain-HTTP remote origin iOS falls back to a slower still-image stream and Android cannot show video" (`docs/user/devices.md`).
- **WebRTC** is used when serve-sim answers 409, or when the MJPEG image fails in a browser with `RTCPeerConnection`. The offer carries every ICE candidate, since "serve-sim does not accept trickled ICE", and "the video element only feeds the same canvas sink" (`docs/internals/devices.md`; `stream.ts`).
- **Only what is looked at streams.** "Only the visible tab streams video; switching tabs keeps both devices running" (`docs/user/devices.md`). Each mounted view has its own client and connection, since "one canvas cannot be in two places" (`apps/web/src/components/device/deviceStreamSession.ts`).
- **Extras** in the panel: a 3D model of the device with the stream as its screen, fold controls, an overlay of accessibility frames, and a Tools drawer for appearance, text size, location and permissions (`docs/user/devices.md`).

## 6. The person's input

- **iOS** is a second connection, a binary WebSocket to `/helper/ws`. Each message is a tag byte and JSON: `0x03` touch `{type: begin|move|end, x, y}`, `0x04` button, `0x06` key `{type, usage}` as a HID usage, `0x07` orientation; the server sends `0x82` screen configuration and `0x83` when input is admitted (`stream.ts`, `IOS_MSG_*`; `llp/0003-serve-sim-http-api.spec.md`, WebSockets). Coordinates are "normalized … from 0 to 1" (`llp/0003`, Input actions).
- **Injected as simulator HID.** serve-sim "uses IndigoHIDMessageForMouseNSEvent to create touch messages and IndigoHIDMessageForButton for hardware button presses, sent via SimDeviceLegacyHIDClient", and on newer simulators per-display HID touch reports and CoreDevice's keyboard (`Sources/SimNative/HIDInjector.swift`). These are private too.
- **Android** shares the video socket, or a second one opened with `video=0` "so input can reconnect without restarting video". Messages are JSON: `{type:"touch", action, x, y}` in fractions, `{type:"key", keycode}`, `{type:"text", text}`, `{type:"back"}` (`stream.ts`; `docs/internals/devices.md`). serve-emu turns them into scrcpy control packets and "must stay on this socket rather than falling back to `adb shell input`, which adds significant latency"; text is capped at 300 bytes a packet (`llp/0008`).
- **What the panel offers**: "click and drag to touch, type while the screen is focused, and use the toolbar for Home, Back, and Recents on Android, rotate on iOS, and power off" (`docs/user/devices.md`). iOS typing is HID key codes, so arbitrary text can't be sent there (`stream.ts`, line 320).

## 7. Agents

- **Four tools, on purpose.** `device_list`, `device_open`, `device_screenshot`, `device_close` (`apps/server/src/mcp/toolkits/device/tools.ts`). "Driving happens through the `agent-device` CLI, which has the semantic snapshot model agents need and stays current with its own releases" (`docs/internals/devices.md`).
- **`device_open`** boots the simulated device if needed, records a session for the calling thread, shows it in the person's panel, and returns "the `agent-device` CLI call pinned to that device". The launcher is a generated script that adds the session, the daemon's address and token, and `--platform ios --udid <id>` or `--platform android --serial <id>`, so "agents need no target flags"; it "refuses the commands that would replace T3's connection" (`apps/server/src/device/AgentDeviceShim.ts`, `apps/server/src/mcp/toolkits/device/handlers.ts`).
- **Instructions arrive with the tool result**, "not kept in an always-loaded prompt or skill: it costs nothing in threads that never open a device and cannot drift from the pinned CLI version". The text tells the agent to run `open <app>` first, then `snapshot -i`, and to "prefer snapshot refs over coordinates" (`handlers.ts`).
- **`device_screenshot`** returns a PNG from the hub's `/api/screenshot`; for iOS a fallback script runs `xcrun simctl io <udid> screenshot --type=png` (`apps/server/src/device/DeviceHubOperations.ts`). `simctl io` documents `screenshot` and `recordVideo` (H.264 or HEVC to a file) and has no live stream (`xcrun simctl help io`, Xcode 27.0).
- **`agent-device`** is [callstack/agent-device](https://github.com/callstack/agent-device), "a CLI, MCP server, and typed Node.js API to control mobile, web, TV, and desktop apps on devices and simulators" (`README.md`). It runs a daemon; T3 Code starts it in HTTP mode with its idle timeout off and a token (`LocalDeviceHost.ts`, `AGENT_DEVICE_DAEMON_SERVER_MODE`).
- **The snapshot** is the app's accessibility tree as text, one line per element with a ref: `@e2 [button] "Add"`. `snapshot -i` lists interactive elements only; a command with `--settle` answers with a diff of the tree, and "refs are valid only in the latest output" (`README.md`; `website/docs/docs/snapshots.md`).
- **How it reaches each platform.** "It uses a local accessibility bridge for iOS Simulator snapshots and XCTest for iOS interactions, physical iOS, and tvOS; ADB and the snapshot helper on Android" (`README.md`). The bridge is a small program compiled for the simulator on first use that calls the simulator runtime's private `XCTAccessibilityFramework`, in the shape Meta's idb used (`apple/snapshot-bridge/README.md`). The runner is an XCUITest target built with `xcodebuild` that serves commands over HTTP (`apple/runner/README.md`); hence "iOS taps build a small test runner on first use, which takes a couple of minutes once per server" (`docs/user/devices.md`). The Android helper is an instrumentation APK that reads every window through `UiAutomation` (`android/snapshot-helper/README.md`).
- **So two input paths exist side by side**: the person's, through the hub's HID injection, and the agent's, through XCTest or adb. Neither goes through the other.
- **Contention.** agent-device keeps "device claims", so a second session on a claimed device fails with `DEVICE_IN_USE`, and defines a "human-control hold", "a device-scoped pause on agent mutations during human operation" (`CONTEXT.md`, `website/docs/docs/sessions.md`). No use of the hold was found in T3 Code's device code.
- **Agents are told to prefer it.** Threads with the `device` capability get a short block of instructions pointing simulator UI work at these tools and away from `simctl`, `idb`, `adb` and ssh, which "stay available for what the tools do not cover". Claude's subagents get it from a `SubagentStart` hook (`docs/internals/devices.md`; `packages/provider-core/src/server/orchestrationInstructions.ts`).
- **Agent access is a separate consent.** agent-device "remains absent and stopped until agent access is granted", and because a provider's environment "is fixed when the provider subprocess spawns", granting access takes effect in agent sessions started afterwards (`docs/internals/devices.md`, `docs/user/devices.md`).

## 8. Other computers, lifecycle and cost

- **A simulator computer over SSH.** T3 Code's server installs the pinned tools there (it needs Node 22.12 or later and npm on a non-interactive SSH path), starts them, and holds one `ssh` with `-L 127.0.0.1:<port>:127.0.0.1:<hub port>` and a second `-L` for the agent-device daemon, `ExitOnForwardFailure=yes`, no connection sharing, and a keep-alive of 10 s (`apps/server/src/device/SshDeviceHost.ts`; `docs/user/devices.md`). "SSH hosts forward both endpoints to server loopback" (`docs/internals/devices.md`). The agent's CLI runs on the server and talks to the far daemon through the forward. macOS and Linux only.
- **Two more kinds of source.** Expo Simulators, cloud sessions billed by the minute, each with its own serve-sim or serve-emu and WebRTC; and Simlock, a Callstack pool of simulators that serves "a lease's screen and input to its holder in serve-sim's formats on both platforms" (`docs/internals/devices.md`). Neither was read further.
- **Who boots.** The person, with Start in the panel, or an agent's `device_open`. Opening the panel alone "does not download or start anything" (`docs/user/devices.md`).
- **Closing.** "Close the tab to stop watching; the device keeps running unless you power it off." Turning device support off "stop[s] the helper processes; simulators and emulators keep running". In the code: "Stops helpers. Devices themselves keep running; the user owns those" (`DeviceHost.ts`). Ending a session closes its agent-device session, "which quits the app that session opened and releases the CLI's claim on the device" (`docs/internals/devices.md`).
- **Sessions** are `{threadId, hostId, deviceId, platform, openedAt}`, kept in memory by the server (`packages/contracts/src/device.ts`; `DeviceService.ts`, "Sessions live in memory"). When an agent opens one, it "floats over the chat in web and desktop clients connected to the thread".
- **Several viewers.** serve-sim's HTTP streams and WebRTC both "support multiple viewers" of one simulator from one capture source (`serve-sim/README.md`).
- **Cost on the Mac.** Neither T3 Code's docs nor the hub's give a CPU or GPU figure. What the sources do say: capture copies nothing while the screen is unchanged except five frames a second; the seed JPEG's encoder "adds no steady-state encoding cost"; `/metrics` reports CPU, memory and network once a second (`llp/0003`); and the capture note admits that "direct copy and viewer-scale latencies still need separate measurements" (`llp/0001`). The Sill note records the other side: Sill's frame rate fell from 57 to about 35 fps while another process encoded an iOS Simulator's screen (its section 4).
- **Local evidence.** This Mac's T3 Code has both tools installed, at older pins: `~/.t3/tools/expo-device-hub/0.19.1` and `~/.t3/tools/agent-device/0.21.31` (directory names only; nothing in them was read).

## 9. Not verified

- **Nothing was run.** No stream, latency, frame rate or CPU figure was observed. Every number above is a default or a claim in the source.
- **Versions.** The hub and agent-device were read at `main`, newer than T3 Code's pins (0.23.2 against 0.22.1; 0.21.38-dev against 0.21.36). The iOS wire formats in sections 2 and 6 match what T3 Code's viewer parses at `c2e54e3a`, which is the check that they hold for the pinned versions. The Android header doesn't (section 5), and the one file of the published 0.22.1 package that was opened to check it is the only pinned source read.
- **The reading was partial.** T3 Code's `DeviceService.ts` (1,707 lines) and `stream.ts` were searched and read in the parts cited, not through. serve-sim's Swift was read at the file headers and the encoder settings; its TypeScript at the stream endpoints. agent-device was read from its README, domain glossary, helper READMEs and two documentation pages; its source was not.
- **`EvanBacon/serve-sim` and `jiunshinn/serve-emu`**, the original repositories, were not read; Expo's copies were.
- **Permissions.** That serve-sim needs neither the Screen Recording nor the Accessibility grant is an inference from its not using ScreenCaptureKit or CGEvents and from its README naming no such permission. It was not tested, and not from a launchd agent.
- **Apple documents none of this.** CoreSimulator, SimulatorKit, the Indigo HID functions and `XCTAccessibilityFramework` are private. Only `simctl io` was checked against Apple's own help text. Android's emulator gRPC API and scrcpy's documentation were not consulted; the Expo notes about them were.
- **Whether serve-sim's AVCC stream shares one encoder between several HTTP viewers**, and whether one viewer's reconnect (which forces a keyframe) disturbs another, was not read.
- **The idle rate on the wire.** The 5 fps floor is capture's; whether the AVCC encoder emits a frame for each was not followed.
- **WebCodecs in weave's page.** As in the Sill note's section 9: Apple's notes put WebCodecs video at Safari 16.4. Whether Tauri's page counts as a secure context on each device, so that `VideoDecoder` exists at all, was not checked.
- **Android on a Linux Host.** The hub supports it by its arguments and T3 Code's docs. Whether the person's Linux Host can run an emulator (KVM, a GPU or software rendering) was not checked.
- **agent-device on the Mac's own apps.** Its README says it drives macOS apps through "a local helper" and Linux through AT-SPI. Not read; it bears on the Sill note's "what an agent is driving".
- **Expo Simulators and Simlock** are described from T3 Code's internals document only.

## 10. Weave as it stands

The Sill note's section 10 lists what a new Block type meets in weave: a Block is a type name and props the Host doesn't read, terminals have a stream of their own with a single-use ticket, a device's stream is carried through the Dispatcher unread, the page gets bytes over the core's loopback WebSocket, the page is a web view everywhere, and a Host listens for no remote client. Three more facts matter here.

- **The Host already offers agents Session-scoped tools** for terminals and Neovim: `list_terminals`, `read_terminal`, `write_terminal`, `nvim_open`, `nvim_state`, which act only on the calling thread's Session (`host/AGENTS.md`, WVE-233).
- **"Giving something a Block makes it the Session's"**, and "closing one closes what it shows: a thread, which can be shown again in another Block, or a terminal, which ends with it" (`CONTEXT.md`, Block).
- **Weave's own app is an iOS app.** It builds with `bun run ios:*` and is checked in the simulator, since each real device pairs once (`AGENTS.md`; `app/AGENTS.md`). The first simulator a weave agent would drive is weave's.

## 11. A device Block: what it could be, and what carries over

Analysis from here on.

### 11.1 A Block of its own, or a window Block pointed at Simulator.app

A simulator could be shown by the screen Block of the Sill note, capturing the Simulator app's window. The framebuffer route is better for this case on nearly every count the Sill note raised.

| | Window capture (Sill note, option 4) | Framebuffer (serve-sim) |
| --- | --- | --- |
| Grants on the Mac | Screen Recording and Accessibility, for a signed identity; the note's largest unknown | None expected (unverified, section 9) |
| A covered or minimized window | Freezes without a virtual display | No window is involved; a simulator booted with no Simulator.app still streams |
| Input | CGEvents that move the Mac's pointer and need the window in front | HID into the simulator; the Mac's pointer and focus are untouched |
| The person at the Mac | Shares the window with the stream | Can keep using Simulator.app or not have it open |
| Geometry | Window chrome and scale to crop | The device's own pixels, with its size and orientation reported |
| Linux Host | No capturer | Android emulators, through serve-emu |
| What it depends on | Public ScreenCaptureKit, plus a private API for the virtual display | Private CoreSimulator and SimulatorKit, which moved in Xcode 27 |
| Reach | Any window | Simulators and emulators only |

The last two rows are the cost. The mechanism is private and belongs to Apple's tooling, so it breaks when Xcode changes, and the fix arrives in Expo's package, not in weave. And it shows nothing but simulated devices. The two Blocks answer different needs, and the Sill note's first case, "the thing the agent is building, where it runs: an iOS Simulator", is this one.

### 11.2 What carries over from T3 Code

- **The split.** A stream for the person and a command line for the agent, joined only by naming the same simulated device. Weave's terminal tools already have this shape: the Block shows what the tool acts on.
- **The hub as a supervised child.** It is the holder's pattern again (ADR 0022): a separate process, so a crash in the native addon doesn't take the Host down. Unlike a holder it should end with the Host or soon after; nothing is lost when it stops, since the simulator keeps running.
- **Loopback only, behind an allowlist.** T3 Code's reasons hold for weave unchanged: the hub has a shell route. The Host would never offer the hub's port, only a stream of its own that reaches the allowlisted routes.
- **The wire formats, as they are.** `/stream.avcc` is a byte stream of length-prefixed chunks with a one-byte tag, and the input socket is messages of a tag byte and JSON. Both fit a carried stream's "a kind byte and a payload" with almost no translation: the Host reads the HTTP body and sends each chunk as a binary frame; the page sends input frames back the other way.
- **The viewer.** `stream.ts` is MIT, has no framework in it, already runs in a web view on T3 Code's mobile app, and already handles the seed frame, decoder recovery and reconnecting for a keyframe. It can be read as a design or adapted with attribution.
- **H.264 lowers the floor.** The Sill note needed HEVC, which Apple's notes put at iOS 17.4. serve-sim sends H.264, which the same notes put at 16.4. The app's minimum is still 15, so the Block still needs a floor of its own.
- **Resync by reconnecting.** A new AVCC subscription gets the parameter sets, a seed picture and a fresh keyframe. That is a ready-made answer to "the device fell behind": the Host drops the device's stream to the hub and opens another, which is Sill's "drop, then ask for a keyframe" without an encoder of weave's own to ask.
- **Instructions in the tool result.** Returning how to drive the simulator from the tool that opens it, with the launcher's absolute path, keeps it out of every other thread and needs no change to how agents are launched. T3 Code also prepends a directory to the agent's `PATH`; the returned path makes that unnecessary, and weave's agents keep their own environment.
- **Stop when nobody looks.** Only the visible view streams. For weave: no hub connection for a Block that no attached device is showing.

### 11.3 What has to differ

- **No SSH hosts.** T3 Code needs them because its server may not be on the Mac. In weave the computer with the simulators runs a Host, and a Session is "one directory on one Host". A simulator is something on the Session's Host, as a terminal is. `hostId` disappears from the tools, as `host` is absent from the terminal tools.
- **The path.** T3 Code's client talks to its server directly. A weave device's frames cross the Host's connection to the Dispatcher, the Dispatcher's to the device, and the core's loopback WebSocket, as the Sill note's 11.3 describes; 6 Mbps is modest beside that note's presets, but the same warning about loss on either leg applies. WebRTC, which the hub also offers, would need a path the Dispatcher doesn't carry.
- **A third stream kind**, beside `host` and `terminal`, with a ticket as `terminals/attach` gives. The same kind could later carry a screen Block, which is the argument for settling its shape on the simpler case.
- **Node on the Host's computer.** The hub and agent-device are Node programs with native parts. The Host is a Rust binary with no such dependency today. T3 Code installs them from npm at exact pins into its own directory on first use, after consent. Weave would need the same: a pinned install outside the repository, an explicit step by the person, and a Host that says it can't serve the Block when Node, Xcode or the SDK is missing.
- **Trust.** Installing and running a package that loads private frameworks is a larger grant than anything the Host does now. T3 Code gates it behind two consents (the hub, then agent access); weave's equivalent is config the person sets, off by default.
- **What closing means.** A terminal ends with its Block. T3 Code leaves a simulator running when its tab closes, because "the user owns those". For weave the nearer reading is that the Block's thing is the *view and the agent's session* on the simulator, which end, while the simulator itself is the computer's, as a file is. That is a small addition to `CONTEXT.md`'s Block entry and should be decided with the person, not assumed.
- **Several devices, one layout.** An iPad and an iPhone may show the same Block. Each would hold its own stream to the hub, which supports several viewers. Input from two devices interleaves; nothing in the hub arbitrates, and for one person that is probably acceptable.
- **The person and the agent at once.** Both can touch the simulator. agent-device has a human-control hold that T3 Code doesn't appear to use. Whether weave wants it depends on how often the two collide in practice.
- **The permission policy.** An agent driving through `agent-device` runs shell commands, which the thread's policy already sees. That is stricter than `write_terminal`, which the policy doesn't check, and needs nothing new.

### 11.4 The Host's tools

Following WVE-233's shape, Session-scoped and few:

- `list_devices`: the simulators and emulators on this Host, which are booted, and which have a Block in the caller's Session.
- `open_device`: boot if needed, give it a Block in the caller's Session (so the person sees it on every device), and answer with the launcher's path and the short driving instructions.
- `device_screenshot`: a PNG, for an agent that only wants to look.
- `close_device`: close the Block and the agent's session; power off only when asked.

Driving stays in `agent-device`. Wrapping its commands as Host tools would copy a surface that changes weekly; exposing its own MCP server (`agent-device mcp`) to the agent is the alternative if a command line proves awkward for some agent. Either way the Host branches on nothing about which agent is connected.

## 12. Options, smallest first

1. **Agents use `agent-device` today, with nothing built.** It is a standalone MIT command line. An agent in a weave thread can install and run it now, and the person watches in Simulator.app at the Mac. *Open:* whether that is already enough for weave's own app, and how well snapshots work on a Tauri web view's accessibility tree.
2. **Tools without a Block.** The Host installs agent-device at a pin and offers `list_devices`, `open_device` and `device_screenshot`. Screenshots reach the agent; the person sees stills in the thread. No stream, no hub, no page work. *Risk:* the Node dependency and the consent step arrive here already.
3. **A Block of stills.** The Block shows `device_screenshot` refreshed every second or two, as the Sill note's option 2. No codec. *Risk:* it reads as broken for anything that moves, and it doesn't prove the stream.
4. **A device Block on a Mac Host.** The hub as a supervised child on loopback; a third carried stream kind passing AVCC chunks down and input frames up; a WebCodecs viewer in the page adapted from T3 Code's; the tools of 11.4. iOS simulators first. *Risks:* the hub from a launchd agent, the Xcode coupling, the path through the Dispatcher, WebCodecs in the web view. *Open:* everything in "What to measure".
5. **Android**, on the Mac and then on the Linux Host: serve-emu's socket instead of the AVCC response, ffmpeg on the computer, the same viewer's second parser. Only if the person builds for Android.
6. **The screen Block of the Sill note**, on the stream kind, viewer and input framing that option 4 settled, with capture as its own remaining problem.

Options 2 and 4 are the ones that change what weave can do. Option 4 is also the Sill note's option 4 with its hardest part removed, so doing it first would answer that note's questions about decoding in the page and the carried path before any capture code is written.

### What to measure before deciding

- **The hub from the Host.** Start `expo-device-hub` at T3 Code's pin as a child of the installed Host (a launchd agent), open one booted simulator, and see whether frames arrive with no permission prompt. Repeat after `scripts/update-hosts --here`.
- **Xcode.** This Mac has Xcode 27.0; the hub's support statement names 26 and 27. Confirm the pinned release works here, and note what a point release of Xcode breaks.
- **Cost.** CPU and GPU of the hub process with one viewer, on a still screen and on a scrolling one, from its own `/metrics`; and the simulator's frame rate with and without a viewer.
- **Decode in the page.** `VideoDecoder.isConfigSupported` for `avc1` in the app on the Mac, iPad and iPhone, whether the page is a secure context there, and time from a chunk's arrival to the canvas. A recorded AVCC response is enough input.
- **The path.** Latency from a tap on the iPad to the changed frame, through the Dispatcher, at home and away; and whether reconnecting for a keyframe recovers cleanly when the device falls behind.
- **Two viewers.** The iPad and the iPhone on one simulator: whether one's reconnect stalls the other.
- **Snapshots of weave's app.** Whether `agent-device snapshot -i` on the weave app in a simulator yields refs an agent can use, given that most of its UI is inside a web view.
- **Contention.** The Sill note's last measurement, from this side: a simulator's stream while something else on the Mac encodes.
