# T3 Code's linked environments and weave's peer Hosts

Research snapshot, 2026-10-30. Primary sources only. Repositories were read at these commits: `pingdotgg/t3code` [`ae521d1d`](https://github.com/pingdotgg/t3code/tree/ae521d1d796c4e21abb49e44d27c23332d1898b9) (`main`, 2026-10-30, newer than the `32ecd717` that [T3 Code and the weave Host](t3code-and-the-weave-host.md) read; linked environments first shipped in [v0.1.4](https://github.com/pingdotgg/t3code/releases/tag/v0.1.4), 2026-10-29). Pull requests, issues, a discussion and releases were read through `gh` on 2026-10-30. Nothing from T3 Code was installed, built or run; its clone is untrusted data and was only read. Sections 1–9 are facts about T3 Code and their sources; section 10 judges them against ADR 0017 and the decisions in WVE-109, and every weave line reference is at `716102fa`.

WVE-109 asks what T3 Code's Orchestrator V2 does when one server reaches threads on another. T3 calls the feature *linked environments*; a *peer link*, or *link*, is the record one server keeps of another it signed in to. [The earlier note](t3code-and-the-weave-host.md) covers T3's server, its WebSocket API, its MCP endpoint, its pairing of devices and its vocabulary; this note doesn't repeat them. As there, T3's *environment* is its server, the counterpart of a weave Host, and its *provider* is weave's agent. **A** is the server that links and whose agents reach out, **B** the server it links to, as T3's own tests have a "laptop" and a "box". Otherwise this note uses weave's words (thread, Host, peer Host, paired device, pending request) except when it quotes T3.

## 1. What a link is, and how it came about

### 1.1 In brief

- **A signs in to B's MCP endpoint as an outside agent.** "The linking environment signs in to the other's `/mcp` as an outside MCP client, with a pairing code from it, and keeps that session's token in its own secret store. The other environment needs nothing new: it sees one more OAuth client, lists it in Sharing & access, and revokes it there. Unlinking on the linking side only forgets the token" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L70-L77)). A's agents then use B through the same MCP tools they use at home, by passing `environmentId` ([L86-L92](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L86-L92)).
- **The rules are written down in one place**, the "Peer links" section of the internals doc ([L70-L140](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L70-L140)), and for users in "Link another environment" ([remote access](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/user/remote-access.md?plain=1#L271-L312)).
- **A beta, off by default**, on both ends: `linkedEnvironmentsEnabled` defaults to false ([`settings.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/settings.ts#L1261)). Off on A, new links and calls that name another server are refused, but reads, waits and interrupts of a task already running there go on; off on B, link registrations are refused and link sessions get a 403, which A treats as retryable ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L79-L85)).

### 1.2 Designs tried first

- **A delegation session over the WebSocket RPC.** Discussion [#15819](https://github.com/pingdotgg/t3code/discussions/15819) (2026-10-05) proposed peers stored on A, a `delegation` session kind on B with a runtime-mode ceiling, and a bridge that launches over `orchestration.launchThread` and follows over `subscribeThread`. It ruled out the MCP route because its OAuth "needs a browser on a loopback redirect, which a headless server can't complete, and its `mcp-client` sessions can't use the WebSocket RPC".
- **Peer grants with their own API.** Theo's [#15966](https://github.com/pingdotgg/t3code/pull/15966) (2026-10-05): an admin on B creates a grant naming projects, the broadest modes and whether setup scripts may run; B stores a hash of its secret; A calls `/api/peer/v1/*` over HTTP through `t3_peer_*` tools; launches name a branch and full commit; "Grants never expire"; peer work may not "reach a third machine". Julius closed it the next day: "I'm doing this one properly" ([comment](https://github.com/pingdotgg/t3code/pull/15966#issuecomment-6019824086)).
- **The client carries the call.** Community PR [#15904](https://github.com/pingdotgg/t3code/pull/15904): "Environments still never talk to each other and no credential is stored"; a client connected to both runs the call over its own session, and it works "only while an app connected to both environments is open". Closed; Julius: "it's being implemented here: #16653-#17130" ([comment](https://github.com/pingdotgg/t3code/pull/15904#issuecomment-6388707822)).

### 1.3 What shipped

Nine pull requests by Julius Marminge, opened 2026-10-07 and 08 and all merged 2026-10-27: [#16653](https://github.com/pingdotgg/t3code/pull/16653) (B's `/mcp` narrows an OAuth client by a `T3-Mode-Limit` header), [#16654](https://github.com/pingdotgg/t3code/pull/16654) (`t3_thread_launch` takes a retry key), [#16655](https://github.com/pingdotgg/t3code/pull/16655) (linking), [#16684](https://github.com/pingdotgg/t3code/pull/16684) (agents use links through any T3 tool), [#16695](https://github.com/pingdotgg/t3code/pull/16695) (work a link starts stays within it), [#16698](https://github.com/pingdotgg/t3code/pull/16698) (clients), [#16719](https://github.com/pingdotgg/t3code/pull/16719) (`delegate_task` to a linked server), [#17129](https://github.com/pingdotgg/t3code/pull/17129) (an agent asks the person to link a machine) and [#17130](https://github.com/pingdotgg/t3code/pull/17130) (`@`-mentioning a machine; the Labs beta). They are listed in the [v0.1.4 notes](https://github.com/pingdotgg/t3code/releases/tag/v0.1.4). The server code is `apps/server/src/peer/` (2,376 lines, with 3,948 lines of tests and a 188-line test kit), with `mcp/linkOrigin.ts` and two migrations ([`070_PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/persistence/Migrations/070_PeerLinks.ts#L7-L23), [`071_PeerLinkFence.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/persistence/Migrations/071_PeerLinkFence.ts#L7-L11)).

## 2. Pairing and identity

- **Three ways to link, all from A.** `t3 environment link <url> --pairing-code <code> --access <mode>`, with `--access` defaulting to `approval-required` ([`environment.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/cli/environment.ts#L78-L117)); Settings → Linked environments → Link in a client; or an agent's `t3_environment_link`, which puts a card in its thread for the person to answer (section 5). The commands read A's database and secret store directly, "whether or not its server is running" ([L22-L25](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/cli/environment.ts#L22-L25)).
- **The code comes from B.** It is an ordinary one-time pairing code from `t3 pair` or B's Sharing & access ([remote access](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/user/remote-access.md?plain=1#L283-L289)), five minutes by default ([`PairingGrantStore.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/PairingGrantStore.ts#L251)), and must carry every scope the chosen access needs ([`EnvironmentAuth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/EnvironmentAuth.ts#L1346-L1363)). A client the person has connected to B with a session that may manage access mints the code there itself, so linking is one click ([`peerPairingCode.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/client-runtime/src/state/peerPairingCode.ts#L1-L5), [L37-L57](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/client-runtime/src/state/peerPairingCode.ts#L37-L57)).
- **A runs B's MCP OAuth flow headless.** It registers a public client with B under the software id `t3code-peer-link` and a loopback redirect that "Nothing ever listens" on, posts an approval decision carrying the pairing code and the access, then exchanges the code with PKCE ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L36-L37), [L226-L316](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L226-L316)). B's client registration is stateless: the client id is B's signature over the name, redirects and a peer-link flag ([`McpOAuth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/McpOAuth.ts#L255-L260), [L303-L340](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/McpOAuth.ts#L303-L340)). This answered #15819's objection without a new endpoint on B: "B needs no new endpoint" ([#16655](https://github.com/pingdotgg/t3code/pull/16655)).
- **The credential is a bearer token for 30 days, with no renewal.** B issues a session with subject `mcp-client`, method `bearer-access-token` and a 30-day lifetime ([`EnvironmentAuth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/EnvironmentAuth.ts#L72-L73), [L1309-L1328](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/EnvironmentAuth.ts#L1309-L1328)) and answers `token_type: "Bearer"` ([`McpOAuth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/McpOAuth.ts#L518-L539)). Only the `authorization_code` grant exists ([L484-L486](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/McpOAuth.ts#L484-L486)): "Links last as long as B's `mcp-client` session: 30 days, with no renewal yet" ([#16655](https://github.com/pingdotgg/t3code/pull/16655)); "Link again with a new pairing code to renew one" ([remote access](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/user/remote-access.md?plain=1#L305)). Neither server holds a key pair for the link.
- **Where each side keeps it.** A writes the token to its server secret store under a random name, then a row in `peer_environment_links` naming it ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L441-L478)); the store is one file per secret, mode 0600 in a 0700 directory ([`ServerSecretStore.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/ServerSecretStore.ts#L160-L171), [L203-L205](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/ServerSecretStore.ts#L203-L205)). The row holds B's id, label, addresses, the access, expiry, and when B last answered and its last error ([`peerLink.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/peerLink.ts#L6-L22)). B keeps an ordinary auth session, labelled `T3 Code · <A's label>` ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L429)).
- **How each side knows the other.** A knows B by its environment id, a random UUID B generates once ([`ServerEnvironment.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/environment/ServerEnvironment.ts#L162)) and reports at the unauthenticated `/.well-known/t3/environment`; before every call A sends the token only to an address whose descriptor reports that id, "so a reused LAN address or a moved hostname never receives it" ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L559-L576)), and follows no redirects ([L180-L184](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L180-L184)). B never learns A's environment id at pairing: it sees a public client with A's label and the peer-link flag, signed into the session ([`McpOAuth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/auth/McpOAuth.ts#L555-L598)). Claiming the flag "only ever adds limits" ([`auth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/auth.ts#L447-L452)).
- **Encryption is the transport's.** A refuses plain `http://` unless the address is loopback or a tailnet name (`*.ts.net` or Tailscale's IPv6 range; numeric `100.x` addresses don't count), because "The pairing code and then the link's token travel to it" ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L128-L156), [`hostClassification.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/shared/src/hostClassification.ts#L83-L88)). HTTPS can be Tailscale Serve or T3's hosted relay, T3 Connect.
- **Checks before linking.** A refuses itself, and a B that doesn't advertise both `mcpModeLimitHeader` and `linkFence`, since such a B couldn't hold A's agents to their limits ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L416-L428), [`environment.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/environment.ts#L144-L155)). A link stored before fencing existed counts as expired and must be made again ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L206-L208)).
- **Revoking happens on B; forgetting on A.** "The link shows up in that machine's Settings → Sharing & access like any outside agent. Revoke it there to end it. Forget on this machine only removes it here" ([remote access](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/user/remote-access.md?plain=1#L302-L304)). After a revoke, A's next call gets a 401 and tells the agent "It may have been revoked there; link it again" ([`PeerMcpClient.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L186-L192)). The agent tool `t3_environment_unlink` forgets a link on A too (section 5).
- **One way.** A link lets A's agents reach B and nothing back. A person who wants both directions links twice; issue [#26772](https://github.com/pingdotgg/t3code/issues/26772) describes two Macs "linked to each other … (M1 → M4 and M4 → M1)".

## 3. Transport and connection lifetime

- **MCP over HTTP, not the client WebSocket.** A posts JSON-RPC to B's `/mcp` with `Authorization: Bearer`, as MCP protocol version `2025-06-18`, `initialize` then `tools/call` ([`PeerMcpClient.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L20-L21), [L103-L153](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L103-L153)). B accepts `mcp-client` sessions only on `/mcp`: "Every other HTTP and WebSocket path rejects that subject, because the RPC surface would let the agent act above its ceiling" ([environment auth](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/environment-auth.md?plain=1#L55-L66)). So A cannot subscribe to B's thread streams; it has only request and response.
- **No standing connection.** Each call first resolves the link: checks expiry, reads the token, and probes the stored addresses in order until one answers as B, waiting up to 3 s on loopback and 10 s elsewhere ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L42-L43), [L536-L587](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L536-L587)). A keeps one MCP session id per peer and address in memory; "The peer keeps sessions in memory, so a restart there answers 404 and we start a new one" ([`PeerMcpClient.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L99-L101), [L176-L185](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L176-L185)). Every outcome is recorded on the link's row for listing ([L240-L256](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L240-L256)).
- **Waiting is a held request, cut into pieces.** B's `/mcp` "sends nothing while a wait is open and T3 Connect's edge drops idle requests after about 100 s", so A splits a `t3_thread_wait` into calls of at most 50 s, the later ones pinned to the run the first found ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L103-L105), [`PeerForwarding.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.ts#L28-L35), [L182-L212](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.ts#L182-L212)).
- **Resuming is retrying.** There is no stream to resume. Retries are made safe by keys: "All callers on one side share the link's single session on the other, so idempotency keys are hashed with the caller's namespace before they leave" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L100-L102), [`PeerForwarding.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.ts#L114-L123)), and `t3_thread_launch` replays a launch with the same key ([#16654](https://github.com/pingdotgg/t3code/pull/16654)). The only long-lived work is A's follower of each delegated task, which outlives A's restarts (section 7).

## 4. What a link may do on B

- **MCP tools only.** As above, a link session reaches `/mcp` and nothing else: no terminals, files, Git, settings RPC or thread streams. B's paired devices, by contrast, get by default a grant that "includes access and relay management" and terminals, because `terminal:operate` "is a shell as the server's user" and either it or `orchestration:operate` "can mint a session with every scope" ([environment auth](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/environment-auth.md?plain=1#L9-L17)).
- **An access level chosen at linking.** One of `read-only`, `approval-required`, `auto-accept-edits`, `auto` or `full-access` ([`auth.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/auth.ts#L402-L422)). "The user grants either read-only access or a runtime-mode ceiling, not a scope list: MCP tools are all orchestration, and `orchestration:operate` alone would let an agent start a thread in full access and act through it" ([environment auth](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/environment-auth.md?plain=1#L55-L62)). Read-only passes only tools declared as reads; the rest hold the ceiling in the session.
- **Narrowed per call to the calling agent's modes.** Every forwarded call carries `T3-Mode-Limit: <runtimeMode>/<interactionMode>`, the calling thread's own modes on A ([`PeerMcpClient.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L155-L162)), which B "only ever narrows the client's approved access with. A plan-mode agent therefore cannot start full-access work through a full-access link" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L93-L96), [`McpInvocationContext.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/McpInvocationContext.ts#L52-L97), [`McpHttpServer.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/McpHttpServer.ts#L173-L184)). T3's modes are ordered, so the narrower of two is defined.
- **Fenced below full access.** B stamps every thread a link session launches with an immutable `linkOrigin {sessionId, label, access}`, carried to its subagents, forks and the threads it creates ([`orchestrationV2.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/orchestrationV2.ts#L108-L128)). Below full access, that work "may change only threads with the same origin, not the user's own threads and not another link's"; it "cannot change projects, settings or scheduled tasks, nor use the receiving environment's own links"; its setup scripts are skipped; "Reads are not fenced" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L107-L125), [`linkOrigin.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/linkOrigin.ts#L11-L60)).
- **Not fenced at full access.** "The link is routing, not isolation: an agent the link starts runs as the receiving environment's user. A full-access link is therefore not fenced: its agents can already do anything that user can, so the fence would only stop T3's own tools" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L136-L140)). The fence first covered every link; [#16695](https://github.com/pingdotgg/t3code/pull/16695) exempted full access because it "kept a host from driving machines it fully trusts: answering a question or steering a thread the user started there". A test confirms a full-access link may rename the person's own thread on B and update a project ([`linkOrigin.test.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/linkOrigin.test.ts#L384-L408)).
- **A refuses first.** Each tool's access declaration checks the caller on A before anything leaves, "so a read-only or ended caller is refused before anything is sent"; the thread or project named "is checked where it lives" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L86-L92)).

| | Paired device (client) | Link session (peer) |
| --- | --- | --- |
| Credential | Bearer or DPoP session from a pairing code ([earlier note](t3code-and-the-weave-host.md)) | Bearer `mcp-client` session, 30 days |
| Surface | WebSocket RPC, HTTP, `/mcp` | `/mcp` only |
| Limit | Scopes; default grant includes managing access | Access level, narrowed per call by the caller's modes |
| Work it starts | Unmarked | `linkOrigin`; fenced below full access |
| Revoked | On B | On B; A only forgets |

## 5. Tools for agents

- **One optional parameter, routed in one place.** About 48 tools take an optional `environmentId`, "Linked environment to act in. Omit for this one" ([#16684](https://github.com/pingdotgg/t3code/pull/16684), [`orchestratorMcp.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/orchestratorMcp.ts#L318-L328)): threads (launch, send, wait, read, interrupt, update, configure, transfer, organize, search), queues, pending questions, projects, scheduled tasks, pull requests, worktree refs and preferences. A tool forwards because its parameters have that field; `McpToolAccess.toLayer` sends the call on after checking the caller, the local handler never sees `environmentId`, and a tool that "acts as its calling thread" fails to build if it takes one ([`McpToolAccess.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/McpToolAccess.ts#L353-L409)). Naming A's own id runs the call on A.
- **Three link tools.** `t3_environment_links` lists links with status (`reachable`, `unreachable`, `expired`), access, expiry and last error, plus a `notListed` line telling the agent to ask for a link rather than "look elsewhere"; `t3_environment_link` asks the person with a card; `t3_environment_unlink` forgets one ([`tools.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/toolkits/orchestrator/tools.ts#L308-L348), [`PeerForwarding.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.ts#L234-L262)). Linking and unlinking are "an environment setting: full access, and never for linked work" ([`handlers.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/toolkits/orchestrator/handlers.ts#L194-L216)).
- **Asking to link.** `t3_environment_link` returns `pending` at once, because "provider CLIs abandon a long tool call"; the person picks the machine and access in the card, their client sends the pairing code straight to A, and "the answer reaches the agent as a notification" in its thread, never the code ([`PeerLinkRequests.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinkRequests.ts#L1-L6), [L377-L417](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinkRequests.ts#L377-L417)).
- **The tool list doesn't follow the peers.** `environmentId` is in the schemas whether or not any link exists; [#17130](https://github.com/pingdotgg/t3code/pull/17130) measured "about 100 tokens of instructions and 760 tokens of tool schemas, mostly the optional `environmentId`" with the beta off. Only the three link tools are hidden, per request, while the beta is off ([`McpInvocationContext.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/McpInvocationContext.ts#L140-L145)). The server sends no `tools/list_changed` (no match in `apps/server/src`), so an agent session started before the beta was turned on doesn't see them until it restarts ([#26722](https://github.com/pingdotgg/t3code/issues/26722)).
- **An unreachable peer fails the call.** `resolve` fails with "`<label>` did not answer at `<addresses>`", which the agent hears as an `orchestration_error`; a revoked or expired link is `capability_denied`; an unknown id is `invalid_request` and no token is sent ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L536-L576), [`PeerMcpClient.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerMcpClient.ts#L67-L77)). "At once" means after the address probes time out, up to 10 s each. Delegated tasks already running are retried instead (section 7).
- **Listing says `reachable` when the address answers, not when the token works.** `statusOf` probes only the unauthenticated descriptor ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L488-L501)), so a revoked link lists as reachable ([#26772](https://github.com/pingdotgg/t3code/issues/26772)).

## 6. Hops

- **One call can't chain.** A strips `environmentId` from the arguments it forwards, so the call runs on B itself ([`PeerForwarding.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.ts#L126-L156)).
- **Fenced work can't use B's links.** Before forwarding, B (as the next A) checks its caller: "Work a link started never uses this environment's links, since the peer would see this environment's session instead of that link, and its fence could not hold" ([`PeerForwarding.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.ts#L100-L112)). A test shows read, send and launch refused with no token reaching the third server ([`PeerForwarding.test.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerForwarding.test.ts#L669-L686)); [#16695](https://github.com/pingdotgg/t3code/pull/16695) calls it "No third environment below full access".
- **Full-access work can.** The check is `assertNotLinked`, which fails only for a fencing origin, and a full-access origin isn't one ([`linkOrigin.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/linkOrigin.ts#L31-L60), [`orchestrationV2.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/orchestrationV2.ts#L121-L128)). Read from the code, a thread a full-access link starts on B may use B's links to C; no test of that case was found, and no document says so. B's own threads, which a full-access link may prompt, use B's links in any case. Clients expect chains: the parent's "waiting" flag is computed so that "Each pass settles one more hop of a chain; flags only grow, so environments delegating to each other settle too" ([`threadShell.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/client-runtime/src/state/threadShell.ts#L232-L279)).
- Theo's closed #15966 had refused a third machine for all peer work (1.2).

## 7. Authority

### 7.1 Where the thread runs, and who answers its pending requests

- **On B, as one of B's threads.** "Its child is then an ordinary thread there" ([remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L127-L134)), run by B's provider, as B's user (L136-L137). A remote `delegate_task` runs in the project on B with the same repository identity as the parent's, or the one `target.projectId` names, and in that project's checkout: "isolation `worktree` is not supported there", since a worktree "would branch from a commit this checkout has and the other may not" ([`RemoteDelegation.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L140-L185), [L212-L221](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L212-L221)). Provider and model are inherited from the parent unless named; modes the caller omits are left to B, which caps the parent's at the link's access ([L222-L249](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L222-L249)).
- **Pending requests stay on B, and only B's clients see them.** A's server records nothing of them: the reporter of [#26527](https://github.com/pingdotgg/t3code/issues/26527) found that `delegate_task` and `task_status` report `hasPendingQuestion: false` and `pendingApproval: null`, "so the `wait` call runs until it times out. The task only moves on if someone opens the box and answers there." A client connected to both servers does flag the parent, since it joins the two itself ([`threadShell.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/client-runtime/src/state/threadShell.ts#L232-L279), [`ThreadNotificationCoordinator.tsx`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/web/src/components/ThreadNotificationCoordinator.tsx#L177-L181)).
- **A proposal to relay answers was closed.** [#26344](https://github.com/pingdotgg/t3code/pull/26344) mirrored B's pending requests onto the parent through a link-only `t3_link_requests` tool and relayed answers given on A back over the link, under the link's access. It was closed unmerged on 2026-10-30 so that maintainers first "establish remote question/approval forwarding and its authority, parent lifecycle and failure behavior" ([comment](https://github.com/pingdotgg/t3code/pull/26344#issuecomment-6523371800)).
- **Agents may answer questions, not approvals.** `t3_pending_request` "cannot approve a permission request", and it takes `environmentId`, so A's agent can answer a user-input question on B within the link's limits ([`tools.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/toolkits/thread/tools.ts#L127-L145)).

### 7.2 The ceiling

The link's access is the most B allows; `T3-Mode-Limit` narrows it to the calling thread's modes on every call; A checks the request against its own thread first (section 4). B also refuses to send into a thread running with broader modes than the caller's: `t3_thread_send` says "The target cannot run with broader modes than yours" ([`tools.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/toolkits/orchestrator/tools.ts#L269-L280)). Refusals keep B's error code, but the message names the "parent mode" even when the limit is the link's, which misleads agents ([#27317](https://github.com/pingdotgg/t3code/issues/27317)).

### 7.3 Origin, and how clients show it

- **Two marks.** `linkOrigin` is set by B from the authenticated session (section 4). `delegatedFrom {environmentId, threadId, title}` names A's thread; A puts it in the launch's arguments, and B keeps it only on a launch that carries a `linkOrigin`: "Only stamped work names a remote parent, so a client cannot claim one" ([`orchestrationV2.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/contracts/src/orchestrationV2.ts#L130-L139), [`Orchestrator.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/orchestration-v2/Orchestrator.ts#L2643-L2647), [`ThreadManagementService.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/orchestration-v2/ThreadManagementService.ts#L81-L84)). B doesn't check `delegatedFrom` against the link, and `t3_thread_launch` exposes the field to agents ("Set by a linked environment launching its agent's delegated task here", [`tools.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/mcp/toolkits/project/tools.ts#L151-L152)); an agent that filled it in itself made its thread vanish from A's lists ([#27004](https://github.com/pingdotgg/t3code/issues/27004)).
- **On B's thread** clients show "From" and A's name ([remote access](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/user/remote-access.md?plain=1#L297)), and "Subagent of `<parent>` on `<environment>`" with "Open parent thread" when the client is connected to A ([`ChatView.tsx`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/web/src/components/ChatView.tsx#L860-L885), [#16719](https://github.com/pingdotgg/t3code/pull/16719)).
- **On A's parent** a task card and a Lineage row say "on box" and open B's thread when the client knows B. A client connected to both lists B's thread under its parent rather than on its own; "A child whose parent the client can't list (that machine switched off, or the parent gone) stays listed on its own, so its work is never out of reach" ([#16719](https://github.com/pingdotgg/t3code/pull/16719), [`threadShell.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/client-runtime/src/state/threadShell.ts#L521-L547)).
- **Thread links name their server.** Agents cite threads as `t3-thread://v2/<environmentId>/<threadId>`, built by the server that owns the thread, "so forwarded results and tasks delegated to a linked environment name that environment" ([orchestrator MCP](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/orchestration-v2/orchestrator-mcp-server.md?plain=1#L393-L404)).

### 7.4 How completion gets back

- **A pulls; B never calls A.** For a remote `delegate_task`, A launches B's thread, records the task on the parent with `remoteChild {environmentId, threadId, label, runId}` instead of a local child, and starts a follower ([`RemoteDelegation.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L256-L353)). The follower waits on B's run (in 50 s pieces, up to 10 minutes a round), reads the run's last reply in full, and completes the task with an internal command that "reuses the parent half of a local finalize, so the parent wakes the same way" ([L537-L640](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L537-L640), [remote internals](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/docs/internals/remote.md?plain=1#L127-L134)). The first result wins.
- **Across drops and restarts.** A revoked, expired or forgotten link, or a thread or run gone on B, fails the task with the reason; anything else ("the other machine asleep, a dropped route") is retried, backing off to five minutes ([L44-L59](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L44-L59), [L101-L114](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L101-L114), [L514-L530](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L514-L530)). At startup A follows every open remote task again, which also keeps restart recovery from treating them as abandoned ([L762-L786](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L762-L786)).
- **Cancelling.** `task_cancel` and the parent's Stop stop B's whole thread (its turn, queue and its own tasks). With B unreachable the task is still cancelled on A, with "It could not be stopped in `<label>` and may still run there", and the follower keeps sending the stop, across restarts, until it lands ([L689-L760](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/RemoteDelegation.ts#L689-L760)).
- **A known gap: launch before record.** B's thread starts before A records the task, so if A dies or loses the answer in between, "the thread there keeps running with no task here to follow, stop, or report it"; recording first is designed but open ([#17051](https://github.com/pingdotgg/t3code/issues/17051)).
- **Only `delegate_task` reports back.** A thread started on B with `t3_thread_launch`, or a follow-up sent with `t3_thread_send`, tells A's thread nothing when it ends ([#26740](https://github.com/pingdotgg/t3code/issues/26740), [#27004](https://github.com/pingdotgg/t3code/issues/27004)); for plain messages between servers that is intended: "Ordinary cross-environment messages are intentionally plain messages with no delegation lineage" ([comment on #18675](https://github.com/pingdotgg/t3code/issues/18675#issuecomment-6126506567)).

## 8. Discovery

- **No network discovery.** No mDNS, Tailscale query or tag is used to find a peer: the server's `tailscale` package isn't used by `peer/`, and the only mDNS reference in the server is for editor targets (searched with `git grep` for `mdns`, `bonjour`, `zeroconf` and `PeerLink` in `packages/tailscale`).
- **The person's client knows the machines.** The link dialog and card list the machines the client has saved, with the addresses each reports itself bound to (`directEndpoints`, its LAN and tailnet addresses), then the client's saved routes, then machines on the person's T3 Connect account ([`linkRequest.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/packages/client-runtime/src/linkRequest.ts#L57-L142)). A tries them in order and keeps those that answer as the chosen machine ([`PeerLinks.ts`](https://github.com/pingdotgg/t3code/blob/ae521d1d796c4e21abb49e44d27c23332d1898b9/apps/server/src/peer/PeerLinks.ts#L343-L385)). From the CLI, the person types the URL.
- **Agents name machines by id.** Typing `@` and part of a machine's name inserts a chip carrying its id and label, "never an address" ([#17130](https://github.com/pingdotgg/t3code/pull/17130)).

## 9. Problems reported since it shipped

In the three days after the stack merged (2026-10-28 to 30, on nightlies and on v0.1.4 and v0.1.5), issues were filed on most of the edges above. Most are open, without a maintainer's answer.

- **Addresses.** Plain `http://` on a LAN, which device pairing accepts, is refused for links ([#26840](https://github.com/pingdotgg/t3code/issues/26840); [#27678](https://github.com/pingdotgg/t3code/issues/27678) closed as its duplicate, with a NetBird overlay in the same position, [comment](https://github.com/pingdotgg/t3code/issues/27678#issuecomment-6527608415)). Automatic linking picks a numeric Tailscale IPv4 address that its own check then rejects, and B advertises its loopback address, which on A answers as A ([#26450](https://github.com/pingdotgg/t3code/issues/26450)).
- **Revocation.** A link's session on B looks like any MCP client, is revoked with one click and no confirmation, and A goes on listing B as reachable; "Use this link" then accepts the revoked link as linked ([#26772](https://github.com/pingdotgg/t3code/issues/26772)).
- **Pending requests** never reach the parent ([#26527](https://github.com/pingdotgg/t3code/issues/26527), [#26818](https://github.com/pingdotgg/t3code/issues/26818); section 7.1). A link card can't even be declined from a client without access management ([#26952](https://github.com/pingdotgg/t3code/issues/26952)).
- **Reporting back** only for `delegate_task` ([#26740](https://github.com/pingdotgg/t3code/issues/26740), [#27004](https://github.com/pingdotgg/t3code/issues/27004)); a narrower thread can't send to the broader one that launched it ([#26293](https://github.com/pingdotgg/t3code/issues/26293)); deleting a parent leaves the child on B pointing at nothing ([#26766](https://github.com/pingdotgg/t3code/issues/26766)).
- **Tools and errors.** Agent sessions don't see the link tools until restarted ([#26722](https://github.com/pingdotgg/t3code/issues/26722)); a refusal for the link's access reads as the parent's mode ([#27317](https://github.com/pingdotgg/t3code/issues/27317)).
- **Migrations.** Private preview builds numbered the peer-link migrations 68–70 and main 70–72, so those databases crash-looped on upgrade; "Reconciled per machine instead" ([#25289](https://github.com/pingdotgg/t3code/issues/25289#issuecomment-6408529406); a related WSL report, [#26830](https://github.com/pingdotgg/t3code/issues/26830), is open).

## 10. Against weave's shape

WVE-109's decisions, from ADR 0017 and the issue: a Host's own P-256 key, in the Secure Enclave if it can be used; one-way pairing through a code from `weave pair` on B; A connects to B's Serve URL as a remote client and proves its key at `host/hello`, staying connected while its threads use B and reconnecting after its journal positions; a peer gets what a paired device gets, less administering the Host; the Host tools take an optional `host`, a tool lists peers and whether each can be reached, the tool list doesn't change, a call to an unreachable peer fails at once; one hop; B runs and journals the thread, applies its policy and holds its pending requests, which B's clients answer; the origin names A's Host and thread; B applies the ceiling A asks for; a client connected to both shows the thread on B with the thread on A that started it.

### 10.1 Side by side

| WVE-109 decision | T3 Code | Judgment |
| --- | --- | --- |
| Host key, P-256, Secure Enclave where possible | Bearer token, 30 days, file 0600; no key on either side; B's identity is a UUID at an address | Keep weave's. ADR 0010 rejected bearer tokens because "whoever copies a token is that device". T3's link also lapses after 30 days with no renewal, so the person links again every month. |
| One-way pairing through a code from B | One-way; ordinary pairing code from B, or minted by a client with access rights on B | Same shape. Client-minted codes need a client to administer B over the protocol, which ADR 0017 rules out. |
| A connects as a remote client over the Host protocol, at `host/hello` | A is an MCP client over HTTP to `/mcp`, refused on the client socket | Keep weave's. T3's choice cost it streaming (chunked 50 s waits), push of pending requests (#26527, and a closed relay PR that needed a new tool), and a polling follower per task. ADR 0017 already turned down Hosts speaking MCP to each other. |
| Device rights, less administration | Far less than a device: MCP tools only, an access level chosen at linking, narrowed per call, fenced below full access | T3 is evidence for WVE-109's third open question; see 10.3. |
| Optional `host` on the Host tools; a list tool; fixed tool list | Optional `environmentId` on about 48 tools, routed generically; `t3_environment_links`; fixed list | Same shape; borrow the details in 10.2. |
| Unreachable peer fails at once | Fails after address probes; running tasks retry with backoff | Same for calls. A Host with a live connection knows at once; one without should not wait on long probes. |
| One hop | Enforced only for links below full access; full-access work may chain | Keep weave's rule unconditional; T3's exemption shows where it leaks (10.2). |
| B runs, journals, holds pending requests; B's clients answer | Same; agents may answer questions but never approvals; relay of answers to A undecided | Same. T3's gap is that A never learns B waits; weave's connection carries B's journal, so it can. |
| Origin names A's Host and thread | `linkOrigin` stamped by B from the session; `delegatedFrom` taken from the launch arguments | Borrow the split, but have A's Host, not the agent, supply A's thread (10.2). |
| B applies A's ceiling | `T3-Mode-Limit` on every call, narrowing only; checked on A first and on B again | Same idea; weave's ceiling is a policy, so "within" is `PermissionPolicy::within` rather than an order of modes ([`host_tools.rs`](../../host/src/host_tools.rs#L172)). |
| A client connected to both shows the pair | Clients join the two: child nested under parent, "Subagent of … on …", parent flagged when the child waits; orphans listed alone | Borrow the presentation rules. |

### 10.2 What to borrow

- **Key retries per calling thread.** B sees all of A's threads as one client. T3 hashes each request key with the calling thread's namespace before it leaves, so two agents' keys don't collide and one agent's retry gets its first answer (3). weave's request keys are global to a Host, not per client ([`admissions.rs`](../../host/src/admissions.rs#L146-L175)), and `start_session` passes the agent's `key` through as it is ([`host_tools.rs`](../../host/src/host_tools.rs#L111-L121)); across a peer, A's Host should derive the key it sends from the calling thread and the agent's key.
- **Record before starting.** T3's open gap (#17051) is that B's thread starts before A records it, so a crash leaves work nobody follows. A's Host should journal in the calling thread that it is starting a thread on B, with the key, before it sends `session/run`, and on restart resend with the same key, which B answers as it did the first time.
- **Follow what A owes reports for, across A's restarts.** T3's followers are the most robust part of the feature: open remote tasks are followed again at startup, transient failures retried, final ones (revoked, gone) end the task with the reason, and a stop A owes B is kept until B takes it (7.4). WVE-109 says A "stays connected while one of its sessions uses B"; A should know which turns on B its threads began (ADR 0023's reports) from its own journals, so that after A restarts it reconnects and still reports how they ended.
- **Report every turn A's agents began on B, not only delegated ones.** T3's reports cover `delegate_task` only, and #26740, #27004 and #26293 are what is missing. ADR 0023 already says "The thread whose agent began a turn hears how it ends, or that it waits on a person"; across Hosts, A's Host has to produce that report from B's journal, since B can't reach A.
- **Tell the calling thread when B's turn waits on a person.** T3's parent waits until a timeout because A never sees B's pending requests (#26527). ADR 0020 already says the calling agent "is told that a delegated thread waits"; with B's journal arriving over A's connection, A can, and clients of A can show the waiting state on the parent as T3's do.
- **Stamp the origin from what is authenticated.** T3's `linkOrigin` comes from the session and can't be set by a client; its `delegatedFrom` comes from tool arguments and an agent misused it (#27004). In weave, B should take the origin's Host from the peer key that said hello, and A's Host, not the agent, should fill in the calling thread.
- **Carry the peer mark to derived threads, and enforce one hop with it.** T3 carries `linkOrigin` to subagents, forks and threads that work creates, and refuses fenced work the use of B's links (4, 6). B should refuse `host` to any thread a peer started, and to threads those threads start, with no exemption; T3's full-access exemption is where its one-hop rule lapses. WVE-109's acceptance test "A's agents can't reach B's own peers" should include a thread on B started by a thread A started.
- **One routing point for `host`.** T3 routes every tool that has the target field in one place, strips the field before the local handler, and refuses to build a tool that acts as its calling thread with it (5). For weave: tools such as `rename_session` and `clipboard_write` that act on the calling thread take no `host`.
- **`start_session` on a peer needs its own working directory.** weave's `start_session` defaults `cwd` to the calling thread's ([`host_tools.rs`](../../host/src/host_tools.rs#L175)), which on B is a path from A. T3 resolves the project on B by the repository's identity, or takes one named, and runs in that checkout, never a worktree it would have to branch from a commit B may lack (7.1). With `host`, `cwd` should be required, or resolved on B by the repository's remote.
- **Reachable means hello succeeds.** T3 lists a revoked link as reachable because it probes an unauthenticated descriptor (#26772). A's list of peers should report what the last `host/hello` answered, with a refusal distinct from an address that doesn't answer.
- **B lists peers apart from devices, and asks before revoking one.** T3's link sessions look like any MCP client in B's list and go with one click (#26772). WVE-109 already has B list A "as a peer Host beside its paired devices".
- **Name the limit that refused.** When B narrows or refuses for the ceiling, the tool error should say it came from the calling thread's policy on A, not from B's thread (#27317).
- **Store the MagicDNS URL.** T3 trips over numeric tailnet addresses and a peer's own loopback address (#26450). weave connects through Serve, so the Serve URL is the one address; it shouldn't take addresses B reports.

### 10.3 What not to borrow, or not yet

- **MCP between Hosts, bearer tokens, expiry.** Covered in 10.1.
- **Plain HTTP, LAN addresses and a hosted relay.** weave reaches Hosts through the tailnet only (ADR 0017).
- **Agents asking the person to pair a peer, with a client minting the code.** T3's card is careful (the code never enters the transcript, the answer arrives as a message), but minting a code on B from a client is remote administration, which ADR 0017 excludes, and an agent able to start pairing is an environment change T3 itself limits to full-access callers. `weave pair` on B, run there or over SSH, stays the way.
- **Agents answering questions on a peer.** T3 lets an agent answer another thread's questions but not its approvals. ADR 0020 has no agent answer another thread's pending requests; nothing in T3's experience argues for changing that.
- **Cancelling on A when B can't be reached.** T3 marks the task cancelled and keeps trying to stop it on B. WVE-109's "fails at once" is simpler and doesn't claim a stop that hasn't happened.

### 10.4 What should change in WVE-109

None of the decisions is contradicted. T3's experience argues for these additions:

1. **What a peer may do: less than a device.** T3 limits a peer to its orchestration tools, a ceiling chosen at pairing, and a narrowing per call, and its maintainers reasoned that a peer's credential would otherwise be a way around the ceiling (4). For WVE-109's third open question this suggests B gives a peer Host only the methods the Host tools project and those needed to follow threads (hello, the session and turn methods, `sessions/get`, observe), not terminals, worktrees or files. It is cheap to check at B and limits what a copied key file could do if the Secure Enclave proves unusable under launchd. A ceiling recorded at pairing, which B intersects with A's per-call ceiling, is a further option; T3 offers it, and its CLI defaults to `approval-required`.
2. **Durability on A.** Add to "Connecting": A journals a start on B before sending it, keys it per calling thread, and after its own restart reconnects to follow every turn on B its threads still owe a report for.
3. **One hop includes derived threads**, and holds whatever the ceiling.
4. **`host` makes `cwd` required**, or names how B resolves it.
5. **Listing reachability is the last hello's outcome.**

The second open question, discovery, gets no help from T3: it finds peers through the person's client and T3 Connect, never through the network (8).
