# ACP agent icons and Zed

_Research snapshot: 2026-08-24. Sources are pinned to the current upstream ACP, ACP Registry, and Zed `main` commits inspected on that date._

## Answer

**Stable ACP v1 does not specify an agent favicon, logo, avatar, or identity icon.** During `initialize`, an agent may return `agentInfo`, but its `Implementation` object has only `name`, optional `title`, `version`, and extensibility `_meta`; there is no standard icon field. ([ACP v1 `InitializeResponse.agentInfo`](https://github.com/agentclientprotocol/agent-client-protocol/blob/62c74ac119ec3296809496482440afca69926ce9/schema/v1/schema.json#L2380-L2390), [`Implementation`](https://github.com/agentclientprotocol/agent-client-protocol/blob/62c74ac119ec3296809496482440afca69926ce9/schema/v1/schema.json#L2808-L2832))

The icons shown for external agents in Zed are therefore **Zed-side installation metadata**, primarily supplied by the separate ACP Registry, not data sent by the running agent over ACP.

## Protocol versus registry

The ACP Registry is a separate distribution catalog. Its agent-entry schema has a top-level `icon: string`, described as an icon URL generated by the registry build from the required `<agent-id>/icon.svg`. Registry submissions require a 16×16, square, monochrome SVG using `currentColor`. ([registry agent schema](https://github.com/agentclientprotocol/registry/blob/d35478ce8311d13f11af06801cb850db117cb0d3/agent.schema.json#L50-L53), [registry contribution rules](https://github.com/agentclientprotocol/registry/blob/d35478ce8311d13f11af06801cb850db117cb0d3/CONTRIBUTING.md#L33-L39))

Draft ACP v2 does define an `Icon` object with `src`, optional `mimeType`, `sizes`, and `theme`, but it is currently attached to `ResourceLink.icons`. It is for linked-resource presentation, not agent identity: v2's agent `Implementation` still has only `name`, `title`, `version`, and `_meta`. ([v2 `ResourceLink.icons`](https://github.com/agentclientprotocol/agent-client-protocol/blob/62c74ac119ec3296809496482440afca69926ce9/schema/v2/schema.json#L1336-L1367), [v2 `Implementation`](https://github.com/agentclientprotocol/agent-client-protocol/blob/62c74ac119ec3296809496482440afca69926ce9/schema/v2/schema.json#L3092-L3116))

An implementation could place proprietary icon metadata under `_meta`, but ACP assigns no interoperable meaning to it. A client such as Zed would have to explicitly implement the same private convention.

## What Zed does

Zed fetches `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`, deserializes each registry entry's optional `icon`, downloads it, caches it as `<agent-id>.svg`, and stores the resulting local path as `RegistryAgentMetadata.icon_path`. ([registry fetch and metadata](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/project/src/agent_registry_store.rs#L20-L35), [download/cache path](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/project/src/agent_registry_store.rs#L479-L532), [registry `icon` parsing](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/project/src/agent_registry_store.rs#L635-L647))

Zed then gives registry-installed agents that cached `icon_path`. For a settings-defined `type: "custom"` agent, it explicitly constructs the entry with no icon and no display-name override. ([agent registration](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/project/src/agent_server_store.rs#L359-L376), [registry icon assignment](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/project/src/agent_server_store.rs#L395-L438)) The current `CustomAgentServerSettings::Custom` schema offers `command`, `args`, `env`, mode, and configuration-option defaults/favorites, but no icon field. ([custom-agent settings schema](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/settings_content/src/agent.rs#L735-L767)) In the new-thread UI, Zed renders an external SVG when it has one and otherwise falls back to its built-in sparkle icon. ([agent menu rendering](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/agent_ui/src/agent_panel.rs#L5916-L5931))

Older Zed agent-server extensions could declare an optional manifest `icon` path, but that is also Zed extension metadata, not ACP, and Zed now documents extension-provided agents as deprecated in favor of the registry. ([legacy `AgentServerManifestEntry.icon`](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/crates/extension/src/extension_manifest.rs#L231-L241), [Zed external-agent documentation](https://github.com/zed-industries/zed/blob/99b0ed6b55017fe110557af7408afff9a6cd9e71/docs/src/ai/external-agents.md#L159-L182))

## Implication for Weave

- Alpha and other Weave clients can carry an agent icon in Weave's own host/catalog metadata; it should not be modeled as a stable ACP capability.
- A `weave-codex` process configured directly as a Zed custom agent cannot currently provide its icon over ACP or through Zed's custom-agent settings. Zed will use its fallback icon.
- To obtain the normal branded icon in Zed without a proprietary Zed change, publish the agent through the ACP Registry. A legacy Zed extension can still carry an icon, but it is the deprecated route.
