# WVE-74: macOS traffic lights in the Alpha top rail

Researched 2026-09-10 against Electron's official documentation, Electron 44.3.0 source, and Chromium source. Alpha pins Electron 44.3.0 in `product/alpha/package.json`. At the start of this change, `electron/main.ts` created a standard framed window; the preload exposed a narrow, isolated desktop bridge. The product top rails are 32 CSS pixels tall.

## Recommended approach

Use macOS `titleBarStyle: 'hidden'`, `titleBarOverlay: true`, and native traffic-light positioning. Keep the real OS controls and the existing product rails. `hidden` extends web content into the titlebar while preserving the native controls; `hiddenInset` supplies a fixed alternative inset, which does not solve centering against a zoomed rail. A transparent window or replacement HTML traffic lights is unnecessary. [Electron custom titlebar guide](https://www.electronjs.org/docs/latest/tutorial/custom-title-bar)

Position controls from the main process using `setWindowButtonPosition({x, y})`; the constructor equivalent is `trafficLightPosition`. Passing `null` resets the position. `setTitleBarOverlay()` is documented for Windows/Linux, so do not depend on it to resize the macOS overlay dynamically. [Electron BaseWindow API](https://www.electronjs.org/docs/latest/api/base-window#winsetwindowbuttonpositionposition-macos), [overlay update API](https://www.electronjs.org/docs/latest/api/base-window#winsettitlebaroverlayoptions-windows-linux)

For a measured rail height `h` and current page zoom `z`, the intended vertical inset is `round((h * z - buttonHeight) / 2)`, clamped nonnegative. This is an implementation inference from native geometry: Electron reads the actual Cocoa button frame height and makes the container `buttonHeight + 2*y` tall. These coordinates are Cocoa points, unaffected by web zoom. There is no documented guarantee that the button height is 14 points; if using 14 as a local platform constant, verify it on the installed OS. The overlay's reported height can approximate the native height after subtracting twice the applied inset, but CSS rounding introduces measurement error. Avoid combining explicit overlay height and custom vertical position: native code gives them interacting meanings. [Electron 44.3.0 button layout implementation](https://github.com/electron/electron/blob/v44.3.0/shell/browser/ui/cocoa/window_buttons_proxy.mm#L80-L140)

## Zoom and space reserved for controls

Enable the Window Controls Overlay API even on macOS. `navigator.windowControlsOverlay.getTitlebarAreaRect()` and the `titlebar-area-*` CSS environment variables describe the **available content rectangle beside the controls**, not their button bounds. `geometrychange` signals updates. Reserve the leading area only in the visible header at the window's top-left; when the sidebar hides, the leading terminal or agent header must inherit that reservation. [WICG API explainer](https://github.com/WICG/window-controls-overlay/blob/main/explainer.md#working-around-the-window-controls-overlay)

Electron recomputes the available rectangle after `setWindowButtonPosition()`, using the native button container's current extent. On macOS fullscreen it returns an empty overlay rectangle because OS controls occupy a separate sliding view. Remove the content inset in that state and restore it on exit. [Electron 44.3.0 macOS window implementation](https://github.com/electron/electron/blob/v44.3.0/shell/browser/native_window_mac.mm)

Chromium converts the native rectangle to CSS coordinates using inverse page zoom and an enclosing rectangle, updates the CSS variables, and repeats this when page zoom changes. Therefore `env(titlebar-area-x)` already accounts for zoom; do not scale it again. When the overlay becomes invisible, Chromium removes these environment variables. A permanent `80px` fallback would leave an unwanted fullscreen gap; use a zero fallback after overlay initialization or gate padding on visibility. [Chromium overlay conversion and zoom refresh](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/frame/local_frame.cc)

Use a small validated IPC operation to report the CSS rail height, then read `webContents.getZoomFactor()` in the main process. Trigger it after load and renderer resize/rail measurement/overlay changes, avoiding repeated identical native updates. `zoom-changed` alone is insufficient: Electron documents it as a mouse-wheel zoom request, while this app also exposes menu zoom commands. [Electron webContents zoom event](https://www.electronjs.org/docs/latest/api/web-contents#event-zoom-changed), [zoom factor API](https://www.electronjs.org/docs/latest/api/web-contents#contentsgetzoomfactor)

## Interaction and validation

Make only actual top rail regions draggable with `app-region: drag` (or its Chromium prefixed spelling); mark buttons, menus, and other interactive descendants `no-drag`. Draggable rectangles suppress pointer events and should disable text selection. Preserve the existing sandbox, context isolation, navigation policy, and narrow bridge; native close/minimize/fullscreen controls need no renderer window-control API. [Electron custom window interactions](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions#custom-draggable-regions)

Verify at 100% and the user's approximately 83% zoom, with the sidebar visible/hidden, left/right agent docking, terminal and agent maximization, window resize, and fullscreen entry/exit. Check native terminal view alignment after removing the titlebar, rail dragging, and clickable header controls. Those runtime checks remain necessary because source/API research cannot establish the exact traffic-light appearance on the installed macOS release.

## Implementation and acceptance

Implemented the hidden titlebar with native controls, overlay geometry, and a validated main-frame IPC measurement. The main process calibrates the native button height from the initial overlay instead of assuming a fixed button size. Rendered header position determines which rails are draggable and which leading rail reserves control space; pane components do not maintain separate window-chrome state.

All 206 Alpha tests pass, including a new observer test for moving the leading inset when the sidebar hides, excluding lower split headers, and responding to fullscreen and overlay geometry changes. Frontend and desktop type checks and Mac/iPad builds pass. Installed macOS rendering confirms centered controls in the existing rail, native terminal alignment, sidebar hiding without title overlap, interactive header controls, and fullscreen entry/exit with the inset removed and restored. Manual verification at a second zoom factor and of window dragging remains outstanding.
