# WVE-79: existing browser-streaming stacks and reusable native media components

Research date: 2026-09-12. Scope: alternatives to the custom Viz export/replay experiment, especially solutions that avoid compiling Chromium. User constraint: open-source solutions only. Commercial and source-available products below are exclusions, not shortlist candidates. This is a source-backed suitability review, not a runtime acceptance result. No candidate was installed, purchased, contacted, or deployed for this review.

## Finding

People are building substantial parts of this. The closest matches divide into **browser appliances with web clients**, **remote desktops with native clients**, and **reusable media SDKs**. The strongest composable alternative for Weave is to keep upstream Chromium and the already demonstrated tab-capture extension, then evaluate a higher-level native media stack such as LiveKit. That can replace connection, subscription, recovery, and rendering glue without changing the browser engine.

I did not verify an off-the-shelf package combining native macOS and Linux browser Hosts, isolated unattended Chromium tabs, audio, an embeddable native Apple client, CDP control, and Portal's focus ownership policy. This is a bounded negative finding about the candidates below, not proof that no commercial or unpublished solution exists.

## Neko: the closest permissively licensed Linux browser appliance

Neko ships ready-to-run browser images and recommends Docker as its documented installation route. Version 3 uses multi-architecture image tags. A Chromium image and persistent profile mount avoid both Chromium compilation and a custom browser supervisor for a single appliance. The project declares Apache-2.0; current release is `v3.1.5`, published 2026-08-05. [Installation](https://neko.m1k1o.net/docs/v3/installation), [v3 image migration](https://neko.m1k1o.net/docs/v3/migration-from-v2), [repository/license](https://github.com/m1k1o/neko), [release](https://github.com/m1k1o/neko/releases/tag/v3.1.5), [profile persistence paths](https://neko.m1k1o.net/docs/v2)

Its concrete capture boundary is an X display, with GStreamer video pipelines and PulseAudio audio capture. H.264 and Opus are configurable. Streaming pipelines start for viewers and stop when the last viewer disconnects, an attractive precedent for keeping browser lifetime separate from display lifetime. The default architecture is not exporting individual Chromium tabs or Viz resources. [Capture configuration](https://neko.m1k1o.net/docs/v3/configuration/capture)

Neko has a documented HTTP API, but this does not make its streaming client a drop-in native SDK. Its v3 migration explicitly distinguishes HTTP APIs from internal WebSocket/WebRTC messages, changes the data-channel byte order, and notes a legacy compatibility path for its current client. A native libwebrtc receiver is technically plausible; the signaling/input adapter would need versioned integration tests. [API](https://neko.m1k1o.net/docs/v3/api/general), [migration contract](https://neko.m1k1o.net/docs/v3/migration-from-v2)

For Weave, one appliance per Workspace could provide profile and desktop separation on Linux, with an additional CDP connection for ACP agents. That is an architectural inference, not a supported Portal integration. Native macOS remains the decisive mismatch: the source dependencies include X.org, XRandR/XTest, PulseAudio, and Linux-oriented tools. Running its Linux container on Mac would introduce a VM and networking/filesystem semantics absent from our current Host model. [Build dependencies](https://neko.m1k1o.net/docs/v3/developer-guide)

## Selkies: active Linux streaming components, with a changed current architecture

Do not assume that today's Selkies is simply the older GStreamer service. Current documentation describes Python orchestration, `pixelflux` video, `pcmflux` audio, default WebSocket/WebCodecs transport, and optional WebRTC using a vendored `aiortc` fork. Capture/input and PulseAudio/PipeWire-Pulse audio are Linux-oriented. Packages include wheels, Debian/RPM/Alpine/Arch packages, and AppImages. [Current components](https://selkies-project.github.io/selkies/component)

The project declares MPL-2.0. The latest release observed was **`v2.0.0rc0`, published 2026-09-12**; its name identifies a release candidate even though GitHub's latest-release endpoint returned it. Default `pixelflux` software H.264 builds include x264; the documented non-GPL build option selects OpenH264. We should record the exact dependency build, not label an entire distributed image merely “MPL.” [Repository](https://github.com/selkies-project/selkies), [release/assets](https://github.com/selkies-project/selkies/releases/tag/v2.0.0rc0), [encoder dependency notes](https://selkies-project.github.io/selkies/component)

It already has view-only/collaborative sharing and a token-protected orchestration control plane. These are useful components and precedents; they do not implement Portal's latest-focused-client viewport rule. Its native Mac host and native Apple embedding paths were not established in the reviewed interfaces. Treat it as a Linux backend contender or a source of concrete protocol/quality ideas, with version-pinned evaluation because of the active transition. [Settings/control options](https://selkies-project.github.io/selkies/settings)

## Kasm and KasmVNC: complete appliance, wrong client boundary

Kasm runs containerized browser applications and renders them in a local browser. Its open-sourced container images can operate standalone or within the wider Workspaces product. KasmVNC is explicitly **not RFB compliant**, so an existing native VNC client cannot be assumed to work. [Browser isolation](https://www.kasmweb.com/docs/develop/guide/browser_isolation.html), [KasmVNC goals](https://www.kasmweb.com/kasmvnc/docs/latest/index.html)

Useful existing behavior includes remote resizing, control permissions, clipboard/input handling, bottleneck statistics and screenshot APIs. The documented client is web-native. Native Apple embedding would involve implementing its client protocol or adopting a webview; a Mac-native server was not verified. KasmVNC declares GPL-2.0 and provides Linux packages; the observed current release was `v1.5.0`, 2026-07-29. This license statement covers KasmVNC, not every Kasm product. [Client](https://www.kasmweb.com/kasmvnc/docs/master/clientside.html), [developer API](https://kasmweb.com/kasmvnc/docs/master/developer_api.html), [repository](https://github.com/kasmtech/KasmVNC), [release](https://github.com/kasmtech/KasmVNC/releases/tag/v1.5.0)

## Sunshine and Moonlight: a real prebuilt cross-platform native alternative

Sunshine's current `v2026.906.222525` release, published 2026-09-06, includes Mac arm64 and x86_64 DMGs and Linux packages. Moonlight has native macOS and iOS clients. This is a credible zero-Chromium-build route if the product can accept remotely operating a browser on a desktop/display. [Sunshine release/assets](https://github.com/LizardByte/Sunshine/releases/tag/v2026.906.222525), [Moonlight desktop](https://github.com/moonlight-stream/moonlight-qt), [Moonlight iOS](https://github.com/moonlight-stream/moonlight-ios)

Older statements that Sunshine cannot capture Mac audio are stale. Its current versioned audio implementation supports system-wide Core Audio taps on macOS 14+, while installation docs describe Mac support as experimental. The audio boundary is system audio, not a particular Chromium tab. [Versioned audio implementation](https://docs.lizardbyte.dev/projects/sunshine/v2026.906.222525/interfaceAVAudio.html), [installation and Mac limitations](https://docs.lizardbyte.dev/projects/sunshine/v2026.516.143833/md_docs_2getting__started.html)

The embeddable part is `moonlight-common-c`, a real C implementation explicitly intended for new clients. It is GPL-3.0, as are the checked Sunshine/Moonlight repositories, and it requires its particular bundled ENet revision. It supplies a reusable streaming core, not a Swift browser-tab control. Standalone-app use and linking it into Alpha are different integration choices; license compatibility needs assessment before choosing embedding. [C client core and dependency contract](https://github.com/moonlight-stream/moonlight-common-c)

This is less direct for our Workspace model than the existence of native apps initially suggests. Display capture, shared host input and system audio would need isolation. Multiple browser profiles alone do not isolate desktop input or tab audio. Sunshine docs also advise against multiple instances. Profile lifecycle/CDP and focused-client resize arbitration would remain Portal work. A remote-desktop benchmark is valuable, but adopting it as a tab substrate would be a product-level change. [Usage/session guidance](https://docs.lizardbyte.dev/projects/sunshine/v2026.516.143833/md_docs_2getting__started.html), [display capture type](https://docs.lizardbyte.dev/projects/sunshine/v2026.906.222525/structplatf_1_1av__display__t.html)

Wolf is a more composable Linux relative: independent virtual desktops, a small Smithay-based Wayland compositor exposed as a GStreamer plugin/C API, virtual PulseAudio sinks, container orchestration, and Moonlight clients. It declares MIT. This is strong evidence that isolated application streaming can reuse existing components; the platform mechanisms remain Linux-specific. The stable container is more informative about ongoing delivery than its old `v2024.07` GitHub release alone. [Architecture](https://games-on-whales.github.io/wolf/stable/dev/how-it-works.html), [container quickstart](https://games-on-whales.github.io/wolf/stable/user/quickstart.html), [repository/license](https://github.com/games-on-whales/wolf)

## Excluded browser automation services and live-view products

**Browserless** has prebuilt Linux amd64/arm64 browser containers, CDP/Playwright connectivity, session management and user-data-directory configuration. Current release observed: `v2.56.7`, 2026-09-10. Its source declares SSPL-1.0 OR Browserless Commercial License; [OSI explicitly classifies SSPL as non-open-source](https://opensource.org/blog/the-sspl-is-not-an-open-source-license). The vendor's deployment documentation calls the core image open source but separates enterprise live-debugging/recording features. We should use the actual edition and license rather than infer that every documented feature ships in the free image. [Deployment/edition matrix](https://docs.browserless.io/enterprise/open-source), [license](https://github.com/browserless/browserless/blob/v2.56.7/LICENSE), [release](https://github.com/browserless/browserless/releases/tag/v2.56.7), [profile configuration](https://docs.browserless.io/enterprise/user-data-directory)

Its `Browserless.liveURL` API offers interactive/read-only mode, image quality/type, browser interface visibility and automatic viewer-based resizing. This is closer to the desired attended-agent workflow than raw CDP screenshots. The reviewed API documents JPEG/PNG-style live display and web clients, not a native WebRTC client SDK. Separate WebM recording supports audio; that does **not** prove audio in LiveURL or an embeddable native stream. Excluded from the open-source-only shortlist: the distributed server uses SSPL/commercial terms, and the additional live features have an edition boundary. [LiveURL API behavior](https://docs.browserless.io/baas/advanced-configurations/hybrid-automation-configurations), [recording contract](https://docs.browserless.io/baas/monitor-sessions/screen-recording)

**Browserbase** provides interactive session live views, per-tab URLs, and `sessions.debug()`; its documented embedding path is an iframe. This proves that agent/human browser sharing is an established product category. It does not establish a downloadable self-hosted Mac/Linux service or native video SDK. Mobile keyboards also require custom handling in the live-view documentation. Excluded: this is a managed service, not an identified open-source, self-hostable Host stack. [Session live view API and embedding](https://docs.browserbase.com/platform/browser/observability/session-live-view)

**BrowserBox** deserves explicit consideration because it now distributes native Linux x64 and Mac arm64 binaries. Current observed release: `v18.8.0`, 2026-09-06. It advertises cross-platform remote browsing and web-component embedding. Its present repository explicitly says proprietary commercial software, with a paid license required even for evaluation. Historical “open source BrowserBox” descriptions cannot be applied to the current release. [Release/assets](https://github.com/BrowserBox/BrowserBox/releases/tag/v18.8.0), [current product contract](https://github.com/BrowserBox/BrowserBox/blob/v18.8.0/README.md)

The public material reviewed does not establish a supported embeddable Swift/native decoder, a stable media protocol for third-party native clients, or the exact unattended CDP/profile contract we need. It is **excluded by the open-source-only requirement**. No paid evaluation was started. Publicly visible legacy source should not be mistaken for the current release under an open-source license.

## LiveKit: the strongest higher-level composable media option

LiveKit offers a self-hosted server with documented native Mac and Linux installation and a Swift SDK for Apple platforms. Both checked core repositories declare Apache-2.0. Observed releases: server `v1.13.6` (2026-08-26), Swift `2.16.0` (2026-08-04). [Local server](https://docs.livekit.io/transport/self-hosting/local/), [Swift setup](https://docs.livekit.io/transport/sdk-platforms/swift/), [server release/license](https://github.com/livekit/livekit/releases/tag/v1.13.6), [Swift release/license](https://github.com/livekit/client-sdk-swift/releases/tag/2.16.0)

This is not merely an iframe library: the Swift `VideoView` is a native view with Metal and sample-buffer renderers. Swift Package Manager consumes an existing WebRTC XCFramework dependency. On the producer side, JS `publishTrack` accepts an existing `MediaStreamTrack`. **Inference:** our extension's proven tab audio/video tracks can plausibly be published using the LiveKit JS SDK, while Alpha uses its native view and audio. That exact extension integration still requires a bounded spike; standard screen-sharing examples alone are not acceptance evidence. [Native view source](https://github.com/livekit/client-sdk-swift/blob/2.16.0/Sources/LiveKit/Views/VideoView.swift), [package dependencies](https://github.com/livekit/client-sdk-swift/blob/main/Package.swift), [publishTrack API](https://docs.livekit.io/reference/client-sdk-js/classes/LocalParticipant.html#publishTrack), [browser audio example](https://docs.livekit.io/transport/media/screenshare/)

Potentially removes custom signaling/reconnection, subscription and bandwidth adaptation, track/audio handling, and native media rendering. Adds a media-server process and the LiveKit room/track protocol. The server is explicitly an SFU, forwarding media among participants. [Server architecture](https://github.com/livekit/livekit) A Host-local server can keep LAN/VPN media local; this is still an additional hop compared with direct browser-to-client peer connections. It does not manage Chromium, CDP, Workspace profiles, tab IDs or authorization. Adaptive media resolution is not browser viewport ownership. Portal should continue to decide viewport/focus and browser lifetime. [Transport responsibilities](https://docs.livekit.io/transport/), [media/quality APIs](https://docs.livekit.io/transport/media/)

The WebRTC XCFramework alone and the full LiveKit Swift SDK are distinct choices: consuming the prebuilt WebRTC binary does not require adopting LiveKit rooms or its server. The full SDK is what supplies those higher-level features. [Package boundary](https://github.com/livekit/client-sdk-swift/blob/main/Package.swift)

The useful comparison is **direct libwebrtc versus LiveKit SDK + local server**, holding stock Chromium capture constant. Measure connection recovery, multiple viewers, overhead, paused streams, native rendering quality and the amount of maintained adapter code. No Chromium rebuild is necessary for that comparison.

## GStreamer: a composable media engine, not a browser manager

GStreamer declares LGPL for the framework, with plugin dependencies requiring separate consideration. [Licensing](https://gstreamer.freedesktop.org/documentation/frequently-asked-questions/licensing.html)

GStreamer distributes native binaries for Mac and iOS, including an XCFramework path in 1.28+, and Linux packages. Its `webrtcsink` provides ready-made signaling hooks, congestion handling, media transport, and a corresponding native `webrtcsrc` consumer. A control data-channel protocol transports `GstNavigation` events. [Binary distributions](https://gstreamer.freedesktop.org/download/), [rswebrtc architecture](https://gstreamer.freedesktop.org/documentation/rswebrtc/index.html)

Current `webrtcsink` pads accept raw video or encoded formats including H.264, and raw/Opus audio. This creates a useful seam for a CEF/offscreen/native capture producer. The framework has a Mac AVFoundation screen source, but screen-crop APIs do not imply isolated headless Chromium tab capture. The documented `wpesrc` interactive browser example uses WPE WebKit, so it does not meet the Chromium requirement. [Sink API](https://gstreamer.freedesktop.org/documentation/rswebrtc/webrtcsink.html), [Mac capture API](https://gstreamer.freedesktop.org/documentation/applemedia/avfvideosrc.html), [navigation/browser example](https://gstreamer.freedesktop.org/documentation/rswebrtc/index.html)

Compared with LiveKit, GStreamer offers more direct pipeline control and less browser/session structure. We would still own capture binding, input translation, profile/CDP control, and Apple UI integration. Its documentation says consumer encoders are not shared in the normal pipeline; multiple viewers can therefore increase encode work. Exact plugin availability in the chosen prebuilt package and the licenses of selected encoders require verification. Do not equate a cross-platform framework download with a fully bundled cross-platform browser appliance. [Consumer encoding design](https://gstreamer.freedesktop.org/documentation/rswebrtc/index.html)

## Recommendation and evidence limits

1. **Compare LiveKit against our existing direct-WebRTC prototype first.** It preserves the accepted Chromium/capture architecture and offers the most credible reduction in native media glue.
2. **Keep Neko or Selkies as Linux alternatives**, if a future product decision permits a separate Linux backend or a managed Linux VM on Mac. Their broad browser features come with a desktop boundary and native-client adapter work.
3. **Use Sunshine/Moonlight as a quality/latency benchmark** and a possible separate remote-desktop feature. Treat its macOS support, audio isolation and embedding license as concrete evaluation items.
4. **Exclude BrowserBox, Browserbase and the current SSPL/commercial Browserless server.** Their live views are useful architectural precedents, not eligible dependencies under the user's open-source-only constraint.
5. Keep the Viz experiment separate: these alternatives stream completed imagery and cannot establish retained Viz-resource replay. Their advantage is avoiding that custom compositor and Chromium patch entirely.

Release freshness was checked using GitHub repository and latest-release metadata on the research date, plus current first-party docs/source. Repository push dates indicate activity, not production support. Some raw GitHub fetches later failed with rate limits/503 responses; relevant API/source claims above were verified through successful documentation or source-page reads. No performance, security, license compatibility, or operating-system acceptance is implied by this document.
