# WVE-79: existing vector, composition, and DOM browser remoting

Research verified 12 September 2026. This is one part of the alternatives investigation; pixel streaming frameworks and graphics/protocol libraries are covered separately. The adoption scope is **open source only**, Chromium on macOS and Linux Hosts, native Mac/iPad display without a platform webview, audio, direct LAN/VPN operation, persistent Workspace profiles, and agent control through Portal. License names below describe project declarations, not a legal determination about a particular integration.

## Finding

People have built the proposed class of system. Google's Blimp implemented remote compositor state, cached pictures, separate image resources, acknowledgements, and local client composition. Cloudflare operates a commercial Skia command streaming service. Carbonyl demonstrates a small replaceable renderer library behind a patched Chromium runtime. None of these is a verified, maintained, open source, prebuilt solution for our complete Mac/Linux-to-native-Mac/iPad requirement.

The most useful new discovery is **the maintained `jmagly/carbonyl` fork**, not just the old original Carbonyl project. It has published Linux runtimes based on Chromium 150 and an explicit Rust/C++ boundary that lets renderer-only work avoid Chromium rebuilds. It still exports bitmap/text output, carries Chromium patches, and its latest releases do not contain the macOS binaries advertised by general installation documentation. This is a concrete architectural precedent and a possible Linux-only experiment, not a replacement for the desired retained-scene transport. [Latest prerelease and assets](https://github.com/jmagly/carbonyl/releases/tag/v0.2.0-alpha.18), [renderer boundary](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/src/browser/renderer.h), [rebuild guide](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/docs/rust-chromium-boundary.md).

These findings support separating two decisions: whether to own a Chromium capture patch at all, and whether transport/rendering iteration should require rebuilding that patch. The second can be solved with an external library or process even when the first cannot.

## Carbonyl: the strongest modular-build precedent

### What the original actually exports

Original Carbonyl's `Renderer` accepts text runs with bounds/color and bitmap buffers with damage rectangles. Its C callback delegate provides navigation, scrolling, keyboard, pointer input, and task posting. The implementation forwards these to a Rust shared library. This is a genuine embedding boundary, but it does **not** expose general Skia operations, an aggregated Viz graph, retained GPU resources, or a browser remoting protocol. [Pinned renderer header](https://github.com/fathyb/carbonyl/blob/ab80a276b1bd1c2c8dcefc8f248415dfc61dc2bf/src/browser/renderer.h), [implementation](https://github.com/fathyb/carbonyl/blob/ab80a276b1bd1c2c8dcefc8f248415dfc61dc2bf/src/browser/renderer.cc), [Rust bridge](https://github.com/fathyb/carbonyl/blob/ab80a276b1bd1c2c8dcefc8f248415dfc61dc2bf/src/browser/bridge.rs).

The browser runtime dynamically loads the core. The project's documented workflow allows rebuilding the Rust library and replacing it in a release distribution without recompiling Chromium. The original v0.0.3 release contains macOS and Linux binaries for both x86_64 and arm64. Its Chromium source pin is 111.0.5511.1, however, and its latest release was published on 18 February 2023. Platform precedent is not current security maintenance. [Original README/build split](https://github.com/fathyb/carbonyl), [release artifacts](https://github.com/fathyb/carbonyl/releases/tag/v0.0.3), [Chromium pin](https://github.com/fathyb/carbonyl/blob/ab80a276b1bd1c2c8dcefc8f248415dfc61dc2bf/chromium/.gclient).

Carbonyl deliberately adapts browser output to terminal cells. Its author describes changes to rendering and text layout, not an untouched high-fidelity browser output path. The software display client receives bitmap output through Viz's display interfaces. Replacing the final terminal renderer would not automatically undo the browser-side assumptions. [Author's technical explanation](https://fathy.fr/carbonyl), [display client source](https://github.com/fathyb/carbonyl/blob/ab80a276b1bd1c2c8dcefc8f248415dfc61dc2bf/src/browser/host_display_client.h).

### Maintained fork: real progress, with concrete gaps

`jmagly/carbonyl` is active: inspected main commit `e55e663777881033fd239ac0a88af0a3dd78d908` is dated 4 September 2026. Its source pin is Chromium **150.0.7871.47**. The latest published prerelease, **v0.2.0-alpha.18, 5 July 2026**, lists a 35-patch stack and Linux x86_64 headless/X11 runtime tarballs, AppImage, RPM, and DEB artifacts. The GitHub `/releases/latest` API returns 404 because releases are prereleases; the release list contains the artifacts. [Pinned source configuration](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/chromium/.gclient), [release](https://github.com/jmagly/carbonyl/releases/tag/v0.2.0-alpha.18), [repository history](https://github.com/jmagly/carbonyl/commits/main/).

There is material documentation drift. The README describes M147, repository metadata describes M148, but source/release evidence gives M150. Installation documentation describes macOS arm64 packages, while the actual latest three inspected releases have **no macOS assets**; alpha.18 explicitly conditions additional platforms on those runtimes being published. Use source pins and real asset lists when assessing availability. [README](https://github.com/jmagly/carbonyl), [installation document](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/docs/install.md), [alpha.17 artifacts](https://github.com/jmagly/carbonyl/releases/tag/v0.2.0-alpha.17), [alpha.15 artifacts](https://github.com/jmagly/carbonyl/releases/tag/v0.2.0-alpha.15).

The current boundary is still `DrawText`/`DrawBitmap`. Its detailed guide describes a patched headless shell, injected C++ bridge, and replaceable `libcarbonyl`; it also documents coupling between physical bitmap dimensions and terminal cell sampling. A Rust-only change preserving the C ABI avoids the expensive runtime build. New capture data, changed ABI, or Chromium-side behavior still requires rebuilding browser code. This is the pattern to borrow if the Viz route proceeds: a narrow, versioned producer interface, independently built transport consumer, and pinned runtime artifact. It does not make a new compositor interception point available in the existing release. [Current header](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/src/browser/renderer.h), [boundary and invariants](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/docs/rust-chromium-boundary.md).

The associated `carbonyl-agent` Python SDK provides terminal-oriented browser automation and persistent sessions. Its runtime pin is alpha.17, and its declaration is AGPL-3.0, distinct from the runtime repository's BSD-3-Clause declaration. It is not a native display SDK; adopting it would also introduce another orchestration layer alongside Portal. The release's CDP smoke test is evidence of project testing, not our validation of full CDP parity. [Agent SDK](https://github.com/jmagly/carbonyl-agent), [runtime pin](https://github.com/jmagly/carbonyl-agent/blob/main/.carbonyl-runtime-version), [runtime license](https://github.com/jmagly/carbonyl/blob/e55e663777881033fd239ac0a88af0a3dd78d908/LICENSE).

### Carboxyl is a different direction

The community `carboxyl-rs/carboxyl` fork is active, but its newest release, `v0.1.0-servo-rc.1` on 14 June 2026, explicitly replaces patched Chromium with embedded Servo. The main branch's Chromium configuration still pins 111.0.5511.1 and its README's Chromium binary links point to the original Carbonyl v0.0.3 release. It is therefore not evidence that current Chromium-based Mac/Linux prebuilts already solve our need. The Servo experiment is excluded by the chosen engine requirement. [Release and rationale](https://github.com/carboxyl-rs/carboxyl/releases/tag/v0.1.0-servo-rc.1), [main Chromium pin](https://github.com/carboxyl-rs/carboxyl/blob/main/chromium/.gclient), [repository](https://github.com/carboxyl-rs/carboxyl).

## Blimp: this architecture existed upstream

Blimp was an experimental Chromium thin-client project with an engine and client. Its build documentation supported Linux and Android. The whole remaining Blimp directory was deleted from Chromium on **18 January 2017**, so it is historical source rather than an upstream feature available in a current Chrome binary. [Blimp README](https://chromium.googlesource.com/chromium/src/+/c2c4f22ff/blimp/), [build documentation](https://raw.githubusercontent.com/chromium/chromium/c2c4f22ff/blimp/docs/build.md), [removal commit](https://github.com/chromium/chromium/commit/7ab5fc81962a872e9dae8c54493360bac7d3d69d).

The implementation is considerably closer to the user's idea than screenshot remoting:

- The client deserializes compositor/layer-tree state, uses Chromium's local `LayerTreeHostInProcess`, and schedules local rendering. Frame acknowledgements and one pending compositor update limit outstanding state. Client viewport/scroll/scale deltas travel back separately. [Blimp compositor implementation](https://raw.githubusercontent.com/chromium/chromium/da3cfdb3e1f0b69e10aaadc30ff05811c26f46af/blimp/client/core/compositor/blimp_compositor.cc).
- A client picture cache maps engine picture IDs to deserialized SkPictures and tracks references to release unused entries. [Picture cache](https://raw.githubusercontent.com/chromium/chromium/da3cfdb3e1f0b69e10aaadc30ff05811c26f46af/blimp/client/core/compositor/blimp_client_picture_cache.cc).
- Image serialization references a separate blob channel/cache and reconstructs images from those resources. The scene stream alone is insufficient. [Image serialization processor](https://raw.githubusercontent.com/chromium/chromium/da3cfdb3e1f0b69e10aaadc30ff05811c26f46af/blimp/client/core/compositor/blob_image_serialization_processor.cc).

This answers “has anyone done it?” with actual open source implementation evidence. It does not provide a small standalone Metal decoder or current native iOS package. Resurrecting it would mean adapting removed Chromium subsystems and porting a client that itself depends on Chromium compositor machinery. The useful transferable ideas are explicit frame ownership/acknowledgements, cached resource identities and lifetimes, and separating image payloads from scene updates. Its input/viewport behavior is precedent, not our chosen latest-focus ownership policy.

## Skia capture prototypes and upstream advice

Garnet implements a three-stage prototype: modified Chromium logs Skia drawing operations; Node/Puppeteer parses them; a browser extension replays through CanvasKit. It requires a Chromium build and a browser-based receiver. The server package explicitly declares **`UNLICENSED`**. Its public visibility therefore does not make it an open source adoption candidate. [Garnet architecture/build instructions](https://github.com/ECS-251-W2020/garnet), [package declaration](https://github.com/ECS-251-W2020/garnet/blob/master/server/package.json). The Browsurrogate repository is a fork of that work, not evidence by itself of a supported SDK. [Fork](https://github.com/metagrapher/Browsurrogate).

The related `html2svg` work extracts layer pictures and draws them through Skia's SVG backend. Its author describes the required Chromium/Electron patches and the difficulty of composing layer results. It is useful vector-export precedent, not a live retained-resource protocol with audio, input, lifecycle, and native clients. [Author's implementation account](https://fathy.fr/html2svg), [project and conversion API](https://github.com/fathyb/html2svg).

In an April 2024 official Chromium discussion, a Chromium engineer points to PaintOpBuffer serialization used for out-of-process rasterization, while explaining that images and fonts travel through other mechanisms and require additional work. Another reply points to historical SKP export through tracing. These are reasons to inspect existing serialization code before inventing it, not evidence of a public continuous browser-remoting API. A one-shot diagnostic picture is a different contract from a complete stream with synchronized resources and frame lifetimes. [Official blink-dev discussion](https://groups.google.com/a/chromium.org/g/blink-dev/c/dxe6uFMNOtM).

## DOM/terminal alternatives are composable, but change the client contract

**rrweb** is a maintained MIT-declared recording/replay stack. It serializes DOM state and records subsequent mutations and interactions; replay reconstructs the DOM. Its live mode accepts events as they arrive, including over a WebSocket. This is reusable JavaScript rather than a Chromium fork. The receiver must still render HTML through a browser engine, however. A native Mac/iPad application without a webview would need to supply that engine or reimplement web layout and rendering. rrweb is promising for development-session recording; it is not a native browser renderer. [Project architecture](https://github.com/rrweb-io/rrweb), [live-mode API](https://github.com/rrweb-io/rrweb/blob/main/docs/recipes/live-mode.md), [license](https://github.com/rrweb-io/rrweb/blob/main/LICENSE).

**Browsh** combines headless Firefox, a WebExtension, and a Go terminal client. That architecture avoids maintaining a Chromium patch, but uses the wrong engine and a terminal representation. Displaying it through Weave's existing terminal renderer would be a different product choice, with different fidelity and audio transport requirements. The project declares LGPL-2.1; its latest listed release is v1.8.3 from January 2024. [Project](https://github.com/browsh-org/browsh), [release](https://github.com/browsh-org/browsh/releases/tag/v1.8.3).

## Commercial precedents, excluded from adoption

These were investigated before the open-source-only decision. They help distinguish “technically exists” from “reusable component available to us.”

**Cloudflare NVR:** official architecture describes remote Chromium Skia operations intercepted, tokenized, compressed, and replayed by a browser client. The original account describes a Wasm Skia receiver and patented technology; current documentation presents Browser Isolation as a Cloudflare-operated service, not a downloadable remoting library. No public open source NVR server, native Mac/iPad SDK, or self-host package was found in the inspected official material. [Architecture](https://developers.cloudflare.com/reference-architecture/diagrams/security/securing-data-in-use/), [technical introduction](https://blog.cloudflare.com/cloudflare-and-remote-browser-isolation/), [product documentation](https://developers.cloudflare.com/cloudflare-one/remote-browser-isolation/).

Cloudflare's April 2026 Canvas Remoting update also shows that a mature command-remoting system can be hybrid: 2D canvas operations receive command remoting while WebGL/3D continue using bitmap delivery. This argues against assuming every Chromium output becomes efficient vectors automatically. Product performance figures are vendor measurements and were not reproduced here. [Canvas Remoting update](https://developers.cloudflare.com/changelog/post/2026-04-10-canvas-remoting-performance/).

**BrowserBox/Hyper-Frame:** current BrowserBox has real Mac arm64 and Linux x86_64 binaries (v18.8.0, 6 September 2026), and its customer guide uses an installed Chrome-family browser. It is a possible prebuilt product in the abstract, but the current repository requires a commercial license even for evaluation and says legacy source was removed in March 2026. It is excluded from this shortlist. Hyper-Frame's API is a web custom element/iframe messaging interface rather than a published native compositor SDK. [Current license statement](https://github.com/BrowserBox/BrowserBox), [release assets](https://github.com/BrowserBox/BrowserBox/releases/tag/v18.8.0), [versioned customer guide](https://github.com/BrowserBox/BrowserBox/blob/v18.8.0/docs/BrowserBox_Customer_Guide_v18.8.0.pdf), [web integration API](https://win9-5.com/api).

**Hyperbeam:** its JavaScript SDK is more flexible than iframe-only embedding: `frameCb` exposes an ImageBitmap or HTMLVideoElement, `audioTrackCb` exposes a MediaStreamTrack, and there are resize/input methods. These remain web runtime types. Its session REST API creates hosted virtual browsers, and persistence documentation stores profile snapshots in its service. The public Unity desktop SDK document says it is still in development; the public Unity package is WebGL. No verified open source self-hosted/native Mac/iPad SDK was found. [JavaScript API](https://docs.hyperbeam.com/client-sdk/javascript/reference), [hosted session creation](https://docs.hyperbeam.com/rest-api/dispatch/start-chromium-session), [profile persistence](https://docs.hyperbeam.com/guides/persist-session-state), [desktop SDK source document](https://raw.githubusercontent.com/hyperbeam/docs/master/docs/client-sdk/unity/unity-desktop-sdk.mdx), [public Unity packages](https://github.com/hyperbeam/packages).

**Surfly** uses a rewriting proxy and JavaScript to share web content, including an on-premises offering; it still depends on local HTML rendering and does not supply our remote Chromium/native display boundary. [Proxy architecture](https://help.surfly.com/en/the-surfly-proxy), [integration](https://help.surfly.com/en/how-to-integrate-surfly).

**Mighty/Whist/CoScreen:** these do not add a verified current OSS adoption candidate. Mighty's former product domain now redirects to Playground. A historical Whist-integrated Brave fork contains browser/protocol build integration, rather than a maintained complete native SDK; known public core-protocol repository paths did not resolve. CoScreen is a current screen-sharing product, not a documented reusable browser composition library. [Former Mighty domain](https://www.mightyapp.com/), [historical Whist Brave fork](https://github.com/philippemnoel/whist-brave-browser), [CoScreen product release notes](https://updates.coscreen.co/announcements/v8-7-performance-and-quality-improvements). These bounded checks are not claims that no private implementation exists.

## Implications for the spike and implementation

1. **A long Chromium build is not inherent to every edit.** Carbonyl provides both historical and current source evidence for compiling a browser-side adapter once and swapping an external renderer library for most iteration. The boundary must already export the data the experiment needs; existing bitmap/text callbacks cannot reveal omitted retained resources.
2. **Avoid reviving Blimp or using Garnet as the product foundation.** Blimp is valuable design/source research, but importing removed Chromium client machinery conflicts with minimal maintenance. Garnet is unlicensed and a prototype.
3. **Do not confuse native pixels, native command replay, and native DOM replay.** The first can use conventional media components; the second needs a graphics/resource contract; the third needs a web engine. A JavaScript SDK with frame callbacks is more composable than an iframe, but still is not a native SDK.
4. **If command remoting remains attractive, specify resources before transport.** Blimp and the upstream PaintOp discussion both show that picture/operation bytes alone omit essential image/font state and lifecycle. Audio and browser control remain additional channels.
5. **No additional user architecture decision is required by this sub-investigation.** Existing Chromium and native-client constraints rule out the DOM/Firefox/Servo alternatives. Carbonyl is worth borrowing as an engineering pattern, not promoting to the production backend on documentation alone.

No browser artifacts were installed or run for this report, no commercial vendor was contacted, and no benchmark claims were independently validated. The ongoing Viz spike must still establish what its actual capture boundary exports; this alternatives research neither proves nor disproves that implementation.
