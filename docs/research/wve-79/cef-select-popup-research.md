# CEF 152 macOS OSR select popup diagnosis

2026-09-15. Bounded source investigation for the interaction pass. No runtime change or successful popup acceptance is claimed here.

**Follow-up source tracing identifies a likely upstream regression, with no public CEF workaround found.** CEF initially selects internal popup menus, but Chromium's later WebPreferences application can overwrite that choice. The initial conclusion that normal OSR configuration was sufficient was incomplete; the additional evidence below supersedes it.

Pinned CEF `708dc14` calls `blink_glue::SetUseExternalPopupMenus(web_view, !config.is_windowless)` when creating a macOS WebView. For OSR this selects Blink's internal popup path. Changing Chrome versus Alloy style is not a meaningful fix: CEF's windowless mode uses Alloy style, running within the current Chrome bootstrap. [Pinned renderer configuration](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/renderer/chrome/chrome_content_renderer_client_cef.cc), [window configuration](https://github.com/chromiumembedded/cef/blob/708dc14/include/internal/cef_types_mac.h)

The absence of a parent NSView can affect native dialogs and menus, as the window configuration documents. That is not evidence that a parent is necessary for the internal OSR select widget. Avoid introducing an invisible native window before proving that the internal popup path is failing.

The official Mac OSR sample calls `SetFocus(true)` on first-responder/show transitions and `SetFocus(false)` on loss/hide. Its ordinary mouse-down/up handlers send `SendMouseClickEvent` without refocusing for each event. Matching this convention is a sound adapter correction. [CEF Mac OSR sample](https://github.com/chromiumembedded/cef/blob/708dc14/tests/cefclient/browser/browser_window_osr_mac.mm)

In CEF's OSR implementation, `SetFocus(true)` calls the main widget's `GotFocus()` and `SetActive(true)`. Source inspection alone does not prove that repeating it closes a popup. `InitAsPopup` calls `OnPopupShow(true)` and `OnPopupSize` before setting up rendering, so zero callback counts distinguish a failure to create a popup from a framebuffer compositing bug. `SendKeyEvent` chooses the focused render widget; mouse events route into an existing popup when inside its bounds. This supports using CEF's native event API for widget interaction. Page-target CDP keyboard events are not proof that the separate popup receives input. [Pinned OSR focus, widget creation, and input routing](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/render_widget_host_view_osr.cc)

Chromium 152 also supports CSS base-appearance select pickers as page popovers. Those do not require a separate OSR popup callback. For ordinary appearance, the select's mouse-down handler focuses the element and calls `ShowPopup`; that can return early when another popup is open, layout is missing, or the element's visible viewport bounds are empty. [Pinned Blink select implementation](https://github.com/chromium/chromium/blob/152.0.7977.83/third_party/blink/renderer/core/html/forms/select_type.cc)

Recommended next diagnostic sequence:

1. Use a new isolated page containing one visible ordinary `<select>`. Record `getComputedStyle(select).appearance`, its bounding rectangle, `document.hasFocus()`, and `document.activeElement`. Attach bounded mouse-down/up event counters including target/button/default prevention to that fixture.
2. Send native mouse-down, wait for processing, and inspect callback counters plus `select.matches(':open')` **before mouse-up**. Then send mouse-up and repeat. A current `popupVisible=false` snapshot alone cannot establish that it never opened.
3. Keep focus stable for the sequence. If the popup opens after down and closes after up, investigate focus transitions and popup overlap rather than painting. The official sample has a special release guard when it repositioned a popup under the original press; apply such a guard only if that geometry actually occurs.
4. If a popup exists, navigate it with upstream `SendKeyEvent`, with correct Mac native key codes and paired key transitions. If no popup exists but `:open` is true, check whether the picker is a page popover. If neither exists despite the correct trusted mouse-down/default action, isolate renderer popup creation with the same pinned CEF sample before choosing new embedder behavior.
5. Keep form-popup behavior distinct from website `window.open`/new-Pane handling. `OnBeforePopup`, popup-blocking preferences, and default popup window style concern a different boundary and do not establish select-menu support.

## Follow-up: ordinary select opens without creating a widget

The implementation probe reported native down/up separated by 100 ms, `appearance:auto`, `document.hasFocus() = true`, and select `:open = true`, but no show/size callbacks or popup pixels. Those observations are consistent with the following source chain; a native debugger confirmation of the actual branch would make the diagnosis conclusive:

1. Chromium 152 `WebViewImpl::ApplyWebPreferences` computes `use_external_popups = !prefs.should_disable_external_popups`, cancels an existing page popup if that choice changes, and unconditionally writes it into the ChromeClient. [Pinned WebView implementation](https://github.com/chromium/chromium/blob/152.0.7977.83/third_party/blink/renderer/core/exported/web_view_impl.cc)
2. `WebContentsImpl::ComputeWebPreferences` derives the field from its external-popup forbid counter. That counter is ordinarily zero. CEF's subsequent `OverrideWebPreferences` and `SetCefPrefs` do not override the field for OSR. [Chromium preference ownership](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/web_contents/web_contents_impl.cc), [CEF override](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/chrome/chrome_content_browser_client_cef.cc), [CEF settings mapping](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/prefs/renderer_prefs.cc)
3. The external path sends `ShowPopupMenu` to the browser. CEF's OSR view does not override that method, so it inherits an empty `RenderViewHostDelegateView::ShowPopupMenu`. This explains an open select state without a created OSR popup widget. Adding a parent NSView does not override that method. [Blink external popup](https://github.com/chromium/chromium/blob/152.0.7977.83/third_party/blink/renderer/core/html/forms/external_popup_menu.cc), [CEF OSR view](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/web_contents_view_osr.h), [empty default handler](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/renderer_host/render_view_host_delegate_view.h)

Chromium provides `content::WebContents::ForbidExternalPopupMenus()` with lifetime-scoped ownership. It is not a public CEF API. The inspected CEF browser settings, preference mapping, and Chromium CDP Page/Emulation handlers provide no stock control for this field. The field is a WebPreferences member, not an arbitrary Profile preference accepted by `CefRequestContext::SetPreference`. No command-line workaround was identified. Mobile emulation, injected CSS that changes picker appearance, and fabricated native menus would change webpage behavior and are not proposed fixes. [Chromium API](https://github.com/chromium/chromium/blob/152.0.7977.83/content/public/browser/web_contents.h)

The official CEF `7977` branch still points to `708dc140cbc3286826a8abef89dc23a44ff9ea72`, and the current CDN index has no later 152 build than 152.0.6. The inspected `master` and `7977` preference-override paths both lack the OSR override. The index contains later development milestones, but no verified fix justifies adopting one. Chromium 154.0.8037.17, used by the newest indexed 154 build, still contains the same unconditional preference application; 150.0.7871.253 also contains it. [Branch history](https://github.com/chromiumembedded/cef/commits/7977/), [current master override](https://github.com/chromiumembedded/cef/blob/master/libcef/browser/chrome/chrome_content_browser_client_cef.cc), [official build index](https://cef-builds.spotifycdn.com/index.json), [Chromium 154 application](https://github.com/chromium/chromium/blob/154.0.8037.17/third_party/blink/renderer/core/exported/web_view_impl.cc)

Recommended upstream repair: ensure the browser-side WebPreferences disable external menus for windowless browsers, or retain Chromium's scoped forbid object for each OSR WebContents. That belongs inside CEF, followed by an official prebuilt containing the fix; it should not become unsupported ABI access in Weave's adapter. Until a public workaround or corrected official binary is verified, ordinary Mac select popup acceptance is blocked. This research does not authorize filing an upstream issue or maintaining a browser fork.

## Product decision

On 2026-09-15 the user chose to defer ordinary HTML select dropdowns pending an upstream fix and keep stock CEF. The experimental popup compositor and popup-specific key mapping were removed from this interaction pass. No upstream issue or message has been posted by this task.
