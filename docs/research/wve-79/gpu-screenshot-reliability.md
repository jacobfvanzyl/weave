# GPU screenshot reliability and Apple energy profiling

Research date: 2026-09-15. Pinned CEF `152.0.6+g708dc14`, Chromium `152.0.7977.83`. This pass inspected source and documentation only; runtime observations below come from the implementation agent or existing evidence.

## Finding and present limit

The strongest source-backed hypothesis is a stalled **GPU compositor screenshot completion path**, rather than an RFB transport problem or a general JavaScript hang. A dedicated Chromium feature, `CDPScreenshotNewSurface`, bypasses one known presentation wait, but the implementation agent's new test still hangs with that feature enabled. It is therefore **not a sufficient fix**. No reliable stock configuration fix has been established by this research pass.

The next bounded diagnostic should compare screenshot completion with ongoing `OnPaint` activity on the same Page, then test an explicit CEF show/refresh and an isolated fresh-process versus second-Page lifecycle. Do not adopt a cached-frame screenshot substitute, viewport-changing workaround, native-window capture, or repeated retries as proof that full CDP screenshots work.

## Observed behavior versus source inference

Existing [worker results](latency-worker-results.md) record GPU RFB PNG creation followed by an intermittent timeout at the independent CDP reference screenshot. Software CEF acceptance passed. The adapter keeps GPU mode diagnostic-only.

During this research, the implementation agent reported that a minimal GPU test captured its first screenshot in about 354 ms, then timed out on a second Page with `Runtime.evaluate` still responsive, `document.visibilityState == "visible"`, and a 1000 × 800 logical / 2× viewport. The `CDPScreenshotNewSurface` feature-only variant failed similarly. The exact cause remains unproven; a visible DOM does not expose every compositor state.

A subsequent parent-run diagnostic called `WasHidden(false)` and `Invalidate(PET_VIEW)` synchronously immediately before the embedded `ExecuteDevToolsMethod` screenshot. Twenty recreate/resize rounds completed in roughly 60–105 ms without the feature flag. The same binary without that nudge still failed, including reuse of a Page; a DOM repaint issued two seconds after an already-pending screenshot did not rescue it. This supports an ordering-sensitive CEF preparation hypothesis, but does not distinguish show from refresh, prove freshness, or establish raw CDP-pipe behavior. Separate those factors before calling this a fix.

Current `cef-host.cc` has no viewer-disconnect call to `WasHidden`, does not enable external BeginFrame control, and pumps CEF every approximately 1 ms. Its `OnPaint` forwards to the RFB adapter; the RFB worker does not call CEF. Consequently, “disconnect hides Chromium” is not supported by current code. Viewer disconnect identifies where the original acceptance observed the failure, not necessarily its trigger.

## Upstream screenshot paths

`Page.captureScreenshot` defaults to surface capture. Chromium increments the WebContents capturer count with `stay_hidden=true` and `stay_awake=true`, then requests a snapshot. The legacy snapshot route calls Blink `ForceRedraw` and waits for its callback before copying the surface. Blink connects that callback to presentation feedback for the next frame, so missing presentation feedback can leave JavaScript responsive while the screenshot request waits. [Pinned PageHandler](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/devtools/protocol/page_handler.cc), [snapshot implementation](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/renderer_host/render_widget_host_impl.cc), [Blink ForceRedraw](https://github.com/chromium/chromium/blob/152.0.7977.83/third_party/blink/renderer/platform/widget/widget_base.cc).

Chromium's `CDPScreenshotNewSurface` feature is **disabled by default** in this pin. It calls ForceRedraw without waiting for its result, requests repaint on a new surface, and immediately submits a copy request. Its source explicitly describes avoiding a possible stall when frames are not presented. Playwright enables this feature in its standard Chromium switches. The diagnostic syntax in CEF is:

```cpp
cmd->AppendSwitchWithValue("enable-features", "CDPScreenshotNewSurface");
```

Merge with an existing enabled-feature list if one is introduced. `CopyFromSurfaceAlwaysCallCallback` is already enabled by default in this Chromium pin; enabling it again adds no fix. [Pinned feature defaults](https://github.com/chromium/chromium/blob/152.0.7977.83/content/common/features.cc#L135-L145), [Playwright switches](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/chromium/chromiumSwitches.ts).

There is a significant CEF qualification: its OSR view does **not** override `RequestRepaintOnNewSurface`; the Chromium base implementation returns false. CEF's separately named `EnsureSurfaceSynchronizedForWebTest` is not that override. The feature can bypass the old wait, but source inspection cannot promise its usual new-surface freshness behavior in CEF. A completing PNG must therefore be checked for newly changed pixels. The new failed test also shows that bypassing the legacy wait does not resolve this case by itself. [Pinned CEF OSR view](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/render_widget_host_view_osr.cc), [Chromium base implementation](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/renderer_host/render_widget_host_view_base.cc).

CEF OSR's `CopyFromSurface` forwards to `DelegatedFrameHost::CopyFromCompositingSurface` if the delegated host exists. That creates an RGBA system-memory copy request for the frame sink/local-surface identity and submits it to Viz. Chromium's screenshot route supplies a zero timeout. CEF's wrapper has no alternative completion path when its delegated host is absent. Whether an absent host, stale surface identity, or Viz readback completion explains this runtime failure requires tracing; these are source-visible candidates, not established defects. [CEF copy wrapper](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/render_widget_host_view_osr.cc), [delegated surface copy](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/renderer_host/delegated_frame_host.cc).

GPU `OnPaint` follows a different route: CEF creates a frame-sink video capturer, disables its auto-throttling, and requests ARGB output for ordinary CPU-buffer OSR. `Invalidate(PET_VIEW)` requests a refresh from this capturer. Continuing OnPaint callbacks therefore do not prove CDP's delegated-surface copy is completing. This distinction is particularly useful for the next trace. [CEF video consumer](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/video_consumer_osr.cc).

## Bounded stock-API experiments

Run each change independently against the same small fixture; preserve a failed attempt rather than silently retrying it away.

| Priority | Experiment | What it establishes |
| --- | --- | --- |
| 1 | During a hung screenshot, sample Page-specific OnPaint count/last physical size, UI-loop progress, and an unrelated `Runtime.evaluate`. Try a screenshot on the other live Page. | Separates Page-specific copy/presentation trouble from process-wide GPU or UI-loop failure. |
| 2 | Compare one fresh Page per fresh process, two simultaneous Pages, and close/recreate in the same process. Keep viewport constant first, then add 1×/2× transitions. | Isolates creation/teardown and local-surface resize triggers without touching transport. |
| 3 | Explicit `WasHidden(false)` followed by `Invalidate(PET_VIEW)`, then wait for a fresh matching OnPaint before taking a new screenshot. | Tests missing show/refresh initialization. An already-showing OSR view makes the show call a no-op; refresh belongs to the video-consumer path, so success is not guaranteed. |
| 4 | On the isolated fixture, mutate a visible marker and verify it reaches OnPaint while the screenshot is outstanding. A separate diagnostic may hide/show once to reattach the compositor. | Distinguishes missing damage from broken copy completion. Hide/show changes page visibility and must not become a transparent production retry. |
| 5 | Capture a short Chromium trace around one failure, including screenshot request, renderer ForceRedraw, compositor/Viz copy and frame-sink events. | Identifies which callback/identity stops advancing and produces an upstream-quality reproducer. |

CEF documents that `WasHidden(true)` stops layout and OnPaint. Its implementation also stops the GPU video consumer and detaches the delegated frame host from the compositor; showing reverses those actions. Keep an authorized unattended page rendering when screenshots are needed. Changing the browser's rendering visibility is separate from granting a human client Portal focus. Do not use `Page.bringToFront` or synthetic input as an implicit screenshot workaround that changes the user's active Pane. [CEF public visibility/paint APIs](https://github.com/chromiumembedded/cef/blob/708dc14/include/cef_browser.h), [OSR show/hide implementation](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/render_widget_host_view_osr.cc).

For the nudge isolation, `WasHidden(false)` propagates through `WebContents::WasShown` and visibility updates even if the document reports visible, but CEF's OSR show function returns immediately when its own `is_showing_` is already true. If show alone is sufficient, test explicit show initialization in `OnAfterCreated` plus navigation/process recovery, keeping all authorized pages renderable independently of human viewers. If only refresh works, `Invalidate` acts on the frame-sink video capturer; it is a transient refresh, so one creation-time call does not automatically cover later static screenshots. [Chromium visibility propagation](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/web_contents/web_contents_impl.cc), [CEF refresh implementation](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/video_consumer_osr.cc).

**The embedded command path is not the complete agent path.** `CefDevToolsController::ExecuteDevToolsMethod` attaches its own DevToolsAgentHost client and dispatches the message. Its observers receive that controller's results/events; `OnDevToolsAgentAttached` is emitted when this controller attaches. It is not a verified interception point for another client attached through the remote-debugging pipe. `OnDevToolsMessage` is a result/event callback, not a before-command hook. Test baseline and candidate screenshots through both paths, including flattened target sessions, and do not claim a `page.cdp` preflight repaired raw-pipe agents. A lifecycle correction is preferable when it passes; a method-specific preparation shim would need an explicit shared ownership boundary and wider acceptance. [CEF DevTools controller](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/devtools/devtools_controller.cc), [observer contract](https://github.com/chromiumembedded/cef/blob/708dc14/include/cef_devtools_message_observer.h).

`fromSurface:false` is unsuitable as the fallback contract: Chromium uses native-view snapshotting for that route, while CEF OSR's `GetNativeView()` is explicitly unimplemented and returns null. Clip/full-page capture adds another independent issue: CEF OSR's `SetSize` is a no-op, so do not change capture bounds to hide this failure. Start with default viewport surface PNGs and validate full-page/clip behavior separately. [CEF OSR native view and sizing](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/render_widget_host_view_osr.cc), [Chromium snapshot routing](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/renderer_host/render_widget_host_impl.cc).

External BeginFrame is an upstream API, but only valid when `CefWindowInfo.external_begin_frame_enabled` was enabled at creation. The product does not enable it. Adding an application-driven frame clock is a larger scheduling change and energy responsibility; do not issue it opportunistically or substitute `HeadlessExperimental.beginFrame`, which is not the general CEF API. Likewise, broad backgrounding/vsync-disabling flags are not a demonstrated repair and may substantially change power/cadence. [CEF BeginFrame contract](https://github.com/chromiumembedded/cef/blob/708dc14/include/cef_browser.h).

The 1 ms CEF polling loop is a separate energy opportunity. CEF supports external-message-pump scheduling through `OnScheduleMessagePumpWork`; its callback can arrive from any thread and must schedule UI-thread work with the requested delay. CEF recommends its own run loop where feasible; `multi_threaded_message_loop` is not supported on Mac. Do not combine this refactor with a screenshot repair comparison. [CEF settings](https://github.com/chromiumembedded/cef/blob/708dc14/include/internal/cef_types.h), [message-pump callback](https://github.com/chromiumembedded/cef/blob/708dc14/include/cef_browser_process_handler.h).

## Bring-to-front discriminator: useful observation, unproven mechanism

The implementation agent subsequently reports 30 successful fresh/idle screenshot rounds when awaiting `Page.bringToFront` first; `WasHidden(false)` alone still failed on idle, and a persistent raw-pipe baseline also failed. These are new probe observations, not yet proof that a focus transition fixes the underlying compositor lifecycle.

Pinned Chromium's `PageHandler::BringToFront` calls `WebContents::Activate()` followed by outermost `WebContents::Focus()`. In pinned Alloy CEF, `CefWebContentsViewOSR::Focus()` is explicitly empty, and `AlloyBrowserHostImpl` does not override `ActivateContents`. That makes an extra scheduled roundtrip a plausible explanation in this runtime. Compare an awaited `Runtime.evaluate` or `Page.getLayoutMetrics` before capture, using equivalent fresh/idle cases and both embedded and pipe CDP paths, before attributing the success to visibility. [Chromium command](https://github.com/chromium/chromium/blob/152.0.7977.83/content/browser/devtools/protocol/page_handler.cc), [CEF OSR focus](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/osr/web_contents_view_osr.h), [Alloy delegate interface](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/alloy/alloy_browser_host_impl.h).

Current upstream Puppeteer's `Page.screenshot` and `CdpPage._screenshot` do not automatically call `bringToFront`; it is a separate method. Chrome DevTools MCP's `take_screenshot` handler calls Puppeteer's screenshot method without its own activation, and no activation call was found in its `ToolDefinition`/`McpContext` wrappers. Do not assume existing agent screenshot clients already perform a preflight. A documented explicit CDP preflight is a conventional API sequence, but requiring it for basic screenshot reliability remains a CEF-host limitation to disclose and test. [Puppeteer page wrapper](https://github.com/puppeteer/puppeteer/blob/main/packages/puppeteer-core/src/api/Page.ts), [CDP implementation](https://github.com/puppeteer/puppeteer/blob/main/packages/puppeteer-core/src/cdp/Page.ts), [MCP screenshot tool](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/src/tools/screenshot.ts).

## Prefer the standard CEF loop before adding screenshot workarounds

The current Host runs `CefDoMessageLoopWork`, reads stdin, dispatches commands directly, then sleeps 1 ms. A bounded next experiment is `CefRunMessageLoop` on the main thread, with a stdin reader posting owned command strings through `CefPostTask(TID_UI)`. CEF explicitly recommends the standard loop for CPU/performance, and its Mac sample uses `MainMessageLoopStd` when `external_message_pump` is false. Keep that flag and `multi_threaded_message_loop` false; the latter is unsupported on Mac. The existing `CefAppProtocol` application subclass and `sendEvent` scope remain required. [CEF API contract](https://github.com/chromiumembedded/cef/blob/708dc14/include/cef_app.h), [Mac sample](https://github.com/chromiumembedded/cef/blob/708dc14/tests/cefclient/cefclient_mac.mm), [standard-loop wrapper](https://github.com/chromiumembedded/cef/blob/708dc14/tests/shared/browser/main_message_loop_std.cc).

This is a scheduling hypothesis, not evidence that native events were never serviced: `CefDoMessageLoopWork` itself executes `base::RunLoop::RunUntilIdle`. The standard loop keeps `Run` alive across idle periods; Chromium's Mac pump uses `NSApp.run` or its native event loop and installs CF run-loop observers. That may change presentation completion/idle behavior, and moves command execution from outside the loop into normal UI tasks. GPU raw-pipe screenshot acceptance must establish whether it repairs the actual failure. Eliminating the fixed 1 ms wakeup is an independent energy opportunity. [CEF implementation](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/context.cc), [CEF persistent loop](https://github.com/chromiumembedded/cef/blob/708dc14/libcef/browser/main_runner.cc), [Chromium Apple pump](https://github.com/chromium/chromium/blob/152.0.7977.83/base/message_loop/message_pump_apple.mm).

Keep all CEF objects, page maps, and command dispatch on UI. Bound pending command bytes as well as line length; start reading only once initialized or use a synchronized ready gate. For shutdown, post a UI task, close browsers, wait for `OnBeforeClose` while the standard loop still runs, then quit; join/stop the reader before main-thread `CefShutdown`. Handle zero pages and pending creation. A signal handler may set a signal-safe flag/write a self-pipe, but must not call CEF task APIs directly; changing the old polling flag alone will not wake the new loop. Handle a rejected task post without a destructor touching UI objects. Stdout backpressure remains an independent source of UI blocking. [Task lifetime contract](https://github.com/chromiumembedded/cef/blob/708dc14/include/cef_task.h).

## Screenshot acceptance that tests the actual contract

Use a deterministic fixture with a numbered/color marker and pause its own animation for exact image comparison. Confirm page readiness and dimensions, change the marker, then request a screenshot without an arbitrary sleep. Require the latest marker, correct physical dimensions, successful PNG decode, and bounded completion time. Keep the existing independent RFB-versus-CDP exact-pixel comparison after both represent a stable fixture state; it checks stream fidelity, while the immediate marker test checks screenshot freshness.

Repeat across a static page after idle, animated/canvas content, scale changes, two live Pages, Page close/recreate, viewer disconnect/reconnect, and never-viewed unattended pages. If a timeout occurs, independently prove the Page and UI loop are alive, save timings, and clean up the pending command through the existing lifecycle. A client timeout is not cancellation of the underlying screenshot. Do not stack uncontrolled retries or mark reliability passed because a subsequent fresh process succeeds. A library/API fix should survive these gates before GPU becomes default; Linux requires its own acceptance.

## Practical Apple CPU/GPU and energy comparison

Measure rendering correctness and resource use together. A presenter can use less CPU by moving work to the GPU while increasing total energy; neither submission time nor CPU utilization alone establishes battery savings.

| Tool/API | Practical use | Interpretation limit |
| --- | --- | --- |
| Instruments Time Profiler plus Metal System Trace / Game Performance template, Mac and connected iPad | Attribute CPU stacks, GPU command work, scheduling, drawable waits, and memory to the actual Alpha process. Separately trace the Host runtime and its Renderer/GPU helper processes. | GPU execution time is not joules. Include WindowServer/system composition context when comparing CALayer and Metal. |
| `MTLCommandBuffer.GPUStartTime` / `GPUEndTime` in completed handlers | Low-maintenance per-command GPU duration for the native Metal presenter, correlated with existing enqueue/submit/visible-frame timings. | Read after completion; do not synchronously wait on the UI thread. It measures this command buffer, not all display-system work. |
| Xcode Energy gauge / Instruments Power Profiler on supported iPadOS | Compare CPU, GPU, display, and networking power impact over the same interaction. Power Profiler is documented for iPadOS 26 or later. | System power and app impact are different metrics. Connected Xcode keeps Apple silicon awake; use on-device battery-powered traces for realistic idle/sleep evaluation. |
| Mac `powermetrics` | Use per-process/coalition CPU, GPU time where supported, wakeups, and energy-impact proxy; include CEF helpers and Portal rather than only the browser executable. | Apple documents energy impact as a rough platform-specific proxy and subsystem watts as estimates; these are not exact per-process battery joules or cross-device comparisons. |
| `XCTCPUMetric(application:)` | Repeatable app CPU-time/instruction/cycle comparison in an existing UI test harness. | Useful automated regression evidence, not a battery meter; avoid creating a large new harness solely for one short experiment. |

Primary sources: [Metal profiling workflow](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-metal-app/), [Metal command GPU timestamps](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpustarttime), [Power Profiler](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler), [Apple power-profiling session](https://developer.apple.com/videos/play/wwdc2025/226/), [CPU test metric](https://developer.apple.com/documentation/xctest/xctcpumetric). Mac `powermetrics` semantics were verified against Apple's installed `/usr/share/man/man1/powermetrics.1`, including `--show-process-coalition`, `--show-process-gpu`, and `--show-process-energy`; unsupported counters must be reported as unavailable.

Use interleaved CALayer/Metal runs on the same device with fixed brightness, refresh policy, viewport, page, route, thermal state and foreground state. Include a matched scroll workload and a static idle interval, warm up before recording, and keep builds, screen recording, and unrelated heavy work out of the measurement. Record completed fresh frames so lower energy caused by dropped work cannot look like an improvement. Sum Host-side process-family cost separately from client-side cost; iPad battery is affected by its own rendering/networking, not by CPU moved to the Mac. Keep power assertions or frame-clock changes identical between variants. Report measured proxies honestly if a battery-powered trace is unavailable.

## Executed repair attempts (15 September)

The GPU screenshot blocker survived the bounded attempt. No diagnostic workaround is adopted. The product retains software CEF and the original message pump.

| Experiment | Result |
| --- | --- |
| Bare embedded `Page.captureScreenshot` after resize and idle | Times out while Runtime.evaluate and the Page remain responsive and visible. |
| `CDPScreenshotNewSurface` | Same failure. |
| `fromSurface:false` | Unsupported OSR view capture: unable to capture screenshot. |
| DOM repaint while capture waits | Did not reliably complete the capture. |
| `WasHidden(false)` / `Invalidate` preflight | Some immediate 20-round tests passed; idle and full Portal acceptance still failed. |
| Standard `Page.bringToFront` in the same CDP session | Some 30-round raw-pipe tests passed; full Portal screenshot acceptance still failed. Removed both embedded and pipe preflights. |
| External 60 Hz begin-frame clock | Raw-pipe 30-round run passed; embedded run failed. Removed. |
| Standard `CefRunMessageLoop`, stdin reader posting bounded UI tasks | First fresh screenshot passed, second after idle failed. Not adopted. The adapter is preserved only as a diagnostic patch; it is not a qualified replacement event loop. |

The reproducer checks current-color pixels as well as PNG geometry, so receiving a stale screenshot cannot count as success. `product/portal/scripts/browser-gpu-screenshot-acceptance.ts` supports fresh and retained Pages, embedded and raw-pipe CDP, scale handoff, idle, and RFB disconnect. Failed attempts and exact source patches live under `experiments/gpu-screenshot/`. Short successful runs are evidence of intermittency, not a repair.

This narrows the next GPU work to an upstream CEF OSR/delegated-surface reproduction and fix. Browser display can work while the separate CDP screenshot path fails; enabling GPU would break a required agent capability.
