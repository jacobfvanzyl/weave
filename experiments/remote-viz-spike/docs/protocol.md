# Capture format, not the live protocol

The current schema is an offline diagnostic format. Live network serialization remains gated on an independently reconstructed actual Chromium frame.

Each frame JSON contains a schema version, capture-session namespace, sequence, source revision, device scale, provider kind and monotonic server timestamp. `render_passes` is the pinned Chromium diagnostic pass representation plus indexed quad supplements for exact RGBA solid/texture-background colors, unsigned resource IDs, explicit empty-mask detection and structured mask bounds, eight corner-radius values and gradient presence. Passes retain dependency order; quads retain front-to-back order. Viz trace matrices are 16 row-major values and rectangles are `[x,y,width,height]` arrays.

`resources` independently identifies each referenced raster image by display resource ID and capture-local generation, with dimensions, tight row stride, immutable file name and whether a new payload was written. Payload byte layout is BGRA8 premultiplied sRGB, top-left rows. The separate `origin_top_left` field preserves the resource sampling-origin convention; the supported texture subset rejects bottom-left resources. A repeated frame can reference the same file/generation without another resource write or native texture upload. Byte equality and dimensions determine reuse; a resource ID alone is not treated as a content version.

A sequenced writer writes new resource files before the referencing frame JSON. Resource reads/copies happen under Chromium's existing scoped lock before that data crosses threads. Browser resource locks are not held for client acknowledgement. The capture is limited to 180 frames per Display; different Display/process sessions have separate cache namespaces. Cache eviction on absence from a frame is a conservative spike policy, not a mirror of Chromium producer-return semantics.

`resource_payload_bytes` measures newly written raster bytes, while `raster_bytes_examined` counts all bytes reread for comparison. Zero payload does not mean zero server memory/readback work. `extraction_us` covers synchronous extraction/comparison; it excludes queued disk writes and is not transport latency.

A replay must fail on incomplete resource copies, unavailable dependencies or unsupported state. The current decoder redraws all passes, accepts finite nonsingular 2D affine transforms, bounded scaled/fractional tiles, solid/plain-pass quads, a restricted texture subset and uniform circular rounded masks. Texture sampling clamps to source-rectangle texel centers and accepts normalized or pixel coordinates. Non-default backgrounds, video/protection flags, bottom-left origins, gradients, unequal corner radii, 3D sorting, unsupported filters and unknown materials reject explicitly. Perspective and singular affine matrices reject explicitly. Passes with nontrivial affine state use four-sample Metal multisampling, with measured coverage differences from Chromium. Some pinned trace fields still use exact default-value checks; this diagnostic representation is not a production schema.

The decoder honors `needs_blending` when choosing Src replacement or SrcOver, and samples a child pass using the consuming quad's pixel extent. With mask coverage, Src replacement is supported only when the source is opaque. CoreGraphics supplies antialiased rounded-mask coverage in render-target coordinates; Metal composites it. Mask textures are cached at bounding-box size, with upload/cache bytes reported separately from server raster resources. Their antialiasing is not byte-identical to Skia; see measured differences.

The single-blur pass subset additionally requires `blur_uses_decal` and `filter_output_rect` captured through Chromium's filter implementation. The client only admits one Gaussian blur with unit `filters_scale`, zero `filters_origin`, no backdrop/mask texture and matching child backing. It runs `MPSImageGaussianBlur` into the expanded target before composing the parent pass. Old filtered captures missing these supplements continue to reject rather than assuming a tile mode or bounds. This does not support general filter chains or SVG/backdrop filters.

Production transport still needs an explicit binary schema independent of Chromium trace JSON, negotiated limits, resource acknowledgement and deletion rules, reconnect/key-state handling, message validation, input/viewport generations, and measured backpressure. None is claimed by the file format.
