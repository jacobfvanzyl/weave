# holder

`weave-holder` (ADR 0022) is the process that keeps one terminal alive for the weave Host. It
holds the terminal's PTY, its shell and the authoritative screen in libghostty-vt, and it speaks
the holder protocol (`../docs/specs/wve-85-host-protocol.md`, "Holders"). Read the root
`AGENTS.md` first. The crate is built under WVE-151, and grew from the spike in WVE-149.

## libghostty-vt

`ghostty.toml` pins the Ghostty commit and the Zig that builds it. The app's terminals (WVE-153)
build their xcframework from the same pin (`app/scripts/ghostty.ts`, into the same cache), since
the app decodes the holder's snapshots. A pin move is checked there too, with
`bun run native:test` in `app/`, which also compares the two codecs.

`build.rs` links `libghostty-vt.a` statically from the first of:

1. `$GHOSTTY_VT_PREFIX`, a prefix that already holds a build;
2. the cache: `$WEAVE_GHOSTTY_CACHE`, else `$XDG_CACHE_HOME/weave/ghostty`, else
   `~/.cache/weave/ghostty`;
3. a build into the cache, which needs Ghostty's source and Zig:
   - the source comes from `$GHOSTTY_SRC`, or from `git fetch --depth 1` of the pinned commit;
   - Zig comes from `$ZIG`, or a `zig` of the pinned version on PATH, or a download from
     ziglang.org checked against the pin's sha256.

The cache keeps:

- one build per commit and target (about 15 MB), shared by every checkout and worktree;
- the Zig it downloaded (about 450 MB) and Zig's global cache.

Once a build is done, the cache drops the source and Zig's local cache. When the pin moves, it
removes other commits' builds and other Zigs. A first build takes about two minutes on an M3.
A `zig build` whose fetch of Ghostty's packages failed is run again, up to three times: a cold
Zig 0.17 compiles its own build system while it fetches, and on Linux its resolver's 5 s
deadline can pass meanwhile (`NameServerFailure`, WVE-154).

To move the pin:

1. Update `ghostty.toml`. If Ghostty's `minimum_zig_version` moved, update Zig's version and its
   checksums from ziglang.org's `index.json`.
2. Regenerate the bindings with `cargo build -p weave-holder --features bindgen`. This needs
   libclang: Xcode's on macOS, `libclang-dev` on Debian.
3. Review the diff of `src/ffi/bindings.rs`, and run the tests.

The codec names the commit (`weave-holder --version`), so a pin change is a codec change. Holders
already running keep theirs, and clients restore from them through the formatter's VT.

`src/ffi.rs` includes the committed bindings, generated with layout assertions, so a platform
whose C layout differs fails to compile rather than misbehaving. `src/vt.rs` is the only module
that calls them.

## Starting the shell

A build into the cache also lays out Ghostty's resources as Ghostty installs its own:

- `share/ghostty/shell-integration`, copied from Ghostty's source;
- `share/terminfo`, generated by Ghostty's `terminfo` module and compiled with `tic`.

`build.rs` embeds them in the binary (a cache layout version, `LAYOUT`, makes older builds
without them build again). `src/resources.rs` writes them out once per commit, under the
holder's directory as `resources/<commit>/`, so a holder copied to another computer needs no
install layout.

`src/launch.rs` starts the shell as Ghostty does, following Ghostty's `src/termio/Exec.zig` and
`shell_integration.zig` at the pin:

- `login(1)` on macOS, and `/bin/sh -c` elsewhere;
- `TERM=xterm-ghostty` with its `TERMINFO`, `COLORTERM=truecolor` and `TERM_PROGRAM=weave`;
- Ghostty's shell integration for zsh, bash (not Apple's `/bin/bash`), fish, elvish and nushell.

When Ghostty changes these rules, the pin move brings the change here.

`login(1)` exits 0 whatever the shell exits with, so a command (`-- …`), whose exit code matters,
runs without it even on macOS.

## The holder

`src/holder.rs` serves one terminal on `<dir>/<id>.sock`, with `<dir>/<id>.json` the record a
Host finds it again by. Both are removed when the program exits, which ends the holder.

- The record carries the Host's `scope` and `opened_from`, so the Host keeps no registry of its
  own (ADR 0022).
- The protocol is in `src/protocol.rs` (framing, Rex's request and answer shapes) and
  `src/event.rs` (Rex's terminal events and weave's additions).
- Threads share one lock around the terminal.
- Each client has an outbox. One that falls 4 MiB behind gets `resync` and a fresh snapshot.
- Only the socket's owner may connect.
- Told to stop (SIGTERM, SIGINT, SIGHUP), the holder hangs its program up and ends with it.

The CLI (`src/main.rs`):

- `serve` holds the terminal in the foreground, as `systemd-run --user` runs it on Linux.
- `spawn` double-forks into a session of its own and returns once the socket answers, as on
  macOS.
- Both print the record as a line of JSON when ready, or `{"error": …}`.
- `--env-file` is a JSON object of the program's environment (the agents', WVE-141), which the
  holder removes once read.

`tests/holder.rs` runs the real binary with `/bin/sh`, and zsh where there is one.

## Commands

The holder builds and tests with the workspace. The Host finds it beside its own binary (WVE-152),
and `scripts/update-hosts` installs it there.

```bash
cargo test -p weave-holder
cargo clippy -p weave-holder --all-targets
cargo build -p weave-holder && ./target/debug/weave-holder --version   # prints the codec
```
